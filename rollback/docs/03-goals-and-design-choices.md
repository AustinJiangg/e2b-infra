# 03 · 设计目标、约束与方案选择

## 本章目标

一个系统的形状，由它**明确不做什么**决定的程度，不亚于由它做什么决定。读完本章，你应当能够：

- 说出目标场景的三个特征各推出了什么，以及"checkpoint ≤ 200 ms、restore ≤ 100 ms"被钉成了什么样的可测口径；
- 列出五条硬约束，说明为什么"产物盘是 ext4"影响最深；
- 用三条理由说明为什么不直接复用原生 snapshot，并说清其中哪一条后来在原生路径上单独修掉了、为什么剩下两条仍然足够；
- 列出六项明确的非目标，说清"划界"换来了什么简化、付出了什么代价；
- 复述贯穿全书的四条设计原则，并能在后面各章里认出它们。

上一章（[02](02-e2b-native-snapshot.md)）把原生 snapshot 当作基线讲透了：它停沙箱、重建进程，成本与虚机规格挂钩。
本章以它为参照，推出本方案要做什么、不做什么、按什么原则做。第二部分从下一章（[04](04-architecture.md)）开始进入实现，
那里的每一个设计决定都能在本章找到出处。

---

## 1. 目标场景

一句话：**沙箱在执行任务时出错，需要退回到上一个已知良好的状态继续跑**（场景见 [01](01-background.md) §1）。

| 特征 | 具体含义 | 推出什么 |
|---|---|---|
| **高频** | 一个任务里十几次，不是一个沙箱一两次 | 单次成本必须低到可以随手用；固定开销不可接受 |
| **低延迟** | 发生在 Agent 的决策循环里 | 量化目标：**checkpoint ≤ 200 ms、restore ≤ 100 ms** |
| **沙箱不能中断** | 有 IP、端口映射、保持中的连接、外部持有的引用 | 排除一切"停掉再拉起"的路线 |

第三条最硬。它单独就排除了原生方案的整条路径 —— `Pause` 和 `Checkpoint` 都要停掉沙箱（[02](02-e2b-native-snapshot.md) §1、§4）。

### 1.1 那两个数字约束的是什么

"≤ 200 ms / ≤ 100 ms"是客户给的上限，本身不是一个可测量的口径 —— 它没说谁的钟、哪一次、哪个统计量。
全书把它钉成下面这一条，钉在**对我们最不利**的一侧：

| 操作 | 达标线 | 判定对象 | 不参与判定 |
|---|---|---|---|
| checkpoint | ≤ 200 ms | **增量** checkpoint（沙箱的第 2 代及以后），客户端墙钟 **p50**，p99 并列给出 | 全量根 —— 每个沙箱一次性的成本，单列说明 |
| restore | ≤ 100 ms | **原地** restore（沙箱 ID 与 Firecracker 进程都不变），客户端墙钟 p50 | 另起新沙箱的恢复形态，那是原生 snapshot 的路径 |

为什么用客户端墙钟：它包含网络往返与服务端的全部工作，是三个钟（客户端墙钟、服务端总耗时、冻结窗口）里最大的一个，
也是客户在自己机器上唯一能复测的一个。完整的口径定义见 [20](20-performance-methodology.md)，逐档的判定结果见 [21](21-benchmarks-and-compliance.md)。

这条目标反过来规定了性能表怎么给：达标线是一个**常数**，而增量的代价随本次改动量走（§5.1），
所以性能表按**脏页量档位**给，不按沙箱内存大小给 —— 同一个 2 GiB 的沙箱，改 1 MiB 和改 256 MiB 是两件事。

## 2. 硬约束

不可协商的，来自交付环境：

| # | 约束 | 后果 |
|---|---|---|
| 1 | **aarch64**（鲲鹏 920B / 950） | x86 上的方案不能照搬；ARM 适配版的既有问题要一起面对（例如 [02](02-e2b-native-snapshot.md) §3.2 的判据退化） |
| 2 | **产物盘是 ext4** | 整条数据路径**不得依赖 reflink**（[04](04-architecture.md#8-为什么交付用-ext4)） |
| 3 | **不改动原生路径的行为** | 两条路径并存，本方案是纯加法：新路径、新端点、新字段 |
| 4 | **沙箱内不装任何代理程序** | 全部动作在宿主侧完成（[04](04-architecture.md)） |
| 5 | **orchestrator 与 Firecracker 成对交付** | 两侧版本配错就用不了（[08](08-firecracker-api-contract.md#6-版本配对)） |

**约束 2 影响最深远。** reflink（`FICLONE`）让两个文件共享同一批磁盘块、写时才分裂，XFS、Btrfs 支持，ext4 不支持。
有 reflink 时，"每代克隆上一代的完整内存镜像、再覆盖本代脏页"是最简单的设计；没有 reflink 时，克隆退化成整份内存的真实拷贝，
**即使这一代什么都没做也要付一次全内存拷贝**，而且完全静默。约束 2 因此直接否掉了"每代自足"这个更简单的设计，
是内存差分树存在的全部原因（[06](06-memory-diff-tree.md)）。

**约束 3** 意味着不能为了本方案的方便去改动原生代码的行为，所有新增能力都是新路径、新端点、新字段。
（第四部分对原生 pause 路径的精确增量修复是另一件事：它改的是原生导出哪些页、按多细的粒度存，原生快照的语义不变，产物仍是"紧凑差分 + header 映射链"，只是 header 的块大小从 2 MiB 降到 4 KiB；
因此兼容是单向的：新 orchestrator 读得了旧快照，旧 orchestrator 读新快照会拒绝启动。影响面与兼容的论证见 [17 §7](17-native-increment-cost-and-verification.md#7-兼容)、[§9.1](17-native-increment-cost-and-verification.md#91-影响面)。）

## 3. 为什么不复用原生

最自然的想法是：原生已经有快照和恢复了，为什么不直接用、或者在它上面改？三条理由。

### 3.1 它会中断沙箱

导出磁盘增量的路径必须先摘出写层、停掉沙箱、等 NBD 设备释放。这不是实现细节 ——
`ExportDiff` 的参数之一就是"关掉沙箱"这个回调（[02](02-e2b-native-snapshot.md) §4.2）。
恢复同样要新建进程。**与特征三（不能中断）直接冲突。**

### 3.2 成本模型不对

恢复要新建 Firecracker 进程，再靠缺页把整个工作集换回内存 —— 代价取决于**虚机多大**，而不是**回退了多少**。
回退一个只改了 40 MiB 的沙箱，和回退一个改了 2 GiB 的沙箱，花的时间几乎一样。

**与特征一（高频）直接冲突**：高频意味着单次改动量通常很小，而原生方案在这种情况下**省不下任何东西**。

### 3.3 ARM 适配基线上增量已经退化

上游 x86 用 uffd 的写保护位区分读缺页与写缺页，增量是精确的。移植到 aarch64 时那条写保护路径被注释掉了，判据退化成
"凡是被换入过的页都算脏"（定义见 [05](05-dirty-page-tracking-and-hdbss.md)）。叠加"每次 snapshot 都重建沙箱、工作集必须重新换入"，
**即使两次 snapshot 之间什么都没做，增量的下限也约等于整个常驻工作集。**

必须说清：这是 ARM 适配引入的退化，**不是 e2b 的设计问题**；本方案绕开它，也不构成"超越 x86 原生"。

### 3.4 第三条修掉之后

第三条理由后来在原生路径上被单独修掉了：本书交付的代码里，原生 pause 在跟踪开着时改用 Firecracker 的写跟踪位图判脏、并把存储粒度从 2 MiB 降到 4 KiB，
增量回到按改动量走（**第四部分 [15](15-native-increment-diagnosis.md)–[18](18-native-and-checkpoint-together.md) 专门讲**）。

但这不改变"不复用原生"的结论：§3.1 和 §3.2 来自"沙箱离场"这个语义本身 —— 停掉沙箱、重建进程、换回工作集 —— 与判据精不精确无关。
单凭其中任何一条，原生就不满足目标场景。第三条的意义在于：它说明原生在 ARM 上连"增量随改动量走"这一点都没做到，
所以本方案的脏页判据不能从原生借，必须自己取（[05](05-dirty-page-tracking-and-hdbss.md)）。

## 4. 明确的非目标

**划界本身是设计的一部分。** 下面这些明确**不做**，交给原生 snapshot：

| 非目标 | 为什么划出去 |
|---|---|
| **宿主崩溃恢复** | 账本活在 orchestrator 进程内存里，进程一死就没了（[14](14-lifecycle-reasoning.md)） |
| **跨节点迁移** | 产物是"相对模板的增量"，且路径绑定在本机 |
| **长期持久化** | 产物随沙箱生命周期回收 |
| **沙箱进程已死后的恢复** | 只有原地回滚一条路，它要求活体 |
| **虚机状态撕裂后的抢救** | 明确标记为死并要求重建（[12](12-failure-semantics.md)） |
| **跨沙箱共享 checkpoint** | checkpoint id 只在所属沙箱的生命周期内有意义 |

### 4.1 划界带来的简化

把这些划出去，换来的不只是"少写点代码"，而是**整类问题不存在**：

| 不做什么 | 因此不用处理 |
|---|---|
| 产物不跨重启存活 | 陈旧条目回收、与已消失沙箱的对账、格式版本迁移 |
| 不跨节点 | 产物上传下载、一致性协议、跨节点的引用计数 |
| 没有兜底重建路线 | 两条恢复路径之间的语义对齐（但代价是失败必须分级，§5.3） |
| 只在活沙箱上工作 | 离线状态的加载、校验、修复 |

[13](13-state-concurrency-durability.md) 里"并发模型少了一整类问题"就是这么来的。

### 4.2 划界的代价

代价同样真实：

- checkpoint **备份不走** —— 把目录完整拷走也恢复不了（推导见 [14](14-lifecycle-reasoning.md)）；
- orchestrator 重启、宿主重启，全部失效；
- 沙箱迁移到别的节点时 checkpoint 不跟随。

**这些不是缺陷，是这笔交易的另一半。** 换来的是零拷贝封存、原地回滚、以及只随回退跨度增长的成本曲线。

## 5. 四条设计原则

从上面推出来，全书各章都在实现它们。

### 5.1 成本只与改动量挂钩

**任何与虚机规格线性相关的固定开销都要消掉。** 体现在：

| 处 | 怎么做 |
|---|---|
| 内存产物 | 每代只存本代脏页，不克隆上一代（[06](06-memory-diff-tree.md)） |
| 磁盘产物 | 封存是改名，零数据搬运（[07](07-disk-layering.md)） |
| 封存的落盘 | 不等 msync，把 O(改动量) 变成 O(1)（[07](07-disk-layering.md)） |
| 恢复 | 按页写回回滚集，不重建镜像（[09](09-in-place-rollback.md)） |
| 内容解析 | 按页沿祖先链寻址，恢复成本与链深无关；删除时同步合并隐藏条目，只为回收空间（[06](06-memory-diff-tree.md)） |

唯一保留的固定开销是**全量根**（每个沙箱的第一次 checkpoint）：模板 memfile 不在本地，树根存一次全量让回滚路径不跨网络。
它有开关（[27](27-configuration-and-capacity.md)），取舍见 [06](06-memory-diff-tree.md)。

### 5.2 不重建任何宿主资源

进程、KVM fd、eventfd、irqfd / ioeventfd 注册、tap、网络槽位、NBD 设备、内存映射 —— **一个都不重建**。

这既是"快"的全部来源，也是"离不开活沙箱"的全部原因，是同一件事的两面（[14](14-lifecycle-reasoning.md)）。

### 5.3 宁可报错，不可静默损坏

这套系统操作的是**一台正在运行的虚拟机的内存**。一次错误的回滚不会让虚机崩溃 ——
它会让某几页内存的内容属于另一个时刻，然后虚机继续跑，可能很久以后才以莫名其妙的方式暴露。所以：

| 情形 | 处理 |
|---|---|
| 路径上缺侧车 | **报错**，不静默降级成全量回滚 |
| 链断了 | **拒绝恢复**，直到下一次全量 checkpoint |
| 账本与层栈不一致 | **标记污染并拒绝服务**，不留下一个看起来正常的错账本 |
| 拓扑不一致 | **拒绝**，不勉强写 |
| 纪元可能丢失 | 以**隐藏条目**保住它，宁可留垃圾也不留坏链 |

没有兜底重建路线（§4.1），这条从"好习惯"变成了"硬要求"。完整讨论见 [12](12-failure-semantics.md)。

### 5.4 能力随硬件自动降级，但要说出来

有 HDBSS 就用硬件标脏，没有就退回 KVM 写保护；**功能永远正确，只是代价不同**。但降级**不能是静默的**：

| 手段 | 说明 |
|---|---|
| 启动时报告能力**和理由** | 启动日志的 `checkpoint capabilities` 一行 |
| 每次调用回报 `memMode` | 第一个之后出现 `full` 就说明没在跟踪脏页 |
| Firecracker 自报脏页后端 | `hdbss` / `kvm-wp` / `off` |
| `FC_HDBSS_REQUIRED` | 生产部署可以选择**宁可启动失败** |

机制见 [05](05-dirty-page-tracking-and-hdbss.md)，字段见 [28](28-observability-reference.md)，开关见 [27](27-configuration-and-capacity.md)。

## 6. 一句话总结这笔交易

> **用"绑定沙箱生命周期"换掉产物自足性与账本持久化，换来零拷贝封存、原地回滚、以及只随回退跨度增长的成本曲线。**

两条路径并存、各管各的：原生管迁移、持久化、崩溃恢复，本方案管高频快速回退。两者的逐项对比、优化点与对照基准、
以及怎么叠加使用，见 [18](18-native-and-checkpoint-together.md)。

## 本章要点

1. 目标场景三个特征：**高频、低延迟、沙箱不能中断**；第三条单独就排除了原生方案的整条路径。
2. 低延迟目标 checkpoint ≤ 200 ms、restore ≤ 100 ms，钉成"增量 checkpoint 与原地 restore 的客户端墙钟 p50"，性能按脏页档位给。
3. 五条硬约束里"**产物盘是 ext4**"影响最深：没有 reflink，"每代自足"不成立，于是有了差分树。
4. 不复用原生的三条理由：**中断沙箱**、**成本模型不对**、**ARM 适配基线上增量已退化**；第三条后来在原生路径上单独修掉了（第四部分），
   前两条来自原生的语义本身，仍然成立。
5. **明确不做**六件事，换来整类问题不存在（陈旧条目、跨节点一致性、离线加载…）；代价是产物备份不走、重启即失效。
6. 四条原则：**成本只与改动量挂钩**、**不重建任何宿主资源**、**宁可报错不可静默损坏**、**能力随硬件降级但要说出来**。
7. 与原生的对比表和优化点表只在 18。
