# 10 · 背景：沙箱、microVM 与快照原理

> 这篇给所有想弄懂"这套东西在做什么"的人看，不要求写过虚拟化代码。
> 读完你能说清三件事：为什么要把一台运行中的机器退回过去某一刻；e2b 的沙箱在宿主上由哪些部件拼成；
> 一次虚机快照要保存什么、怎么保证各部分属于同一瞬间，以及"重建"与"原地回写"两种恢复形态的成本差别。

---

## 1. 需求从哪来

### 1.1 一个具体的场景

一个 AI Agent 在隔离环境（**沙箱**）里执行"把这个项目的测试跑通"：

```
① 拉代码  ② 装依赖  ③ 改配置  ④ 跑构建  ⑤ 构建失败，看日志
⑥ 装一个缺的系统库  ⑦ 改另一个配置文件
⑧ 跑构建 —— 连步骤 ④ 原来能过的部分都过不了了
```

第 ⑦ 步把环境搞坏了。Agent 需要回到第 ⑥ 步结束时的状态，换个改法再试。

扔掉沙箱、重做 ①–⑥ 行不通，原因有三：

| 问题 | 说明 |
|---|---|
| **时间** | 装依赖可能要几分钟，一次任务里可能要退十几次 |
| **外部副作用** | ①–⑥ 里可能调用过 API、写过数据库、消耗过配额，重做会重复这些动作 |
| **不可复现** | 依赖源会变、网络会抖、时间戳不同，重做出来的环境不保证与原来一致 |

第三条最要命：重做的结果如果和原来不完全一样，Agent 面对的就不再是"第 ⑥ 步之后的环境"，
而是"一个大致像它的环境"。

这个需求有三个特征，后面所有技术选择都由它们决定：

- **高频**：一个任务里十几次，不是一天几次；
- **低延迟**：回退发生在 Agent 的决策循环里，几百毫秒和几秒是两种产品体验；
- **不能中断**：沙箱有 IP、端口映射、保持中的连接、外部持有的引用，中断一次这些全要重建。

### 1.2 三种做法

| | 重建沙箱 | 应用层撤销 | 虚机快照 |
|---|---|---|---|
| 能回退什么 | 一切（但结果可能不同） | 只有被显式建模的操作 | **一切** |
| 依赖对操作的理解 | 是 | **是** | **否** |
| 外部副作用 | 会重复 | 需要单独处理 | 不重复，也不撤销 |
| 结果确定性 | 不保证 | 取决于实现 | **逐字节一致** |

应用层撤销的问题是**覆盖不全**：要撤销一次 `apt install`，得知道它装了哪些文件、改了哪些配置、
跑了哪些 postinst 脚本。Agent 执行的是**任意**命令，没有办法为任意命令写反操作；反操作本身也可能失败。

虚机快照不关心做了什么，只记录状态是什么：把整台虚拟机某一时刻的内存、CPU、设备、磁盘保存下来，
需要时整体恢复。

> **硬边界**：虚机快照能把机器内部退回去，**退不回外部世界**。已经发出的 HTTP 请求、
> 已经写进外部数据库的记录，任何快照方案都管不着。

### 1.3 "快照"在四个层次上

| 层次 | 例子 | 捕获什么 | 看不见什么 |
|---|---|---|---|
| 文件系统快照 | LVM、ZFS、Btrfs | 某一时刻磁盘上的文件 | 内存里的一切：进程、页缓存、未落盘的写 |
| 容器镜像层 | Docker layer / commit | 文件系统的变更集 | 同上，且不含运行中的进程 |
| 进程 checkpoint | CRIU | 一组进程的内存、寄存器、打开的文件、套接字 | 内核态的很多东西；磁盘完全不管 |
| **虚拟机快照** | 本方案 | guest 的全部：内存、vCPU、设备、磁盘 | 外部世界 |

进程 checkpoint 能把进程树退回去，但**磁盘还停在未来**：被退回的进程会读到它"还没写过"的文件。
**内存和磁盘必须一起退**，否则 guest 会看到一个自相矛盾的世界（[§4.2](#42-一致性为什么必须是同一瞬间)）。

### 1.4 本方案的位置

一句话：**虚机级、进程内、高频、宿主本地。**

| 特征 | 含义 |
|---|---|
| 虚机级 | 捕获 guest 的全部状态，包括内存和磁盘 |
| 进程内 | 恢复时不重建虚拟机进程，往活着的进程里写回差异 |
| 高频 | 单次代价低到一个任务里可以用十几次 |
| 宿主本地 | 产物不进对象存储，随沙箱生命周期回收 |

"进程内"是核心选择，"宿主本地"是它的代价：产物离不开这个沙箱，长期保存和跨机器迁移交给 e2b 原生
snapshot（分工见 [02](02-semantics-and-limits.md)，边界推导见 [22](22-lifecycle-reasoning.md)）。
目标是把虚机快照的代价从"与虚机规格挂钩"变成"与改动量挂钩"。

## 2. microVM 与 Firecracker

### 2.1 三种隔离

| | 容器 | 传统虚拟机 | microVM |
|---|---|---|---|
| 隔离边界 | 共享宿主内核（namespace + cgroup + seccomp） | 独立内核，硬件虚拟化 | 独立内核，硬件虚拟化 |
| 内核漏洞的影响 | 可能逃逸到宿主 | 被硬件边界挡住 | 被硬件边界挡住 |
| 设备模型 | 无 | 完整仿真：BIOS、PCI、显卡、USB… | 极简：几个 virtio 设备 |

跑不受信任的任意代码时共享内核的风险不可接受，传统虚拟机又太重。microVM 保留硬件隔离边界，
把设备模型砍到最小。

### 2.2 Firecracker 砍掉了什么

| 砍掉 | 保留 |
|---|---|
| BIOS / UEFI | 直接加载 Linux 内核镜像 |
| PCI 总线 | virtio-mmio |
| 显卡、USB、声卡… | virtio-net、virtio-block、virtio-rng、串口 |
| 设备热插拔 | 启动时固定的设备集 |

设备越少，"一台虚机的状态"就越简单。除了 guest 内存（一个 2 GiB 沙箱就是 2 GiB），
vCPU 寄存器、中断控制器（aarch64 上是 GIC）、virtio 设备的逻辑状态加起来通常只有几十 KB。
**这个悬殊比例是后面所有优化的前提**：优化内存那一项，就等于优化了整个快照。

上游 Firecracker 已有 Full / Diff 快照、`track_dirty_pages` 脏页跟踪、`PUT /snapshot/load` 加载、
Pause / Resume；但恢复只有"**新建一个进程去加载**"这一条路。本方案增加的核心能力是
**往活着的进程里写回**（[17](17-in-place-rollback.md)），接口扩展见 [15](15-firecracker-api-contract.md)。

## 3. e2b 的对象模型

### 3.1 四个概念

| 概念 | 是什么 |
|---|---|
| **Template** | 沙箱的"出厂状态"。用户定义（类似 Dockerfile），构建产出一份可被反复加载的快照 |
| **Build** | 一次 template 构建的产物，有自己的 id |
| **Sandbox** | 一个正在运行的沙箱实例，由某个 build 加载而来 |
| **envd** | 跑在 guest 里的守护进程，负责执行命令、读写文件 |

一个 build 由 `memfile`（guest 内存镜像）、`rootfs`（根文件系统镜像）、`snapfile`（vCPU、GIC、设备状态）
三份东西组成 —— **它本身就是一个快照**。所以 e2b 的用户沙箱不是"启动"出来的，是"恢复"出来的：
`Factory.CreateSandbox`（冷启动，普通内存）只在 template 构建时用；所有用户沙箱走 `Factory.ResumeSandbox`
（`internal/sandbox/sandbox.go`），内存由 UFFD 托管。这个事实决定了脏页跟踪必须在"从快照加载"这条路径上武装
（[13](13-dirty-page-tracking-and-hdbss.md)）。

### 3.2 内存按需拉取

一个 build 的 memfile 可能有几个 GB，而且**不在本地**，在对象存储里。e2b 用 **userfaultfd（UFFD）**：

```
guest 访问一个还没有内容的内存页
    ▼ 缺页 → 内核转交给用户态
UFFD handler（orchestrator 里的组件）
    ▼ 从本地缓存取；没有就经 chunker 从对象存储按块拉
填进这一页，guest 继续跑
```

对本方案的影响：**模板 memfile 在宿主本地并不存在**，回滚路径不能依赖它 —— 这是差分树"全量根"默认开启的原因
（[14](14-memory-diff-tree.md)）。

### 3.3 磁盘分层

rootfs 是只读底座，上面盖一层写时复制（COW）的写层：guest 的写落写层，读先查写层、没有再查底座。
同一个 build 因此可被许多沙箱共享，每个沙箱只占自己写过的部分。本方案的磁盘增量就做在这一层上
（[16](16-disk-layering.md)）。

### 3.4 一个沙箱在宿主上的样子

```
┌──────────────────── orchestrator 进程 ─────────────────────┐
│  沙箱表      代理（端口路由）      Checkpoint Service      │
│    ├── Sandbox 对象                                        │
│    │     ├── process         → Firecracker 的 API socket  │
│    │     ├── Rootfs Provider → Overlay + NBD              │
│    │     ├── Slot            → 网络命名空间、tap、IP       │
│    │     └── Template        → memfile / rootfs / snapfile│
│    └── UFFD handler（每沙箱一个）                          │
└────────────────────────────────────────────────────────────┘
        ▼                   ▼                 ▼
 Firecracker 进程        /dev/nbdX       tap 设备 + netns
        ▼
   KVM（/dev/kvm）
```

"沙箱不能中断"在这里具体化了：中断一次意味着新进程、新 KVM fd、新 tap、新 NBD 设备，
以及把整个工作集重新缺页拉回内存。

用户调 `sandbox.commands.run("ls")` 时，请求经沙箱的公开地址到达 orchestrator 的代理，代理解出
`(sandboxID, port)` 后转发进沙箱。本方案的 API 复用这条路径，只是在最后一跳之前被截下：checkpoint 请求发给
沙箱的 49984 端口，由宿主直接应答（[12](12-architecture.md)）。理由很直接：打快照要暂停虚机，
沙箱内的程序没法暂停自己。

## 4. 虚拟机快照的基本原理

### 4.1 "状态"包括七项

| # | 部分 | 大小量级 | 容易忽略吗 |
|---|---|---|---|
| 1 | guest 内存 | GB | 不会 |
| 2 | vCPU 寄存器 | 每 vCPU 几 KB | 不会 |
| 3 | 中断控制器（aarch64 上的 GIC） | 几 KB | 有点 |
| 4 | 设备逻辑状态（virtio 队列位置、协商特性、中断状态） | 几 KB | **是** |
| 5 | 磁盘 | GB | 不会 |
| 6 | **时间** | —— | **是** |
| 7 | **外部世界对它的记忆** | —— | **非常** |

**时间。** guest 里有单调时钟（`CLOCK_MONOTONIC`）和墙钟（`CLOCK_REALTIME`）。恢复之后单调时钟会**倒退**，
因为它来自 vCPU 的计时器寄存器，而寄存器被恢复成了快照时刻的值。这在快照语义下是唯一自洽的做法；
墙钟则需要外部校回来。验收测试因此不能用时间做活性判据（[18](18-rollback-pitfalls.md)）。

**外部世界的记忆。** guest 退回去了，外部没有：

| 外部记忆 | 退回后的后果 |
|---|---|
| 宿主内核的连接跟踪表（TCP 序号窗口） | guest 发出的包序号"倒退"，被判非法直接丢弃 —— 连接挂死而不是报错 |
| TCP 对端 | 对端记得的序号和 guest 现在用的对不上 |
| 代理的连接池 | 池里的连接对应的 guest 侧状态已经不存在 |
| 已发出的 API 调用 / 已写入的外部数据库 | 无法撤销 |

前三项本方案会处理（[18](18-rollback-pitfalls.md)），最后一项是任何快照方案的硬边界
（用户视角见 [02](02-semantics-and-limits.md)）。

**还要告诉 guest。** guest 完全不知道自己被回滚，随机数种子会被复用、依赖单调时间的缓存和租约会出错。
**VMGenID** 是一个 ACPI 设备，在 guest 内存里放一个 128 位代号，代号变了就意味着"你被从快照恢复了"，
guest 内核据此重新播种。

### 4.2 一致性：为什么必须是同一瞬间

假设内存在 T1 保存、磁盘在 T2 保存（T1 < T2），恢复后 guest 看到的是 T1 的内存和 T2 的磁盘。
guest 的文件系统在内存里维护着页缓存、inode 缓存、未提交的日志事务，于是可能出现：

- 日志里记着一笔已提交的事务，而内存里那个提交操作还没发生；
- 页缓存里一个块的内容比磁盘上的**旧**；
- inode 说文件有 10 个块，磁盘上的分配位图只记了 8 个。

guest 内核可能直接报文件系统损坏，也可能不报、只是静默读到错的数据。唯一正确的做法是**一次暂停内完成**：

```
暂停虚机
  ├── 保存内存
  ├── 保存磁盘
  └── 保存 vCPU / 设备状态
恢复虚机
```

三者于是是同一瞬间的镜像；guest 还没刷盘的数据留在内存镜像里，恢复后它会照常刷下去。
暂停的这段时间叫**冻结窗口**，是快照唯一对业务可见的代价（业务感受到的是"卡了 N 毫秒"）。
这条是本方案的不变量之一（[20](20-failure-semantics.md)）。

### 4.3 全量与增量

全量快照要写出整个 guest 内存：冻结窗口与虚机规格成正比，存储是"每代 × 全量"。

增量快照只写"自上次以来变了的页"，前提是**知道哪些页变了**。宿主上的软件看不到 guest 的写，
必须借助硬件或内核：

| 机制 | 原理 |
|---|---|
| 写保护 + 陷出 | 把页设成只读，第一次写时陷入内核记一笔再放行 |
| 硬件标脏 | CPU 在页表更新时自己把地址记进缓冲区 |

两者的代价差两个数量级，详见 [13](13-dirty-page-tracking-and-hdbss.md)。

有了增量就有了"代"和"链"，也就有了新问题：恢复到第 n 代要不要把 1..n 代全部重放？
删掉中间某一代会怎样？回滚之后比目标更新的那些代还有用吗？答案是
**不重放、按页寻址、历史是树不是链**（[14](14-memory-diff-tree.md)）。

### 4.4 恢复的两种形态：重建与原地回写

**这是全书最重要的分野。**

**重建**：新建进程 → 建 KVM VM、vCPU、中断控制器、设备 → 注册各种 fd、建网卡、挂内存后端 →
加载 vmstate → 跑起来，guest 逐页缺页把工作集换回内存。上游 `PUT /snapshot/load` 和 e2b 原生 resume 都是这条路。
成本 = 建一台虚机的固定开销 + 把工作集换回内存，后者与虚机规格成正比，与"回退了多少"无关。

**原地回写**：虚机暂停 → 把变了的那些页写回活着的内存映射 → 把 vCPU / 设备状态写回既有对象 → 恢复运行。
进程、KVM fd、中断控制器、设备、网卡、内存映射，以及已经在物理内存里的整个工作集，全部原样保留。
成本 = 变了多少就写多少。

| | 重建 | 原地回写 |
|---|---|---|
| 成本正比于 | 虚机规格 | 回退跨度 |
| 沙箱身份 | 新进程（外部标识可以不变） | 同一个进程 |
| 网络、存储连接 | 全部重建 | 保留 |
| 恢复后的性能 | 一段时间内持续缺页 | 立刻满速 |
| 能处理"进程已死"吗 | **能** | 不能 |
| 能跨机器吗 | **能** | 不能 |
| 实现复杂度 | 低（构造函数保证对象自洽） | **高**（要让既有对象重新自洽） |

最后几行是代价：原地回写换来的速度，付出的是适用范围（进程死了、要跨机器都做不了）
和实现复杂度（要处理"从活对象推导出来、又没进快照的状态"，见 [18](18-rollback-pitfalls.md)）。
**本方案选原地回写**，第三部分大半篇幅是在讲这个选择的后果。

### 4.5 一个强判据：kill -9 之后能否复活

怎么证明恢复回来的确实是那个时刻？

```
① 在 guest 里起一个后台进程，记下它的 PID 和启动时刻
② 打一个快照
③ kill -9 那个进程
④ 回滚到 ②
⑤ 检查：进程回来了吗？PID 一样吗？启动时刻一样吗？
```

三个都对上，说明恢复回来的是**完整的内存现场**：进程表、页表、文件描述符、内核里那个进程的全部结构，
都回到了那一刻。**重放操作做不到这件事**，没有任何"反操作"能让一个被 `kill -9` 的进程带着原 PID 回来。
同一条测试顺带证明另一件事：多代快照之间该进程的 PID 和启动时刻不变，说明**打快照的过程没有重启虚机**。
这项验收的结果见 [25](25-results-and-compliance.md)。

## 5. 小结

1. 需求是"Agent 退回上一个已知良好的状态"，特征是**高频、低延迟、不能中断**；重做在时间、副作用、可复现性上都不行，
   应用层撤销覆盖不全。
2. 虚机快照不需要理解做了什么，只记录状态；它退不回外部世界。**内存和磁盘必须一起退。**
3. microVM 设备极少，除内存外的状态只有几十 KB，**优化内存就是优化整个快照**。
4. e2b 的用户沙箱都是由快照恢复来的；内存按需从对象存储拉取，模板 memfile 本地不存在；磁盘是只读底座加 COW 写层。
5. 状态有七项，时间和外部记忆最容易被忽略；各部分必须在**一次暂停内**保存。
6. 恢复分**重建**（成本随规格）与**原地回写**（成本随回退跨度）。本方案选后者，代价是适用范围变窄、实现变复杂。
7. 强判据：**kill -9 的进程回滚后带着原 PID 复活**。
