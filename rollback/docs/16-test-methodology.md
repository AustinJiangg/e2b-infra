# 16 · 测试体系、环境与测量口径

本章定义测试层次、负载、判据和计时口径。方法适用于结果判读，不能替代某一轮实际执行的证明；950 结果在第 17～19 章，920B 的完整结果在附录 B。

## 1. 三层测试

| 层 | 位置 | 证什么 | 怎么跑 |
|---|---|---|---|
| 单元测试与属性测试 | 代码仓库 `KASandbox_0904`（分支 `deltabox-dev`），与被测代码同目录；Go 在 `packages/orchestrator/internal/checkpoint/`、`internal/sandbox/{block,fc,network,rootfs,uffd}/`，FC 在各源文件的 `#[cfg(test)]`，SDK 在 `py-sdk/tests/test_checkpoint_errors.py` | 部件与不变量 | 见[第 27 章](27-development.md) |
| 交付态验收 | `e2b-infra/rollback/scripts/acceptance/`：五个单文件脚本，互不依赖；另有滚动保留长跑驱动 `rolling_keep10.py`，从同目录导入 `checkpoint_concurrent.py` | 整机正确性、耗时、并发、长跑 | 单文件脚本单独拷到目标机即可跑；`rolling_keep10.py` 要与 `checkpoint_concurrent.py` 一起拷 |
| 补充测试与开发态工具 | `rollback/scripts/crtest/`（20 个用例 + 基准）、`rollback/scripts/dev/`（共享 `lib.py` 的工具箱） | 盲区、边界、故障注入、长稳 | 一站式入口 `rollback/scripts/950/run.sh` |

单元测试证的是**部件**，本部分讲的是**整机**。单测守着哪些不变量见 [第 11 章](11-failures-and-invariants.md) 的不变量清单与[第 27 章](27-development.md)；
其中有一类值得单独一提：**属性测试**（`compact_sim_test.go`、`layer_refs_test.go`、`blockset_test.go`）不是写死几个例子，
而是随机生成大量操作序列，每一步都拿实现与一个简单的参照模型（或从盘上重算的结果）比对；其中几组还故意往实现里注入变异，确认测试真的会失败——
这正是"先自证会失败"用在单测上。

几条约定，每一条背后都有一个"为什么"：

- **RPM 构建不跑单元测试。** `%build` 只做 `go build`，单测要在代码仓库里单独跑。
- **交付态脚本故意各带一份宿主探针，不抽公共模块。** 这看起来像没来得及重构，其实是 [附录 C §7](C-evolution-and-cases.md#7-为什么测试要多问一句) 的逻辑用在测试代码自己身上：
  探针取不到信息时，"脏页后端""产物文件系统"这些条件标签会打印成"未知"。一个抽成公共模块、却只拷走一半的脚本，
  不一定会报 `ImportError`，更可能被补一个空壳或被 `try/except` 兜住，然后条件标签整列变成"未知"——
  数字照样打印、报告照样归档，只是再也说不清它们是在什么后端上跑出来的。重复几十行代码，换掉一种静默降级，这笔交易划算。
  crtest 的 `common.py` 出于同一理由从 `checkpoint_concurrent.py` 复制而不 import。
- **正确性与性能分开跑。** 正确性现场（每代上百 MB）不给性能垫噪声，性能档位也不拖慢正确性。
- **开发态脚本按位置参数选判据，顺序敏感。** `correctness.py <方案> [df挂载点]`、`loop.py <方案> [次数]`。
  交付的是 ext4 方案，第一个参数写 `ext4`。手敲时把挂载点当成方案名，会用错的规则去判对的产物、报假 FAIL；
  假 FAIL 比假 PASS 好，但仍会浪费一轮上机时间。
- **都在宿主机上以 root 跑。** 脚本能量到"跑在什么上"，取决于它跑在哪台机器上：

| 能量到的东西 | 在宿主机上跑 | 从别的机器连过来 |
|---|---|---|
| 脏页后端（`hdbss` / `kvm-wp` / `off`） | 问沙箱的 Firecracker API 套接字 | "未知"（套接字是本地文件） |
| 产物路径与文件系统 | 读 orchestrator 进程的 environ 与 `/proc/mounts` | 空 |
| 每代内存 / 磁盘产物实占 | 量 `mem_diff` 与新封层的 `st_blocks` | 量不到 |
| 服务端分段计时 | 读 `timings.json` | 量不到 |
| 客户端墙钟、全部正确性断言 | 有 | 有 |

结论：**正确性可以远程验，性能必须上宿主机**；远程跑出的耗时缺条件标签，按 [第 16 章 §4](#4-条件标签) 不允许引用。

## 3. 口径定义

### 3.1 客户给的是上限，不是口径

"checkpoint ≤ 200 ms"这句话里缺六件事：**谁的钟**（客户端还是服务端）、**哪一次**（第一次还是第 n 次）、
**哪个统计量**（平均、中位数还是最坏值）、**什么负载**（改了多少）、**什么恢复形态**（原地回滚还是另起沙箱）、**什么机器**。
任何一项换一种取法，同一批数据都能得出相反的结论。所以判定之前先把六项钉死，而且钉在**对我们不利**的那一侧——
口径一旦对自己有利，结论就没有说服力。

| 维度 | 本书口径 | 为什么这么定 |
|---|---|---|
| **量什么钟** | **客户端墙钟**：`time.monotonic()` 夹住 SDK 的 checkpoint / restore 调用，含网络往返、代理和服务端全部工作 | 三个钟里最大、最保守；也是客户在自己机器上唯一能复测的（另外两个要读宿主机上的文件） |
| **哪类 checkpoint** | **增量 checkpoint**：服务端回报 `mem_mode=incremental` | 客户指标约束的是高频回退里的每一次；全量根每个沙箱只发生一次（[§3.5](#35-为什么全量单列)） |
| **哪类 restore** | **原地 restore**（沙箱 ID 与 FC 进程不变）。分档基准里是"撤销本档改动"的单跳：从 cpB 回到 cpA | 一跳的代价取决于起点与终点之间差了多少（回滚集），不是目标那一代多大（[第 6 章](06-memory-diff-tree.md)） |
| **统计量** | **p50 判定，p99 并列**；同时给 p90 / max / n | p50 回答"通常多久"，p99 回答"最坏能不能接受"；单次会抖（节点刚重启后的第一轮尤其明显），任何单次数字都不作判定 |
| **分档变量** | **名义改动量**：总改动 0 / 4 / 8 / 16 / 32 / 64 / 128 / 192 / 256 MB，按内存:文件 = **3:1** 拆；512 MB 是极限档，只作拟合锚点 | 增量的成本随"改了多少"走，不随沙箱内存大小走（[§3.4](#34-为什么按改动量分档)） |
| **样本构造** | 每遍一个新沙箱，默认 3 遍；每档样本数由档位表给出（小档密、大档稀），均摊到各遍 | 遍与遍之间可以查漂移；小档耗时短、抖动占比大，样本多 p99 才量得稳 |
| **全量 checkpoint** | 单列，不参与判定（每遍开头那一次） | 一次性成本、不在高频回退的路径上；但必须列出来，否则"增量快多少"没有分母（[§3.5](#35-为什么全量单列)） |
| **冻结窗口** | 解释项，列在墙钟旁边，不用来判定 | 它比墙钟小，拿它判定等于放水；但它才是业务感受到的停顿（[§3.2](#32-三个钟)） |
| **判据前提** | 该轮所有增量迭代 `mem_mode` 必须是 `incremental`，出现 `full` 整轮作废 | 防"增量静默退化成全量"（[附录 C §7](C-evolution-and-cases.md#7-为什么测试要多问一句)）：那种状态下测到的根本不是增量 |

达标线照抄客户，**未限定改动量**：

| 操作 | 达标线 | 判定对象 | 不判定的部分 |
|---|---|---|---|
| checkpoint | ≤ 200 ms | 增量 checkpoint 的客户端墙钟 p50（p99 并列） | 全量根（单列说明） |
| restore | ≤ 100 ms | 原地 restore 的客户端墙钟 p50（p99 并列） | 另起新沙箱的恢复形态（那是原生 snapshot 的路径，[第 15 章](15-native-cooperation-and-cost.md)） |

因为达标线没有限定改动量，判定结果必然是"改动量在多少以内达标"，而不是一句笼统的"达标"。
[第 18 章](18-950-performance.md) 用拟合直线反推"碰线改动量"，就是为了把这句话说完整。

### 3.2 三个钟

| 钟 | 谁产生 | 用途 |
|---|---|---|
| 客户端墙钟 | 脚本自己掐表 | **判定**（单沙箱基准） |
| 服务端 `total` | orchestrator 的 `timings_ms` | 长跑与并发的主口径（[§8.5](#85-计时口径)）；定位"慢在服务端还是路上" |
| 冻结窗口 `frozen` | orchestrator 从 pause 到 resume 的计时 | 解释业务感受到的停顿 |

判定只用第一个，理由是**可复测**加**保守**：冻结窗口要读宿主机上的计时或在 guest 里跑采样器才测得到，客户复现不了，
而且它天然更小，用它判定是在挑一个对自己有利的口径；服务端分段不在宿主机上跑就整列缺省，它回答的是"没达标该改哪"，不是"达没达标"。

三者有一层固定的包含关系：**客户端墙钟 ⊇ 服务端 `total` ⊇ 冻结窗口**。所以墙钟达标，冻结窗口必然达标；反过来不成立。
但"各分段之和"不受这个约束：`timings_ms` 里既有冻结窗口内的段，也有窗口外的段
（例如 restore 的 `assemble_view_pre`、`conntrack_bg`、`wait_envd`），全部相加会超过冻结窗口；
而且 `seal` 只计到换层完成、不等数据落盘（[第 7 章](07-disk-layering.md)），它的耗时也不代表那一步的全部成本。
所以**分段只用来看时间分布，不做加总核对**。全部计时键与含义见 [第 25 章](25-observability.md)。

冻结窗口为什么还要列：墙钟里有多少是虚机真停住的，决定了"要更快该往哪使劲"。
如果某一档墙钟里绝大部分都是冻结，说明这条路上没有"虚机还在跑"的部分可省，要更快只能让暂停窗口本身变短；
反之则说明时间花在了窗口之外（排队、网络、窗口外的准备），优化方向完全不同。

### 3.3 分位数怎么算

三类脚本用了三种取法，引用时要知道是哪一种：

| 脚本 | 取法 | 注意 |
|---|---|---|
| `crtest/bench/analyze.py` | p50 为中间两项取平均的中位数；p90 / p99 用最近秩 `ceil(q·n)`，不插值 | n < 100 时 p99 就是最大值；本轮 950 短表各档为 10～30 个样本 |
| `crtest/bench/compliance.py` | `s[round(q·(n−1))]`，不插值 | n = 60 时 p99 是第二大的样本，可能比 `analyze.py` 的小 |
| `crtest/bench/serial_restore.py`、`acceptance/checkpoint_concurrent.py` | p50 为中位数；其他分位数按 `round(q·(n−1))` 选排序项 | 串行 n=100 的 p99 可小于 max；并发 A 样本少，展示 p50 / max |
| 长跑分析脚本 | 线性插值：`k = (n−1)q`，取 `xs[f] + (xs[c]−xs[f])(k−f)` | 只统计起止标记之间的日志行（[§8.5](#85-计时口径)） |

同一批样本，不同取法的 p99 可以差出一截；偶数样本时，`compliance.py` 的 p50 选单个排序项，也可能与中位数略有差别。所以 [第 18 章](18-950-performance.md) 的分档表 p50 / p99 统一取 `analyze.py` 的主表，
长跑数字统一取线性插值；跨表比较 p99 之前，先确认两边是同一种取法。

### 3.4 为什么按改动量分档

"不同内存快照大小下的性能"是一个自然的提法，但对本方案是问错了变量。
增量 checkpoint 写出的是本代脏页，成本是 O(本代脏页)，与虚机规格无关（[第 6 章](06-memory-diff-tree.md)）：
一台 8 GB 沙箱只改了 4 MB，和一台 2 GB 沙箱改 4 MB 是一样的代价。restore 也一样，它的成本跟回滚集走，不跟内存大小走。
所以"内存快照大小"这个自变量在本方案里被翻译成"**改动量档位**"，这也是唯一能让客户按自己的负载对号入座的分法：
客户知道自己两次 checkpoint 之间大约改多少内存、写多少文件，却很难说清"快照有多大"。

沙箱内存大小只影响两处，都不在判定范围内：全量根的耗时，以及产物的逻辑体积（稀疏文件的表观大小恒等于整份内存）。

### 3.5 为什么全量单列

树根必须自包含，否则一棵树没有可解析的底（[第 6 章](06-memory-diff-tree.md)）。它的代价是写整份 guest 内存，
比常见的增量档高出数倍到数十倍。但它**每个沙箱只发生一次**：一个沙箱做一百次 checkpoint，这一次的代价摊到每次上只剩百分之一，
而且它不在"回退到上一步"这个动作的路径上。

把它算进判定，会得到一个既不反映客户体验、也不反映实现质量的数字；把它藏起来，又会让"增量快多少倍"这句话没有分母。
所以它单列一行，标注"一次性成本，不参与判定"，同时充当增量数字的参照系。

## 4. 条件标签

任何一个耗时或体积数字，不带下面这些不允许被引用：

| 标签 | 为什么 | 从哪读 |
|---|---|---|
| 机型 | 950 与 920B 的 CPU、内核都不同 | `lscpu`、`uname -r` |
| 脏页后端 | `hdbss` / `kvm-wp` / `off`，同样的代码能差几倍 | 问沙箱的 FC API（`dirty_tracking`），脚本开头会打印 |
| 产物盘文件系统与介质 | 真盘还是 loop，ext4 还是别的 | 读 orchestrator **进程**的 environ 与 `/proc/mounts`，不读配置文件（配置只说"本该是什么"） |
| 模板规格 | 全量代价按 guest 内存走 | [附录 E §2](E-environment-and-tools.md#2-测试环境与沙箱规格) |
| 二进制 | 换过二进制的机器上唯一能对上号的东西 | orchestrator 与 FC 的 sha256 |
| 脚本与参数 | 默认值改过就不是同一组数 | 命令行原样抄 |
| 负载形态 | 单沙箱串行、并发几路、页缓存冷热 | 人填 |

以 kvm-wp 为例说明标签为什么不能省：软件写保护下，每个干净页在每次 checkpoint 之后的第一次写都要陷出一次虚机，
这笔开销全含在 920B 的每个数字里，换到有 HDBSS 的机器上会消失。一个不带"脏页后端"的数字，读者没法知道它含不含这笔钱。

三条纪律：

- **不同条件的数不相减。** 950 与 920B 的脏页后端、机型、盘至少三项同时不同，差值不能归因于其中任何一项，尤其不能归因于 HDBSS。
  要量 HDBSS 的收益，只能在同一台 950 上各跑一遍、其余条件不动。
- **空着比错的数强。** 读不到的格子写"-"或"待测"，不猜、不折算、不用"大约"填格子。一个错的数会被引用很多年，一个空格只会被人问一句。
- **口径说明和数字放在一起。** 分开放，数字一定会被单独引用。所以每一轮实测都要有一份写明条件的留档（[第 20 章](20-acceptance.md)）。

## 5. 负载构造：三种失真

判定表第一列是"改动 N MB"，这一列成立的前提是**标签上的 N 等于服务端实际搬运的量**。
这是整套性能测试里最容易做错的一步，比调哪个 API 难得多。

### 5.1 失真一：分配成本混进档位

第一次申请并写一块新内存，内核要清零、建页表；第一次写一个新文件，文件系统要分配块。这笔开销与"改"无关，
但如果每档都重新分配，它就被算进了档位，而且档位越大混进去的越多，曲线的斜率被抬高。

### 5.2 失真二：写放大

用 shell 字符串拼接、命令替换之类的方式造内存负载，看起来"写了 N MB"，实际上缓冲区要复制、增长过程中 `realloc` 留下中间态、
上一代释放之后重新缺页——每一步都在弄脏额外的页。在同一张档位表上对照原生快照时，那一侧早期的负载脚本就是这么造的，
实测的内存差分是名义量的数倍，表完全没法看（那一侧后来重写了负载生成）。

### 5.3 失真三：负载放错层

**快照只能带回它覆盖范围内的东西。负载放在覆盖范围之外，测出来的既是零成本，也是假通过。**
本方案对整个 guest 内存与整块根盘做快照，于是有一个很干净的分工：

| 负载写在哪 | 脏的是什么 | 在哪一列出现 |
|---|---|---|
| `/dev/shm`（tmpfs） | tmpfs 的页就是 guest 内存的页，且不落块设备 | 只进内存差分 |
| 根文件系统（`/bench-root`） | 磁盘写层（[第 7 章](07-disk-layering.md)） | 进盘层，**同时**在内存里留一份页缓存 |

两半分开放，就能分别控制、分别验证。

### 5.4 解法：预热加原地覆写

所有基准脚本最后都收敛到同一个两步法：

1. **预热**：先把内存文件和磁盘文件一次撑到最大档位。这一代承担全部分配成本，不计入任何档位。
2. **原地覆写**：之后每档用 `dd ... conv=notrunc` 只覆写前 N MB。`conv=notrunc` 是要害：没有它，`dd` 会先把文件截断成零再写，
   文件大小每档都在变、每档都重新分配，失真一原样回来。

数据用随机源（`/dev/urandom` 或预生成的随机块），不用全零：全零页会被稀疏文件、去重、压缩各层特殊对待，随机数据量到的是最坏、也是最诚实的情况。
造负载的命令本身也要"干净"：一条 `dd` 从随机源直接写到目标文件，中间不经过 shell 变量。

### 5.5 文件那份故意不用 `O_DIRECT`

文件负载是**普通缓冲写 + `sync`**：真实用户就是这么写的。数据先进 guest 页缓存再刷到虚拟盘，所以一份文件写会**同时**出现在
内存差分（页缓存那些页）和盘层（落盘的块）里。这不是测量误差，是页缓存的本性。于是读表时有两条固定预期：

- **实测内存 ≈ 名义内存 + 名义文件，实测盘层 ≈ 名义文件。** 偏离这个关系，先查负载，再读时间。
- 验证读回时反过来，必须 `iflag=direct` 绕开页缓存，否则读到的可能是缓存里的内容而不是盘上的（[第 17 章 §1.4](17-functional-verification.md#14-pause_verifypy一个自洽的静默损坏)）。

### 5.6 3:1 从哪来，以及三组附表

总改动量按内存:文件 = 3:1 拆分，理由是沙箱里跑代码的真实负载通常改内存远多于改文件。所以 256 MB 档实际是内存 192 MB + 文件 64 MB。
**判定表固定用 3:1**，换了比例的数据属于另一条曲线，不和判定表混排。另有三组附表用来求各自的斜率、也各自是一道哨兵：

- **纯内存**、**纯文件**两组：把混合档的成本拆成两条斜率，看各自是否线性；
- **只读触碰**一组：只读、不写。读不算脏，它的产物与耗时应当与 0 MB 档几乎相同；一旦明显变大，就是 [附录 C §7](C-evolution-and-cases.md#7-为什么测试要多问一句) 说的"读被算成脏"。

冻结窗口只有在 guest 里采样才看得见；链深与写入量这两个变量，只有专门设计的对照才拆得开。

### 6.1 `bench_tiers.py`：一次迭代为什么这样设计

一次迭代 = 处在基线 checkpoint cpA 的状态 → 在 guest 里造本档规定量的改动 → 增量 checkpoint 出 cpB（记分段、墙钟、产物字节）→
restore 回 cpA（撤销这份改动）→ 校验现场 → 删掉 cpB。

这个设计同时解决了三件事：

- **链深配平**：cpB 每次都挂在 cpA 下面、用完就删，链不会随迭代变深，档与档之间、同档前后样本之间，链深都相同。
  链深是另一个可能影响耗时的变量，不配平的话档位之间就没法比。
- **restore 的量就是本档的量**：从 cpB 回 cpA 的回滚集，正好是本档造的那份改动，所以 restore 那一列也能按同一个档位读。
- **每次都校验**：restore 之后读回代号与内容，落错代记异常。耗时数字只有在"落对了"的前提下才有意义。

判据前提与异常：`mem_mode` 全是 `incremental`、每次 restore 后现场一致，否则判失败；**超达标线不判失败**，那是结论不是故障。

### 6.2 `checkpoint_bench.py`：时机成本与直接量产物

交付态脚本，单文件、零依赖，一个沙箱一条链：全量根 → 预热 → 两遍档位 → 逐级退回。它回答两个别处不回答的问题。

**快照时机值多少钱。** 同一套档位拍两遍，唯一区别是什么时候拍：

| 遍 | 做法 | 口径 |
|---|---|---|
| ① 立刻拍 | 写完立刻 checkpoint | 最坏上界：刚写的文件数据正被宿主内核往盘上刷，会和写内存差分抢磁盘 |
| ② 冲干净再拍 | 写完先 `sync` 并歇 1 s 再 checkpoint | 日常口径，贴近"写完跑了一会儿才拍" |

两遍负载完全相同，所以 **① 减 ② 就是"写完立刻拍"这个时机的成本，不是快照机制的成本**。用主动 `sync` 而不是干等，
是因为内核平时按自己的节奏刷脏页（脏页过期约 30 s），干等太慢；`sync` 等价于"已经过去了一会儿"，而且只刷脏页、无破坏性。

**服务端到底写下多少。** 直接去产物目录上量：内存看这一代 `mem_diff` 的 `st_blocks × 512`（差分是稀疏文件，表观大小是整个地址空间，实占才是真写下去的量）；
磁盘看 `layers/` 下这一代新出现的封层实占。这一列的价值是**把档位标签和服务端行为对上账**：[§5.2](#52-失真二写放大) 那种放大一眼就能看出来。

**退一代的代价归上一行。** 逐级退回时，每一跳要撤销的是"被退掉的那一代建之前弄脏的量"，不是目标那一代自己弄脏了多少，
所以每一跳的档位标签取自被退掉的那一代。每一跳都读回代号确认真落到了目标代；落错就整轮判失败。

restore 表里另有一列"读盘"（`materialize_disk_read_mb` 与 `fc_rollback_disk_read_mb`）。没有这一列，一次真读了盘的恢复和一次没读的长得一模一样，只是慢些；
"恢复成本与链深无关"也就分不清是结论，还是"链正好还热着"。

### 6.3 冻结窗口怎么测

`freeze_probe.py` 是推进 guest 里跑的一个约 2.5 kHz 的单调时钟采样器。虚机被暂停时，guest 里的一切都停住，包括这个采样器，
于是它的时间序列里会留下一个"洞"，洞的宽度就是虚机真正被冻结的时长。

几个设计取舍：采样率再高就成了忙等、和被测负载抢 CPU，再低就分辨不出几毫秒的抖动；采样器只写一个预分配好的数组，
不产生额外脏页、不刷盘，否则它会污染低档位的脏页量；探针只启动一次，因为解释器启动本身要弄脏十几 MB。

这个测法自带分辨率下限，所以每档先跑一遍**底噪**：同样的弄脏节奏但不做 checkpoint，取采样器观测到的最大间隔。
判据是 `min(冻结) > 2 × 底噪` 才标"可区分"，否则标"与底噪不可区分"，那一格的冻结值不作数。

`bench-ckpt.py` 另有一段**持续连打**：不停 checkpoint 一段时间，比较前 1/3 与后 1/3 的 p50。单次快不等于扛得住连打；
劣化倍数明显大于 1 时，单次的数字就不能直接外推到高频场景。

### 6.4 把两个绑在一起的变量拆开

连打变慢时，有两个变量同时在涨：链在变深，累计写入量在变大。不拆开就不知道该往哪治。

`timing.py` 拆"回滚集大小"和"链深"：链深 5 / 20 / 50 各建一条链，每代写脏不同的 4 MB（错开偏移，没有任何后代覆盖它，是内容解析的最坏情况），
然后测两种跳：

| 跳法 | 路径纪元数 | 变的是什么 |
|---|---|---|
| 深集 tip ↔ root | 随链深涨 | 回滚集随链深一起涨，两个变量绑在一起 |
| 浅集 tip ↔ tip−1 | 恒为 1 | **只有目标所处的深度在变**——这才是链深本身的成本 |

浅集的曲线平，说明链深本身不收费，只有要撤销的量收费；这正是 [第 6 章](06-memory-diff-tree.md) 的成本模型所预言的，
也是本方案不需要周期性压平历史的依据。

`probe-ramp.py` 拆"代数"和"字节"：做同样多次 checkpoint，但把每次的脏页量拉开（例如 0 MB、32 MB、256 MB 三档）。
如果爬升由代数驱动，三条曲线按"第几代"对齐时应当重合；如果由写入量驱动，按"累计写了多少 GB"对齐时才重合。
两种归一化各算一遍斜率，看哪一种把三条曲线收拢：`spread_per_gen < spread_per_gb / 2` 判 `depth`，反过来判 `bytes`，都不成立判 `mixed`。
**判据写在脚本里，不靠人看图。**

### 6.5 怎么读一份报告

拿到 `bench_tiers.py` 的一轮结果，按这个顺序读：

1. `analyze.log` 开头的"异常记录：0 条"与"`mem_mode` 取值"两行。**不过关就不用读时间。**
2. "缓存与漂移"一节：`materialize_disk_read_mb` 与 `fc_rollback_disk_read_mb` 是否全为 0（页缓存全热），遍与遍之间的冻结窗口比值是否接近 1。
   这决定了这批数字是冷还是热、有没有随时间漂。
3. "实际产物对名义改动"：是否满足 [§5.5](#55-文件那份故意不用-o_direct) 的两条固定预期。不满足先查负载。
4. 这之后才读主表、判定与拟合。

体积有三种口径，必须分开读：**逻辑体积**（`du --apparent-size`）恒等于整份内存，因为每一代给出的都是一份完整的内存视图；
**实占**（按 `st_blocks`）才是这一代真写下的量；**新增物理空间**（整段跑完 `df` 的净增量）才是盘上真正少掉的空间，
在有块共享的存储上，只有它可以横向比较。

## 7. 空闲后 restore 与串口的专项测法

这两项不在仓库脚本里，数据来自工作区的定向复现工具。这里记测法和每一臂的用意，便于复测时对齐口径：

- **空闲后 restore**：同一沙箱串行。先拍 cpA 作目标，然后循环"sleep T 秒 → checkpoint cpB → restore cpA → 删 cpB"，
  T 取 0 / 0.5 / 2 / 5 / 10 s，看 restore 耗时是否随空闲时长上涨。另两臂各拆一个变量：
  a 臂 sleep 2 s 后**不拍** cpB 直接 restore，看"restore 之前先 checkpoint 一次"是否掩盖了空闲的影响；
  b 臂在 guest 里常驻一个 100 ms 一次的忙循环，看"guest 从未真正空闲"时现象是否消失。
  `serial_restore.py` 是背靠背连续 restore，在它外面加 sleep 不等于"空闲后 restore"：它没有中间那次 checkpoint。
- **串口段**：每段一个新沙箱、单沙箱随机负载跑 180 s，旁路抓 tap 与 eth 报文、采样 vCPU，
  判据是串口是否卡死、串口行间隔是否有 > 2 s 的缺口。每段一个新沙箱，是为了让"某一段卡死"不污染后面的段。

## 8. 并发与长跑的测量

单沙箱基准回答"一次多快"。有一类问题它永远回答不了：**跑久了、跑多了会怎样。**
隐藏条目会不会越积越多、层文件会不会漏回收、链会不会越来越深、盘会不会一直涨、GC 停顿会不会越来越长、
罕见的截断与失联一小时出几次——这些都不会在第一次、第一百次里露出来，只会在数万次操作、数十分钟之后露出来。
本节定义920B历史D段及滚动保留长测的测量方法，对应[附录B的轮次与结果](B-920b-results.md#9-轮次总表)。950的A/B、T36和T40分别采用[第 19 章](19-950-concurrency.md)所列的实际负载、客户端墙钟和统计口径，不统一套用本节的服务端长测口径。

### 8.1 驱动与负载

驱动是 `checkpoint_concurrent.py --stages D`（[第 16 章 §9](#9-checkpoint_concurrentpy并发四段)）：
每个沙箱一个线程，随机循环：50% 写脏（内存 8 MB + 文件 4 MB + 代号标记 + `sync`）后 checkpoint、35% restore 到随机一个已有 checkpoint、
15% delete，每次 restore 后逐项校验 5 个字段。在它之上用三种负载，它们回答的问题不同，数字**不混排**；另加 [§7](#7-空闲后-restore-与串口的专项测法) 的串口段，长跑与并发一共是"三种负载 + 串口段"：

| 负载 | 怎么造 | 代表什么 | 用途 |
|---|---|---|---|
| **上限 60** | 服务端设 `CHECKPOINT_MAX_PER_SANDBOX=60`，16 沙箱 30 min；驱动收到 429 不主动删，只记一条失败继续随机循环 | 客户"把数量卡住"的常规用法 | 常规负载的耗时、占盘与走平判定 |
| **滚动保留 10** | 驱动每个沙箱只保留最新 10 个：写脏 → checkpoint → 可见数超过 10 就删最旧的；每轮以 0.25 的概率 restore 到保留集合里随机一个并逐项校验，之后从那里继续 checkpoint | 客户"保留最新 N 个、删最旧"的用法 | 合并（compact / fold）是否让条目、层、链深、占盘收敛；长期运行时 restore 是否随时间变慢 |
| **无上限压测** | 不设上限、驱动只随机删 | 找问题用 | 链深会长到几百上千、页缓存与回收压力远大于常规用法；只用来暴露问题和验证正确性，**耗时不进判定** |

以下说明用于判读[附录B的920B长测](B-920b-results.md#10-最终版的结果)：

- **上限 60 下 restore 占比远高于名义的 35%。** 可见 checkpoint 很快顶到 60，之后大部分 checkpoint 被 429 拒掉（客户端记为失败；
  服务端在准备阶段就拒绝，不暂停虚机），循环里真正落到服务端的操作以 restore 为主。所以这种负载的 restore 次数远多于不设上限时，429 也不算故障。
- **滚动保留 10 专门制造"删的都是下一个的父节点"。** 每次删最旧的，它都还有一个子节点，只能隐藏；合并正是为这种形态设计的（[第 6 章](06-memory-diff-tree.md)）。
  这个负载配一组**关掉合并**（`CHECKPOINT_COMPACT=false`）的对照，才能说明走平是合并带来的。
  滚动保留的驱动是 D 段之上的一层薄封装 [`rolling_keep10.py`](../scripts/acceptance/rolling_keep10.py)：复用 D 段的建沙箱、写脏与逐项校验，只把随机循环换成上表的滚动逻辑；保留个数 `--keep`（默认 10）与 restore 概率 `--restore-p`（默认 0.25）是它自己的参数，沙箱寿命由环境变量 `SPAWN_TIMEOUT` 给（默认 10800 s），用法写在脚本头注释里。
- **T36 全规模**（`--sandboxes 16 --seconds 1800`）是另一个独立的长稳负载，计时是客户端的，与 D 段的服务端数字不并表。
- **超过 1 h 的长跑要显式把沙箱寿命设大。** 驱动建沙箱默认 timeout 3600 s，到点沙箱被回收，客户端会对着死沙箱空转，整轮作废。
- **起跑前的现场要干净。** 确认 netns 数已稳定、跑的是想要的二进制与开关（看能力文件或能力行），否则长尾里会混进环境噪声。

并发扩展性（N 个沙箱同时做同一操作时耗时怎么涨）用 A 段测，同沙箱多调用方用 B 段测，它们是短测，口径同 [§3](#3-口径定义)。

### 8.2 正确性判据

- **逐项一致**：`D.json` 的 `verified` = 场景校验通过数 / 进入校验的 restore 数。每次 restore 后在 guest 里取 5 个字段
  （`/dev/shm/gen`、`/bench-root/gen`、两个 blob 前 4 MiB 的 md5、心跳进程 pid），与该 checkpoint 拍下时记录的值逐项比，必须完全相同。
  判据是**不一致数为 0**，不是"成功率很高"。
- **什么不进入校验**：restore RPC 成功、但紧接着的 guest 命令被截断的，不进入校验，也不算不一致——它是可用性问题（单独计数），不是正确性问题。
- **出现不一致时全体停手、保留现场**：滚动保留负载复用同一套校验；D 段第一次 restore RPC 失败的沙箱停手留现场。
- **存活**：每个 worker 线程跑满全程；结束时每个沙箱仍然可用（`alive`）。线程提前退出要当作失败追查，而不是当作"样本少了一点"。
- **多轮累加的口径**："restore 总数"只累加各轮 `D.json` 的 `verified` 分子（以及同口径的串口段），不把 T36、分档基准、func 档里的 restore 混进去；
  另计的写明另计。
- **客户端失败要分类**：429（上限拒绝，预期）、截断（按 [§8.6](#86-旁路取证) 两侧对照定位）、客户端连接层错误（服务端没收到请求的那类，只记录）分开数，不能混成一个"失败率"。

### 8.3 资源判据："走平"怎么判

长跑要证明的不是"跑完了"，而是"**再跑下去也不会出事**"。所以资源类指标要看趋势：

- **旁路采样**：产物盘 `df` 每 10 s 一次；另一个只读 manifest 的采样器每 60 s 统计一次每沙箱的目录数、可见 / 隐藏条目数、层文件数和
  **真实链深**（沿 `parent_id` 走到根的最大深度，含隐藏条目）。D 段自己打印的"链深"是**每沙箱同时存在的可见 checkpoint 数**，不是真实链深，两者不能混用。
- **走平的判法**：对采样序列在**最后 15 min** 做最小二乘，得到每分钟斜率，与**最前 15 min** 的斜率并列。
  后段斜率接近 0（或为负）判"走平"；后段斜率与前段相当，说明还在线性增长，跑得再久也会写满。
  只看终值不够：一个还在线性涨的量，终值多大都只是"跑得不够久"。
- **对照**：走平要有一组不走平的对照才有说服力（例如关掉合并的滚动保留、修复前的二进制），同负载、同时长、同一台机器。
- **其他要看的**：FC 进程数、netns 数、orchestrator 的文件描述符数在收尾后回到起跑前的水平；产物目录在沙箱销毁后清空。

### 8.4 读盘量：用哪个键

restore 的读盘量有两套口径，并发时读数完全不同（各键的定义只在 [第 25 章 §3.3](25-observability.md#33-restore)）：

- `materialize_read_mb`、`materialize_base_read_mb` 由物化过程自己边读边计，含页缓存命中，只计本沙箱，并发时也可直接比较；
- `materialize_disk_read_mb` 是 **orchestrator 进程级**的真实读盘差值，并发时会混入同时段其他沙箱的读；
- `fc_rollback_disk_read_mb` 是该沙箱 FC 进程的真实读盘差值，FC 每沙箱一个进程，不混入别的沙箱。

单沙箱基准里，后两个键非零表示真的读了盘、页缓存不热；并发和长跑里看 `materialize_read_mb`：
它反映的是"这次 restore 要搬多少"，长跑中它若随时间上涨，restore 变慢就是工作量变大，而不是实现退化。

### 8.5 计时口径

- **上述920B长测的主口径是服务端 `timings_ms`**：从 orchestrator 日志里每次操作的完成行（`created checkpoint`、`restored checkpoint`、`deleted checkpoint`）取。
  不用客户端墙钟，是因为长跑时一台客户端上有几十个线程、每个线程还在做写脏与校验，客户端墙钟里混着客户端自己的调度与排队，
  量到的不全是服务端的事。客户端墙钟只在注明时使用（例如 T36）。
- **时间窗**：驱动起跑前和结束后各写一个时间标记，只统计两个标记之间的日志行；起跑前的建沙箱、结束后的清理都不算。
- **分段看漂移**：按 300 s 或 600 s 一段分别算 p50 / p99，看是否随时间上涨。一个全程 p50 掩盖不了"后半程比前半程慢一倍"。
- **分位数用线性插值**（[§3.3](#33-分位数怎么算)）。
- **全量 checkpoint 仍然单列**：起跑时每个沙箱的第一个 checkpoint 是全量，它们会出现在 checkpoint 的最大值里；读最大值时先排除这一簇。
- **修复前后的对照**：同一台机器、同一种负载、同一时长，只换二进制。耗时类数字不跨负载做前后对比（无上限压测的链深上千，与上限 60 不是一回事）；
  计数类指标（GC 长停顿次数、截断次数）如果修复前只有另一种负载的数据，对比时必须写明两边各是什么负载。

### 8.6 旁路取证

长跑里出现的长尾，要靠旁路数据才解释得了：

- **GC 停顿**：服务端开 `GODEBUG=gctrace=1`，STW 取每行的清扫终止 + 标记终止两段之和；需要区分"等所有 P 停下"和"收集器本身"时，
  再开 `CHECKPOINT_RUNTIME_METRICS=1`，每 10 s 一行 runtime/metrics 直方图（分位取桶上界，不会低估）。开关见 [第 24 章](24-configuration-and-capacity.md)。
- **内存压力**：orchestrator 与它拉起的 FC 在同一个 memory cgroup 里（记账的是页缓存与进程堆，guest 内存走大页不记账，
  [第 12 章 §8](12-state-and-lifecycle.md#8-节点级效应)），采样 cgroup 的用量与 `failcnt`，用来解释 GC 停顿和缺页路径上的回收。
- **流式截断**：客户端按异常类（`incomplete chunked read` 一类）计数，同时在 orchestrator 与 client-proxy 日志里数 `ReverseProxy read error`，
  两侧对照判断截断发生在哪一跳；需要逐请求取证时开 `PROXY_TRACE`（[第 25 章](25-observability.md)）。
- **宿主连接跟踪表**：每 5 s 采一次 `nf_conntrack_count`，用来解释 `conntrack_bg` 的变化——它的耗时随宿主表大小走。

## 9. `checkpoint_concurrent.py`：并发四段

前面的脚本都是一个沙箱、一个调用方。真实部署里同一台宿主上几十个沙箱各自在拍，偶尔还有同一个沙箱被两个客户端同时操作。
这个脚本把并发拆成四段，每段回答一个问题：

| 段 | 做什么 | 断言 |
|---|---|---|
| **A** 跨沙箱扇出 | N 个沙箱用 barrier 对齐同时发同一操作，N 从 1 涨到 16（`--fanout`），每跳验回到了哪一代 | 看 p50 / 最坏随 N 怎么涨、涨在服务端哪一段；宿主侧同时记产物盘写入与 orchestrator CPU |
| **B** 同沙箱争用 | 一个沙箱 T 个线程（默认 4）各自循环 checkpoint → restore → list，默认各走各的连接 | 不断言现场（并发下没有定义）；断言操作全部收敛、没有错误、沙箱存活、`list` 不比成功数多（无幽灵）、每个 checkpoint 都回得去 |
| **D** 混合稳态 | S 个沙箱（默认 8）各自单线程随机循环 T 秒：50% 写脏（内存 8 MB + 文件 4 MB）后 checkpoint、35% restore 到随机一个已有 checkpoint、15% delete | 每次 restore 后逐项比 5 个字段：`mem_gen`、`file_gen`、内存 blob 前 4 MiB md5、文件 blob 前 4 MiB md5、心跳 pid |
| **C** 生命周期竞争 | checkpoint / restore 进行中 kill 或原生 pause | 默认不跑，要 `--lifecycle`；可能打挂 orchestrator，宿主上有别人的沙箱时不要开 |

A 段存在的理由：服务端跨沙箱的共享点只有三处——store 的全局锁、产物盘带宽、宿主连接跟踪表——A 段就是去量这几处到底贵不贵。
B 段的要点是"排队而不是出错"：服务端按沙箱串行，要看的是排队是否算进客户端超时、超时之后服务端是否照做了（幽灵 checkpoint）。
D 段把"每个沙箱内部串行"和"沙箱之间并发"组合起来：沙箱内部串行，所以每次 restore 的现场是良定义的、可以逐项验；沙箱之间并发，所以能看出互相踩没踩。

D 段的循环体整体包在 `try` 里，任何异常只记一条失败、不带走线程；第一次 restore RPC 失败时该沙箱停手
（否则之后每次调用都往死沙箱上叠一条错误，几分钟就把服务端日志冲光、现场没了），
在 `--keep-on-failure` 时留下沙箱、抄 FC 状态与日志。收到 429 不主动删，只记失败继续。
`D.json` 的 `verified` = 校验通过数 / 进入校验的 restore 数。长跑怎么用它、怎么判定、怎么计时，见 [第 16 章 §8](#8-并发与长跑的测量)。

## 10. 为什么要长跑

分档基准每一档只跑几十到一百次迭代，每遍都换新沙箱，测的是"一次操作本身"。有三类问题它天然看不见：

| 类别 | 特征 | 本次的真实例子 |
|---|---|---|
| **积累类** | 每次操作留下一点东西，单次无害，累计到几千、几万次才显形 | 隐藏 checkpoint 无上界积累（[附录 C §8.8](C-evolution-and-cases.md#88-隐藏-checkpoint-无上界积累磁盘随时间线性增长)）：可见数被上限卡在 60，目录数却在 30 min 里从 1562 涨到 3943，产物盘增长 340.6 GiB 且没有走平的迹象；rootfs 层文件从不回收（[附录 C §8.7](C-evolution-and-cases.md#87-rootfs-层文件从不回收)）：30 min 后层文件数等于累计 checkpoint 数 |
| **概率类** | 每次操作有极小概率撞上一个竞态或长尾，短测里期望次数小于 1 | 流式命令偶发截断（[附录 C §8.1](C-evolution-and-cases.md#81-流式命令偶发截断)）：实测约每万次代理请求 0.5 次，16 沙箱 30 min 才 5–10 次；Go GC 的长暂停（[附录 C §8.4](C-evolution-and-cases.md#84-gc-长暂停落进别的沙箱的冻结窗口)）：修复前一轮 30 min 里 ≥ 100 ms 的有 180 次（long2），最长一次 609 ms（long1），单沙箱串行的基准里一次也看不到；16 路并发首个增量 checkpoint 的两种形态（[附录 C §8.11](C-evolution-and-cases.md#811-16-路并发的首个增量-checkpoint-有两种形态)） |
| **随时间劣化类** | 某个量随运行时间单调增长，操作耗时跟着涨 | 视图块数（[附录 C §8.9](C-evolution-and-cases.md#89-视图块数增长restore-随时间变慢)）：guest 的 ext4 不断在新块上重写小文件，2 h 里每沙箱视图块数从约 4.1 万涨到约 9.4 万，restore p50 随之从 90.9 ms 涨到 160.7 ms；`commit_index` 随链深线性变慢（[附录 C §8.2](C-evolution-and-cases.md#82-每次-checkpoint-整份重写-indexjson)）：链深 2000 以上时 p50 132 ms |

还有第四类是**跨沙箱干扰**：同一节点上的沙箱共享账本锁、宿主 conntrack 表和一个 memory cgroup（[第 12 章 §8](12-state-and-lifecycle.md#8-节点级效应)）。
一个沙箱在锁里删文件、一次宿主表清扫、一次卡在内存回收里的缺页，代价都会落到**别的**沙箱的冻结窗口里。
单沙箱基准没有"别的沙箱"，这类问题只能在并发下看到。

所以本期的做法是：每修一个问题，就用同一套负载再跑一轮 30 min 以上的长跑，对照上一轮。十几轮下来，
既验证了修复，也不断暴露下一个问题。本章 [附录 B §9](B-920b-results.md#9-轮次总表) 的轮次总表就是这条链。

## 11. 偶发问题怎么缩小范围

正确性脚本和 crtest 用例抓的是"每次都会出现"的错。长跑里偶尔出现一次、几百次里出一次的问题，要换一种做法。
下面几条来自本项目追查偶发挂死、偶发截断的经历，写成可复用的方法：

1. **先把"慢"和"挂"分开。** 给被怀疑的操作设一个明显大于正常最坏值、又明显小于服务端兜底超时的时限
   （例如正常 restore 在亚秒级，服务端等 guest 应答要 45 s，那就取 20 s）：既能把挂死和正常长尾分开，又不必每次都等满兜底超时。
2. **复现脚本不能被单次失败打断。** 正确性脚本挂住就整条挂住，一晚上只拿到一个样本；复现脚本要超时后记下现场、接着跑下一轮，
   并把结果**边跑边写**到 JSON，中途被打断也不丢数据。
3. **阴性结果也是结果，要写下来。** "纯跨分支 restore 连打一百多次零异常"说明触发条件不是跨分支本身；
   这样的阴性结果能把搜索空间砍掉一大半，逼出"问题在别的维度上"的判断。
4. **从唯一异常的观测量出发施压。** 失败那次现场里唯一与众不同的量（例如回滚瞬间在途的网络接收描述符特别多），
   即使不是充分条件，也是唯一能施加压力的方向：构造负载把这个量推到极端，再看失败率是否上升。
5. **失败那一轮自动抓现场。** 循环脚本在失败时按沙箱 ID 把服务端日志切出来存好，通过的轮次日志直接删掉；
   事后在几百轮的日志里翻，是翻不动的。D 段的"第一次 restore 失败就停手并留现场"（[§9](#9-checkpoint_concurrentpy并发四段)）是同一条思路。

这类复现脚本是一次性的追查工具，不是验收资产，不随交付件发布；把它们沉淀成固定用例的，是 crtest 里的回归用例（例如 T26 串口、T40 restore 紧跟请求）。

## 12. 验证：五类证据

证据按 [第 14 章 §2](14-native-precise-increment.md#2-原生内存增量的三层) 的三层，加上"退路""与 checkpoint 叠加""与本方案共存"组织。每一类证明的东西不同，缺一类就有一层没被证明。

### 12.1 体积等于位图真值（证明 ① 生效）

- `pb2.py` 修复后"实际导出"与"写跟踪位图"逐行相等（[附录 B §13.1](B-920b-results.md#131-pb2py-三列并排)）。
- `native_snapshot_bench.py` 六档 memfile 从恒约 440 MB 变成随写入量线性（[附录 B §13.3](B-920b-results.md#133-native_snapshot_benchpy六档)）。

### 12.2 跨代拼接正确（证明 ② ③ 生效）

- `native_snapshot_bench.py` 两种模式全部档位：内存代号、文件代号、大文件 md5 全部回到目标代（920B，09-11 与 09-14）。
  snapshot 模式每一代都另起新沙箱恢复，意味着每一代的 4 KiB header 都被实际用来填页。
- `pb5.py`：三代快照分别改**同一个 2 MiB 块里的不同 4 KiB 页**，第二代还把一页清零；每一代另起沙箱验 md5。第三代视角下，这个 2 MiB 块由三代拼成：
