# 19 · 测试体系与功能验证

## 本章目标

读完本章，你应该能：

1. 说出这套方案特有的四种"静默失效"，并对每一种说清它为什么不会让任何断言变红、要靠什么才看得见；
2. 解释正确性判据为什么是"内存标记、内存大块、磁盘标记与大文件"三重证据再加上进程，每一重排除了什么；
3. 看懂 `checkpoint_verify.py` 的 59 项、`correctness.py` 的 28 项是怎么数出来的，知道项数变了意味着什么；
4. 说出三层测试、crtest 各用例和 `run.sh` 各档各自证明什么，在哪台机器上证到了哪一步；
5. 在排查偶发问题、编写新用例时，用上"先自证会失败""磁盘内容一律 `O_DIRECT` 读回""报告记项数"这几条纪律。

上一章（[18](18-native-and-checkpoint-together.md)）把两种快照的分工讲完，第四部分到此结束。第五部分从这一章开始。前四部分讲的是原理：内存差分树怎么只存本代脏页（[06](06-memory-diff-tree.md)）、
磁盘怎么零拷贝封层（[07](07-disk-layering.md)）、Firecracker 怎么在同一个进程里原地回滚（[09](09-in-place-rollback.md)）、
失败时凭什么"宁可报错、不可静默损坏"（[12](12-failure-semantics.md)），以及原生快照的增量怎么改精确（[15](15-native-increment-diagnosis.md)–[17](17-native-increment-cost-and-verification.md)）。
原理讲得再通，也还欠两句话没有证明：**它真的对**，以及**它真的快**。第五部分就回答这两句话。
本章讲"怎么证明它对"：测试体系怎么分层、每个正确性脚本用什么判据、为什么判据要长成那样；
下一章 [20](20-performance-methodology.md) 讲"怎么证明它快"时用的口径；[21](21-benchmarks-and-compliance.md) 与 [22](22-long-run-and-concurrency.md) 给出实测结果。

本章不放实测数字，数字在 [21](21-benchmarks-and-compliance.md)、[22](22-long-run-and-concurrency.md)；上机操作步骤在 [30](30-acceptance-runbook.md)。

## 1. 为什么测试要多问一句

普通的功能测试只问一句"结果对不对"。这套方案的麻烦在于：它有四种失效，其中三种**不改变结果**。
回滚回来的内容一个字节都没错，断言全部通过，坏掉的是成本、是覆盖范围、或者是判据本身。
剩下的一种会改变结果，但它改得"自洽"，同样没有任何断言会变红。

所以本部分所有测试的出发点是：除了问"做对了没有"，还要多问一句"**是怎么做到的**"。
下面四节各讲一种失效，每一种都配一个在本项目里真实出现过的例子。

### 1.1 增量静默退化成全量

**是什么。** 增量 checkpoint 的前提是 Firecracker 在虚机启动时就武装了脏页跟踪（[05](05-dirty-page-tracking-and-hdbss.md)）。
机器上没有 HDBSS、orchestrator 又没有显式设 `FC_TRACK_DIRTY_PAGES=true` 时，跟踪默认关闭（为什么默认关见 [26 §1](26-deployment-prerequisites.md#1-先分清两层要不要记脏页用什么方式记)），
这时每一次 checkpoint 都只能整份拷走 guest 内存。

**真实例子。** 920B 开发机没有 HDBSS，靠 nomad job 里显式写的 `FC_TRACK_DIRTY_PAGES=true` 得到增量。
这一行不在交付件里（950 不需要它），所以只要在 920B 上按交付件原样部署、忘了补这一行，就会进入这种状态：
沙箱照常建、checkpoint 照常成功、restore 照常回到那一刻，一次 checkpoint 却从几十毫秒变成全量的耗时，
每一代产物从几十 MB 变成整份 guest 内存（全量与增量的实测对比见 [21](21-benchmarks-and-compliance.md) 的分档表）。

**为什么静默。** 全量捕获当然能精确地恢复到那一刻：内存标记、blob 的 md5、根文件系统上的文件，一项都不会错。
普通测试只看得见"回来的内容对不对"，看不见"用什么方式回来的"。性能测试倒是会变慢，
但"变慢"没有对照时看不出是退化——你不知道它本来应该多快。

**靠什么看得见。** 只能加一条报告"**怎么做的**"而不是"做对没有"的通道：服务端每次 checkpoint 都回报 `mem_mode`
（`full` 或 `incremental`，[28 §2](28-observability-reference.md#2-能力行与-memmode)）。
判据一句话：**除了沙箱的第一个 checkpoint（以及断链后的那一个），出现 `full` 就是有问题。**
所有正确性脚本和性能脚本都把它当硬断言，性能脚本更进一步：一轮里出现一个 `full`，整轮作废。

### 1.2 checkpoint 之后原生 pause，封层丢了

这是四种里唯一**真的丢数据**的一种，而且丢得自洽。

**是什么。** checkpoint 会把当前写层原地封存成只读层、另开一个新写层（[07](07-disk-layering.md)）。
所以从第一次 checkpoint 起，当前写层里只有那之后的写，更早的写在下面的封存层里。
e2b 原生 pause 导出磁盘差分时，如果只取当前写层，做过 checkpoint 的沙箱一 pause 就会丢掉最后一次 checkpoint 之前的所有写。
本项目的早期实现里真的出现过这个缺陷（现已修复：原生 pause 导出时把整个层栈压平再导出）。

**为什么静默。** 三道本应抓住它的防线全都失效了：

| 本应抓住它的 | 为什么没抓住 |
|---|---|
| 导出产物自己的一致性 | 差分的 header 是**从导出内容推出来的**：导出多少，header 就描述多少。块数对得上、校验对得上，只是内容少了一截。没有独立的第二方来源可以打脸 |
| 已有的正确性脚本 | 一个都不做原生 pause。它们测的是 checkpoint / restore 自己那条链，pause 是 e2b 原有的生命周期操作，两者的**组合**没人走过 |
| 修复后补的第一版验证 | 写一个小文件、pause / resume、读回比对——**假通过**。pause / resume 不清 guest 的页缓存，刚写过的文件从缓存里读一定是对的，根本没碰到磁盘 |

最后一行才是真正的教训：**guest 的页缓存能把磁盘层的错误完全盖住。**

**靠什么看得见。** 在 checkpoint 两侧各写一份足够大的随机数据（大到不可能全留在缓存里），pause / resume 之后用
`O_DIRECT` 绕开页缓存读回、比哈希。抓缺陷的是 checkpoint **之前**写的那份：它落在被封存的层里，是唯一会丢的；
之后写的那份是对照，证明脚本本身在正常工作（§4.4）。另外，兼容矩阵把"checkpoint 与原生操作的组合"系统地过一遍（§4.5），
补上"没人走过组合"这个盲区。

### 1.3 把读过的页当成脏页

第三种发生在**对照的那一边**：原生快照路径上，而不是本方案的 checkpoint 上。但它教的东西一样重要。

**是什么。** 增量快照应该只导出"写过"的页。如果判据把"读过"也算成"写过"，脏页集就塌缩成了**工作集**：
guest 碰过的页全部导出，与改了多少无关。

**真实例子。** 在 950 上用同一张档位表跑 e2b 原生快照的基准时，最值得看的一列不是时间，而是产物大小：
名义改动量从 0 一路加到 192 MB，导出的内存差分一直停在 400 MB 上下不动（950，2026-09-09～10，修复前的代码，`native_snapshot_bench.py`；六档数字见 [17 §2.3](17-native-increment-cost-and-verification.md#23-native_snapshot_benchpy六档)）。追下去，原因是 ARM 适配版的原生路径用
"页驻留且 uffd 写保护位未置"当脏页判据，而 arm64 内核没有 uffd 写保护，这个判据塌缩成了"**驻留即脏**"
（完整推导见 [15](15-native-increment-diagnosis.md)，修法见 [16](16-native-increment-fix.md)）。

**为什么静默。** 快照本身没有错：它多带了一些没必要带的页，恢复出来的状态完全正确。
每个正确性断言都过，只是每一代都按工作集导出，时间和空间都白花了。

**靠什么看得见。** **把"名义改动量"和"实测产物大小"并排放**，这一列才会说话：名义档位加倍、产物不动，就是判据坏了。
本方案的判据来自 KVM 写保护或 HDBSS 的写跟踪，读不算脏（[05](05-dirty-page-tracking-and-hdbss.md)）；
分档基准里专门有一个"只读触碰 192 MB"的档，它的产物应当与 0 MB 档几乎相同——这一档就是为防这种失效而设的哨兵（[20 §3](20-performance-methodology.md#3-负载构造三种失真)）。

### 1.4 判据本身静默消失

第四种是前三种的"元问题"：**防静默退化的那道判据，自己也可能静默地不在了。**

**是什么。** `checkpoint_verify.py` 读 `mem_mode` 的写法是 `getattr(ck, "mem_mode", None) or "?"`。
这个字段要经过三段才能到脚本手里：服务端在响应里带上它、SDK 把它填进 `CheckpointInfo`、`CheckpointInfo` 有这个属性。
任何一段缺失，取到的都是 `?`，而脚本对 `?` 的处理是**跳过**"第一代全量、后两代增量"这两条断言，打印一行说明，继续跑完其余各项。

**真实例子。** 同一个脚本、同一套服务端二进制，只换了客户端的 SDK：装了交付的 SDK 覆盖层那次是 **59 项全过**；
换成一版 `CheckpointInfo` 里没有 `mem_mode` 字段的 SDK，三代都报 `mem_mode=?`，末行是 **57 项全过**。
两次都打印"全部通过"，差别只有把两份日志并排、去数项数才看得出来。

**为什么静默。** 跳过而不是报错，本意是让脚本在老服务端上也能跑完；代价是"增量有没有生效"这条最关键的判据消失时，
没有任何东西提醒你。

**靠什么看得见。** 两条：装 SDK 覆盖层是这条判据有效的前提，所以覆盖层的 `install.py --check` 会专门自检
`CheckpointInfo` 与 proto 两侧都有 `mem_mode`，验收流程把它列为第一步（[30](30-acceptance-runbook.md)）；
报告里必须**记项数与 SDK 版本**，59 和 57 的差不是噪声，是两条判据的生死。

### 1.5 共同点与三条纪律

| # | 失效 | 结果对吗 | 靠什么才看得见 |
|---|---|---|---|
| 1 | 增量退化成全量 | 对 | 服务端每次回报的 `mem_mode` |
| 2 | checkpoint 之后 pause 丢封层 | **错，且自洽** | checkpoint 两侧各写一份，pause / resume 后 `O_DIRECT` 读回 |
| 3 | 读过的页被算成脏页 | 对 | 名义改动量与实测产物大小并排 |
| 4 | 判据本身消失 | 对 | 报告记项数与 SDK 版本 |

一句话：**测试通过不等于测的是那个东西。** 由此得到三条纪律，贯穿本部分：

- **先自证"这个检查会失败"。** 一个永远返回真的断言比没有断言更糟，它让人以为测过了。
  比对恢复结果之前，先确认各代现场确实彼此不同（§4.2）；判定"弄坏了原生能力"之前，先测原生能力本来是好的（§4.5）；
  HDBSS 的数据面判据先在没有 HDBSS 的机器上取到负样本（§4.6）。
- **验磁盘内容一律 `O_DIRECT` 读回。** guest 页缓存会把磁盘层的错误完全盖住。
- **报告记项数。** 同一个脚本少了两项仍然打印"全部通过"。

## 2. 三层测试

| 层 | 位置 | 证什么 | 怎么跑 |
|---|---|---|---|
| 单元测试与属性测试 | 代码仓库 `KASandbox_0904`（分支 `deltabox-dev`），与被测代码同目录；Go 在 `packages/orchestrator/internal/checkpoint/`、`internal/sandbox/{block,fc,network,rootfs,uffd}/`，FC 在各源文件的 `#[cfg(test)]`，SDK 在 `py-sdk/tests/test_checkpoint_errors.py` | 部件与不变量 | 见[附录 B](B-extending.md) |
| 交付态验收 | `e2b-infra/rollback/scripts/acceptance/`：五个单文件脚本，互不依赖；另有滚动保留长跑驱动 `rolling_keep10.py`，从同目录导入 `checkpoint_concurrent.py` | 整机正确性、耗时、并发、长跑 | 单文件脚本单独拷到目标机即可跑；`rolling_keep10.py` 要与 `checkpoint_concurrent.py` 一起拷 |
| 补充测试与开发态工具 | `rollback/scripts/crtest/`（20 个用例 + 基准）、`rollback/scripts/dev/`（共享 `lib.py` 的工具箱） | 盲区、边界、故障注入、长稳 | 一站式入口 `rollback/scripts/950/run.sh` |

单元测试证的是**部件**，本部分讲的是**整机**。单测守着哪些不变量见 [12](12-failure-semantics.md) 的不变量清单与[附录 B](B-extending.md)；
其中有一类值得单独一提：**属性测试**（`compact_sim_test.go`、`layer_refs_test.go`、`blockset_test.go`）不是写死几个例子，
而是随机生成大量操作序列，每一步都拿实现与一个简单的参照模型（或从盘上重算的结果）比对；其中几组还故意往实现里注入变异，确认测试真的会失败——
这正是"先自证会失败"用在单测上。

几条约定，每一条背后都有一个"为什么"：

- **RPM 构建不跑单元测试。** `%build` 只做 `go build`，单测要在代码仓库里单独跑。
- **交付态脚本故意各带一份宿主探针，不抽公共模块。** 这看起来像没来得及重构，其实是 §1 的逻辑用在测试代码自己身上：
  探针取不到信息时，"脏页后端""产物文件系统"这些条件标签会打印成"未知"。一个抽成公共模块、却只拷走一半的脚本，
  不一定会报 `ImportError`，更可能被补一个空壳或被 `try/except` 兜住，然后条件标签整列变成"未知"——
  数字照样打印、报告照样归档，只是再也说不清它们是在什么后端上跑出来的。重复几十行代码，换掉一种静默降级，这笔交易划算。
  crtest 的 `common.py` 出于同一理由从 `checkpoint_concurrent.py` 复制而不 import。
- **正确性与性能分开跑。** 正确性现场（每代上百 MB）不给性能垫噪声，性能档位也不拖慢正确性。
- **开发态脚本按位置参数选判据，顺序敏感。** `correctness.py <方案> [df挂载点]`、`loop.py <方案> [次数]`。
  交付的是 ext4 方案，第一个参数写 `ext4`。手敲时把挂载点当成方案名，会用错的规则去判对的产物、报假 FAIL；
  假 FAIL 比假 PASS 好，但仍会浪费一轮上机时间。
- **都在宿主机上以 root 跑。** 脚本能量到"跑在什么上"，取决于它跑在哪台机器上：

| 能量到的东西 | 在宿主机上跑 | 从别的机器连过来 |
|---|---|---|
| 脏页后端（`hdbss` / `kvm-wp` / `off`） | 问沙箱的 Firecracker API 套接字 | "未知"（套接字是本地文件） |
| 产物路径与文件系统 | 读 orchestrator 进程的 environ 与 `/proc/mounts` | 空 |
| 每代内存 / 磁盘产物实占 | 量 `mem_diff` 与新封层的 `st_blocks` | 量不到 |
| 服务端分段计时 | 读 `timings.json` | 量不到 |
| 客户端墙钟、全部正确性断言 | 有 | 有 |

结论：**正确性可以远程验，性能必须上宿主机**；远程跑出的耗时缺条件标签，按 [20 §2](20-performance-methodology.md#2-条件标签) 不允许引用。

## 4. 正确性脚本的判据

### 4.1 三重证据加一条最硬的

回滚的正确性不能用"没报错"来判。restore 返回成功、沙箱还能执行命令，这和"内容真的回到了目标时刻"是两件事——
一个什么都不做、只返回 `true` 的实现也能满足前两条。所以要回答的问题是：**用什么观测量，能把"回到了那一刻"
和所有"看起来像回到了那一刻"的情形区分开？**

把"看起来像"的情形一个个列出来，每一重证据正好排除其中一类：

| 证据 | 观测点 | 它排除的假象 | 它单独证明不了的 |
|---|---|---|---|
| 内存标记 | `/dev/shm/marker` | "只换了磁盘，内存没动"：tmpfs 完全在 guest 内存里、从不落虚拟盘，它变回去只可能是**内存**被搬回去了 | 只有一行字，一页对上不代表一大片 |
| 内存大块 | `/dev/shm/blob`（默认 128 MB 随机数据）的 md5 | "碰巧那一页对了"：一大片逐字节对上，排除零页共享、只回了部分页、回滚集算漏了一段这类局部正确 | 磁盘那一半 |
| 磁盘标记与大文件 | 根文件系统上的标记与几十 MB 文件的 md5 | "只回了内存，磁盘没动"：磁盘视图也被整体换掉了 | 元数据、删除动作 |
| **进程** | 快照前起的心跳进程的 PID 与启动时刻 | "虚机重启 + 按记录重放"：内容可以靠记账重放伪造，进程身份不能 | —— |

为什么内存要两重、磁盘要一重加两个补充：内存回滚走的是"按回滚集写回页"（[06](06-memory-diff-tree.md)），出错的典型形态是**局部**的——
回滚集算漏几页、某段读错了代——一个小标记抓不住，必须有一大片随机数据兜着；而 tmpfs 的标记负责钉死"是内存本身被搬回来"。
磁盘回滚是整体换视图（[07](07-disk-layering.md)），出错的典型形态是**层选错**，内容标记加大文件就够抓；
但"只回数据块不回元数据"的实现也能让内容对上，所以另加两样"不好回滚"的东西：**删除**和**权限位**。
新建能回滚不稀奇，被删的文件复活、权限位回到那一刻的值，才说明是块级快照而不是在文件层面打补丁。

前三重都是"内容"，理论上都可以靠重放伪造。最硬的一条是**进程**：快照前起的后台进程，恢复后 PID 和启动时刻都不变，
说明是内存被搬回去了，而不是虚机重启了。`checkpoint_verify.py` 把它推到极限：先 `kill -9` 掉这个进程再回滚，
它必须连同 PID 与启动时刻一起活回来。**复活一个已经被杀掉的进程**，是任何重放式实现都做不到的。

### 4.2 `checkpoint_verify.py`：一条直链上的 59 项

交付态脚本，默认参数直接跑。它只走**一条直链**（三代 A → B → C），图的是好读、跑得快；树形语义交给 `correctness.py`（§4.3）。

**三代现场怎么设计。** 三代不是同一件事做三遍，每代都换掉**全部**观测点，另外各动一样不好回滚的东西：
`victim` 文件 A 建、B 删、C 保持删掉，于是"回到 A"必须让一个已被删除的文件复活；权限位三代分别 600 / 640 / 755，
于是回滚必须连 inode 元数据一起回；标记写在 `/`、`/etc/ckpt-root.conf`、`/ckpt-root/` 下，**不是** `/home/user`——
用户目录在 e2b 里另有挂载，只测它等于只测了一层。

**先自证会失败。** 每次恢复后脚本会判"11 项现场全部一致"。可是如果这 11 项在三代之间本来就一样，这句 PASS 什么也没证明。
所以开始回滚之前，脚本先把三代现场并排，做两条方向相反的断言：9 项现场必须三代**各不相同**；
心跳的 `hb_pid`、`hb_start` 两项必须三代**相同**（它们不是"现场"，是"同一个进程没被重启"的证据）。两条合起来才把这张表钉住。

**活体判据只用计数器，不用时间。** 恢复会把 guest 的单调时钟拨回快照那一刻（[10](10-rollback-pitfalls.md)），时间倒流是对的行为，不是故障，
所以"时间在往前走"不能当活体判据。心跳 0.2 s 一拍往日志追加一行，脚本分两段各数 1.5 s，硬断言只要求 `g1 + g2 >= 1`（在推进），
不要求速率：恢复后头一两秒这个循环偶尔只跳一两下，判成"vCPU 没恢复"是错的诊断。节奏照样打印给人看，**打印但不判定**——
这是噪声大、信息量也大的观测量的正确处理方式。

**`mem_mode` 两条。** 树根必须自包含所以是全量，之后每代只写脏页所以是增量：`gA == full`，`gB / gC == incremental`。
取值写法与跳过规则见 §1.4；装好 SDK 覆盖层是这条判据有效的前提。

59 项由四种断言单元组合而成：`verify_live` 每次 5 项（还能执行命令 / 根文件系统能写能读回 / 能起新进程 / 新进程能算出正确结果 /
快照前的后台进程仍在推进），`verify_scene` 每次 2 项（restore 的 API 返回成功 / 11 项现场全部一致），外加 `mem_mode` 2 项与区分度 2 项。
按脚本的五节数（默认 `--rounds 3`）：

| 节 | `verify_live`（每次 5 项） | `verify_scene`（每次 2 项） | 其他 | 小计 |
|---|---|---|---|---|
| 1. 建三代现场 | 3 次 = 15 | —— | `mem_mode` 2 + 区分度 2 | 19 |
| 2. 逐级回退 C → B → A | 1 次 = 5 | 2 次 = 4 | —— | 9 |
| 3. 跨 2 代前滚 A → C | 1 次 = 5 | 1 次 = 2 | —— | 7 |
| 4. A / C 交替 3 轮 | 1 次 = 5 | 6 次 = 12 | —— | 17 |
| 5. `kill -9` 心跳后回滚到 A | 1 次 = 5 | 1 次 = 2 | —— | 7 |
| **合计** | 35 | 20 | 4 | **59** |

第 2 节只在第一次回退后做活体检查：活体检查里有两段 1.5 s 的等待，每次都做只会变慢、信息量不增加。

**59 不是常数**，三处会变：`--rounds r` 时第 4 节是 `4r + 5` 项；模板里没有 `python3` 时算术那项跳过，每次活体检查降为 4 项，总数 52；
有 `k` 项现场不一致时 `verify_scene` 记 `1 + k` 项（每个不一致项单独一条 FAIL，附"期望 X 实际 Y"）。
逐项比而不是比一个总哈希，是为了失败时能直接说出**是内存没回来还是文件没回来**。
**57** 说明 SDK 没透出 `mem_mode`，增量判据失效（§1.4）。末尾那张 API 耗时表样本少、每代现场上百 MB，只当量级看，不是性能基准。

读输出时从上到下看四处：开头两行的"脏页后端"与"产物落盘文件系统"（后面所有数字的条件标签）；
每代一行的 `mem_mode`（是不是 `?`，三代是不是 `full` / `incremental` / `incremental`）；三代现场对照表（9 行各异、2 行相同）；末行项数。

### 4.3 `correctness.py`：树语义

交付态脚本只走直链。分叉之后回滚集怎么算、删一个被引用的节点会怎样、算不出回滚集时拒绝还是硬来，
在直链上根本构造不出来，由开发态的 `correctness.py ext4` 负责。每次 restore 都用 §4.1 的三重证据判定。

| 节 | 做什么 | 断言 |
|---|---|---|
| 1. 线性链 | ck1..ck5，脏页 0 / 64 / 256 / 512 / 0 MB | 树根 `mem_mode`（随 `CHECKPOINT_FULL_ROOT` 切换期望值）；ck2..ck5 全增量：2 项 |
| 2. 回退与前滚 | ck5→ck4→…→ck1，再前滚到 ck5、再回 ck1 | 7 次 restore：7 项 |
| 3. 分叉跨 LCA | 站在 ck1 建 ck6（ck2..ck5 成旁支），跨支来回；再建 ck7（父 ck5），覆盖 LCA = ck2 | 2 条父节点断言 + 6 次 restore：8 项 |
| 4. 删除 | 删 ck2（有后代，非基准，只有一个子节点 ck3） | 见下 |
| 5. 失败 | 移走 ck5 的 `mem_bitmap`，从 ck7 回 ck4 | 先站到 ck7、被拒绝、拒绝没动沙箱状态、沙箱照常运行、放回后能恢复：5 项 |

几处设计值得说明：

- **0 MB 的两代是故意的**：什么都不改的一代也必须能正确回，它是回滚集为空时的边界。
- **第 3 节先断言父节点**：`ck6.parent_id == ck1` 证明树真的分叉了，不是接在链尾；之后 `ck6 → ck3` 这一跳的回滚集是
  `ck6→ck1` 与 `ck3→ck2→ck1` 两段的并，最近公共祖先是 ck1，正是 [06](06-memory-diff-tree.md) 里回滚集定义要处理的情形。
- **判据跟着部署配置走**：第 1 节的树根断言读 `CHECKPOINT_FULL_ROOT` 自动切换期望值，第 4 节按合并开关分支，不硬编码。

第 4 节按合并开关分两支（脚本自己判断走哪支）：

- **`CHECKPOINT_COMPACT` 开（默认）**：ck2 不是基准、只有一个子节点，删除结尾被合并进 ck3。
  断言 **ck3 的父节点变成 ck1**（ck2 的目录已消失），1 项。
- **合并关**：ck2 隐藏保留，断言 `hidden == true`、`mem_bitmap` 保留（跨它回滚要用它算回滚集）、`snapfile` 已丢（隐藏条目不再是恢复目标）、
  `mem_diff` 保留（后代靠祖先的差分解析内容），4 项。

两支之后相同：`list` 里看不到 ck2；回 ck1（跨 ck2 纪元）、回 ck4；删叶子 ck6 必须物理删除；回 ck3 其余分支不受影响。
所以默认配置下共 2 + 7 + 8 + 6 + 5 = **28 项**，合并关时 **31 项**。合并为什么不改变任何 restore 的结果，见 [06](06-memory-diff-tree.md)。

第 5 节要求三件事：**拒绝**（抛异常，而不是返回后继续）、**拒绝没有动沙箱状态**（前后两个标记原封不动）、
**沙箱在拒绝之后照常运行**。报的错形如 `failed to materialize revert files: failed to read sidecar of checkpoint ...`；
侧车放回去之后再回滚立刻成功，说明拒绝没有留下任何半吊子状态。这是"宁可报错，不可静默损坏"（[12](12-failure-semantics.md)）的可执行版本。

### 4.4 `pause_verify.py`：一个自洽的静默损坏

这个脚本是为 §1.2 那个缺陷写的，它示范了一整类测试盲区的抓法。

结构：checkpoint 前写 `before.bin` → checkpoint（封层）→ 写 `after.bin` → 原生 pause / resume →
两份都用 `dd iflag=direct` 读回比 sha256。每份 16 MiB 随机数据（`--mb` 可改）：大到不可能全留在缓存里，随机到不会被稀疏或去重特殊对待。
抓缺陷的是 `before.bin`：它在被封存的层里，是唯一会丢的那份；`after.bin` 是对照，证明脚本本身在正常工作。
不加 `O_DIRECT` 时，刚写过的数据还在 guest 页缓存里，读回来一定对——修复后的第一版验证就是这样假通过的。

脚本另钉住一条边界：pause / resume 之后回不到 pause 之前的 checkpoint。这是一条**断言**而不是一句注释：
哪天行为变了（无论是变得支持、还是变成静默返回错数据），它会立刻报出来。语义见 [24](24-semantics-and-limits.md)。

### 4.5 `compat_matrix.py`：与原生生命周期的组合

本方案给 e2b 加了 checkpoint / restore，e2b 原有 create / connect / pause / kill（connect 对已 pause 的沙箱等于 resume）。
两组操作动的是同一个沙箱的层栈和内存，§1.2 的缺陷正是在它们的**组合**里。每格三种判定：

| 判定 | 含义 |
|---|---|
| `OK` | 能做，做完沙箱和数据都对 |
| `REFUSED` | 服务端明确拒绝且没留下半吊子状态，**是边界不是缺陷** |
| `BROKEN` | 能调用但结果不对，或本该能做的原生操作被弄坏了，**唯一的真问题** |

`BROKEN` 的后半句是这个脚本存在的理由：它要回答的不是"我们的功能好不好用"，而是"**我们有没有弄坏别人的功能**"。
所以第一组是基线：先在没有 checkpoint 的沙箱上跑一遍 pause → connect，确认原生能力本来就是好的，后面才有资格说"是我们弄坏的"。

六组 15 格：A 基线 1 格；B checkpoint 之后做原生操作 8 格；C restore 之后 3 格；
D 连做三次 checkpoint（多层封存）之后 pause 1 格——§1.2 缺陷的本质是"当前层之下还有 N 个封存层"，一层测不透；
E 反向（pause / resume 之后走完整 checkpoint 流程）1 格；F kill 1 格。
数据一律 `O_DIRECT` 读回 8 MiB 比 sha256。预期的两个 `REFUSED`：pause / resume 之后回不到之前的 checkpoint
（账本不跨 pause，[24 §3.1](24-semantics-and-limits.md#31-原生-pause--resume-与-checkpoint-的代际边界)）；kill 之后不能 connect（e2b 原有行为，放进矩阵是为了让基线完整）。

### 4.6 `hdbss_evidence.py`：能力不等于数据面

| 层 | 问什么 | 怎么问 |
|---|---|---|
| L1 能力 | 宿主 KVM 认不认 cap 502 | `cap_test.c`：`KVM_CHECK_EXTENSION`，再在临时 VM fd 上真的 `KVM_ENABLE_CAP(502)`（两者可能不一致，所以都问） |
| L2 自报 | FC 给**这个沙箱**选了哪个后端 | FC API `GET /` 的 `dirty_tracking`：`hdbss` / `kvm-wp` / `off` |
| L3 数据面 | 硬件是否真在记 | 写密集负载：先把文件整份分配出来，再计时覆写两遍（`conv=notrunc`），比"冷/热"耗时；有 `perf` 时另数 `kvm_exit` |

为什么要三层：前两层都只说明"能力打开了"，不说明"硬件真的在记脏页"。L3 的物理含义是：软件写保护下，checkpoint 会把所有页重新写保护，
之后每个干净页的第一次写都要陷出一次，所以刚做完 checkpoint 的第一遍写明显慢于第二遍；HDBSS 下由 CPU 自己记录，两遍接近，冷/热接近 1。
先把文件整份分配出来，是为了让两遍都不用付 guest 侧的页分配成本，剩下的差别只有 stage-2 写故障。

920B 没有 HDBSS，是这条判据的**负样本**：有了它，950 上的判定才有参照。如果 950 上 `dirty_tracking=hdbss` 而冷/热仍明显大于 1，
说明能力启用了但数据面没生效。原理见 [05](05-dirty-page-tracking-and-hdbss.md)。

### 4.7 `loop.py`：稳定性

前面几个脚本各跑一遍就给结论，`loop.py` 回答另一个问题：**跳几百次会不会跳着跳着就不对了。**
状态泄漏和累积误差（位图没清干净、层引用计数漂移）通常不会在第一次露出来。

默认在两个 checkpoint 之间**交替**回滚 200 次：交替才会真正换回滚集，反复回同一个的话回滚集每次都一样，测不到路径计算；
`--same` 保留作对照组。每次都做三重证据校验，任何一次内容错误立即停下并打印现场，判据是 `failures: 0`——
判定用的不是"restore 返回成功的比例"，因为静默的内容错误比崩溃危险得多。分位数顺带打印，不判定。

## 5. crtest 用例

`rollback/scripts/crtest/` 覆盖上面几个脚本碰不到的盲区。每个用例失败即停、按"断言失败 / 期望 / 实际 / 依据"三段式打印；
退出码 0 全过、1 断言不过、**3 前置不满足**（`run.sh` 记为 SKIP）。原始数据写 JSON（`ops` 每次操作一条、`assertions` 每条断言一条，
`ok` 为 `null` 的是只记录不判定的观测项）。默认规模都按一次 ≤ 5 分钟定。

| 用例 | 测什么 | 硬断言要点 |
|---|---|---|
| T11 生命周期竞争 | checkpoint / restore 进行中 kill 或 `beta_pause` | 服务端不崩（旁观沙箱全程正常）；在途操作要么成功要么给明确错误，且不超过 200 s（锁排队 60 s + FC 调用 120 s）；kill 后目录、FC 进程、netns 都回收 |
| T12 同沙箱多客户端 | 按沙箱串行化 | 风暴后对账：无幽灵 checkpoint、删掉的不再出现、没删的不失踪、残留的每个都能回 |
| T13 冻结窗口干扰 | 别的沙箱 checkpoint 会不会拉长我的冻结 | 只硬判 restore 全成功、现场一致、心跳有数据；随并发数的曲线只记录 |
| T14 写密集并发正确性 | 大脏集 + 并发 | 默认先 `SIGSTOP` 写者：内存与文件 md5、seq 精确回到快照时刻，写者状态回到 `T`；`--no-stop` 只做页级 / 行级自校验。拍摄时刻正在写的那一页（至多 1 页）放过 |
| T15 树形分支并发 | 分支语义 + 隐藏条目回收 | 每次 restore 现场一致；`list` = 本地账本 |
| T18 orchestrator 重启 | 账本不跨重启 | 重启前 store 下的沙箱目录一个不剩；新沙箱 `list` 为空，第一次 checkpoint 是全量新根且能回；netns 不增长。要 `--allow-restart` 才执行 |
| T21 故障注入 | `CHECKPOINT_FAULT_INJECT` 的 `envd_timeout` / `torn_assemble` / `seal_move` / `commit_late`，每次一条 | 按常开与 `:once` 两套期望：失败后账本没坏（隐藏条目、链没断）或自愈；`envd_timeout` 下一次 checkpoint 的父节点是刚才 restore 的目标。要在宿主机上读 manifest |
| T22 深链随机回滚 | 深链 + 分支下的回滚集 | 随机顺序回每一个都一致；删中间层后后代仍能回；`list` = 账本 |
| T23 文件系统边界 | 写到一半拍、open fd、rename、fsync | 流式文件是快照那一刻的前缀；fd 上行号连续且 restore 后能接着写；rename 被回滚；fsync 过又删掉的文件回来 |
| T24 网络状态 | 活连接跨 restore | guest 内 loopback 长连接仍可用；新连接立刻可用；给了 `--external` 时跨出沙箱的旧连接干净失效 |
| T25 时间与 CPU | restore 后定时器健康 | uptime 必须倒退；`date` 不倒退且与宿主差 < 5 s；`sleep 1` = 1.0±0.1 s；10 s 窗口 CPU0 空闲 ≥ 90%；arch_timer < 200 次/s |
| T26 串口 | 串口自锁回归 | 每轮 restore 前后写 4 KB 到 `/dev/ttyS0`，退出码 0 且 < 3000 ms |
| T32 restore 随脏集 | O(脏页) | `fc_bitmap` 各档 p50 极差 < 2 倍；`fc_memory` 随脏集单调不降 |
| T34 运行期读链深 | 链深会不会拖慢 guest 冷块读 | 只硬判前置（层建得出、`drop_caches` 生效等），曲线只记录 |
| T36 混合稳态 | 长时间乱序负载下漏账、漏回收 | 每个 worker 线程跑满全程且循环体没抛过；restore 后 0 不一致；收尾 `list` = 账本；删干净后为空；活 FC 归零。全规模 `--sandboxes 16 --seconds 1800` |
| T37 两道配额闸 | `CHECKPOINT_MIN_FREE_BYTES` / `CHECKPOINT_MAX_PER_SANDBOX` | 507 `disk_full` / 429 `too_many_checkpoints`，异常类与 `.reason` 对，沙箱不受影响。字节配额没有对应用例 |
| T38 FC 侧 faulted | FC 过了提交点才失败（需带 `rollback-fault-inject` 特性的 FC 与 `FC_ROLLBACK_FAULT_INJECT=post_commit`） | 抛 `CheckpointTornException`、`.reason == "torn"`；之后 checkpoint / restore 都被拒；服务端与 FC 日志有对应行 |
| T39 checkpoint 之后原生 pause/resume | 做过 checkpoint 的沙箱原生 pause 时，导出的内存差分必须含全部该含的页（位图曾被 checkpoint / restore 清过，[16 §4](16-native-increment-fix.md#4-与-checkpoint-叠加累积位图)） | 三个场景（checkpoint 后直接 pause；checkpoint → 改 → restore → pause；反复 3 轮再 pause）：内存 md5 与 pause 前一致、页级坏页 0、写者 pid 不变、内存与盘上标记符合场景 |
| T40 restore 紧跟请求 | restore 前后流式请求的截断 | 只硬判沙箱存活、账本 = `list`、线程没提前死；截断次数只记录 |
| T41 干净沙箱原生 pause/resume | 没做过 checkpoint 的沙箱 | pause/resume 后内存、盘、进程、连接都正常；连做三轮；resume 后能重新 checkpoint / restore；`list` 为空 |

用例的一个共同写法是"**硬判**"与"**只记录**"分开：能从语义推出唯一正确答案的（现场一致、账本相等、异常类正确）才硬判；
依赖负载与机器的量（曲线、截断次数、并发下的耗时）只记录，留给 [21](21-benchmarks-and-compliance.md) 和 [22](22-long-run-and-concurrency.md) 去读。
把后者也写成断言，只会得到一批在别的机器上随机失败的用例。

三条口径容易问错，记在这里：

- **并发下"拍那一刻的现场"没有定义**：A 线程写完标记还没拿到锁，B 线程一个 restore 就把标记退回去了。
  所以 T12 只在风暴后对账；T14 / T15 每个沙箱内部串行，现场才良定义。
- **串口只在 T26 里碰**，其余用例一律走 `commands.run`：restore 之后的串口发送不作为采集通道。
- **撕裂的沙箱不再碰 guest**：`torn_assemble` 之后不调用现场采集，否则测试自己会挂住。

`crtest/tests/` 下是离线单测（不需要沙箱），`python3 -m unittest discover -s tests` 即可跑。

## 6. `checkpoint_concurrent.py`：并发四段

前面的脚本都是一个沙箱、一个调用方。真实部署里同一台宿主上几十个沙箱各自在拍，偶尔还有同一个沙箱被两个客户端同时操作。
这个脚本把并发拆成四段，每段回答一个问题：

| 段 | 做什么 | 断言 |
|---|---|---|
| **A** 跨沙箱扇出 | N 个沙箱用 barrier 对齐同时发同一操作，N 从 1 涨到 16（`--fanout`），每跳验回到了哪一代 | 看 p50 / 最坏随 N 怎么涨、涨在服务端哪一段；宿主侧同时记产物盘写入与 orchestrator CPU |
| **B** 同沙箱争用 | 一个沙箱 T 个线程（默认 4）各自循环 checkpoint → restore → list，默认各走各的连接 | 不断言现场（并发下没有定义）；断言操作全部收敛、没有错误、沙箱存活、`list` 不比成功数多（无幽灵）、每个 checkpoint 都回得去 |
| **D** 混合稳态 | S 个沙箱（默认 8）各自单线程随机循环 T 秒：50% 写脏（内存 8 MB + 文件 4 MB）后 checkpoint、35% restore 到随机一个已有 checkpoint、15% delete | 每次 restore 后逐项比 5 个字段：`mem_gen`、`file_gen`、内存 blob 前 4 MiB md5、文件 blob 前 4 MiB md5、心跳 pid |
| **C** 生命周期竞争 | checkpoint / restore 进行中 kill 或原生 pause | 默认不跑，要 `--lifecycle`；可能打挂 orchestrator，宿主上有别人的沙箱时不要开 |

A 段存在的理由：服务端跨沙箱的共享点只有三处——store 的全局锁、产物盘带宽、宿主连接跟踪表——A 段就是去量这几处到底贵不贵。
B 段的要点是"排队而不是出错"：服务端按沙箱串行，要看的是排队是否算进客户端超时、超时之后服务端是否照做了（幽灵 checkpoint）。
D 段把"每个沙箱内部串行"和"沙箱之间并发"组合起来：沙箱内部串行，所以每次 restore 的现场是良定义的、可以逐项验；沙箱之间并发，所以能看出互相踩没踩。

D 段的循环体整体包在 `try` 里，任何异常只记一条失败、不带走线程；第一次 restore RPC 失败时该沙箱停手
（否则之后每次调用都往死沙箱上叠一条错误，几分钟就把服务端日志冲光、现场没了），
在 `--keep-on-failure` 时留下沙箱、抄 FC 状态与日志。收到 429 不主动删，只记失败继续。
`D.json` 的 `verified` = 校验通过数 / 进入校验的 restore 数。长跑怎么用它、怎么判定、怎么计时，见 [20 §6](20-performance-methodology.md#6-并发与长跑的测量)。

## 7. `run.sh` 各档

入口 `rollback/scripts/950/run.sh`，退出码 = FAIL 项数，每档写一份 `SUMMARY.md`。测试套件不在 RPM 里，跟着 e2b-infra 仓库走。

| 档 | 跑什么 | 判据 |
|---|---|---|
| `smoke` | `crtest/portability/preflight-customer.sh`（宿主预检）；SDK 覆盖层 `install.py --check`；orchestrator 的启动能力（能力文件，或日志里的 `checkpoint capabilities` 行）；FC 二进制 sha256；`acceptance/checkpoint_verify.py` | 5 项全 PASS |
| `func` | crtest T12 T15 T22 T24 T23 T34 T32 T41 T39 T26 T14 T40 T25 T36 T11 T13（不需要重启、不改服务端 env 的 16 个）+ `crtest/sdktests/test_checkpoint_errors.py` | FAIL = 0 |
| `func --allow-restart --restart-cmd ...` | 加跑 T18 | 同上 |
| `func --fault-cases` | 加跑 T21 ×4 与 T38（需要服务端先带对应注入重启；没装的那条退 3 记 SKIP） | 同上 |
| `func --quota-cases` | 加跑 T37 `disk_full` / `too_many`（需要服务端带对应开关重启） | 同上 |
| `perf` | `crtest/bench/bench_tiers.py --tier-set short` → `compliance.py` + `analyze.py`；`serial_restore.py -n 100`；`checkpoint_concurrent.py --stages A,B` | 无 FAIL；**超达标线不判 FAIL**，看 `compliance.log` 末尾 |
| `long` | 不自动跑，只打印长测清单：D 段长跑、C 段、T36 全规模、串行 5000 次、分档全表 | —— |

`smoke` 的顺序就是 §1 的逻辑：先确认"跑在什么上"（宿主预检、能力、FC sha），再确认判据在不在（SDK 自检），最后才验正确性。
SDK 覆盖层自检的异常族判据是：原有 8 个子类都在、并且映射表里每一项都是 `CheckpointException` 的子类
（现在是基类加 9 个子类，新增 `CheckpointBytesLimitException`，见 [25](25-errors-timeouts-concurrency.md)）。
`perf` 档"超线不判 FAIL"的理由：超线是结论不是故障，把它当 FAIL 会让一次正常的性能摸底看起来像一次失败的验收。

## 8. 测试环境与沙箱规格

全书的测试用同一个模板，规格变了数字要重采：

| 项 | 值 | 怎么核对 |
|---|---|---|
| 模板别名 | `base` | 各脚本与 `run.sh` 的默认模板（`--template` 可改） |
| 基础镜像 | `harbor:443/e2b-orchestration/ubuntu:22.04-custom` | `benchmark/build_template.py` 里的 `FROM` |
| vCPU | 2 | `GET /templates` 的 `cpuCount` |
| 内存 | 2048 MB | `GET /templates` 的 `memoryMB` |
| 磁盘 | 约 940 MB（guest 内 ext4，240640 块 × 4 KiB） | `GET /templates` 的 `diskSizeMB` |

在宿主机上核对（access token 取部署时写下的 SDK 凭据）：

```bash
AT=$(jq -r .accessToken /root/.e2b/config.json)
curl -s -H "Authorization: Bearer $AT" http://127.0.0.1:3000/templates \
  | jq -r '.[] | select(any(.aliases[]?; . == "base"))
           | "cpuCount=\(.cpuCount) memoryMB=\(.memoryMB) diskSizeMB=\(.diskSizeMB) buildStatus=\(.buildStatus)"'
```

预期 `cpuCount=2 memoryMB=2048 diskSizeMB=940 buildStatus=ready`。
为什么内存规格要写进条件标签：全量 checkpoint 的代价约等于整份 guest 内存，增量只跟本代脏页量有关。
换一个内存更大的模板，全量那一列等比变大、增量各档基本不动，所以两组数字只能并列，不能相减、也不能并表。

## 9. 偶发问题怎么缩小范围

正确性脚本和 crtest 用例抓的是"每次都会出现"的错。长跑里偶尔出现一次、几百次里出一次的问题，要换一种做法。
下面几条来自本项目追查偶发挂死、偶发截断的经历，写成可复用的方法：

1. **先把"慢"和"挂"分开。** 给被怀疑的操作设一个明显大于正常最坏值、又明显小于服务端兜底超时的时限
   （例如正常 restore 在亚秒级，服务端等 guest 应答要 45 s，那就取 20 s）：既能把挂死和正常长尾分开，又不必每次都等满兜底超时。
2. **复现脚本不能被单次失败打断。** 正确性脚本挂住就整条挂住，一晚上只拿到一个样本；复现脚本要超时后记下现场、接着跑下一轮，
   并把结果**边跑边写**到 JSON，中途被打断也不丢数据。
3. **阴性结果也是结果，要写下来。** "纯跨分支 restore 连打一百多次零异常"说明触发条件不是跨分支本身；
   这样的阴性结果能把搜索空间砍掉一大半，逼出"问题在别的维度上"的判断。
4. **从唯一异常的观测量出发施压。** 失败那次现场里唯一与众不同的量（例如回滚瞬间在途的网络接收描述符特别多），
   即使不是充分条件，也是唯一能施加压力的方向：构造负载把这个量推到极端，再看失败率是否上升。
5. **失败那一轮自动抓现场。** 循环脚本在失败时按沙箱 ID 把服务端日志切出来存好，通过的轮次日志直接删掉；
   事后在几百轮的日志里翻，是翻不动的。D 段的"第一次 restore 失败就停手并留现场"（§6）是同一条思路。

这类复现脚本是一次性的追查工具，不是验收资产，不随交付件发布；把它们沉淀成固定用例的，是 crtest 里的回归用例（例如 T26 串口、T40 restore 紧跟请求）。

## 本章要点

- 这套方案有四种静默失效：增量退化成全量、checkpoint 之后 pause 丢封层、读过的页被算成脏页、判据本身消失。只有第二种改变结果，而且改得自洽；
  所以测试必须多问一句"是怎么做到的"，而不只问"做对了没有"。
- 每种失效都要一条专门的通道才看得见：`mem_mode` 回报、checkpoint 两侧写数据并 `O_DIRECT` 读回、名义改动量与实测产物并排、报告记项数与 SDK 版本。
- 正确性判据是四重证据，每一重排除一类假象：tmpfs 标记排除"只换了磁盘"，大块 md5 排除"局部碰巧对"，磁盘标记与大文件排除"只回了内存"，
  进程的 PID 与启动时刻排除"重启加重放"；删除与权限位能回滚，说明是块级快照而不是补文件。
- 三条纪律贯穿第五部分：先自证检查会失败、磁盘内容一律 `O_DIRECT` 读回、报告记项数。
- `checkpoint_verify.py` 默认 59 项（35 + 20 + 4），随 `--rounds`、模板里有没有 `python3`、失败项数而变；57 说明 `mem_mode` 判据失效。
  `correctness.py` 默认 28 项、合并关时 31 项，覆盖分叉跨 LCA、删除与合并、失败时拒绝且不动状态。
- 三层测试各证一件事：单测与属性测试证部件与不变量，交付态单文件脚本证整机，crtest 与开发态工具补盲区、边界、故障注入与长稳；
  交付态脚本故意不共享代码，免得条件标签静默变成"未知"。
- 正确性可以远程验、结论可以从 920B 搬到 950；性能必须上宿主机测，数字不能跨机搬。
- 用例把"硬判"和"只记录"分开：能从语义推出唯一答案的才断言，依赖负载与机器的量只记录，交给 [21](21-benchmarks-and-compliance.md)、[22](22-long-run-and-concurrency.md) 去读。
