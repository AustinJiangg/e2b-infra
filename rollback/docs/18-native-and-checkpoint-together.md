# 18 · 两种快照的分工与配合

## 本章目标

读完本章，你应该能够：

1. 说清 e2b 原生快照（pause / resume）与本方案 checkpoint / restore 各解决什么问题，以及决定这一分工的根本差别：产物是否自足、恢复是否依赖活着的进程；
2. 逐项对比两条路径的机制与成本模型，并能按"对照基准"正确解读本方案的每一个优化点；
3. 论证两者为什么互补、为什么都必需，为什么原生做到精确增量之后分工也不变；
4. 在一个实际工作流里把两者叠加使用，并说出方向规则：checkpoint 之后可以原生 pause，原生 pause / resume 之后旧的 checkpoint 全部作废；
5. 说清 checkpoint 之后做原生 pause 的正确性前提：内存与磁盘两半各要满足什么、由谁保证、保证不了时退到哪里。

## 1. 两种快照各解决什么问题

### 1.1 checkpoint / restore：活沙箱里的高频快速回退

本方案的目标场景是一个 AI Agent 在沙箱里一步步执行任务，某一步把环境搞坏了，要退回上一步结束时的状态、换个做法重试（场景见 [01](01-background.md)）。
这个场景有三个特征（它们怎样推出目标、约束与"不复用原生"的结论，见 [03](03-goals-and-design-choices.md)）：

- **高频**：一个任务里要打十几个点，单次成本必须低到可以随手用；
- **低延迟**：回退发生在 Agent 的决策循环里，客户给的参考上限是增量 checkpoint ≤ 200 ms、restore ≤ 100 ms；
- **沙箱不能中断**：沙箱有 IP、端口映射、外部持有的引用，中断一次这些都要重建。

为此本方案选择**只在活着的那个 Firecracker 进程上工作**：checkpoint 不停沙箱，restore 把差异页原地写回，宿主资源一个都不重建。代价是产物离不开这个进程，
随沙箱生命周期回收（[14](14-lifecycle-reasoning.md)）。

### 1.2 原生快照：沙箱离场之后

原生快照面向的是另一类需求：

- **沙箱离场后再回来**：暂停一个暂时不用的沙箱、释放宿主资源，之后在原来的状态上继续；
- **长期保存、跨会话**：把一个状态固化下来，几天后再用；
- **跨节点迁移**：在另一台宿主上恢复；
- **崩溃恢复**：宿主或 orchestrator 挂掉之后，从持久存储里的快照重新拉起；
- **冷启动**：e2b 的每一个用户沙箱本身就是从模板快照加载出来的（[01](01-background.md)），原生快照与恢复的机制是沙箱启动的底座。

这些需求的共同点是：**恢复的时候，原来那个进程已经不在了，甚至原来那台机器也不在了。** 所以原生快照必须产出**自足的产物**：
snapfile、内存差分、磁盘差分和 header 映射链，进对象存储或本地模板存储，任何一个节点都能据此新建一个进程、按需把内存和磁盘拉回来。

### 1.3 分工

| 需求 | 用哪个 |
|---|---|
| 任务执行中的快速回退、试错、在几个方案之间来回切换 | **checkpoint / restore** |
| 同一个起点上反复复位（例如每轮测试前） | **checkpoint / restore** |
| 沙箱要离场，之后还想回来 | 原生 snapshot |
| 跨会话、长期保存状态 | 原生 snapshot |
| 跨节点迁移 | 原生 snapshot |
| 进程或宿主崩溃后恢复 | 原生 snapshot |
| 从模板冷启动沙箱 | 原生 snapshot 的加载机制 |

一句话：**沙箱活着时的回退用 checkpoint，沙箱离场用原生 snapshot。**

## 2. 根本差别：活体原地，还是自足重建

两条路径的一切差别，都可以追到一个选择上：**快照的产物是否自足，恢复是否依赖原来那个活着的进程。**

原生选择"自足 + 重建"。`Pause` 拍完快照就停掉沙箱；SDK 的 `create_snapshot()` 走的 `Checkpoint` RPC 拍完快照也要停掉沙箱，再从新快照拉起一个新进程，
对外保持同一个 `SandboxID` 与 `ExecutionID`，但 `LifecycleID` 换新，底下是全新的 Firecracker 进程（[02](02-e2b-native-snapshot.md) §1）。
恢复就是新建进程：建 KVM 虚机、vCPU、中断控制器、virtio 设备、tap 网卡、uffd，加载 snapfile，然后靠缺页把工作集换回内存。

本方案选择"活体 + 原地"。checkpoint 在一次短暂停里让 Firecracker 写出本代脏页的稀疏差分、把磁盘写层原地封存，然后继续跑；
restore 在一次暂停里把回滚集的页、vCPU、中断控制器、设备状态写回同一个进程，磁盘视图原地切换（[09](09-in-place-rollback.md)）。

这个选择决定了各自的长处，也决定了各自的边界：

- 自足的产物可以跨节点、跨重启、跨任意时长；代价是每次拍都要停机导出、每次恢复都要重建进程、重新换入工作集。
- 原地回滚不重建任何东西，代价只与"改了多少、退多远"有关；代价是产物离开这个进程就没有意义。[14](14-lifecycle-reasoning.md#5-补齐需要什么) 推导过：
  要让 checkpoint 脱离活沙箱，需要补齐全量产物、压平磁盘层、从文件重建账本、恢复路径改成新建进程，补齐之后得到的就是原生 snapshot 本身，而沿途丢掉的正是本方案的全部收益。

## 3. 逐项对比

### 3.1 机制

| 维度 | e2b 原生 | 本方案 |
|---|---|---|
| 打快照时沙箱 | 停掉，再从新快照拉起一个新进程 | **不停**，同一个进程 |
| 快照后的身份 | SandboxID / ExecutionID 不变，LifecycleID 换新 | 无进程更替 |
| 内存搬运 | orchestrator 用 `process_vm_readv` 从 Firecracker 进程地址空间拷出，存成紧凑差分 + header 映射链 | Firecracker 自己写稀疏差分，位图同一次调用落地 |
| 内存判据 | x86：uffd 写保护；ARM 适配基线：退化为驻留判据；第四部分修复后，开了脏页跟踪时取写跟踪位图（与本方案同一份） | KVM / HDBSS 脏页日志 |
| 内存差分粒度 | 修复前随 guest 页为 2 MiB；修复后开了跟踪时 4 KiB | 4 KiB |
| 磁盘增量 | 停沙箱后把写层紧凑导出成差分 | 写层就地封存成只读层，零拷贝 |
| 磁盘增量的落盘 | 同步导出 | 不等待落盘 |
| 历史结构 | 线性链 | **树**，可前滚、可跨分支 |
| 恢复方式 | 新建进程 + uffd，靠缺页把工作集换回 | **原地写回**差异页，宿主资源全保留 |
| 恢复成本 | 与虚机规格和工作集挂钩 | 与回退跨度挂钩 |
| 产物 | 自足，进对象存储或模板存储 | 相对模板的增量，宿主本地 |
| 生存期 | 独立于沙箱 | 随沙箱（准确说是随这一代 Firecracker 进程）回收 |
| 跨节点 / 崩溃恢复 | 可以 | 不可以 |
| 典型频次 | 一个沙箱一两次 | 一个任务里十几次 |

### 3.2 成本模型

设 guest 内存 M、本次改动量 D、回退跨度 R、工作集 W：

| 操作 | 原生 | 本方案 |
|---|---|---|
| 打快照 · guest 停顿 | 整个操作：停掉、导出、（`Checkpoint` RPC 还要）重建、换页 | O(D) 的冻结窗口 |
| 打快照 · 内存 | x86：O(D)；ARM 适配基线：O(W)；第四部分修复后开跟踪：O(D) | O(D) |
| 打快照 · 磁盘 | O(脏块) 紧凑导出，必须停沙箱 | O(1) 改名 |
| 恢复 · 进程与设备 | 全部重建 | 零 |
| 恢复 · 内存 | O(W) 缺页换入 | O(R) 写回 |
| 恢复 · 磁盘 | 重建 Overlay | 按视图重开各层、建块归属索引，无数据搬运 |

> **推论**（基于成本模型的判断，不是实测）：原生的代价基本是常数，与规格和工作集挂钩；本方案随 D、R 线性增长。理论上 R 接近整个工作集时，两者的恢复代价趋同。
> 即使在那一点，本方案仍保留"沙箱不中断"和"没有进程重建的固定开销"两项。所以交叉点不是"该切换到原生"的信号，而是"回退跨度太大，也许该考虑重建沙箱"的信号。

第四部分的修复只改变了表中"打快照 · 内存"一格在 ARM 上的量级：原生每一代导出从 O(W) 降到 O(D)。它没有改变原生"停机、重建、换页"的结构，
所以其余各格不变。原生路径自身各项成本的实测见 [17](17-native-increment-cost-and-verification.md#2-体积修复前后)，本方案的见 [21](21-benchmarks-and-compliance.md)。

## 4. 优化点与对照基准

**"对照基准"这一列不能省**，否则整张表会被读成"比 e2b 强 N 项"。

| 层次 | 优化点 | 带来什么 | 对照基准 |
|---|---|---|---|
| 脏页跟踪 | HDBSS 自动接管，启动探测，无硬件安全退回 | CPU 记录脏页，950 上开箱即用 | 新增能力 |
| | 判据取自 KVM / HDBSS 日志，绕开 uffd | 补回精确增量 | ARM 适配基线 |
| 内存产物 | 差分树：每代只存本代脏页 | 成本只与改动量有关，不需要 reflink | 本方案内部取舍 |
| | 位图随快照同一次调用落地 | 省一轮接口往返和一次全内存扫描 | 原生 |
| | 树形历史 | 回滚后可再前滚、可跨分支，历史不丢 | 原生 |
| | 树根存一次全量 | 整棵树自给自足，回滚路径不跨网络 | 本方案内部取舍 |
| | 删除时合并隐藏条目 | 条目数有上界，空间可回收 | 本方案内部取舍 |
| 恢复路径 | 按页沿祖先链解析，不重建完整镜像 | 恢复成本与链长无关 | 本方案内部取舍 |
| | 进程内原地回滚 | 宿主资源全部保留，无需重新换入工作集 | 原生 |
| | 回滚集精确到页 | 代价与回退跨度成正比 | 原生 |
| 磁盘 | 写层就地封存 + 视图活体切换 | 打快照与回滚都不停沙箱 | 原生 |
| | 封存不等待落盘 | 封存耗时不随改动量增长 | 本方案内部取舍 |
| 一致性 | 内存与磁盘在同一次暂停窗口内完成 | 两者是同一瞬间的镜像 | 原生 |
| 架构 | 接口在宿主侧接管 | 沙箱内不需要任何代理程序 | 新增能力 |
| 工程保障 | 失败分级、断链拒绝恢复、删除不打断后代 | 杜绝"看起来成功、实际数据已坏" | 新增能力 |
| | 分阶段计时 + 全量 / 增量模式回报 | 能定位阶段，能发现静默退化 | 新增能力 |

16 项里：4 项是**新增能力**（原生根本没有这个场景）；5 项是**本方案内部取舍**（相对自己的其他可选设计）；
1 项是**补回 ARM 适配丢掉的东西**（x86 原生本来就有）；其余 6 项才是相对原生路径的改进，而且是在"活沙箱内高频回退"这个特定场景下的改进。

第四部分的原生精确增量不在这张表里：它不是本方案相对原生的优化，而是对原生路径自身的修复，对照基准同样是 ARM 适配基线。
它与表中第二行是同一个问题（ARM 上 uffd 写保护不可用）在两条路径上的两种解法：本方案绕开 uffd、直取 KVM / HDBSS 日志；
原生不能绕开 uffd（它要懒加载），所以改为读同一份写跟踪位图，并把存储粒度降到 4 KiB（[16](16-native-increment-fix.md)）。

## 5. 为什么互补，为什么两者都必需

### 5.1 checkpoint 替代不了原生

checkpoint 的产物随这一代 Firecracker 进程回收：沙箱删除、超时回收、orchestrator 重启、宿主重启、迁移到别的节点，checkpoint 都随之消失（[24](24-semantics-and-limits.md#3-checkpoint-什么时候失效)）。
这不是"没来得及做持久化"，而是由原地回滚的前提决定的：restore 要往**活着的**那个进程里写，进程不在了，差分就没有可以写回的对象
（[14](14-lifecycle-reasoning.md#3-四层依赖)）。凡是"原来的进程已经不在了"的需求，也就是 §1.2 列的全部需求，checkpoint 都做不到。

### 5.2 原生替代不了 checkpoint

原生每一次拍快照都要停掉沙箱（`Pause` 停了就不再起来；`Checkpoint` RPC 停掉之后另起一个新进程），每一次恢复都要新建进程、重新换入工作集。
这些是结构性的固定开销，与改了多少无关，所以原生满足不了"高频、低延迟、不中断"三条中的任何一条。它的历史也是一条线性链：
回到早先的快照之后，后来的快照就失去了意义，做不到在几个分支之间来回切换。

### 5.3 原生做到精确增量之后，分工变了吗

没有。第四部分让原生每一代导出的内存量从工作集降到写入量，改变的是原生**拍**这一侧的体积与上传量；停机、重建进程、缺页换回工作集这几项固定开销一项没变
（[17](17-native-increment-cost-and-verification.md#23-native_snapshot_benchpy六档) 里修复前后 pause、resume 两列在同一噪声带）。
反过来，本方案精确的增量也不会让 checkpoint 获得持久性。两者各自变得更好，但各自的边界没有移动。

精确增量对配合使用的意义在于成本模型的一致：用 checkpoint 找到想要的那一刻之后，再用原生 pause 固化它，这一步导出的量现在也只与"这一代写了多少"有关，
而不是与"guest 这一代碰过多少页"有关。

### 5.4 为什么不把两者做成一个

因为它们在"产物是否自足"这个问题上取相反的答案，而这个答案决定了成本模型：自足就要全量可寻址的产物、就要能在别处新建进程；不自足才能零拷贝封存、原地回滚。
§2 已经说过，把 checkpoint 做成自足的，终点就是原生；反过来，让原生不停机、不重建、原地回滚，终点就是 checkpoint。一套机制无法同时站在两端。
所以正确的形态是两套并存，本方案对原生路径是**加法**：新路径、新端点、新字段（[03 §2](03-goals-and-design-choices.md#2-硬约束) 的约束 3）。原生路径上确实改动过的地方都是有意的：第四部分对原生增量的修复，以及 §7 为叠加使用加的正确性保证；前者在关掉脏页跟踪时整体退回原来的行为，后者在从不 checkpoint 的沙箱上什么都不做。

### 5.5 两者还互相依赖

两条路径不只是并列，还彼此依赖：

- checkpoint 依赖原生的加载机制：用户沙箱本身是从模板快照加载出来的，脏页跟踪（包括 HDBSS）也必须在"从快照加载"这条路径上武装（[05](05-dirty-page-tracking-and-hdbss.md#44-引导和加载两条路径都要武装)）。
- 原生 pause 在一个做过 checkpoint 的沙箱上要导出正确的内容，依赖本方案在 checkpoint / restore 时替它记账（§7）。

## 6. 怎么叠加使用

### 6.1 方向规则

两者可以串起来用，但方向是单向的：

- **checkpoint / restore → 原生 pause：可以。** 先用 checkpoint / restore 把沙箱精确定位到想要的那一刻，再对这个状态做一次原生 pause 固化下来。
  pause 导出的是此刻完整的状态，包括 restore 写回的内容（§7）。
- **原生 pause / resume → 旧的 checkpoint：作废。** resume 用同一个沙箱 ID 新建了一个 Firecracker 进程，是新的一代。
  上一代的差分没有可以写回的对象，服务端按"代"管理 checkpoint：新一代看不到上一代的条目，restore 旧条目得到 `not_found`；
  新一代可以照常 checkpoint，第一次是一棵新的全量根（[14](14-lifecycle-reasoning.md#11-代际边界的规则)、[24](24-semantics-and-limits.md#31-原生-pause--resume-与-checkpoint-的代际边界)）。
- SDK 的 `create_snapshot()`（原生 `Checkpoint` RPC）同样会换一代：它停掉旧进程、从新快照拉起新进程，所以它之前的 checkpoint 同样作废。

### 6.2 一个 Agent 工作流，以及底下发生了什么

```
① 沙箱由模板快照加载起来                          ← 原生加载机制；第 1 代进程
② checkpoint「干净环境」                           ← 这一代的第一次，全量根
③ 装依赖 → checkpoint「依赖装好」                   ← 增量
④ 改配置 → 跑构建 → 失败
⑤ restore 到「依赖装好」                            ← 原地回写，沙箱不中断
⑥ 换个改法 → 跑构建 → 成功 → checkpoint「构建通过」  ← 从③分出的新分支
⑦ 跑测试 → 失败 → restore 到「构建通过」
⑧ 任务告一段落，对当前状态做一次原生 pause           ← 固化，产物进存储；第 1 代结束
⑨ 几天后 resume                                    ← 第 2 代进程；②③⑥ 已作废，⑧ 的状态还在
⑩ 继续工作，需要时重新 checkpoint                    ← 第 2 代的第一次又是全量根
```

几点值得注意：

- **⑤ 之后 ④ 那条分支还在**，⑦ 回退到「构建通过」不需要重新装依赖。这是树形历史和原地回滚的收益，原生做不到。
- **⑧ 导出的内容**：内存是第 1 代启动以来写过的全部页（包括 ⑤、⑦ 两次 restore 写回的页），磁盘是第 1 代的全部写层压平后的结果。
  两者都相对模板表达，所以 ⑨ 恢复出来的正是 ⑧ 那一刻。
- **⑨ 之后**，第 2 代的"自启动以来脏页集"从空开始，它的父代是 ⑧ 的快照；第 2 代再 pause 时，导出的是相对 ⑧ 的差分。
- **②③⑥ 在 ⑨ 之后消失是设计使然**，不是缺陷。checkpoint 的定位是任务执行期间的工作台，跨会话的东西交给原生 snapshot。

使用者需要的具体操作和注意事项见 [24](24-semantics-and-limits.md#5-与原生-snapshotpause--resume怎么配合)。

## 7. checkpoint 之后做原生 pause 的正确性前提

### 7.1 不变量

原生 pause 的产物相对父代（第一代的父代是模板）表达。恢复时，没有出现在差分里的内容一律从父代读。所以必须满足：

> **原生 pause 导出的差分，必须覆盖这一代启动以来与父代不同的全部内容。**

对从不 checkpoint 的沙箱，"与父代不同的内容"就是"这一代写过的内容"，原生路径原本的做法（内存取写跟踪位图、磁盘导出当前写层）就能满足。
checkpoint 与 restore 会从两个方向打破这个朴素做法。

### 7.2 checkpoint / restore 怎样打破朴素做法

| | 内存 | 磁盘 |
|---|---|---|
| checkpoint 做了什么 | Firecracker 写完差分后清零写跟踪位图，位图此后只记"这次 checkpoint 以来" | 当前写层被原地封存成只读层，换上一个新的空写层 |
| restore 做了什么 | 回滚阶段 9 再清零一次；回滚集的页经 Firecracker 对 guest 内存的映射写回，**KVM 不记这种写** | 磁盘视图切换到目标时刻的层栈 |
| 只看"当前"会怎样 | 只导出最近一次 checkpoint 或 restore 以来的页，更早的写和 restore 写回的页都丢失 | 只导出最后一个写层，更早封存的层丢失 |
| 后果 | 恢复后 guest 内存由两个时刻拼成，内核崩溃或数据错乱 | 恢复后磁盘缺掉 checkpoint 之前的写 |
| 最危险之处 | pause **报成功**，错误要到 resume 才暴露 | 同左 |

### 7.3 两半各由谁保证

- **内存**：orchestrator 为每个虚机维护"自启动以来脏页集"，在 Firecracker 每次清位图之前，把即将被忘掉的位图并进去：增量 checkpoint 的侧车、
  全量 checkpoint 拍之前的活跃脏图、restore 前的活跃脏图、restore 的回滚集位图。pause 时把这个集合并回写跟踪位图再导出（[16](16-native-increment-fix.md#4-与-checkpoint-叠加累积位图)）。
- **磁盘**：原生 pause 导出磁盘时摘出当前视图的全部层（封存层加当前写层），有封存层时把它们压平成一份差分（[07](07-disk-layering.md#2-原生怎么导出磁盘增量)）。

两半都满足时，原生 pause 的产物就是"这一代此刻的完整状态"，与这一代里做过多少次 checkpoint、restore 无关。

### 7.4 保证不了时退到哪里

内存一侧，任何一份位图并不进去（侧车缺失、格式不对、几何对不上），集合就被标为不可信；Firecracker 没有 `save-dirty-bitmap` 端点、或者这台 orchestrator 没开脏页跟踪时，
也不用写跟踪位图。这些情形下 pause 一律退回**驻留判据**：凡是驻留的页都导出。它一定是写过的页的超集，所以结果正确，只是导出量回到工作集口径
（[16](16-native-increment-fix.md#5-退路什么时候回到驻留判据)）。

这里的取舍与全书"宁可报错，不可静默损坏"的原则同向，但形式不同：原生 pause 有一个一定正确的退路，所以不需要报错，只需要多导。
**多导只费时间，少导会毁掉恢复出来的沙箱。**

### 7.5 两条路径共用的唯一接口

内存一侧两条路径只共用 Firecracker 的 `save-dirty-bitmap` 端点。它是非破坏性的读：把 KVM 日志折进用户态位图后导出，不清零
（[08](08-firecracker-api-contract.md#4-扩展三put-snapshotsave-dirty-bitmap)）。所以原生 pause 取位图不会影响之后 checkpoint 的增量；
反方向，checkpoint 与 restore 对位图的清零由 §7.3 的集合补回。两条路径不共享任何产物文件。

### 7.6 怎么验证

- 内存：crtest T39 覆盖"checkpoint 之后""checkpoint + restore 之后""多轮之后"三个场景的 pause → resume，逐项核对现场并做页级自校验；
  在没有累积位图的版本上它必然失败（[17](17-native-increment-cost-and-verification.md#84-与-checkpoint-叠加后导出完整证明累积位图)）。
- 磁盘：`pause_verify.py` 在 checkpoint 前后各写一份数据，pause / resume 之后绕开 guest 页缓存读回；`compat_matrix.py` 覆盖 checkpoint、restore、多层封存之后的各种原生操作
  （[19](19-testing-and-functional-verification.md#44-pause_verifypy一个自洽的静默损坏)、[19](19-testing-and-functional-verification.md#45-compat_matrixpy与原生生命周期的组合)）。
- 从不 checkpoint 的沙箱：crtest T41 多轮原生 pause → resume，确认原生生命周期没有被弄坏。

## 8. 几个常见误解

- **"本方案比 e2b 原生快。"** 要看比什么。在活沙箱内快速回退这个场景下是的，因为原生不是为它设计的；在"沙箱离场后再回来"这个场景下，本方案**做不到**。
- **"原生 snapshot 是 pause + resume，沙箱没变。"** id 没变，进程变了（§2）。这也解释了原生的成本为什么与虚机规格和工作集挂钩：每次都在重建。
- **"e2b 的增量有一个与改动量无关的下限。"** 分两段说。修复前：这只在 ARM 适配基线上成立，x86 上 e2b 的增量是精确的；原因是 ARM 上 uffd 写保护不可用，
  判据塌缩成"驻留即脏"，这是适配引入的退化，不是 e2b 的设计问题（[15](15-native-increment-diagnosis.md)）。修复后：开了脏页跟踪时，ARM 上的原生增量也只含写过的页；
  没开跟踪时（例如无 HDBSS 且未显式开启的节点）原生仍按驻留判据导出，行为与修复前相同（[17](17-native-increment-cost-and-verification.md#5-写保护的运行期代价平台差异)）。
- **"原生做到精确增量了，就不需要 checkpoint 了。"** 不对。精确增量只让原生每一代导出得更少，停机、重建进程、换回工作集这些固定开销都还在，历史也仍是线性链（§5.3）。
- **"checkpoint 之后做原生 pause 不安全。"** 在当前代码上是安全的：内存与磁盘两半都有保证，保证不了时退到一定正确的驻留判据（§7）。
  不能做的是反方向：原生 pause / resume 之后再用旧的 checkpoint（§6.1）。

## 本章要点

1. **分工**：沙箱活着时的高频回退用 checkpoint；沙箱离场之后的一切（长期保存、跨会话、跨节点、崩溃恢复、冷启动）用原生 snapshot。
2. **根本差别在于产物是否自足**：原生自足、每次重建进程，成本与规格和工作集挂钩；本方案依赖活体、原地回滚，成本与改动量和回退跨度挂钩。把任何一方补成另一方的形态，都会丢掉自己的收益。
3. **对比表与优化点表只在本章**；优化点必须带对照基准：16 项里 4 项新增能力、5 项内部取舍、1 项补回 ARM 适配的退化、6 项才是相对原生的改进。
4. **原生精确增量没有改变分工**：它只把原生每代的导出从工作集降到写入量，停机、重建、换页的固定开销不变。
5. **叠加方向是单向的**：checkpoint / restore 之后可以原生 pause；原生 pause / resume（以及 `create_snapshot()`）之后是新的一代，旧 checkpoint 全部作废，新一代第一次 checkpoint 是全量根。
6. **正确性前提**：原生 pause 的差分必须覆盖这一代启动以来与父代不同的全部内容。内存靠"自启动以来脏页集"补回 checkpoint 与 restore 清掉的记录，磁盘靠导出时压平全部层；补不上时退回驻留判据，多导而不少导。
7. 两条路径只共用非破坏性的 `save-dirty-bitmap` 端点，不共享产物；证据是 crtest T39（内存）、`pause_verify.py` 与 `compat_matrix.py`（磁盘）、T41（原生生命周期）。
