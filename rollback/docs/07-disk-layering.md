# 07 · 磁盘分层与回收

本章回答一个具体问题：**沙箱里的文件已经被修改了，怎样恢复到某次 checkpoint 时的内容，并在以后删除不再需要的磁盘数据？**

例如，`/root/a.txt` 初始内容是 A，改成 B 后保存 c1，再改成 C。恢复 c1 后，它应该重新呈现 B。系统既要保留 B，又要接收后续的 C；恢复时还要让文件内容、ext4 元数据与恢复的内存状态相符。

磁盘侧处理的是**磁盘块**，不是文件操作记录。guest 内核中的 ext4 驱动把文件修改转换成磁盘块的写入，其中既有文件内容，也可能有目录、长度、日志等元数据。本章所说的“层”，保存的是这些块的内容及其归属信息。内存使用“页”，磁盘使用“块”。

阅读顺序按实际操作展开：先看正常读写，再看保存、恢复、删除和合并；最后深入文件格式、索引、同步和失败处理。下面的 W1、W2、W3 是为了跟踪数据而使用的层名称，不是固定文件名。

## 1. 运行中的沙箱：读写落在哪里

### 1.1 先区分数据、管理对象与设备

刚创建的沙箱使用模板中的磁盘内容，但后续写入不能覆盖模板，因此会为自己创建一个**活写层文件**。

| 对象 | 实际是什么 | 用途 |
|---|---|---|
| 模板 rootfs | 初始磁盘的数据来源 | 提供尚未被沙箱修改的块；经 chunker 从对象存储按需读取并在本地缓存 |
| 活写层文件 W1 | host 上的稀疏文件 | 保存这个沙箱运行后写入的磁盘块 |
| `Cache` | orchestrator 内存中的对象 | 管理层文件的 mmap 和“哪些块属于本层”的位图；封存后仍可用它读取层文件 |
| `Overlay` | orchestrator 内存中的读写对象 | 所有写入交给当前活写层；读取优先取活写层，没有再查封存层或模板 |
| `LayerStack` | orchestrator 内存中的对象 | 第一次封存后管理封存层及其块归属索引 |
| `/dev/nbdX` | host 内核块设备 | 将 Firecracker 的后端读写请求转交 orchestrator |
| `/dev/vda` | guest 中的虚拟磁盘设备 | 由 Firecracker 模拟 virtio-blk 设备，guest 的驱动为它命名 |

没有保存过 checkpoint 时，读块 100 的规则是：W1 写过它就从 W1 读取，否则从模板读取。写块 100 则始终进入 W1。

### 1.2 请求怎样到达活写层

```text
guest 内部
    ext4 文件系统驱动：把文件读写转换为磁盘读写
                 │
    virtio-blk 驱动：设备名 /dev/vda
                 │ 通过 virtio 队列提交请求
─────────────────┼────────────────────────────────────
host 上          ▼
    Firecracker：模拟 virtio-blk 磁盘设备
                 │ 对配置的后端设备执行读写
                 ▼
    /dev/nbdX：host 内核中的 NBD 块设备
                 │ NBD 驱动通过连接转发请求
                 ▼
    orchestrator 进程中的 NBD dispatcher
                 │ 调用 Overlay 的读写方法
                 ▼
    Overlay：读合并、写落上层
      ├─ Cache（活写层）：稀疏文件 + mmap + 块位图
      └─ 只读数据来源
           ├─ LayerStack：封存层 + 块归属索引（封层后才有）
           └─ 模板 rootfs：按需拉取并缓存
```

**`/dev/vda` 和 `/dev/nbdX` 分属两个操作系统。** `/dev/vda` 是 guest 内核为 Firecracker 提供的 virtio-blk 虚拟磁盘命名的设备；
`/dev/nbdX` 是 host 上的块设备，作为这块虚拟磁盘的数据后端。guest 不直接访问 host 的 `/dev/nbdX`。

以 guest 读取一个磁盘块为例：guest 的 virtio-blk 驱动把请求提交到 virtio 队列，Firecracker 处理请求并读取后端 `/dev/nbdX`；
host 内核的 NBD 驱动再把读请求转发给 orchestrator。orchestrator 通过 Overlay 从写层、封存层或模板取得内容，
沿原请求路径返回；Firecracker 把数据写入 guest 的接收缓冲区并完成 virtio 请求，guest 的磁盘驱动得到读取结果。
写请求走同样的路径，Overlay 把数据写入当前活写层。

Firecracker 负责虚拟磁盘的设备行为，orchestrator 经 NBD 提供磁盘的数据内容。后面的封层和换视图发生在 Overlay 内部，
不需要把 guest 的 `/dev/vda` 或 host 的 `/dev/nbdX` 换成另一个设备。

### 1.3 活写层为什么与磁盘等大，却不占满空间

活写层是**稀疏文件**：创建时，通过 `truncate` 将文件的逻辑大小设置为沙箱磁盘的总容量，也就是 host 上 `/dev/nbdX` 的容量，也是 guest 通过 `/dev/vda` 看到的容量。此时不为整个文件分配存储空间；后续写入哪些磁盘块，就为文件中的对应位置分配空间。尚未写入的块，由 Overlay 从封存层或模板读取。
所以一个刚起来的沙箱，写层文件逻辑上与磁盘等大、物理上接近 0。


mmap 在这里的具体作用是：把 host 上的层文件映射进 orchestrator 的虚拟地址空间。代码访问映射中的某段字节，就能访问文件相同偏移处的内容；当前实现使用共享文件映射，修改由 host 的页缓存管理，之后由文件系统写回。它没有把 guest 的整块磁盘复制进 guest 内存，也不表示写入已经持久化到物理存储。

### 1.4 怎样知道哪些块已经写过

`Cache.dirty`（`block/cache.go:54-56`）是按块号索引的位图 `blockSet`（`block/blockset.go:30`），`NewCache` 时按设备大小一次分配（每块 1 位）。
位只置不清，读写用原子 OR / Load，不需要锁；一个位被置上之前写进映射的字节，对看见这个位的读者可见。

这里的位图记录磁盘块的归属：**本层是否保存了这个块**，不记录块的内容，也不是 guest 内存脏页位图。`DirtyOffsets()`（`cache.go:534`）把它排序后返回，后续用它登记封存层、写入块清单文件。


稀疏文件中的空洞读出来也是零。Overlay 不能仅凭“读出的字节是不是零”判断该不该读模板：guest 可能确实写了一块零。位图为 1 时应使用本层内容，即使内容全零；位图为 0 时继续查下面的数据来源。

## 2. 保存 checkpoint：封存旧写层，接替新写层

### 2.1 保存前后，哪些对象发生变化

假设文件内容所在的磁盘块是 100，模板中为 A，修改后 W1 中为 B。这里假设内容仍位于同一块；实际文件修改涉及的其他数据和元数据块按同样规则处理。

| 时刻 | 活写层 | 封存层 | guest 读取块 100 |
|---|---|---|---|
| 保存 c1 之前 | W1，块 100 为 B | 无 | 从 W1 读 B |
| 保存 c1 之后 | 新建的空 W2 | W1，块 100 为 B | W2 没有该块，从 W1 读 B |
| 继续修改为 C | W2，块 100 为 C | W1，块 100 仍为 B | 从 W2 读 C |

**封存**是停止把后续正常写入送到旧写层，并保留它已有的内容。c1 的完整磁盘由“模板 + W1”共同提供；W1 本身不是完整磁盘副本。

如果继续保存 c2，W2 也会被封存，后续写入进入新活写层。c2 的磁盘由“模板 + W1 + W2”提供，同一个块以较新的层为准。W2 没有保存的块仍可能需要 W1。

### 2.2 暂停期间具体做什么


`NBDProvider.SealLayer`（`rootfs/nbd.go:141`）在同一个 Overlay 上另开一条路径，在虚机暂停期间做三步：

```go
o.sync(ctx)                                                             // ① 刷屏障：ioctl(BLKFLSBUF) + flush
newCache, _ := block.NewCache(size, o.blockSize, newCachePath, false)   // ② 新空写层：open + truncate（稀疏）+ mmap
sealed, _ := o.overlay.Seal(newCache)                                   // ③ 旧写层进层栈，接替为当前活写层
```

这三步不逐块复制旧写层的数据来生成新层，但同步仍可能产生 I/O，登记块归属也需要计算。封存文件移入 store 在恢复运行之后进行。

### 2.3 为什么先暂停，再做同步

`BLKFLSBUF` 让内核把这个块设备上缓冲的写全部推下去，经 NBD dispatcher 落进写层的 mmap。

- 它**保证**：内核块层已经接受的每一个写，都到了写层里；
- 它**不保证**：guest 停止产生新的写。

所以调用契约里明确写着**虚机必须已经暂停**：刷屏障处理的是"内核手里还攥着的"，暂停处理的是"guest 还要写的"，两者缺一不可。
`SealLayer` 与 `ResetView` 的注释都以这个前置条件开头 —— 它是调用方的责任，不是这个函数能自己保证的事。

### 2.4 代码怎样接替活写层

下面的 `o.cache` 指向当前活写层的 Cache，`o.device` 指向活写层没有该块时使用的只读数据来源。首次封存前，后者是模板；首次封存后，它是包含模板和 W1 的 LayerStack。

`Overlay.Seal`（`block/overlay.go:128`）持 Overlay 的独占锁：

```go
sealed := o.cache
stack, ok := o.device.(*LayerStack)
if !ok {
    stack = NewLayerStack(o.device, size)   // 第一次封存：把模板包进一个层栈
}
stack.AppendLayer(sealed)                   // 旧写层叠上去，它持有的块在归属索引里记成"归这一层"
o.device = stack
o.cache = newCache                          // 接替为当前活写层
```

旧写层没有被丢弃 —— 它成了层栈的最上一层，运行中的沙箱继续能读到自己封存前写的每一个块，只是现在是**从读路径**读到的。
代价与**本层写过的块数**成正比（在归属索引里登记）；首次构造层栈还要为整个磁盘建立索引，不能把整个封存过程视为严格常数时间。

`o.mu` 是一把读写锁，读写路径持共享锁，`Seal` 持独占锁 —— 换指针发生在 NBD dispatcher **底下**，它手里那个 `*Overlay` 指针从头到尾没变过，
所以换层对它们是原子的。

`Seal` 成功之后，代码注释写明"从这里起失败只报告、不回退"（`rootfs/nbd.go` 中 `Seal` 之后）：栈已经换了，是既成事实；
回退要把一个已经接收过新写的新写层再拆下来，反而会让层栈与账本对不上。这里的“账本”是 store 在内存中维护的当前层清单和映射等记录；它与实际层栈必须保持一致，异常处理见 [§8](#8-异常处理实际层栈与管理记录必须一致)。

### 2.5 恢复运行之后，封存文件放到哪里

封存出的层文件先留在沙箱缓存目录，checkpoint 在 resume **之后**才调 `SealedLayer.MoveInto`（`rootfs/rootfs.go:62`；
调用在 `internal/sandbox/checkpoint.go:240`，计时键 `seal_move`）把它移进 `layers/`。

同一文件系统内这是一次 `rename`：**inode 不变**，所以那个还活着的 mmap 继续有效 —— 它映射的是 inode，不是路径。

跨文件系统时 `rename` 返回 `EXDEV`，`Cache.MoveFile`（`cache.go:570`）退回**保洞的稀疏拷贝**，然后 unlink 原文件。
这条路径会复制数据，但不改变读出的内容：活着的 mmap 继续从那个已被 unlink 的 inode 提供读服务，而这只发生在**已封存**的层上 ——
封存内容再也不会改变，映射看到的和 store 里那份拷贝永远一致；等映射消失时，被 unlink 的 inode 的块才被真正释放。
也就是说跨文件系统的路径在**正确性**上没问题，只是**代价**退化成一次拷贝；放在暂停窗口之外，是为了不让冻结时长随改动量增长。
把 store 和沙箱缓存放在同一个文件系统上（默认都在 `ORCHESTRATOR_BASE_PATH` 下），这条路径就不会走到。

## 3. 恢复 checkpoint：改用目标层，创建新活写层

### 3.1 恢复 c1，不是把 B 复制回当前写层

恢复前，模板块 100 是 A、W1 是 B、当前 W2 是 C。恢复 c1 后，应使用 c1 的封存层 W1，并准备一个新的空活写层 W3：

| 对象 | 恢复前 | 恢复 c1 后 |
|---|---|---|
| Overlay 的只读数据来源 | 模板 + W1 | 模板 + W1 |
| Overlay 的活写层 | W2，块 100 为 C | 新空 W3 |
| 读取块 100 的结果 | C | B |
| 后续新写入的位置 | W2 | W3 |

如果恢复前已有更多封存层，也要换成 c1 自己的层清单。**恢复改变的是 Overlay 使用的数据来源，不需要逐块把目标内容复制回旧活写层。** `/dev/vda`、`/dev/nbdX` 和 NBD 使用的 Overlay 对象继续保留。

本章把“模板以及按顺序列出的封存层，共同提供某一时刻的完整磁盘内容”称为**磁盘视图**。“装配视图”就是打开这些层文件、恢复块归属信息、建立用于读取的 LayerStack。

### 3.2 暂停前，先准备目标的读取对象

`DiskViewForEntry` 读取目标 checkpoint 的层清单与各层 `.meta` 块清单，`Sandbox.AssembleView` 打开文件并构造新的 LayerStack。具体格式见 [§6](#6-文件与映射怎样记录磁盘状态)。这时旧 Overlay 继续服务，尚未切换。

如果文件或块清单无法读取，准备阶段就失败，沙箱继续处于当前状态，不会先暂停再发现目标不可用。装配读取的是封存数据，同一沙箱的 checkpoint 管理操作串行执行。

### 3.3 暂停后，切换读取对象和活写层


回滚时磁盘侧要换掉的是**整个视图** —— 读路径和写层一起换（`Overlay.ResetView`，`block/overlay.go:168`；`NBDProvider.ResetView`，`rootfs/nbd.go:194`
先刷屏障、再建新空写层）：

```go
o.mu.Lock()
oldDevice, oldCache := o.device, o.cache
o.device = device      // ← 目标 checkpoint 的层栈（§3.2 准备好的）
o.cache = cache        // ← 全新的空写层
o.mu.Unlock()

errs = append(errs, oldCache.Close())              // 被丢弃时间线的写层：连文件一起删
if stack, ok := oldDevice.(*LayerStack); ok {
    errs = append(errs, stack.Close())             // 旧层栈：只解映射，文件留给 store
}
```

两类旧对象的处理**不同**，理由很明确：

| 旧对象 | 处理 | 为什么 |
|---|---|---|
| 旧写层 | `Close()`：解映射并**删除文件** | 它记录的是被丢弃时间线上的写，没有任何人会再需要 |
| 旧层栈 | `LayerStack.Close()`：各层 `CloseKeepFile()`，**只解映射** | 文件归 store 所有，别的 checkpoint 的视图可能还引用着它 |

**失败语义。** 上述 `Overlay.ResetView` 在锁内完成两次指针赋值，随后才清理旧对象；它返回的清理错误不表示指针切换未发生。外层 `NBDProvider.ResetView` 的同步、新写层创建仍可能失败，不能把这两个函数的错误范围混为一谈。
所以它报错（泄漏了一些映射），但视图是对的，而回滚需要的正是视图对。泄漏一些映射比让上层以为回滚失败要好，因为它没失败。


### 3.4 为什么还必须恢复内存和设备状态

guest 内存可能缓存着恢复前的文件内容和 ext4 状态，只切磁盘会让它们与目标磁盘不一致。因此，完整 restore 在受控暂停期间协调磁盘、guest 内存和虚拟设备状态的恢复，完成后才恢复运行；具体顺序见[第 9 章](09-in-place-rollback.md)。本节只拆解其中的磁盘动作。

## 4. 删除 checkpoint：先判断哪些层仍被需要

### 4.1 删除记录，不等于删除它封存的层

假设 W1 保存块 100 的 B，后面的 W2 只保存块 200 的 Y。c2 的磁盘需要“模板 + W1 + W2”。即使删除 c1，c2 仍须从 W1 读取 B，因此不能顺便删除 W1。

**回收依据是哪些磁盘视图和当前运行状态还列着这个层。** 删除 checkpoint 释放它自身的引用；其他使用者仍在，就保留数据。

### 4.2 用引用计数判断是否可以删除


每个 checkpoint 封存一层。store 何时可以移除层文件的路径？**没有管理记录再引用它时**。这里的引用来自层清单（`internal/checkpoint/layer_refs.go:13-59`）：

- 每个已发布条目的视图（`Entry.Rootfs`），restore 从它重组磁盘；
- 活账本（`rootfsState.layers`），下一个视图从它复制，它也描述着沙箱正在读的栈。

例如 c1 列出 W1，c2 列出 W1、W2，当前运行的管理记录也列出 W1、W2，则 W1 的引用数为 3，W2 为 2。删除 c1 只把 W1 从 3 减到 2，并不能删除它。这个例子尚未发生层合并。

两者都计数，每列一次一个引用（`Store.layerRefs`，`store.go:480`），**计数归零**的层连同 `.meta` 进 reclaim，锁外删除：

| 位置 | 引用变化 |
|---|---|
| `appendLocked` | 新层进活账本，+1 |
| `publishLocked`（Commit） | 视图列出的每层 +1；`CommitHidden` 没有视图，不加 |
| `SetRootfsToEntry`（restore） | 恢复的视图每层 +1，然后被替换的活账本每层 −1（先加后减，两边都列的层不会碰到零） |
| `deleteLocked` | 条目的视图每层 −1，无论物理删除还是隐藏（隐藏条目不再有视图） |
| `pruneLocked` | 被级联删除的条目若还有视图，每层 −1 |
| 层合并切换 | 一对 [A, B] 的计数移给合并层（[§5](#5-层合并保留读取结果减少层文件)） |
| `dropStateLocked` | 随整棵沙箱树一起丢弃 |

计数不会从零回升：引用只来自发布从已计数状态复制的视图、restore 到仍被计数的视图、或新封存的层。`PoisonRootfs` 与 `InvalidateBase`
不还引用，因为活栈仍在读 `st.layers`。代码在 `refLayersLocked` / `unrefLayersLocked`（`layer_refs.go:63`、:86）；调试断言 `checkLayerRefs`（:115）从视图重算计数。

**为什么不能按 checkpoint 树回收。** 直觉上"删一个叶子条目，就删它封存的那一层"。但层栈不是 checkpoint 树：`appendLocked` 完全不看 `ParentID`，
只往活账本上叠；而全量捕获是树根（`ParentID == ""`），它的视图却叠在此前封存的每一层上。于是树的叶子可能拥有一层、而它子树之外的条目还在读这一层。
两个反例：跟踪关着时每个 checkpoint 都是全量根，但层一路叠加，删一个叶子若按树回收它的层，后面的条目就永远恢复不了；断链后的新全量根同理。

**跟踪关闭时仍会累积。** 那时每个视图列着此前全部层，删掉一个条目只放掉它自己那份引用，其它视图和活账本仍列着这些层；
也没有"隐藏且只有一个子"的条目，层合并不会发生。层文件因此随 checkpoint 次数累积，直到 restore 替换活栈或沙箱销毁。


引用计数归零后，store 可以删除文件路径；如果运行中的旧 LayerStack 仍保留 mmap，文件的数据块可能要等映射解除后才真正释放。删除路径与立即释放全部存储空间不是同一件事，层合并后的情况见下一节。

## 5. 层合并：保留读取结果，减少层文件

### 5.1 两层怎样合成一层

只有保留所有需要的内容，才能删除旧层。例如下层 A 保存块 100 的 B，上层 B 保存块 200 的 Y，合并层应同时保存这两个块。如果上下层都保存块 100，则合并后采用上层 B 的内容。

合并后的读取规则必须对每个仍存在的 checkpoint 和当前运行状态成立。如果还有某个 checkpoint 单独依赖下层 A 的旧内容，就不能用上层覆盖后的结果替代它。因此当前实现只在严格的共同引用条件成立时合并，并非每次删除都会合并。

### 5.2 当前实现何时允许合并


内存合并（[第 6 章 §10](06-memory-diff-tree.md#10-删除隐藏与合并)）把隐藏的 H 并入它唯一的子 C 时，磁盘这一半顺带尝试把
**C 封存的层 B 和紧挨在它下面的层 A** 合成一层（`internal/checkpoint/compact_layers.go`）。不合的话，内存那边条目收敛了，磁盘这边层文件还在一层层叠。

**条件看持有者，不看树**（`planLayerFold`，:155）：所有列 A 的持有者（各条目视图与活账本）都在 A 正上方列 B，所有列 B 的持有者都在 B 正下方列 A，
即 A、B 永远以相邻的一对 `[.., A, B, ..]` 出现。不满足（例如 restore 到 H 之后又做了一次全量捕获，A 被列在别的层下面）就只合内存。

**为什么合并不改变任何视图读到的块。** 视图里每个块由列着它的最上层提供。把相邻的 [A, B] 换成一层"B 的块叠在 A 上"：

- B 持有的块，之前之后都由 B（或更上层）提供；
- A 有而 B 没有的块，之前由 A 提供，之后由合并层在**同一偏移**提供（层文件原样封存，存储偏移 = 设备偏移）；
- 两者都没有的块照旧落到下面。

header 里原来指向 A 的映射改指合并层，偏移不变。由于"永远成对出现"对每个持有者成立，这个论证对每个视图都成立。

### 5.3 文件与引用怎样切换

**做法**：字节往少的一边拷（`foldLayers`，:291）—— A 有 B 无的块填进 B 的空洞，或者 B 的块覆盖到 A 的文件上（每个持有者都只在 B 没有的地方读 A）；
接收方以新名字 `layer-<B 的 uuid>.<H-id>` 硬链接进来，写新的 `.meta`，每个列着这对层的视图改写一份新名字的 header
（`rootfs.header.<条目-id>.<H-id>`）；活账本换成新层清单与改名后的映射。切换时在锁内再用引用计数核对持有者没变（`layerHoldersUnchangedLocked`，
`compact.go:953`），然后 A、B 计数归零进 reclaim，合并层接过它们的计数（`switchLayersLocked`，:989）。

**活栈不重建。** 正在运行的沙箱继续经已建的映射读 A、B：unlink 不影响已有映射，合并写进去的字节恰好在活栈从不从该文件读的块上。
旧映射占用的空间要等下一次 restore 替换层栈，或沙箱销毁解除映射后，才具备实际释放条件。

## 6. 文件与映射：怎样记录磁盘状态

封存层保存块内容，但恢复还需要知道：本层保存哪些块、整个目标磁盘各区间从哪里读取。它们分别由 `.meta` 块清单和 `rootfs.header` 映射记录。下面区分三种信息：

| 信息 | 保存在哪里 | 回答什么问题 |
|---|---|---|
| 块的内容 | 层数据文件 | 这个块的字节是什么 |
| 本层持有的块 | 内存位图；封存后另写 `.meta` 文件 | 哪些块应从本层读取 |
| 完整磁盘的区间来源 | `rootfs.header` | 每段磁盘内容对应哪个数据来源及文件偏移 |


### 6.1 磁盘偏移与层文件偏移相同

这里的“映射”是一条偏移对应记录，不是 mmap。例如块大小为 4096 字节，磁盘块 100 的起始偏移是 `100 × 4096 = 409600`。该块写入 W1 时，字节放在 W1 文件的偏移 409600 处。读取时从该位置取 4096 字节即可。mmap 则是程序访问层文件字节的一种方式，两者含义不同。

因为层文件就是原来那个写层文件、块还在原来的偏移上，映射关系是**恒等**的：

```
设备偏移 0x1000  →  层文件偏移 0x1000
```

`identityMappings`（`internal/checkpoint/rootfs.go:393`）把连续的块合成一个 run，每个 run 一条 `BuildStorageOffset == Offset` 的映射：

```go
mappings = append(mappings, &header.BuildMap{
    Offset:             uint64(runStart),
    Length:             uint64(runLength),
    BuildId:            layerID,
    BuildStorageOffset: uint64(runStart),   // ← 与 Offset 相同
})
```

比原生少一步偏移换算。代价是**不剔除全零块**：guest 写了一整块零，紧凑 diff 会把它记成一个 empty 位（0 字节），层文件则实打实占一个块。
对高频 checkpoint 这个取舍是划算的：省下的是每次封存的一整趟 I/O，多花的是磁盘空间，而写层本来就是稀疏的、只有真写过的块才占盘。

### 6.2 rootfs.header：记录完整磁盘的区间来源

沿用 W1 保存块 100、W2 保存块 200 的例子，c2 的记录需要表达：块 100 从 W1 读、块 200 从 W2 读，其余范围按模板映射读取。`rootfs.header` 保存这种区间来源关系，文件里不是整块磁盘的内容。“合并 header”指合并这些记录，不是把层数据复制到一个文件。

每打一个 checkpoint，`AppendLayer`（`rootfs.go:64`）在全局锁下把新层的映射折进沙箱当前的合并 header：

- `MergeMappings`：上层覆盖下层；
- `NormalizeMappings`：合并相邻同源区间；
- `ValidateMappings`：检查结果**无缝无叠、恰好覆盖整个设备**。

结果序列化成该条目的 `rootfs.header`，它描述的是"模板 rootfs 的映射 + 到此为止每一层的恒等映射"—— 也就是那一时刻的完整磁盘视图。
序列化和两次写文件在锁外。

### 6.3 .meta：单独记录本层保存了哪些块

例如 W1 只写过块 100 和 200，在块大小为 4096 字节时，它的块清单列出字节偏移 409600 和 819200。重新打开 W1 时，根据这份清单设置内存位图，程序才知道这两个位置是有效内容，其他位置应向下层查找。

每个层文件旁边写一个 `.meta` 块清单文件（`writeLayerMeta`，`rootfs.go:356`）：每个块偏移 8 字节小端一条，记录这一层持有哪些块。

它的作用只有一个：**restore 重新打开这个层文件时，要恢复"它持有哪些块"这份知识**。文件里有数据，但仅靠读取文件内容，无法判断哪些块是"这一层写的"、
哪些是稀疏空洞 —— 空洞读出来是零，而零也可能是 guest 真写的内容。所以数据由文件提供，归属由块清单文件提供，两者合起来才是一个可用的层。

块清单文件丢了会怎样？restore 在暂停之前就要读块清单文件（[§7.2](#72-restore-怎样批量建立目标索引)），`DiskViewForEntry`（`rootfs.go:331`）读不出来就返回错误，restore 在动虚机之前失败，
沙箱照常运行在当前状态。这类错误会被发现，不会静默读到错数据。

## 7. 实现细节：读取索引、装配成本与落盘


### 7.1 运行中怎样直接找到块所属的层

封存 k 次之后，写层之下有 k 个封存层。最朴素的读法是一层层往下问："最上层有没有这个块？没有就问下一层……"——
最坏一次读要走 k + 2 层，链越长读越慢。

`LayerStack`（`block/layerstack.go:40`）不这样做。它维护一个**按块的归属索引** `owner []uint16`（0 表示模板提供，k 表示第 k 层持有）。例如 W1 保存块 100、W2 保存块 200，则 `owner[100] = 1`、`owner[200] = 2`；其余未被封存层修改的块为 0。若 W2 也写了块 100，则 `owner[100]` 更新为 2。当前活写层仍由 Overlay 优先检查，只有未命中才查这个索引。
后封存的层覆盖它持有的块的索引项，正是"最较新的封存层提供内容"。读一个块时从数组里取出归属、直接去那一层读（`ReadAt`，:156），**代价与层数无关**。

代价是每块 2 字节：按 4 KiB 磁盘块计算，每 GiB rootfs 每个视图 512 KiB。索引最多容纳 65535 层（`maxStackLayers`，:14）。LayerStack 自己不加锁，
靠 `Overlay.mu`：读在共享锁下、`Seal` 在独占锁下原地追加，读永远看不到半更新的索引。

### 7.2 restore 怎样批量建立目标索引

restore 不沿用运行中的栈，而是按目标条目自己的层清单重新叠一个（`Sandbox.AssembleView`，`internal/sandbox/checkpoint.go:341`）：

```go
stack := block.NewLayerStack(base, size)
for _, layer := range layers {                                 // 自底向上
    cache, _ := block.NewCache(size, blockSize, layer.Path, false)
    cache.MarkCached(layer.DirtyOffsets)                       // 块清单文件给出"哪些块是这一层的"
    stack.AppendLayerWithBlocks(cache, layer.DirtyOffsets)     // 按区间填归属索引
}
```

装配在**暂停之前**做：读的全是不可变的封存层和块清单文件，沙箱的 checkpoint 操作又是串行的，没人能在底下再封一层。装配不出来时
沙箱照常运行在当前状态。目标层栈的装配不占暂停窗口；暂停窗口内仍要同步、创建新活写层并调用 `ResetView` 切换（[§3](#3-恢复-checkpoint改用目标层创建新活写层)）。相比之下，原生恢复要重建整个 Overlay 并靠缺页把工作集换回来。

块清单文件先由 `DiskViewForEntry`（`internal/checkpoint/rootfs.go:331`）读出解码（计时键 `disk_view_read`），再逐层重开。两处都**按区间批量**处理块清单文件列表：
`MarkCached`（`block/cache.go:506`）把连续块合成 run、再按 64 块一个字做一次原子 OR；`AppendLayerWithBlocks`（`layerstack.go:88`）对每个 run
做一次索引区间填充（`claimRun`，:130；run 由 `forEachRun` 切出，`blockset.go:161`）。

块集合为什么用位图而不用以块偏移为键的哈希表？后者每块要一次哈希插入和一次分配、每块约占上百字节堆，装配视图的时间和存活堆都随块数线性增长；
位图 + 区间批量之后，restore 随块数增长的斜率很小（前后对比见 [附录 C §8.9](C-evolution-and-cases.md#89-视图块数增长restore-随时间变慢)）。

### 7.3 长期运行后，为什么需要处理更多块

一个视图的块数是它各层块清单文件列出的块数，最底层（经层合并后常常是一层大层）约等于"guest 自启动以来写过的块的并集"。
guest 里的 ext4 在截断重写小文件时往往**分配新块**而不是复用旧块，于是在保留这些历史层的过程中，累计写过的块集合可能增长，长期运行的沙箱视图块数随时间增长。

它有上界：块集合不会超过 guest 能写到的块 —— 严格上界是整个磁盘的块数；具体负载下会受文件系统分配方式、空闲区和元数据写入范围影响。对交付模板的 rootfs，这个上界约 16 万块
（长跑中的块数曲线与 restore 随块数的斜率都见 [附录 C §8.9](C-evolution-and-cases.md#89-视图块数增长restore-随时间变慢)）。restore 剩下的随块数增长的部分主要来自读块清单文件和内存回滚量，是真实工作量。


### 7.4 不额外等待 msync，具体省掉什么

`SealLayer` 不额外调用 msync 来等待封存层数据写回底层存储。层文件通过共享 mmap 访问；在正常运行且文件未受外部修改的条件下，同一文件的映射与读取使用 host 页缓存，不需要先写到物理存储再读回来。跨文件系统移动时则由拷贝保留封存内容，见 §2.5。

这不等于没有同步操作：封存前仍有 NBD 同步屏障；也不表示 checkpoint 能承受 host 崩溃。当前 checkpoint 的管理记录在 orchestrator 进程内存中，不能仅靠 msync 获得进程重启后的恢复能力，生命周期边界见[第 12 章](12-state-and-lifecycle.md)。

源码注释记录过额外同步约每脏 MB 0.49 ms 的成本，但未注明平台和负载，只能作为历史量级参考。去掉额外 msync，减少了等待数据写回的时间，**不能据此声称整个磁盘 checkpoint 是 O(1)**：封存时还要登记本层块，首次建立归属索引涉及磁盘块数，块清单和 header 的生成、序列化也有成本。实际耗时应分阶段测量，见[附录 B §6.3](B-920b-results.md#63-拟合与碰线点)。host 内核仍会按自身策略写回脏页。

## 8. 异常处理：实际层栈与管理记录必须一致

这里的“磁盘账本”具体指 store 的 `rootfsState`：其中保存当前层清单、合并映射等管理记录。运行中的 Overlay 则通过 LayerStack 实际提供磁盘读取。两者必须对应，否则后续 checkpoint 可能漏记已经存在的层。


`appendLocked`（`internal/checkpoint/rootfs.go:130`）一旦越过"层已经进了活栈"这一点，任何失败都把沙箱的磁盘账本标为**污染**。
为什么？封存已经发生，层已经在活的栈里了，账本就**必须**跟上它。如果跟不上（例如合并校验失败），后面每一个用这份账本构造的视图都会**少一层** ——
restore 时静默读到旧数据。

所以处理方式不是"重试"，也不是"回滚"，而是**把账本标记为不可信**，此后一切 `AppendLayer` 直接报错（`ErrRootfsPoisoned`）。
header 写不出来、封存层没能进 store 等发生在 `AppendLayer` 之外的同类失败走 `PoisonRootfs`（:245）。

> **账本跟着栈走，不跟着 RPC 的成败走。** 栈已经变了，这是既成事实；RPC 失败只是调用方没拿到结果。
> 把两者混为一谈，就会产生"账本说有 3 层、实际有 4 层"这种没法自愈的状态。

污染由一次成功的 restore 清除：`SetRootfsToEntry`（:276）用该条目自己的 header 重建当前管理记录，此时账本与栈重新对齐。
那些进了活栈却没进账本的层记在 `rootfsState.unrecorded`（:47），它们不在任何视图里、不被计数，等下一次 restore 替换活栈时回收；没有 restore 就随沙箱走。
污染对调用方意味着什么（先 restore 一个已有的 checkpoint）见 [第 22 章](22-api-semantics.md)。

## 9. 与原生 pause 的区别：导出后不继续使用原 Overlay

前面讲的沙箱级 checkpoint 要求恢复运行后继续写，因此采用“封存旧层 + 新活写层”。原生 pause 会结束当前沙箱运行，可以摘出全部层再生成紧凑导出文件。这是两种不同用途，不能把原生导出直接当作不停用原 Overlay 的封存操作。


原生 pause 走 `NBDProvider.ExportDiff`（`rootfs/nbd.go:72`，逐步拆解见 [第 13 章 §4](13-native-snapshot.md#4-磁盘增量)）：摘出写层（`Overlay.EjectLayers`，
Overlay 就此作废）→ 停沙箱、等 NBD 设备释放 → 全零块只记 empty 位、非零块紧凑追加进 diff → 关闭写层。

产物是一个**紧凑**的 diff 文件：块在文件里按顺序排列，与它在设备上的位置无关，所以要一张映射把设备偏移翻译成存储偏移。
它的语义是**沙箱生命的终点**：摘出之后任何写都没有去处，遍历 mmap 也必须没有并发写。对"沙箱离场"合适，对高频 checkpoint 不能接受。

沙箱打过 checkpoint 之后，写层已经被封存过多次，当前写层只含最近一次之后的写。所以 `EjectLayers`（`block/overlay.go:96`）交出**全部**层
（封存层自底向上，再加当前写层），`ExportLayersToDiff`（`block/cache.go:181`）按"最上层有就取最上层"把整个栈压平导出，
与沙箱自己读到的内容一致。内存那一半在同一场景下的正确性前提见 [第 14 章 §9](14-native-precise-increment.md#9-与-checkpoint-叠加累积位图)，两半合起来见 [第 15 章 §7](15-native-cooperation-and-cost.md#7-checkpoint-之后做原生-pause-的正确性前提)。


### 9.1 两种路径对比

| | 原生 `ExportDiff` | `SealLayer` |
|---|---|---|
| 数据搬运 | 逐块从 mmap 读出、写进输出流 | 不逐块复制旧层；跨文件系统移入 store 可能拷贝 |
| 沙箱 | 必须停 | 暂停即可，之后继续跑 |
| Overlay | 作废 | 继续用，只是换了一层 |
| 产物布局 | 紧凑，存储偏移 ≠ 设备偏移 | 原样，存储偏移 == 设备偏移 |
| 全零块 | 剔除（只记 empty 位） | 保留，按块占盘 |
| 之后还能写吗 | 不能 | 能，写进新写层 |
