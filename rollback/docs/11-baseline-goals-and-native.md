# 11 · 基线、目标与原生对比

> 这篇给评审、选型和要接手开发的人看。读完你能说清：e2b 原生 snapshot 做了什么、成本落在哪；
> 本方案要解决什么、明确不解决什么、由此推出哪几条设计原则；以及两条路径逐项差在哪里、
> 每个"优化点"是相对谁而言的。全书与原生的对比表只在本篇出现。

## 1. 基线：e2b 原生 snapshot

### 1.1 两个 RPC

| RPC | 做什么 | SDK 里对应 |
|---|---|---|
| `Pause` | 打快照 + **停掉沙箱** | 暂停沙箱 |
| `Checkpoint` | 打快照 + 停掉沙箱 + **从新快照重新拉起一个** | `create_snapshot()` |

两者共用 `snapshotAndCacheSandbox`（`internal/server/sandboxes.go`；`Server.Pause` 在 :380，
`Server.Checkpoint` 在 :444），区别只在之后要不要再拉起一个。`Pause` 打完就 `stopSandboxAsync`，
产物进对象存储，这是"沙箱离场"的语义。

`Checkpoint` 拉起新沙箱时：

| id | 语义 | `Checkpoint` 之后 |
|---|---|---|
| `SandboxID` | 对外的沙箱标识 | **不变** |
| `ExecutionID` | 一次"执行"的标识，给 API、路由目录、分析用 | **不变** |
| `LifecycleID` | 一个 Firecracker 进程实例的标识 | **换新** |

`LifecycleID` 换新的理由写在代码注释里（`sandboxes.go:490-491`）：老沙箱的清理协程用自己的
`LifecycleID` 调 `RemoveByLifecycleID` 删表项，新沙箱若沿用同一个 id 就会被误删。

> 所以"snapshot 之后沙箱 id 不变"成立，但**底下已经是一个全新的 Firecracker 进程**：
> 新进程要重建 KVM VM、vCPU、GIC、设备、tap、UFFD，然后靠缺页把工作集换回内存。

### 1.2 打快照的六步

`Sandbox.Pause`（`internal/sandbox/sandbox.go`）依次：停健康检查 → 暂停虚机 → 让 Firecracker 写出 snapfile
（vCPU、GIC、设备状态，不含内存）→ 从内存后端取脏块集合 → 按脏块集合用 `process_vm_readv` 把内存从
Firecracker 进程地址空间拷出 → 导出磁盘增量 → 写元数据。**暂停之后一直没有 resume**。

**内存增量**的产物是紧凑的（只含脏块、按序排列），靠一张链式 header 寻址：本次写过的块指向本次的 diff，
没写过的块指向上一代 build。

**磁盘增量**走 `NBDProvider.ExportDiff`（`internal/sandbox/rootfs/nbd.go:72`）：摘出写层（Overlay 就此作废）→
停沙箱、等 NBD 设备释放 → 逐块处理（全零块只记一个 empty 位，非零块紧凑追加）→ 关闭并删除写层文件。
"必须停沙箱"是代码结构决定的：`RootfsDiffCreator` 把沙箱自己的 `Close` 作为 `closeHook` 传进
`ExportDiff`（`internal/sandbox/diffcreator.go:17-21`）—— **导出磁盘增量这个动作，参数之一就是"关掉沙箱"**。

### 1.3 恢复：`ResumeSandbox`

```
新建 Firecracker 进程
   ├── 建 KVM VM、vCPU、GIC、virtio 设备；注册 eventfd / irqfd / ioeventfd
   ├── 建 tap、分配网络槽位；起 UFFD handler 挂上 guest 内存
   ├── 建 NBD 设备 + Overlay（模板 rootfs + 新写层）
   └── 加载 snapfile
跑起来 → 每访问一个没内容的页 → 缺页 → 按 header 从本地缓存或对象存储取
```

成本两项：建一台虚机的固定开销（与规格弱相关），以及**把工作集换回内存**（与规格强相关，与回退跨度无关）。
e2b 的 prefetch（按上次的缺页顺序提前拉）能缓解，但改变不了成本模型。

### 1.4 它擅长什么

| 场景 | 为什么合适 |
|---|---|
| 跨节点迁移、长期持久化 | 产物自足、进对象存储，不依赖任何活体资源 |
| 进程崩溃后恢复 | 恢复本来就是新建进程加载 |
| 沙箱离场后再回来 | 停掉沙箱本来就是这个场景的一部分 |

它不擅长的恰好是本方案的目标场景：高频、低延迟、沙箱不能中断。这不是实现缺陷，是**成本模型和场景不匹配**。

### 1.5 ARM 适配基线上的增量判据

上游 x86 用 uffd 写保护位区分读缺页与写缺页，增量是精确的。ARM 适配版把这条写保护路径注释掉了
（`internal/sandbox/uffd/userfaultfd/userfaultfd.go:383-385`），判据退化成"凡被换入过的页都算脏"，
叠加"每次 `Checkpoint` 都重建沙箱、工作集要重新换入"，**即使两次 snapshot 之间什么都没做，增量的下限也约等于常驻工作集**。
这个判据差异（"读也算脏"）的完整定义见 [13](13-dirty-page-tracking-and-hdbss.md#5-判据差异读也算脏)。
必须说清：这是 ARM 适配引入的退化，不是 e2b 的设计问题；本方案绕开它，也不构成"超越 x86 原生"。

原生路径的增量判据问题及修复另有专题，不属于本方案交付。与本方案相关的只有一条：打过 checkpoint 或做过 restore
的沙箱再做原生 pause 时，导出的内存差分仍须完整，这个正确性前提见
[14](14-memory-diff-tree.md#9-checkpoint-之后再做原生-pause-的正确性前提)。

## 2. 目标

### 2.1 目标场景

**沙箱在执行任务时出错，需要退回到上一个已知良好的状态继续跑**（场景见 [10](10-background.md)）。

| 特征 | 具体含义 | 推出什么 |
|---|---|---|
| 高频 | 一个任务里十几次 | 单次成本必须低到可以随手用；固定开销不可接受 |
| 低延迟 | 发生在 Agent 的决策循环里 | 量化目标：**checkpoint ≤ 200 ms、restore ≤ 100 ms** |
| 沙箱不能中断 | 有 IP、端口映射、保持中的连接、外部持有的引用 | 排除一切"停掉再拉起"的路线 |

第三条单独就排除了原生的整条路径：`Pause` 和 `Checkpoint` 都要停掉沙箱。

两个数字是客户给的上限。全书把它钉在对我们最不利的一侧：checkpoint 判**增量** checkpoint
（沙箱的第 2 代及以后）的客户端墙钟 p50，p99 并列；restore 判**原地** restore（沙箱 ID 与 Firecracker 进程都不变）
的客户端墙钟 p50。树根全量是每个沙箱一次性的成本，单列说明，不参与判定。口径定义见
[24](24-performance-methodology.md)，判定结果见 [25](25-results-and-compliance.md)。
达标线是常数，增量的代价随本次改动量走，所以性能表按**脏页量档位**给，不按沙箱内存大小给。

### 2.2 硬约束

| # | 约束 | 后果 |
|---|---|---|
| 1 | aarch64（鲲鹏 920B / 950） | ARM 适配版的既有问题要一起面对 |
| 2 | **产物盘是 ext4** | 整条数据路径不得依赖 reflink（[12](12-architecture.md#8-为什么交付用-ext4)） |
| 3 | 不改动原生路径的行为 | 两条路径并存，本方案是纯加法：新路径、新端点、新字段 |
| 4 | 沙箱内不装任何代理程序 | 全部动作在宿主侧完成（[12](12-architecture.md)） |
| 5 | orchestrator 与 Firecracker 成对交付 | 配错就用不了（[15](15-firecracker-api-contract.md#6-版本配对)） |

约束 2 影响最深远：它否掉了"每代克隆上一代完整镜像"这个更简单的设计，是差分树存在的全部原因
（[14](14-memory-diff-tree.md)）。

### 2.3 明确的非目标

**划界本身是设计的一部分。** 下面这些明确不做，交给原生 snapshot：

| 非目标 | 为什么划出去 |
|---|---|
| 宿主崩溃恢复 | 账本活在 orchestrator 进程内存里，进程一死就没了 |
| 跨节点迁移 | 产物是"相对模板的增量"，路径绑定本机 |
| 长期持久化 | 产物随沙箱生命周期回收 |
| 沙箱进程已死后的恢复 | 只有原地回滚一条路，它要求活体 |
| 虚机状态撕裂后的抢救 | 明确标记为死并要求重建 |
| 跨沙箱共享 checkpoint | checkpoint id 只在所属沙箱的生命周期内有意义 |

划界换来的是整类问题不存在：产物不跨重启存活 → 不用处理陈旧条目、与已消失沙箱的对账、格式迁移；
不跨节点 → 没有上传下载和跨节点一致性；没有兜底重建路线 → 两条恢复路径之间不用做语义对齐
（代价是失败必须分级，见 §3.3）；只在活沙箱上工作 → 没有离线加载与修复。代价同样真实：checkpoint 备份不走，
orchestrator 或宿主重启全部失效，沙箱迁到别的节点时不跟随（推导见 [22](22-lifecycle-reasoning.md)）。

## 3. 四条设计原则

### 3.1 成本只与改动量挂钩

任何与虚机规格线性相关的固定开销都要消掉：

| 处 | 怎么做 |
|---|---|
| 内存产物 | 每代只存本代脏页，不克隆上一代（[14](14-memory-diff-tree.md)） |
| 磁盘产物 | 封存是改名，零数据搬运；封存不等落盘（[16](16-disk-layering.md)） |
| 恢复 | 按页写回回滚集，不重建镜像（[17](17-in-place-rollback.md)） |
| 内容解析 | 按页沿祖先链寻址，恢复成本与链深无关；删除时同步合并（compact / fold）隐藏条目只为回收空间（[14](14-memory-diff-tree.md)） |

唯一保留的固定开销是**全量根**（每个沙箱的第一次 checkpoint），它有开关（[06](06-configuration-and-capacity.md)）。

### 3.2 不重建任何宿主资源

进程、KVM fd、eventfd、irqfd / ioeventfd 注册、tap、网络槽位、NBD 设备、内存映射，一个都不重建。
这既是"快"的全部来源，也是"离不开活沙箱"的全部原因。

### 3.3 宁可报错，不可静默损坏

一次错误的回滚不会让虚机崩溃，它会让某几页内存属于另一个时刻，然后虚机继续跑。所以：

| 情形 | 处理 |
|---|---|
| 路径上缺侧车 | 报错，不静默降级成全量回滚 |
| 链断了 | 拒绝恢复，直到下一次全量 checkpoint |
| 账本与层栈不一致 | 标记污染并拒绝服务 |
| 拓扑不一致 | 拒绝，不勉强写 |
| 纪元可能丢失 | 以隐藏条目保住它 |

没有兜底重建路线，这条从"好习惯"变成了"硬要求"（[20](20-failure-semantics.md)）。

### 3.4 能力随硬件自动降级，但要说出来

有 HDBSS 就用硬件标脏，没有就退回 KVM 写保护；功能永远正确，只是代价不同。降级不能静默：
启动时报告能力和理由、每次调用回报 `memMode`、Firecracker 自报脏页后端、`FC_HDBSS_REQUIRED` 可以让生产部署宁可启动失败
（字段见 [07](07-observability-reference.md)，开关见 [06](06-configuration-and-capacity.md)）。

## 4. 与原生的逐项对比

| 维度 | e2b 原生 | 本方案 |
|---|---|---|
| 打快照时沙箱 | 停掉，再从新快照拉起一个新进程 | **不停**，同一个进程 |
| 快照后的身份 | SandboxID / ExecutionID 不变，LifecycleID 换新 | 无进程更替 |
| 内存搬运 | orchestrator 用 `process_vm_readv` 从 FC 进程地址空间拷出 | Firecracker 自己写稀疏差分，位图同一次调用落地 |
| 内存判据 | uffd 写保护；ARM 适配基线上退化为驻留判据 | KVM / HDBSS 脏页日志 |
| 磁盘增量 | 停沙箱后把写层紧凑导出成 diff | 写层就地封存成只读层，零拷贝 |
| 磁盘增量的落盘 | 同步导出 | 不等待落盘 |
| 历史结构 | 线性链 | **树**，可前滚、可跨分支 |
| 恢复方式 | 新建进程 + UFFD，靠缺页把工作集换回 | **原地写回**差异页，宿主资源全保留 |
| 恢复成本 | 与虚机规格挂钩 | 与回退跨度挂钩 |
| 产物 | 自足，进对象存储 | 相对模板的增量，宿主本地 |
| 生存期 | 独立于沙箱 | 随沙箱回收 |
| 跨节点 / 崩溃恢复 | 可以 | 不可以 |
| 典型频次 | 一个沙箱一两次 | 一个任务里十几次 |

### 4.1 成本模型

设 guest 内存 M、本次改动量 D、回退跨度 R：

| 操作 | 原生 | 本方案 |
|---|---|---|
| 打快照 · guest 停顿 | 整个操作：停掉、导出、重建、换页 | O(D) 冻结窗口 |
| 打快照 · 内存 | O(D)（x86）/ O(常驻工作集)（ARM 适配基线） | O(D) |
| 打快照 · 磁盘 | O(脏块) 紧凑导出，必须停沙箱 | O(1) 改名 |
| 恢复 · 进程与设备 | 全部重建 | 零 |
| 恢复 · 内存 | O(工作集) 缺页换入 | O(R) 写回 |
| 恢复 · 磁盘 | 重建 Overlay | 按视图重开各层、建块归属索引，无数据搬运 |

> **推论**（基于成本模型的判断，不是实测）：原生的代价基本是常数，本方案随 D、R 线性增长，理论上
> R 接近整个工作集时两者恢复代价趋同。即使在那一点，本方案仍保留"沙箱不中断"和"没有进程重建的固定开销"两项。
> 所以交叉点不是"该切换到原生"的信号，而是"回退跨度太大，也许该考虑重建沙箱"的信号。

### 4.2 优化点与对照基准

**"对照基准"这一列不能省**，否则整张表会被读成"比 e2b 强 N 项"。

| 层次 | 优化点 | 带来什么 | 对照基准 |
|---|---|---|---|
| 脏页跟踪 | HDBSS 自动接管，启动探测，无硬件安全退回 | CPU 记录脏页，950 上开箱即用 | 新增能力 |
| | 判据取自 KVM / HDBSS 日志，绕开 uffd | 补回精确增量 | ARM 适配基线 |
| 内存产物 | 差分树：每代只存本代脏页 | 成本只与改动量有关，不需要 reflink | 本方案内部取舍 |
| | 位图随快照同一次调用落地 | 省一轮接口往返和一次全内存扫描 | 原生 |
| | 树形历史 | 回滚后可再前滚、可跨分支，历史不丢 | 原生 |
| | 树根存一次全量 | 整棵树自给自足，回滚路径不跨网络 | 本方案内部取舍 |
| | 删除时合并隐藏条目 | 条目数有上界，空间可回收 | 本方案内部取舍 |
| 恢复路径 | 按页沿祖先链解析，不重建完整镜像 | 恢复成本与链长无关 | 本方案内部取舍 |
| | 进程内原地回滚 | 宿主资源全部保留，无需重新换入工作集 | 原生 |
| | 回滚集精确到页 | 代价与回退跨度成正比 | 原生 |
| 磁盘 | 写层就地封存 + 视图活体切换 | 打快照与回滚都不停沙箱 | 原生 |
| | 封存不等待落盘 | 封存耗时不随改动量增长 | 本方案内部取舍 |
| 一致性 | 内存与磁盘在同一次暂停窗口内完成 | 两者是同一瞬间的镜像 | 原生 |
| 架构 | 接口在宿主侧接管 | 沙箱内不需要任何代理程序 | 新增能力 |
| 工程保障 | 失败分级、断链拒绝恢复、删除不打断后代 | 杜绝"看起来成功、实际数据已坏" | 新增能力 |
| | 分阶段计时 + 全量 / 增量模式回报 | 能定位阶段，能发现静默退化 | 新增能力 |

16 项里：4 项是**新增能力**（原生根本没有这个场景）；5 项是**本方案内部取舍**（相对自己的其它可选设计）；
1 项是**补回 ARM 适配丢掉的东西**（x86 原生本来就有）；其余 6 项才是相对原生路径的改进，而且是在"活沙箱内高频回退"
这个特定场景下的改进。

### 4.3 三个常见误解

- **"本方案比 e2b 原生快。"** 要看比什么。在活沙箱内快速回退这个场景下是的，因为原生不是为它设计的；
  在"沙箱离场后再回来"这个场景下，本方案**做不到**。
- **"原生 snapshot 是 pause + resume，沙箱没变。"** id 没变，进程变了（§1.1）。这也解释了原生成本为什么与虚机规格挂钩：每次都在重建。
- **"e2b 的增量有一个与改动量无关的下限。"** 只在 ARM 适配基线上成立（§1.5），x86 上 e2b 的增量是精确的；
  本方案不走那条判据，不受影响。

两条路径怎么分工、怎么叠加使用（先用 checkpoint 精确回到想要的时刻，再用原生 snapshot 固化），见
[02](02-semantics-and-limits.md)。

## 5. 小结

1. 原生 `Pause` = 快照 + 停；`Checkpoint` = 快照 + 停 + 从新快照重新拉起，id 不变、进程换新。成本与虚机规格挂钩，
   磁盘增量在结构上必须停沙箱。
2. 目标场景三个特征：高频、低延迟、不能中断；量化目标 checkpoint ≤ 200 ms、restore ≤ 100 ms，只约束增量与原地 restore。
3. 五条硬约束，"产物盘是 ext4"影响最深；六项明确非目标换来整类问题不存在，代价是产物离不开活沙箱。
4. 四条原则：成本只与改动量挂钩、不重建宿主资源、宁可报错不可静默损坏、降级要说出来。
5. 对比表只在本篇；优化点必须带对照基准列。原生路径的增量判据修复是另一个专题，不属于本方案交付。
