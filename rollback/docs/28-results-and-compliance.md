### 1.2 为什么这两台机器的数字不能相减

差的不是一项，是**四项同时在差**：脏页后端（硬件标脏 vs 软件写保护）、
产物介质（真盘 vs loop 卷）、产物文件系统、模板内存规格。

一个具体例子：950 的 `checkpoint_verify.py` 那轮全量 0.283 s，920B 09-04 同一个脚本
同样参数是 2.108 s，差 7.4 倍。这 7.4 倍里至少混着「HDBSS 省掉的 VM exit」
「真盘 vs loop」「模板内存规格可能不同」三笔，**没有办法把其中一笔单独摘出来**。
写成「HDBSS 带来 7 倍收益」是错的
（[第 24 篇 §4.5](24-test-overview.md#45-不同条件的数不相减)）。

要量化 HDBSS 的收益，唯一正确的做法是**在同一台 950 上跑两遍**——
一遍走 HDBSS、一遍强制走软件写保护，其余条件全不动。这一项在 §8 里列为缺口。

### 2.2 判据失效时靠什么顶

09-08 那一轮三个脚本全报 `mem_mode=?`。当时用的旁证是**产物实测**：
对照组脚本的内存产物列里，第一代是 **2048 MB**（整份 guest RAM），第七代只有 **276.5 MB**——
增量确实生效了（`benchmark/checkpoint-bench-对比.md` §5.1）。

这条旁证成立，但它是**人看出来的**，不是脚本判的。判据该修的方向也在那份文档里：
把断言从「服务端自报的 `mem_mode`」换成「内存产物是否接近 guest RAM 总量」，
宿主机上一个 `st_blocks` 就够，不依赖服务端与 SDK 的任何改动。

### 2.3 pause 与兼容矩阵

`pause_verify.py` 09-04 跑了两轮（旧 SDK 一轮、交付 SDK 一轮），**都通过**：

```
before.bin  写入 510c2dceeccc7126  读回 510c2dceeccc7126
after.bin   写入 153060e6779190cd  读回 153060e6779190cd
  [PASS] **checkpoint 之前**写的 16MB 在 pause/resume 后完好   ← 这条抓 bug
  [PASS] checkpoint 之后写的 16MB 在 pause/resume 后完好
```

`O_DIRECT` 是这两条断言成立的前提，理由在
[第 25 篇 §4](25-functional-tests.md#4-pause_verifypy一个自洽的静默损坏)。

> **两份 pause 日志末尾的 traceback 要正确解读。** `ours-pause.log` / `t-pause.log`
> 都以一个 `missing header` 的 Python traceback 结束。那是脚本**旧版第 6 节**
> （pause/resume 之后再 restore）直接调 API 抛出来的，**不是前五节的断言失败**——
> 前五节两条 `[PASS]` 已经打完。追下去发现是 SDK `connect()` 路径没带
> `E2b-Sandbox-Id` / `E2b-Sandbox-Port` 两个头；补上之后错误变成
> `not found: checkpoint ckpt_… not found`（`ours-pause2.log`），说明**服务端是好的**，
> 而 pause/resume 之后 checkpoint 账本确实不再可用。
> **交付版脚本已经把第 6 节改写成边界断言**（预期被拒绝而不是预期成功），
> 所以现在这条是一条「行为边界」而不是一条失败。

`compat_matrix.py` 的两个 `REFUSED` 与上面是同一件事的两面：

| 项 | 结果 | 说明 |
|---|---|---|
| B4 `pause → connect` 之后 restore 旧 checkpoint | **REFUSED** | pause/resume 之后账本不再可用。**拒绝而不是拿失效层栈去恢复**，属于边界不是缺陷 |
| F1 `kill` 之后 connect | **REFUSED** | 沙箱已删除，原生本来就不允许 |
| 其余 13 项（含 B7「pause 之后新建的 checkpoint 能正常 restore」、E1「pause → connect → checkpoint → restore」） | **OK** | 原生生命周期能力没有被 checkpoint / restore 破坏 |

边界的完整讨论见[第 16 篇](16-lifecycle-and-portability.md)与
[第 25 篇 §5](25-functional-tests.md#5-compat_matrixpy与原生生命周期的组合矩阵)。

### 4.1 这一轮怎么测的

**条件**（开跑前实测，逐项记在数据目录里）：920B · 脏页后端 `kvm-wp`（`FC_TRACK_DIRTY_PAGES=true`，

orchestrator `orchestrator-dev-4af2872c6`、FC `18f3faa7f47c173a`。

每遍新建一个沙箱 → 预热 → 建**基线 checkpoint cpA**（全量）；此后每一次迭代：
造规定量的改动 → **增量 checkpoint** → **restore 回 cpA**（= 撤销这份改动）→

文件那半缓冲写 + `sync`，**不绕页缓存**。

**档位与样本数**（全部跑满，没有降档）：混合档（**内存 : 文件 = 3 : 1**，与
[第 28A 篇 §1](28a-historical-results.md#1-全量-vs-增量920b-0824-bench) 同口径）
0 / 4 / 8 / 16 / 32 / 64 MB 各 **n = 100**，128 / 192 / 256 MB 各 **n = 60**，

一条 20 层链。合计 **1040 次分档迭代 + 150 次场景迭代 + 100 次链 checkpoint + 5 次链 restore**，
**失败 0、校验不一致 0、心跳进程 pid 每次都没变**（内存是真回来了，不是虚机重启），
**1040 次迭代全部 `mem_mode=incremental`**，没有一次静默退回全量。

### 4.4 拟合与反推

对全部单次迭代做最小二乘（x = 名义总改动 MB，y = ms）：

| 拟合 | 式子 | R² | n |
|---|---|---|---|
| **checkpoint 墙钟 ~ 总改动（≤ 256）** | `y = 22.9 ms + 0.904 ms/MB · x` | 0.974 | 780 |
| **restore 墙钟 ~ 总改动（≤ 256）** | `y = 45.5 ms + 0.269 ms/MB · x` | 0.846 | 780 |
| checkpoint 冻结窗口 ~ 总改动（≤ 256） | `y = 21.0 + 0.902·x` | 0.974 | 780 |
| restore 冻结窗口 ~ 总改动（≤ 256） | `y = 20.4 + 0.251·x` | 0.878 | 780 |
| **纯内存 · checkpoint 冻结窗口 ~ 内存 MB** | `y = 19.6 + **0.505**·x` | 0.959 | 220 |
| **纯文件 · checkpoint 冻结窗口 ~ 文件 MB** | `y = 21.5 + **1.975**·x` | 0.979 | 190 |
| 内存差分 MB ~ 总改动（≤ 256） | `y = 21.6 MB + 1.034 MB/MB · x` | 0.9986 | 780 |
| 盘层 MB ~ 总改动（≤ 256） | `y = 0.57 + 0.2508·x` | 0.9999 | 780 |

- **固定项高度一致**：四条耗时拟合的截距都落在 19.6–22.9 ms，与 0 档实测对得上 ——
  **一次 checkpoint / 一次 restore 的冻结窗口，不管改了多少都得付约 20 ms**。
  restore 的**墙钟**截距 45.5 ms 比它的冻结窗口截距多出的 25 ms 落在冻结窗口**之外**（§4.5）。
- **盘层斜率 0.2508 = 1/4**，正是「混合档里文件占四分之一」；**内存差分斜率 1.034** ——
  4 KB 写跟踪的记账几乎是精确的，**没有 2 MB 块放大，也没有内容去重**。
- **R² 最低的是 restore 侧（0.85 / 0.88）**：量级小、常数项占比高，噪声相对更大，**不是非线性**。

**512 极限档落在直线上吗**：拟合预测 checkpoint 墙钟 485.5 ms（实测 465.8，**−4.1%**）、
restore 墙钟 183.1 ms（实测 144.5，**−21.1%**）。即 **checkpoint 侧的线性一直延伸到 512 MB，
restore 侧明显跑在直线下方** —— restore 对大改动量是**次线性**的，每 MB 的边际成本随改动量变大而下降
（要搬的是更连续的大段）。

**反推：多大的改动量刚好碰线**（用 ≤ 256 的墙钟拟合）——
**checkpoint 到 200 ms ↔ 约 196 MB**（实测 192 MB 档 192.1 ms）、
**restore 到 100 ms ↔ 约 203 MB**（实测 192 MB 档 87.3 ms、256 MB 档 120.1 ms）。
**两条指标线几乎同时在约 200 MB 改动量处被突破。**

### 4.6 「真实一步」场景

上面的档位是人为构造的。这一组反过来问：**用户真做一步事情，落到哪一档？** 各 30 次，单沙箱串行。

> **guest 工具链先探过**：模板里有 `python3`（3.10）、`curl`、`tar`，**没有 `pip`、没有 `git`**，但能出网。
> 所以场景 2 用 `curl` 取 sdist → `tar` 解包 → `compileall` 代替 `pip install`，
> 场景 3 用「建 400 个小文件」代替 `git clone`。**这是替代动作，不是原动作。**

| 场景 | 这一步自身 s (p50) | 内存差分 MB | 盘层 MB | checkpoint p50 | checkpoint p99 | restore p50 | restore p99 | 相当于混合档 |
|---|---|---|---|---|---|---|---|---|
| s1 跑一段 Python 计算（200 万随机数排序聚合） | 0.97 | **112.7** | 0.77 | 58.2 | 70.5 | 68.0 | 91.8 | 产物 ≈ 64–128 档，耗时 ≈ 32–64 档 |
| s2 装一个包（curl sdist + 解包 + compileall） | 1.13 | 38.5 | 1.40 | 31.7 | 106.0 | 52.9 | 91.5 | 产物 ≈ 16 档，耗时 ≈ 8–16 档 |
| s3 取一份代码（400 个小文件，无 git） | 0.39 | 31.4 | 4.13 | 36.8 | 50.0 | 47.0 | 64.4 | ≈ 8–16 档 |
| s4 改一批小文件（新建 200×8 KB、改写 50、删 20） | 0.20 | 35.3 | 2.32 | 32.2 | 43.4 | 49.6 | 64.8 | ≈ 8–16 档 |
| s5 什么都不做（sleep 2） | 2.01 | 22.1 | 0.00 | 22.5 | 52.5 | 54.0 | **154.0** | ≈ 0 档 |

**五个场景的 checkpoint 与 restore 按 p50 全部满足 200 / 100 ms，
150 次 checkpoint 里 0 次超过 200 ms。** s5 的 restore p99（空闲后的长尾，已知问题）见 §4.8、
[§7.2](#72-空闲一段时间之后的-restore-长尾) 与 [§8 第 18 条](#8-尚未覆盖)。

两条要讲给使用方听的：

- **决定成本的是这一步碰了多少内存，不是它写了多少文件。** 最贵的是 s1：一次 Python 计算把
  112 MB 内存写脏，产物量比「用户改了几个文件」大一个量级；而它的耗时只有 32–64 档的水平 ——
  因为纯内存的改动每 MB 比文件便宜 3.9 倍（§4.3）。
- **空闲也有基底**：s5 只 sleep 2 秒，内存差分照样有 22.1 MB（0 档那 0.3 s 窗口是 20.22 MB）——
  空闲脏页是**有上限的低频背景**（定时器 / 调度 / envd），不是线性涨；但**间隔越久基底越大**，
  要估生产环境的产物大小得按实际间隔重新量基底。

### 4.7 链深 20 层

同一沙箱**不 restore**，连做 20 次「约 4 MB 混合改动 → checkpoint」形成 20 层链，
再 restore 回第 1 层；做 5 轮。

| 链层 | n | checkpoint 墙钟 p50 | checkpoint frozen p50 | 内存差分 MB | 盘层 MB |
|---|---|---|---|---|---|
| 第 1 层 | 5 | 29.5 | 27.9 | 28.04 | 2.05 |
| 第 5 层 | 5 | 22.1 | 20.4 | 18.70 | 1.42 |
| 第 10 层 | 5 | 23.9 | 22.2 | 19.52 | 1.38 |
| 第 15 层 | 5 | 23.4 | 21.4 | 21.31 | 1.42 |
| 第 20 层 | 5 | 24.5 | 22.5 | 20.31 | 1.45 |

全部 100 次链 checkpoint：墙钟 **p50 23.3 ms、p99 38.0 ms、max 59.2 ms**。**链变深不会让
checkpoint 变慢** —— 第 1 层略高（29.5 ms）是因为它紧跟基线全量、要写的量也大一点，
第 5–20 层完全平（22–25 ms，无单调趋势）。

**链深 20 没有给 restore 带来可观测的额外成本**，与「按最终态物化、不逐层回放」的实现一致
（[第 8 篇 §7.1](08-memory-diff-tree.md#71-恢复为什么不随链深变慢)）。

### 4.8 条件与不覆盖的场景

条件在 §4.1；另补一条实测确认的：**页缓存全热** —— 1040 次 restore 的
`materialize_disk_read_mb` 与 `fc_rollback_disk_read_mb` **全部为 0**。

**这些数字不代表**：

- **并发场景。** 本轮是 N = 1 的下界。已有的并发数据：16 路并发下 48 + 16 MB 那一档，
  增量 checkpoint 的**冻结窗口** p50 约为单路的 **1.46 倍**（76.9 → 112.6 ms）——
  注意它量的是**冻结窗口**，不是客户端墙钟，与本篇主表的墙钟列不是同一个量。
- **冷缓存。** restore 的盘读全为 0；沙箱闲置一段时间后页缓存被挤掉，`materialize` 与
  `fc_rollback` 要从 ext4 读回差分，会显著变慢。**本轮完全没有覆盖这一面。**
- **有 HDBSS 的 950。** 硬件标脏的 checkpoint 侧开销与 `kvm-wp` 不同，**不能外推**（§1.2）。
- **更大的 guest、更深的链。** 模板固定 2 GiB，链深只测到 20。
- **长间隔。** 所有档的产物都含「两次 checkpoint 间隔 0.3 s」的基底（§4.6）。

**本轮如实记下的异常**：自动离群扫描（单次冻结窗口 > 该档中位数 2 倍）**零命中**；
唯一的长尾是 **s5「什么都不做」场景的 restore** —— 三次运行的 30 次里分别有 **3 / 4 / 7 次**
客户端墙钟 > 100 ms（最大 **140.1 / 122.7 / 154.0 ms**），慢段是冻结窗口**之外**的
`assemble_view_pre`（正常约 15 ms，慢时 **44.7–84.6 ms**）加上冻结窗口本身抬升，
而**同一轮里改动量为 0 的连续档 100 次一次都没超**。2026-09-21 做过定向调查：由空闲触发、随空闲时长加重，
磁盘与锁已排除，一次针对性改动在空闲档未见改善，**原因未定位**；只在 920B 上观察过，950 上待测。
列为已知问题（[§7.2](#72-空闲一段时间之后的-restore-长尾)），调查结果记在[§8 第 18 条](#8-尚未覆盖)。
另有一次 `s2` 的 `step_s = 136 s`，是 guest 里 `curl` 出网卡住，**不是 checkpoint / restore**。

### 5.3 那个 100 ms 为什么不能拿来判定

950 唯一有数的一轮里，`checkpoint.restore` 的 p50 是 **0.100 s**，
恰好落在客户指标那条线上。这个巧合很容易被当成「950 上 restore 刚好达标」，
但它不构成判定，四条理由都是硬的：

1. **样本量与构造**：10 次，且这 10 次混了退一代（2 次）、跨 2 代前滚（1 次）、
   A/C 交替（6 次）、杀进程后回滚（1 次）四种跳法。判定要求**浅集与深集分列**，
   这一批混在一起，任何一个 p50 都不属于其中任何一列。
2. **不在档位上**：每代脏内存 128 MB + 根文件系统 32 MB，名义总量约 160 MB，
   既不是 128 MB 档也不是 256 MB 档；而且现场是**重建**的，分配成本混在里面。
3. **链深不可比**：那条链只有 3 代，判定表的链深是 33。
4. **最大值 153 ms**：10 个样本里的 max 已经超过 100 ms，没有 p99 可言。

结论一句话：**它是一个「量级正确」的旁证，不是一个判定值。**
950 的判定要等 §5.2 那张表填满。

### 5.4 全量为什么单列

树根必须自包含，否则一条链没有可解析的底
（[第 8 篇 §6.3](08-memory-diff-tree.md#63-全量根为什么是默认)）。它的代价是写整份 guest RAM，
920B 上 2 GB 模板实测 p50 1.511 s，比任何增量档都高一个数量级。

但它**每个沙箱只发生一次**：一个沙箱做 100 次 checkpoint，这 1.5 s 摊下来是 15 ms/次，
而且不在「回退到上一步」这个动作的路径上。把它算进判定，得到的既不反映客户体验、
也不反映实现质量。

**它单列的另一个作用是当分母**：没有 1.511 s 这一行，「增量快 51 倍」这句话没法说。

## 6. 附表：与 gsd/CRIU 及原生 snapshot 的实测并列

**只并列，不作差。** 三套的快照范围不同 —— 进程级只装选中进程的地址空间，
虚机级装整个 guest RAM —— 所以有些列语义就不一致
（[第 27 篇 §4.5](27-cross-implementation.md#45-哪些列可以并排)）。
措辞统一为「**快照范围不同，所以快的地方不同**」，不写优劣
（[第 27 篇 §6](27-cross-implementation.md#6-定性结论)）。

文件那 64 MB **完全不在内存产物里**（由 overlayfs 单独管）；本方案同档 276.5 MB ≈
192（内存）+ 64（那次文件写留在 guest 页缓存里的页）+ 本底。两个数字都能从各自的覆盖范围
推出来 —— 定性结论与它的两条语义推论在
[第 27 篇 §6](27-cross-implementation.md#6-定性结论)，这里只放数字。

读这两张表必须带上的四条限定：

- **本方案 cp1 那一行反常**（68.5 ms 的 e2e，产物只有 16.9 MB 却比 cp2 的 12 MB 档还慢），
  原因见[第 28A 篇 §13](28a-historical-results.md#13-全量之后紧接的第一次增量偏慢920b-0908)。**进程级 cp1 同样反常**（143.9 ms，比 cp2 的 30.8 ms 慢 4.7 倍），
  两边现象类似，**进程级那一侧的机理未查**。
- **进程级 cp1 的产物 193 MB 与 cp2 的 14 MB 之间那个跳变没有解释。**
  按覆盖范围推，cp1（名义 0/0）本该最小。原始材料只记录了数值，没有给出原因，
  本篇**如实照抄，不做解读**；单次数据，不宜过度推断。
- **进程级那一侧的文件负载走 SDK 上传**（HTTP 推几十兆），本方案是 guest 内 `dd` 生成。
  这一段是否计进它的 checkpoint 计时，**源材料里两句话方向相反**：
  一句写「E2E 里 gsd 那边含上传时间」，紧接着一句写「从 `overlay_sink_ms` 只有 0.3~0.8 ms 看，
  这部分没有计进 checkpoint 计时」。**未裁决**，两个说法都记在这里；
  它只影响进程级那一列的 checkpoint e2e，不影响 restore 列与产物列。
- **两轮跨实现对照都跑在 `kvm-wp` 上。** 这个条件对三套的影响**不对称**：
  软件写保护的 VM exit 全部落在虚机级那两套身上，进程级走 soft-dirty，基本不受影响
  （[第 27 篇 §5.3](27-cross-implementation.md#53-三套的脏页判据)）。
  **换到 HDBSS 上这张表很可能变样，届时要整轮重跑，不是补一列。**

### 6.2 与 e2b 原生 snapshot · 950-native

数据在 §3.3 的表 3-I。三条并列时的口径：

| 列 | 能不能逐行并排 | 理由 |
|---|---|---|
| checkpoint 端到端 | 可并排 | 档位表逐格相同 |
| 内存产物量 | **可并排，不可相减**（950-native 轮）；修复后**可相减**（表 3-J） | 950-native 轮原生的判据把读也算脏，量的是工作集；2026-09-11 起原生改读与本方案同一份写跟踪位图 |
| restore / resume 端到端 | **只可并列** | 恢复语义不同：本方案是原地回滚（沙箱 ID 与 Firecracker 进程都不变），原生 snapshot 是**另起一个新沙箱** |
| `touch`（恢复后首次整读） | **仅原生非零，且必须加进它那一边** | 原生是懒加载，950 上这笔约 165 ms，比 resume 本身（约 90 ms）还大 |
| `upload` | 仅原生有 | 本方案产物就地可用 |
| 脏页后端 / `mem_mode` | 仅本方案有 | 另两套没有对应判据 |

还有一条介质差异必须说：本方案的产物在 `/orchestrator/build/checkpoints`，**真落盘**；
原生快照的最终产物默认落 `/tmp/templates`，而这两台机器的 `/tmp` 恰好是 **tmpfs**——
也就是在内存里。这不是 e2b 的设计，是 `LOCAL_TEMPLATE_STORAGE_BASE_PATH` 没设时的默认值
碰上这两台机器的挂载布局。做对比时两套的产物写在不同介质上，原生那一列的 `upload`
换成磁盘存储会显著变大。

### 7.1 对使用场景的含义与缓解方向

## 9. 小结

1. **950 与 920B 的数字只能并列，不能相减。** 脏页后端、产物介质、产物文件系统、
   模板规格四项同时不同，任何差值都无法归因到其中一项 —— 尤其不能归因给 HDBSS。
2. **功能正确性：950 在硬件标脏路径上 59/59 全过；920B 全套（59/59、31/31、
   `ALL CORRECT`、200 次 0 失败、pause ×2、兼容 13 OK / 2 REFUSED / 0 BROKEN）全过。**
   950 上的树语义、pause、兼容矩阵、稳定性四项**尚未跑过**。
3. **57 与 59 都写着「全部通过」。** 判据本身会静默失效，所以结果表必须逐轮标注
   SDK 与 `mem_mode` 判据是否有效 —— 这是本篇 §2 那张表存在的理由。
4. **判定结论（920B · ext4 方案 · 软件写保护 · loop ext4 · 2 vCPU / 2 GiB 模板 ·
   2026-09-21 · `deltabox-dev@4af2872c6`）：按 p50，checkpoint 与 restore 两条线都守到
   192 MB 改动量这一档，256 MB 档双双越线；按 p99，checkpoint 守到 128 MB、restore 守到 64 MB。**
   拟合反推的碰线点是 **196 MB / 203 MB** —— **两条指标线几乎同时在约 200 MB 改动量处被突破**。
5. **成本是一条直线**：checkpoint 墙钟 ≈ 22.9 ms + 0.904 ms/MB，restore 墙钟 ≈ 45.5 ms + 0.269 ms/MB
   （R² 0.974 / 0.846）。固定项约 20 ms 是冻结窗口，restore 墙钟多出的 25 ms 落在冻结窗口**之外**
   （`assemble_view_pre` + `conntrack_bg` + `wait_envd`），**与改动量无关**。
   **写文件每 MB 比写内存贵 3.9 倍**，因为写 1 MB 文件要存两份：约 1.06 MB 的页缓存脏页进内存差分，
   1 MB 进盘层。
6. **五个「真实一步」场景（跑计算 / 装包 / 取代码 / 改小文件 / 什么都不做）按 p50 全部达标**，
   150 次 checkpoint 里 0 次超过 200 ms。**决定成本的是这一步碰了多少内存，不是它写了多少文件。**
   空闲之后的 restore 有长尾（§7.2，已知问题，原因未定位，950 上待测）。
7. **全量单列，不参与判定**（920B 2 GiB 模板冻结窗口约 1071 ms）—— 它是每个沙箱一次性的成本。
8. **链深 20 层不让 checkpoint 或 restore 变慢**（§4.7），与「按最终态物化、不逐层回放」的实现一致。
9. **950 唯一那个 restore 0.100 s 不是判定值**：样本 10 次、混了四种跳法、
   现场是重建的、链深只有 3、max 已经 153 ms。
10. **跨实现的两张表只并列不作差**，而且都跑在软件写保护上；
   换到硬件标脏要**整轮重跑**，不是补一列。
11. **2026-08 / 09 旧栈的数据整体保留在[第 28A 篇](28a-historical-results.md)**，
   和本篇的数字**不是同一套代码、不可相减**；XFS 方案、33 步深集、60 秒连打、时机成本
   这四项新一轮没有测，**仍以那一篇为准**。
12. **§8 那张缺口表是全书唯一维护的一份**，十八条里有一条不需要机器就能修：把条件标签记全。
