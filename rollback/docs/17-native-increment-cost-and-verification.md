# 17 · 代价与验证

## 本章目标

读完本章，你应该能够：

1. 读懂原生精确增量前后的体积数据：修复前为什么恒在 400 MiB 上下，修复后为什么随写入量线性，"只换判据"的预测落在哪；
2. 说清"4 KiB 存、2 MiB 拼"在恢复热路径上付了什么，第一版为什么贵了 100~200 ms，零拷贝快路径和缓冲池各收回了多少；
3. 说出哪些看起来该做的优化量过之后决定不做，以及理由；
4. 解释为什么 950 上默认就是精确增量、920B 上默认退回修复前口径，以及与 checkpoint 叠加使用时额外付了什么；
5. 按"体积、拼接、退路、叠加、共存"五类列出验证证据，说出每一类证明的是哪一层，以及还缺什么。

---

上一章（[16](16-native-increment-fix.md)）讲了改法：① 判据换成 4 KiB 写跟踪位图，② header 块大小降到 4 KiB，③ 缺页时三级取源、跨代才拼；
沙箱做过 checkpoint / restore 时，用"自启动以来脏页集"把 Firecracker 清掉的记录并回；四道门都退回驻留判据。

本章看这些改动的代价与证据。全书判定性的数字只放在 [21](21-benchmarks-and-compliance.md)、[22](22-long-run-and-concurrency.md) 和本章；
本章只放原生精确增量自己的数据，本方案 checkpoint / restore 的数据在那两章。下一章（[18](18-native-and-checkpoint-together.md)）把两种快照放在一起，讲分工与配合。

## 1. 数据的来源与条件

原生精确增量的数据分三批，条件不同，读的时候要带着条件标签：

| 批次 | 平台与脏页后端 | 日期 | 代码 | 用途 |
|---|---|---|---|---|
| 修复前对照 | 950（HDBSS）；920B（KVM 写保护） | 2026-09-09～10 | ARM 适配基线（驻留判据） | 现象与"只换判据"的预测 |
| 修复后体积与恢复开销 | 920B（KVM 写保护，显式 `FC_TRACK_DIRTY_PAGES=true`） | 2026-09-11、09-14 | 4 KiB 写跟踪差分的首个实现，与现在 `deltabox-dev` 上的同一改动逻辑相同 | 体积、`touch1`、拼接正确性 |
| 与 checkpoint 叠加 | 920B（KVM 写保护） | 2026-09-18（修复验证）、2026-09-29（最终回归） | 09-29 为 `deltabox-dev@8ea5322`，与 `93ccb02` 在原生路径上代码相同 | 累积位图的正确性与开销 |

几点说明：

- 修复后的体积和恢复开销测于该改动迁入当前代码库之前。迁入之后与这条路径有关的变化只有两处：拼接缓冲池取缓冲时少了一次无用分配（§3.3），
  以及累积位图（只在做过 checkpoint 的沙箱上起作用，§6）。两者都不改变体积，前者只会让 `touch1` 更好。
- 950 上**只有修复前**的数据。修复后的原生路径在 950 上尚未复跑（§9）。两台机器代码路径相同，差别只在位图由谁供数（§5）。
- 920B 上修复后的数据全部是显式 `FC_TRACK_DIRTY_PAGES=true` 下测的；不设这个变量时 920B 默认不开跟踪，原生 pause 走驻留判据（§5）。

用到的脚本都在 `rollback/scripts/` 下：

| 脚本 | 测什么 |
|---|---|
| `probes/pb2.py` | 同一沙箱上三列并排：`GET /memory/dirty`、写跟踪位图、实际导出的 memfile |
| `probes/pb4.py` | 把 4 KiB 写跟踪位图按 2 MiB 归并，预测"只换判据"的导出量 |
| `probes/pb3.py` | 原生 pause 先做的那次快照是否擦掉写跟踪位图 |
| `probes/pb5.py` | 三代快照改同一个 2 MiB 块里的不同 4 KiB 页，外加一页清零，逐代另起沙箱验 md5 |
| `acceptance/native_snapshot_bench.py` | 与本方案同一张档位表跑原生路径：pause 模式（同一沙箱反复 pause → resume）与 snapshot 模式（每代持久快照、另起新沙箱恢复） |
| crtest T39 | 做过 checkpoint / restore 的沙箱原生 pause → resume，逐项核对现场与页级自校验 |
| crtest T41 | 从不 checkpoint 的沙箱原生 pause → resume，含多轮 |

## 2. 体积：修复前后

### 2.1 `pb2.py` 三列并排

模板 `base`，guest 内存 2 GiB，2 MiB 大页。每一步都真做一次快照，步与步之间沙箱经历 pause + resume。左列是修复前原生 pause 用的判据（2 MiB 粒度），
中列是 Firecracker 写跟踪位图（4 KiB 粒度），右列是实际导出的 memfile。单位 MiB。

| 步骤 | 950 HDBSS，修复前（09-10）<br>`/memory/dirty` / 位图 / 导出 | 920B KVM 写保护，修复前（09-10）<br>`/memory/dirty` / 位图 / 导出 | 920B KVM 写保护，修复后（09-11）<br>位图 / 导出 |
|---|---|---|---|
| A 刚建好 | 118.0 / 4.6 / 118.0 | 154 / 4.1 / 154 | 5.5 / 5.5 |
| B 写 192 MiB | 324.0 / 205.2 / 324.0 | 370 / 219.8 / 370 | 209.5 / 209.5 |
| C 空转 | 122.0 / 3.9 / 122.0 | 162 / 4.1 / 162 | 4.5 / 4.5 |
| D 只读 192 MiB | 324.0 / 15.0 / 324.0 | 358 / 14.6 / 358 | **12.7 / 12.7** |
| E 空转 | 134.0 / 3.8 / 134.0 | 152 / 4.1 / 152 | 4.1 / 4.1 |
| F 只改 12 MiB | 148.0 / 19.7 / 148.0 | 176 / 20.5 / 176 | **20.3 / 20.3** |

读法：

- 修复前左列与右列逐行相等：原生 pause 就是按它导出的。D 行"只读"比 C 行多了约 200 MiB，说明读被算成了脏（[15](15-native-increment-diagnosis.md#2-现象改-12-mib导出-148-mib)）。
- 中列在两台机器、两种后端下形状一致，都是"写入量加几 MiB 本底"，说明写跟踪位图本身是精确的，与后端无关。
- 修复后右列等于中列，逐行相等：只读 192 MiB 从 358 降到 12.7 MiB，只改 12 MiB 从 176 降到 20.3 MiB。

|---|---|---|---|---|
| 空转 | 162 MiB | 134 MiB | 17% | 4.1 MiB |
| 只读 192 MiB | 366 MiB | 148 MiB | 60% | 14.6 MiB |
| 只改 12 MiB | 184 MiB | 156 MiB | 15% | 20.5 MiB |
| 只改 48 MiB | — | 192 MiB | 13% | — |
| 写 192 MiB | 382 MiB | 358 MiB | 6% | 219.8 MiB |

每代约 130 MiB 是归并地板。这张表是 [15](15-native-increment-diagnosis.md#5-只换判据够不够2-mib-归并的地板) 结论"只换判据修不到底"的依据，
也是选择改动 ② ③ 的依据。（"修复前导出"一列与 §2.1 的 920B 列不是同一次运行，数值有几 MiB 到几十 MiB 的差别，这是工作集本身的波动。）

### 2.3 `native_snapshot_bench.py`：六档

920B，同一份脚本、同一张档位表（名义脏内存 / 名义脏文件，单位 MB）。"修复前"列是同机同 Firecracker 的前一轮（09-11），"修复后"列是 09-14 那一轮。
cp0 含预热写入的 192 + 64 MB，是本底。pause 模式下每一档都是一次 pause → resume，也就是一代新进程。

| 档 | 名义内存 / 文件 | memfile 修复前 | memfile 修复后 | pause ms（修复后） | resume ms（修复后） |
|---|---|---|---|---|---|
| cp0 | 0 / 0 | 442 | 281.7 | 519 | 271 |
| cp1 | 12 / 4 | 432 | **38.4** | 260 | 226 |
| cp2 | 24 / 8 | 434 | **54.2** | 289 | 211 |
| cp3 | 48 / 16 | 440 | **87.5** | 309 | 203 |
| cp4 | 96 / 32 | 442 | **153.1** | 496 | 289 |
| cp5 | 192 / 64 | 450 | **287.6** | 684 | 301 |

- 修复前 memfile 恒在 440 MB 上下：每档恢复后脚本都把 192 MB 负载读一遍验证内容，这些页每代都被换入、被判脏（[15](15-native-increment-diagnosis.md#42-两个放大叠在一起每代新进程换入即脏)）。
  950（HDBSS）上同一脚本修复前的一轮（2026-09-09～10，负载同样按"预热 + 原地覆写"构造、档位相同）形状一样：cp0–cp5 的 memfile 为 406 / 394 / 402 / 398 / 404 / 410 MB，恒在 400 MB 上下；同一轮 resume 端到端约 90 ms，恢复后第一次把负载整读一遍另需约 165 ms（懒加载推迟付的账）。950 上修复后的数据待补（§9.2）。
- 修复后 memfile = 该档写入量 + 二三十 MB 本底，随写入量线性。
- snapshot 模式（每代持久快照、另起新沙箱恢复）的 memfile 与 pause 模式一致（38.6 / 56.2 / 87.5 / 152.9 / 286.1 MB），本地存储里的实占与导出缓存相等，说明上传路径没有改变布局。
- 上传时间（pause 返回到存储目录文件落齐）从修复前的约 200 ms 降到 50~150 ms（09-14 那一轮为 50~100 ms），这是导出量变小的直接收益。
- pause、resume 两列修复前后都在同一噪声带（pause 数百 ms，resume 200~300 ms，snapshot 模式恢复端到端 0.2~1.3 s），看不出系统性差别。
  这两列的抖动主要来自另起沙箱时的网络槽位配置，与快照无关。

## 3. 恢复开销：一个设计取舍的来龙去脉

体积是"拍"这一侧的收益；代价落在"填"这一侧，也就是恢复后 uffd 懒加载的热路径上。本节用恢复后第一次把负载整个读一遍的耗时 `touch1` 来衡量它。
`touch1` 比 resume 一列更接近用户真正等到的时间：resume 很快返回，搬内存的活推迟到了每一次缺页上。

### 3.1 第一版为什么贵

第一版的 ③ 很直接：每次 2 MiB 缺页都 `make` 一块 2 MiB 缓冲，经 `File.ReadAt` 沿映射链读满，再交给 `UFFDIO_COPY`。
一个 400 MB 的工作集约 200 次缺页，就是 400 MB 的分配、清零、拷贝和随后的 GC。920B 上 pause 模式六档的 `touch1`：

| | cp0 | cp1 | cp2 | cp3 | cp4 | cp5 | 均值 |
|---|---|---|---|---|---|---|---|
| 修复前 | 210 | 258 | 217 | 248 | 303 | 223 | 243 |
| 第一版 | 327 | 325 | 328 | 357 | 502 | 363 | 367 |
| 只加零拷贝快路径 | 402 | 374 | 278 | 285 | 266 | 290 | 316 |
| 最终（两轮） | 202 / 268 | 235 / 267 | 205 / 233 | 209 / 235 | 274 / 228 | 333 / 205 | 241 |

（ms，920B，2026-09-11，同机同 Firecracker。）第一版每档多了 100~200 ms。

### 3.2 两步收回

1. **零拷贝快路径**（[16](16-native-increment-fix.md#33-③-填一次-2-mib-缺页三级取源) 的第二级）：先查一次映射，如果一条映射覆盖了整个 2 MiB，
   直接把那一代 mmap 缓存里的切片交给 `UFFDIO_COPY`，与修复前完全相同。guest 物理页在 2 MiB 块里虽然混着，但整块同代的仍占多数。均值从 367 回到 316。
2. **缓冲池**（第三级）：跨代的块才拼，缓冲从 `sync.Pool` 取、拷完即还；`ReadAt` 自己清零空洞，调用方不必预清零。均值回到 241，与修复前的 243 持平。

snapshot 模式（另起新沙箱恢复）最终两轮 `touch1` 为 237~287 / 203~245 ms，修复前 206~427 ms，同样回到噪声内。
09-14 那一轮（§2.3 的修复后数据）pause 模式 `touch1` 为 202~264 ms，snapshot 模式 241~266 ms。

**这一步的教训是一条设计原则**：懒加载路径上**每一次缺页都是热路径**，多一次 2 MiB 分配就是多一次可测的延迟。所以现在的 ③ 按"能不拷就不拷、要拷就不分配"来设计：
块等于页走原路，整块同代零拷贝，只有跨代的块才拼，而且拼接用池里的缓冲。

### 3.3 池本身的一次无用分配

缓冲池的取法后来又收紧了一次。最初取缓冲时无条件调 `sync.Map.LoadOrStore(size, &sync.Pool{New: ...})`；Go 先求值参数，所以**每次缺页**都构造一个 `sync.Pool`
和一个闭包、逃逸到堆上，然后因为池已存在而丢掉。现在先 `Load`，只有第一次才 `LoadOrStore`（`block/page.go:28-45` 的注释）。
920B 上 `BenchmarkGetPageBuffer`（池已热）：每次 207.2 ns、4 次分配 → 82.7 ns、1 次分配（2026-09-17）。
在一次 2 MiB 拷贝面前这只是零头，但它说明同一条原则：热路径上连"看不见"的分配也要数。

## 4. 量过之后决定不做的

| 候选优化 | 量到了什么 | 决定 | 理由 |
|---|---|---|---|
| 限制 header 膨胀：同一 2 MiB 内脏页占比超过阈值就整块导出 | 4 KiB 碎片化后映射条目增多，六代 header 从 141 KiB 长到 232 KiB，每代约 +18 KiB（920B，09-11） | 不做 | `NormalizeMappings` 已合并相邻区间；这个规模相对 memfile 可以忽略，折中会重新引入"陪绑导出" |
| 零页走 `Empty` 映射，不导出 | 导出的页里 0.8%~8.4% 是全零页 | 不做 | 要在导出前多扫一遍全部脏页，省下的量不值这次扫描 |
| 路线 A（关大页）作为交付形态 | 未实测 | 不做 | 缺页次数 ×512、所有沙箱失去大页（[16](16-native-increment-fix.md#2-两条路线)），不需要实测就能排除 |

还有一个观察：修复后 pause 模式全档位期间对 orchestrator 进程树做 perf 采样（920B，09-11），CPU 大头是每次另起沙箱时逐条 exec 的 `iptables`（约 55%），
orchestrator 本体约 37%（其中 Go GC 约四分之一），Firecracker 与 vCPU 约 6%；内存导出与缓存相关的函数合计不到 1%。
所以原生路径上剩下的端到端抖动主要来自网络配置，与本改动无关，不在本改动的范围内处理。

## 5. 写保护的运行期代价：平台差异

新判据不选后端，只读位图；位图由谁供数，是 Firecracker 启动时 `setup_dirty_tracking` 决定的（[05](05-dirty-page-tracking-and-hdbss.md#4-hdbss-怎么被启用)）：

| | 950（HDBSS） | 920B（无 HDBSS） |
|---|---|---|
| 位图怎么来 | CPU 硬件记脏，guest 写页不陷出 | KVM 写保护，每个干净页第一次被写陷出一次 |
| 谁付这笔账 | 几乎没有 | **所有开了跟踪的沙箱**，不管做不做快照 |
| 默认是否开跟踪 | 开（探到 KVM 能力 502） | 关 |
| 原生快照口径 | 精确增量 | 默认驻留判据（修复前口径）；`FC_TRACK_DIRTY_PAGES=true` 才精确 |

这条策略与本方案 checkpoint 的完全一致，用的是同一个开关（[05](05-dirty-page-tracking-and-hdbss.md#47-默认值为什么跟着硬件走)）：
**有 HDBSS 时精确增量几乎零副作用；没有 HDBSS 的机器上，"精确增量"与"不让所有沙箱付写保护代价"二选一，默认选后者。**
920B 上 `FC_TRACK_DIRTY_PAGES=false` 的实测（09-11）：pause 日志命中 `dirty tracking is off`，memfile 回到 172 / 178 MB 的工作集口径，内存与文件校验全过。

两台机器代码路径逐行相同，写跟踪位图的内容也一致：§2.1 中列"只读 192 MiB"一步，950 上 15.0 MiB、920B 上 14.6 MiB，差的是模板本底。
差别只在写保护这笔运行期代价，以及 950 上修复后的数据还没有测（§9）。

## 6. 与 checkpoint 叠加的代价

[16](16-native-increment-fix.md#4-与-checkpoint-叠加累积位图) 的累积位图在 checkpoint / restore 路径上加了记账，在原生 pause 路径上加了一次并集。代价如下：

| 位置 | 多做了什么 | 实测（920B，2026-09-18） |
|---|---|---|
| 全量 checkpoint 的冻结窗口内 | 拍之前多导出一次活跃脏图（每 GiB guest 内存 32 KiB 的位图文件） | 计时键 `save_live_bitmap`：21 次全量 checkpoint 全都出现，2.01~4.95 ms，p50 约 2.2 ms；另一次单独测量 0.918 ms。增量 checkpoint 42 次都没有这一步 |
| 增量 checkpoint 之后、restore 期间 | 读一个位图文件，与集合做一次按位并 | 内存里的位运算，未单独计时；restore 本来就要导出活跃脏图（这一步不是新增的） |
| 原生 pause 时 | 集合并进写跟踪位图 | 同上 |

`save_live_bitmap` 这个计时键在 restore 路径上一直都有；全量 checkpoint 上是新增的。计时键的全表见 [28](28-observability-reference.md)。

还有一个"代价"不是开销，而是正确结果本来的样子：做过 checkpoint 的沙箱，原生 pause 导出的是**这一代启动以来**写过的全部页，而不只是最近一段。
T39 的服务端日志（§8.4）里，写跟踪位图本身只有 2.6k~5.1k 页，导出却有 31k~34k 页，差出来的约 28k 页（约 110 MiB）正是 checkpoint 清掉、由集合补回的部分。
这个量与"从不 checkpoint、同样负载"的沙箱导出量同一量级，不是额外负担。

## 7. 兼容

| 场景 | 行为 |
|---|---|
| 新 orchestrator 起旧的 2 MiB 快照 | 块等于页，走第一级（`Slice`），与修复前逐字节相同 |
| 新 orchestrator 起新的 4 KiB 快照 | 走第二、三级 |
| **旧** orchestrator 起新的 4 KiB 快照 | `NewUserfaultfdFromFd` 的"相等"检查报 `block size mismatch`，**拒绝启动**，不会静默读错数据 |
| 没有 `save-dirty-bitmap` 端点的 Firecracker | 退回驻留判据，记 warn |
| 从不 checkpoint 的沙箱 | 自启动以来脏页集为空，导出与没有累积机制时逐位相同 |

兼容方向是单向的：新 orchestrator 读得了旧快照，旧 orchestrator 读新快照会拒起。所以一个集群应先把 orchestrator 全部升级，再让沙箱产生 4 KiB 快照；
旧快照不受影响。"拒起"而不是"警告后继续"是有意的：块大小不符时强行按旧逻辑填页，填进去的是错位的内容，比起不来更糟。

## 8. 验证：五类证据

证据按 [15](15-native-increment-diagnosis.md#3-原生内存增量的三层) 的三层，加上"退路""与 checkpoint 叠加""与本方案共存"组织。每一类证明的东西不同，缺一类就有一层没被证明。

### 8.1 体积等于位图真值（证明 ① 生效）

## 9. 影响面与缺口

### 9.1 影响面

两个改动的影响面不同，分开说：

- **4 KiB 写跟踪差分**只在原生路径的内存侧。打快照：`Sandbox.Pause` → `Uffd.DiffMetadata`（① 换源）→ `ToDiffHeader`（② 块大小）→ `ExportMemory`（步长 4 KiB）；
  原生 `Checkpoint` RPC 复用同一段。恢复：`ResumeSandbox` 建新进程 → uffd 缺页与预取 → `block.ReadPage`（③ 三级取源）。
  不在链上的：模板构建（`NoopMemory.DiffMetadata` 未动，模板 header 仍是 2 MiB）、rootfs 差分与 NBD、SDK、上传与模板存储，以及本方案 checkpoint / restore 的全部代码。
- **累积位图**则进了本方案的 checkpoint / restore 路径：全量 checkpoint 的冻结窗口里多一次位图导出，checkpoint 与 restore 各多一两次位图并入（§6）。
  这些步骤失败不会让 checkpoint 或 restore 失败，只让之后的原生 pause 退回驻留判据。

两边共用的只有 `save-dirty-bitmap` 这个端点，它是非破坏性的读：把 KVM 日志折进用户态位图再导出，**不清零**（[08](08-firecracker-api-contract.md#4-扩展三put-snapshotsave-dirty-bitmap)）。
所以原生 pause 取位图不会影响之后的 checkpoint 增量，反过来 checkpoint 对位图的清零则由累积位图补回。

## 本章要点

1. **体积**：修复前原生导出恒在 400 MiB 上下（工作集口径）；只换判据的预测有约 130 MiB 的地板；修复后导出等于写跟踪位图，只读 192 MiB 从 358 降到 12.7 MiB，六档随写入量线性。
2. **代价在懒加载热路径上**：第一版每次缺页分配 2 MiB 缓冲，`touch1` 多 100~200 ms；零拷贝快路径加缓冲池后回到修复前的噪声内。懒加载路径上每一次缺页都是热路径。
3. **量过不做**：header 膨胀每代约 18 KiB、零页占 1%~8%，都不值得换额外的复杂度或扫描。
4. **平台策略与本方案一致**：950 上默认开跟踪、精确增量几乎零副作用；920B 默认不开，原生快照自动退回驻留判据，显式 `FC_TRACK_DIRTY_PAGES=true` 才精确。
5. **与 checkpoint 叠加**：全量 checkpoint 多一次约 2 ms 的位图导出；T39 三场景全过，导出页数由位图的几千页补到三万多页，正是 checkpoint 清掉的部分；没有累积位图时同一用例必败。
6. **兼容是单向的**：新 orchestrator 读得了旧快照，旧 orchestrator 读新快照会拒起而不是读错。
7. **缺口**：950 上修复后的原生路径数据、开跟踪对原生生命周期的影响都待补。
