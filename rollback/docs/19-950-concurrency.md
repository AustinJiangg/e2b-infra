# 19 · 950 并发与持续运行证据

本章的[950 测试结果摘要](../evidence/950/README.md)记录轮次与验证边界。原始日志仅保留在本地 `rollback/scripts/950/results/`，由 Git 忽略，不提交或分发；尚未回传的 JSON/JSONL 或部署身份仍属验证缺口。

本章集中记录 950 的短时跨沙箱并发、同沙箱争用、混合短稳态和恢复后请求。小时级结果需要对应证据；920B 的长跑数据保留在附录 B。

## 1. 950 短时并发：2026-10-13 A/B

| 条件 | 日志记录 |

| 宿主内核 / Python | `6.6.0-159.4.12.166.oe2403sp4.aarch64`；Python 3.14.6 |
| 模板 / 脏页后端 | `base`；FC 自报 **`hdbss`**、版本字符串 `1.12.1` |
| 产物目录 / 文件系统 | `/orchestrator/build/checkpoints`；**ext4**，块设备 `dm-0` |

这是一轮短时并发，使用**客户端墙钟 p50 / max**；服务端 `frozen` 只解释业务停顿。日志墙钟原以秒输出到小数点后三位，下面乘 1000 写成 ms，不增加精度。每个 N、每个步骤仅有 N 个样本，N=1 就是一次操作，不提供稳定的 p99 或长期服务能力结论。

### 1.2 A：跨沙箱突发扩展性

每个沙箱先预热，再拍全量根 cp0；每代改内存 48 MiB（`/dev/shm`）和根文件系统文件 16 MiB 并 `sync`，拍 cp1、cp2 两个增量，随后依次 restore 到 cp1、cp2、cp0。各沙箱在每步用 barrier 对齐；checkpoint 前还要取现场，所以这是突发并发，不能假定所有 RPC 在完全相同的时刻到达服务端。造负载与现场校验不计入下面的 RPC 墙钟。

| 并发沙箱 N | cp1 墙钟 p50 / max ms | cp2 墙钟 p50 / max ms | 回 cp1 墙钟 p50 / max ms | 回 cp2 墙钟 p50 / max ms | 回 cp0 墙钟 p50 / max ms |
|---|---|---|---|---|---|
| 1 | 53 / 53 | 47 / 47 | 41 / 41 | 44 / 44 | 41 / 41 |
| 2 | 50 / 53 | 43 / 45 | 45 / 47 | 49 / 50 | 43 / 43 |
| 4 | 54 / 58 | 55 / 63 | 56 / 61 | 49 / 53 | 50 / 52 |
| 8 | 68 / 74 | 74 / 79 | 54 / 65 | 54 / 85 | 61 / 64 |
| 16 | 103 / 116 | 100 / 111 | 75 / 87 | 71 / 92 | 60 / 76 |

各档建沙箱均全部成功（合计 31 个）；cp0、cp1、cp2 合计 **93 次 checkpoint 成功**，三次 restore 跳转合计 **93 次成功、93 / 93 现场逐项一致**。全量 cp0 单列：N=1 的墙钟 395 ms，N=16 的 p50 / max 565 / 574 ms，不混入增量数字。

本轮在 N=16 时，增量 checkpoint 两步的客户端最大值为 116 / 111 ms，三次 restore 跳转的最大值为 87 / 92 / 76 ms；相对 N=1，cp1 / cp2 的 p50 为 1.9 / 2.1 倍，三次 restore 为 1.8 / 1.6 / 1.5 倍。这说明本轮固定负载下突发到 16 个沙箱时的延迟与成功情况；它不是 [第 18 章](18-950-performance.md) 的单沙箱分档判定，也不是持续 QPS 测试。

冻结窗口以 N=16 为例，与客户端墙钟并排看：

| 步骤 | 客户端墙钟 p50 / max ms | 服务端 frozen p50 / max ms |
|---|---|---|
| cp1 | 103 / 116 | 99 / 111 |
| cp2 | 100 / 111 | 95 / 106 |
| 回 cp1 | 75 / 87 | 64 / 74 |
| 回 cp2 | 71 / 92 | 53 / 73 |
| 回 cp0 | 60 / 76 | 46 / 61 |

cp1 / cp2 的 `snapshot` p50 为 91 / 85 ms，冻结窗口主要在这一步。回 cp1 的 `reset_view` p50 / max 为 19 / 26 ms、`conntrack` 为 0 / 14 ms，其他两跳的 `reset_view` 与 `conntrack` 在日志整数 ms 精度下均为 0 / 0。各列分位数不是同一条请求，不能把各列 p50 或 max 直接相加。单轮结果不足以判定某一分段是否为稳定的并发瓶颈。

### 1.3 B：同一沙箱的四调用方争用

一个沙箱，4 个线程各自 `Sandbox.connect()`（日志 `per-thread`），各做 5 轮 checkpoint → restore → list。每轮先在 guest 中写各自的小标记；**没有每轮再覆写 A 段的 48 + 16 MiB**。同一沙箱的 checkpoint / restore 在服务端串行，因此这一段看排队、超时与操作收敛，不用于证明多调用方能并行改写同一虚机，也不逐项断言并发写标记的现场属于哪一代。

| 项 | 本轮记录 |
|---|---|
| checkpoint | 20 / 20 成功；客户端 p50 / max **41 / 61 ms**；frozen **7 / 9 ms**；服务端 total **40 / 60 ms** |
| restore | 20 / 20 成功；客户端 p50 / max **38 / 55 ms**；frozen **11 / 19 ms**；服务端 total **37 / 52 ms** |
| list | 20 次；客户端 p50 / max **1 / 2 ms** |
| 客户端超时 / 幽灵 checkpoint | **0 / 0**；服务端 21 个 checkpoint = 全量根 1 个 + 成功增量 20 个 |
| 风暴后状态 | 沙箱可用；**21 / 21** 个 checkpoint 都能 restore，且心跳 pid 不变 |
| 短批次耗时 | 日志四舍五入为 **0.5 s**，包含 guest 标记、连接与 list 等工作，不换算成持续 checkpoint / restore QPS |

**B 并非整轮零异常。** 日志另列 **18 条 `mark` 命令异常**：8 条 `incomplete chunked read`，10 条明确提示沙箱被回滚、跨 restore 的连接需要重建。它们是同一沙箱的一路 guest 流式命令与另一路 restore 并发时记录的错误，不是上述 20 次 checkpoint / 20 次 restore RPC 失败，也不是 18 次现场不一致。跨 restore 的流连接失效属于已声明的使用边界（[第 22 章 §11.3](22-api-semantics.md#113-两类流式截断要分清)）；没有服务端逐请求日志，不能把那 8 条通用截断逐条归因，或把它们直接当作 [附录 C §8.1](C-evolution-and-cases.md#81-流式命令偶发截断) 历史缺陷复发。

`SUMMARY.md` 的 perf 四项 PASS 与日志末行 `A/D 段失败或不一致：0 条` 不能省略这 18 条：该脚本末尾仅将 A/D 的失败或不一致、段级异常汇总到退出码，B 的 `mark` 记录不在其中。本轮实际只跑 A/B，没有 D；B 的结论要结合上面的 RPC 成功数、命令异常与风暴后检查一起读。

### 1.4 这轮能说明的范围

本轮已给出 950、`hdbss`、ext4 下最多 16 沙箱的短时突发延迟与现场一致性，以及同沙箱四调用方的 RPC 收敛与连接边界。另有稍后 func 的 120 s 混合短稳态（[§2](#2-950-func-中的短稳态与恢复后请求)），但尚没有持续混合 D 段、小时级滚动保留、资源走平与长期尾延迟证据，也没有据本轮计算持续 QPS。950 的长期结论仍按 [§3](#3-到-950-上要重测什么) 另行安排；短时 A/B 不并入 [附录 B §10.1](B-920b-results.md#101-731877-次-restore0-不一致) 的 920B restore 累计数。

## 2. 950 func 中的短稳态与恢复后请求

来源为 `rollback/scripts/950/results/20261013-163056-func/` 的 `crtest-T36.log`、`crtest-T40.log`、`run.log` 与 `SUMMARY.md`，
整轮 2026-10-13 16:30:56–16:48:43（+08:00）。主机 `slot6`、aarch64，内核 `6.6.0-159.4.12.166.oe2403sp4.aarch64`、Python 3.14.6；
模板 `base`、私有沙箱，FC 自报 `hdbss` / 1.12.1，产物盘 ext4。完整功能结果与身份缺口见 [第 17 章 §3](17-functional-verification.md#3-950-默认功能回归2026-10-13)。
本次仅回传文本，没有各用例 JSON，下列分位数为日志原值，不独立重算；墙钟由秒换算成 ms，保留日志精度。
crtest 的 p50 为中位数，p99 使用排序后下标 `round(0.99 × (n−1))`，与 perf 分档的最近秩法不同，不合并样本。

### 2.1 T36：4 沙箱 × 120 s 混合短稳态

每个沙箱一个工作线程，随机交替 create、restore、delete、list、命令和文件写入；**跨沙箱并发，同沙箱顺序执行**。
默认场景权重为 create / restore / exec 各 3、list / write 各 2、delete 1。四线程全部跑到收尾（日志各为 120～121 s），循环体异常 0。
这不是每轮固定几十 MiB 改动的性能分档，也不是同沙箱多线程与 restore 重叠的 B 段。

| 操作 | 次数 | 失败 | 客户端墙钟 p50 ms | p99 ms | 最大 ms |
|---|---|---|---|---|---|
| create | 253 | 0 | 23 | 330 | 425 |
| restore | 272 | 0 | 42 | 59 | 63 |
| delete | 162 | 0 | 9 | 26 | 32 |
| list | 184 | 0 | 1 | 3 | 4 |
| exec | 279 | 0 | 1512 | 1516 | 1516 |
| write | 172 | 0 | 71 | 85 | 85 |
| **合计** | **1322** | **0** | — | — | — |

**正确性与收尾：**272 次 restore 的现场检查报告不一致 0，跑动中 list 与账本差异 0；四个沙箱收尾账本均一致，
删除剩余 checkpoint 后 list 均为空，命令、文件读写与心跳全部可用。销毁后本用例的 FC 进程归零；netns 槽位总数开跑 / 收尾均为 358。
这支持本轮短时混合操作及收尾没有观测到对应异常，不是小时级资源走平的证明。

表内 **1322 是混合循环的操作数**，不含后续收尾对账、删除等；日志末尾 1421 条操作记录包含这些工作，不能当作多跑了 99 次混合负载。
create 包含各沙箱首次全量，未按 `mem_mode` 拆开，p99 / max 不作为增量达标判据；exec 是带活体观察的测试场景时长，不是单条简单命令的服务延迟。
日志“失败数”在 T36 默认属于记录项，本轮是实际值为 0，不能仅凭用例 PASS 推定任意一轮都零失败。120 s 也不足以估计长期 p99 或持续服务容量。

### 2.2 T40：恢复完成后立即发起命令

4 个沙箱各做 50 轮：restore 返回后不主动等待，同时发起一条约 2 s、20 行输出的流式命令与一条 unary 命令，
**等本轮命令结束，再进行下一次 restore**。本轮没有 `--overlap`，不测试长流在途时再次回滚。

| 项 | 本轮结果 |
|---|---|
| restore | **200 / 200 成功**；客户端墙钟 p50 / p99 / max **26 / 47 / 48 ms** |
| 流式命令 | **200 / 200 成功**；墙钟 p50 / p99 / max **2027 / 2038 / 2039 ms**（含约 2 s 的脚本执行） |
| unary 命令 | **200 / 200 成功**；墙钟 p50 / p99 / max **10 / 15 / 15 ms** |
| 400 条请求的失败分桶 | 截断 **0**、`409 sandbox_restored` **0**、其他失败 **0** |
| 请求发出距 restore 返回 | 352 条在 0～1 ms，36 条在 1～2 ms，12 条在 2～5 ms；间隔 p50 / p99 / max **0.568 / 2.48 / 3.06 ms** |
| 收尾 | 四线程各完成 50 轮；账本一致、沙箱可用；销毁后本用例 FC 进程归零 |

**面向业务的结论：本轮验证了 restore 返回成功后即可继续发起命令，没有要求额外等待固定时间。**
它支持恢复后立即请求的可用性，不承诺所有请求零失败，也没有覆盖历史排障中的 13～20 ms 全时序窗口（本轮请求均在 3.06 ms 内发出）。
T40 默认的截断、409、其他失败计数是记录项，本轮从明细确认均为 0，不仅依赖 PASS。

这与 [§1.3](#13-b同一沙箱的四调用方争用) 的并发 `mark` 被打断并不矛盾：后者命令与同一沙箱的另一路 restore 重叠，本轮命令只在恢复完成后执行。
**同一沙箱执行 restore 时，应暂停其他命令和文件操作，恢复完成后再继续。** 原生 pause / resume 的回环连接检查也不能外推为外部 TCP 跨回滚保持有效。

## 3. 到 950 上要重测什么

950 与 920B 的脏页后端、CPU、盘都不同，不能把[附录 B](B-920b-results.md)的920B历史数字当作950指标。2026-10-13 已有 950 短时 A/B 并发（[§1](#1-950-短时并发2026-10-13-ab)）、func 的 4 沙箱 × 120 s 混合短稳态与恢复后请求（[§2](#2-950-func-中的短稳态与恢复后请求)），尚未覆盖长期资源走势。以下是按所需结论安排的补测方向，不是要求交付时逐一重演全部 920B 调试过程：

1. **最终长测原样复跑**（上限 60，16 沙箱，30 min）：逐项一致、restore / checkpoint 时间序列、df 与目录是否走平、GC、cgroup；
2. **滚动保留 10，至少 2 h**：看块数增长与 restore 的斜率，与 920B 上部署件的 2 h 结果（long11，[附录 B §10.3](B-920b-results.md#103-滚动保留-10一小时与两小时)）对照；
3. **conntrack 分解**：`conntrack_bg` 与宿主表规模，决定下一步优化的优先级；特别看滚动负载第二个小时宿主表是否也上涨、涨的是哪一类条目（920B 上的现象与根因见 [附录 C §8.6](C-evolution-and-cases.md#86-conntrack-清理占了冻结窗口) 末）；
4. **串口段**与 **T36 全规模**；
5. **16 路并发 A 段**已有一轮：cp1 墙钟 p50 / max 为 103 / 116 ms（[§1](#1-950-短时并发2026-10-13-ab)）。若要判断首个增量 checkpoint 的两簇现象是否仍会出现，再做重复测量；一次短测不能关闭这个概率项；
6. 每轮按 [附录 B §18.5](B-920b-results.md#185-一轮怎么跑) 记全条件标签。当前安排只量 HDBSS 自身，不做软件写保护对照（[第 20 章 §7](20-acceptance.md#7-已知项与缺口)、[第 20 章 §5.1](20-acceptance.md#51-hdbss-档hdbss-专项)）；不能拿 920B 与 950 的差值归因于 HDBSS。
