# 01 · 项目、交付范围与阅读方法

## 本章目标

读完本章，应当能回答五个问题：这个特性解决什么问题，交付物是什么，全书的主要结论是什么，每条结论在什么条件下成立，哪些范围测过、哪些没有测过。本章同时给出不同读者的阅读路径。本章的数字全部摘自后面的章节，条件和样本量随数字一起写出，完整数据在所链接的章节里。

## 1. 这个特性解决什么问题

AI Agent 在 E2B 沙箱里执行任意命令，中途经常需要退回到之前某一步的状态重试。扔掉沙箱重做一遍有三个问题：耗时长，会重复调用外部 API，重做的环境也不保证和原来逐字节相同。这个需求有三个特征：一个任务里要退十几次（高频）；回退发生在 Agent 的决策循环里（低延迟）；沙箱的 IP、端口映射和连接不能中断（[第 2 章](02-background.md)）。

E2B 原生的 pause / resume 要停掉沙箱，resume 时新建 Firecracker 进程，代价由固定开销和工作集决定，不随回退量变小（[第 3 章](03-goals-and-boundaries.md)）。本特性增加了另一条路径：**在同一个活沙箱里保存和恢复虚拟机状态**。

- `sandbox.checkpoint` 提供四个接口：`create`（执行 checkpoint）、`restore`、`list`、`delete`。
- 保存的状态包括 guest 内存、vCPU、中断控制器、设备逻辑状态和根盘。restore 保留当前的 Firecracker 进程、宿主资源和沙箱标识。
- 历史是一棵树，可以分支，也可以在保留的 checkpoint 之间前滚和回退。
- checkpoint 绑定所属活沙箱的当前生命周期，不跨 orchestrator 重启、不跨节点，也不跨原生 pause / resume。长期保存和重建用原生快照（[第 15 章](15-native-cooperation-and-cost.md)）。
- 外部数据库、已发出的 API 请求和跨 restore 的 TCP 连接不随 guest 回退，使用方按[接口语义](24-api-semantics.md)处理。

客户参考线是**增量 checkpoint ≤ 200 ms、原地 restore ≤ 100 ms**，按客户端墙钟 p50 判定，p99 并列给出，首次全量 checkpoint 单列不判定（[第 3 章](03-goals-and-boundaries.md)）。

## 3. 总体结构

![总体结构：SDK、宿主 orchestrator、分叉 Firecracker、KVM 四个层次与产物目录](img/01-1-总体结构.svg)

图中有四个层次：SDK 发请求，orchestrator 编排并持有账本，分叉的 Firecracker 读写内存与设备状态，KVM 和硬件提供脏页信息。全书反复用到两个设计选择：

- **控制面在宿主侧。** 做 checkpoint 要暂停虚机，沙箱里的程序无法暂停自己，所以请求虽然发往沙箱的 49984 端口，却在 orchestrator 的代理处被截下，由宿主应答。沙箱内因此不需要任何代理程序（[第 4 章](04-architecture-and-flow.md)）。
- **restore 是原地写回，不是重建。** restore 不新建 Firecracker 进程，而是向活进程写回发生变化的页和设备状态，代价随回退跨度变化，不随虚机规格变化（原理在[第 2 章](02-background.md)，实现在[第 9 章](09-in-place-rollback.md)）。

## 4. 关键结论

### 4.1 读数规则

- **平台不混用。** 950 的脏页后端是 HDBSS（`hdbss`），是客户平台和实测主线。920B 没有 HDBSS，脏页后端是 KVM 软件写保护（`kvm-wp`），是开发和长跑平台。920B 的数字不是 950 指标，两边的差值也不能算作 HDBSS 收益。
- **口径不混用。** 客户端墙钟包含网络往返和服务端全部工作，用于达标判定；服务端 `total` 是服务端总耗时；`frozen` 是虚机被暂停的时长（[第 16 章](16-test-methodology.md)）。
- **流程、断言和性能分开判断。** 脚本 PASS 表示流程和断言通过，不表示每档性能都在线内。

- 920B 的单沙箱分档（`kvm-wp`，页缓存全热，1040 次迭代）里，512 MiB 档 checkpoint p50 / p99 为 176.7 / 183.9 ms，restore 为 108.2 / 113.0 ms，restore 超线（[第 20 章](20-920b-performance.md)、[附录 B](B-920b-results.md)）。

| 总改动 | checkpoint 墙钟 p50 | 原生 pause p50 | restore 墙钟 p50 | 原生 resume p50 |
|---|---|---|---|---|
| 0 MiB | 17.2 | 251.9 | 22.4 | 109.3 |
| 16 MiB | 23.8 | 262.7 | 30.4 | 107.2 |

### 4.5 原生精确增量

ARM 适配基线上，原生 pause 用驻留判据决定导出哪些页：被换入过的页都算脏，读也算脏，粒度是 2 MiB。本书交付的代码在脏页跟踪开启时改用 Firecracker 的写跟踪位图，并把差分存储粒度从 2 MiB 降到 4 KiB，恢复时缺页单位仍是 2 MiB，内容从 4 KiB 映射拼接（[第 13 章](13-native-snapshot.md)、[第 14 章](14-native-precise-increment.md)）。

| 平台与日期 | 场景 | 修复前 | 修复后 |
|---|---|---|---|
| 920B，`kvm-wp`，2026-09-10 / 09-11，`pb2.py` | 只读 192 MiB，导出内存 | 358 MiB | **12.7 MiB** |
| 同上 | 只改 12 MiB，导出内存 | 176 MiB | **20.3 MiB** |
| 950，`hdbss`，修复前 2026-09-09～10，修复后 2026-11-06 | 改动 0～256 MiB 六档，导出内存 | 约 400 MiB，不随改动量变化（负载构造不同） | 15.9～294.3 MiB，随改动量增长 |

- 950 修复后这一轮 108 个样本失败 0，内容校验和常驻进程校验全部通过。pause p50 为 251.9～429.9 ms，主要是固定开销；resume p50 在 0～128 MiB 档为 106.1～109.3 ms，256 MiB 档为 120.7 ms，这一点的原因未查。
- 只换判据、不改 2 MiB 粒度不够：920B 上每代有约 130 MiB 的归并地板（[第 14 章](14-native-precise-increment.md)）。
- 兼容是单向的：新 orchestrator 能读旧快照，旧 orchestrator 读新快照会拒绝启动（[第 15 章](15-native-cooperation-and-cost.md)）。
- 没有 HDBSS 的机器默认不开跟踪，原生 pause 走驻留判据。要精确增量需要显式设置 `FC_TRACK_DIRTY_PAGES=true`，并让所有沙箱承担写保护的运行期代价（[附录 B](B-920b-results.md)）。

### 4.6 HDBSS

条件：950，2026-10-13，默认 order 1，Kunpeng 950 7592C，guest 2 vCPU，arena 256 MiB 和 1024 MiB，每组合 n = 3（[第 18 章](18-950-performance.md)）。

- **已启用的证据有三级。** KVM cap 502 可用；Firecracker 自报 `hdbss`，dmesg 与 Firecracker 日志的 buffer order 都是 1；常驻写者的冷写每页 KVM 退出数为 0.0072（arena 256 MiB）和 0.0023（arena 1024 MiB），远小于每页首写退出一次，恢复后 MD5 一致。
- **首写仍有代价。** 冷写和热写耗时比约 2.2，额外耗时约 46 ns/页。这是这个负载上的估计，不是隔离测出的纯硬件成本。
- **页分布影响很大。** 连续页 16 / 64 / 256 MiB 两项都在参考线内，512 / 1024 MiB 的 restore 超线。随机散页从 64 MiB 起 restore 超线（单写者 125.2 ms），512 MiB 的 checkpoint 也超线（单写者 281.8 ms）。这张表主要写内存，不能和第 4.2 节的混合档拼成一条曲线。
- **没有净收益结论。** 没有同机软件写保护对照，所以不给 HDBSS 相对软件后端的加速倍数；也没有其他 order 的数据，所以不比较 order。

## 本章要点

- 本特性在同一个活沙箱里做 checkpoint 和 restore，不重建 Firecracker 进程；长期保存和跨节点仍用原生快照。
- 950 单沙箱：混合 0～128 MiB 档两项达标，256 MiB 的 restore 超线，512 MiB 两项超线；样本少，身份待补。
- 920B 上 731877 次 restore 逐项一致，另有 long11 的 147557 次；950 目前只有短时并发证据。
- 原生精确增量让导出量随写入量变化；950 的 pause / resume 六档已测，`create_snapshot()` 路径未测。
- HDBSS 在 950 默认 order 1 上已启用并通过内容校验；没有同机软件对照，也没有其他 order 的比较。
- 读数字时要同时看平台、口径、样本量和负载。
