# 03 · 虚拟机快照的基本原理

> 「保存一台机器的状态」这件事，难的不是保存，是**说清楚「状态」到底包括什么**、
> 以及**怎么保证保存下来的各部分属于同一瞬间**。本篇讲这两件事，
> 并引出全书最重要的一个分野：**重建**与**原地回写**。
>
> **读者**：所有人。有操作系统基础会读得更顺。
> **预备**：[第 2 篇 · microVM 与 e2b](02-microvm-and-e2b.md)。
> **接下来**：[第 4 篇 · e2b 原生 snapshot](04-e2b-native-snapshot.md)。

---

## 0. 本篇要回答的问题

1. 「一台虚机的状态」由什么构成？哪些部分容易被忽略？
2. 为什么内存和磁盘必须取自同一瞬间？不一致会怎样？
3. 增量快照的前提是什么？
4. 恢复有哪两种形态？它们的成本模型为什么完全不同？
5. guest 被恢复之后，它的时间是什么样的？

---

## 1. 「状态」包括什么

一台运行中的虚拟机，它的状态分布在这些地方：

| # | 部分 | 大小量级 | 容易忽略吗 |
|---|---|---|---|
| 1 | **guest 内存** | GB | 不会 |
| 2 | **vCPU 寄存器** | 每 vCPU 几 KB | 不会 |
| 3 | **中断控制器**（aarch64 上的 GIC） | 几 KB | 有点 |
| 4 | **设备逻辑状态**（virtio 队列位置、协商特性、中断状态） | 几 KB | **是** |
| 5 | **磁盘** | GB | 不会 |
| 6 | **时间** | —— | **是** |
| 7 | **外部世界对它的记忆** | —— | **非常** |

前五项是「机器里的东西」，直觉上都想得到。后两项才是真正的坑。

### 1.1 第 6 项：时间

guest 里有两种时钟：

- **单调时钟**（`CLOCK_MONOTONIC`）：从某个起点单调递增，用于测量间隔；
- **墙钟**（`CLOCK_REALTIME`）：当前的年月日时分秒。

快照恢复之后，**单调时钟会倒退** —— 因为它来自 vCPU 的计时器寄存器，
而那些寄存器被恢复成了快照时刻的值。

这违反了 POSIX 对 `CLOCK_MONOTONIC` 的承诺，但在快照语义下是唯一自洽的做法：
guest 相信自己一直在那个时刻，它的**所有**状态都与那个时刻一致。

墙钟则不能留在过去（那会让所有时间戳都错），需要外部把它校回来。

> 这条直接决定了怎么写验收测试 ——
> 见[第 12 篇 §5](12-rollback-pitfalls.md#5-时间)和[第 17 篇 §3.3](17-observability-and-verification.md#33-为什么活性判据不能用时间)。

### 1.2 第 7 项：外部世界对它的记忆

这是最容易被忽略的一项，也是最难排查的。

guest 被退回到十分钟前，但**外部世界没有退**：

| 外部记忆 | 退回后的后果 |
|---|---|
| 宿主内核的连接跟踪表（TCP 序号窗口） | guest 发出的包序号「倒退」，被内核判为非法直接丢弃 —— **连接挂死而不是报错** |
| TCP 对端 | 对端记得的序号和 guest 现在用的对不上 |
| 代理的连接池 | 池子里的连接对应的 guest 侧状态已经不存在了 |
| 已发出的 API 调用 / 已写入的外部数据库 | **无法撤销** |

前三项本方案会处理（[第 12 篇 §4](12-rollback-pitfalls.md#4-连接跟踪)）；
最后一项是任何快照方案的硬边界。

### 1.3 还有一项 guest 需要被告知

如果 guest 完全不知道自己被回滚了，某些东西会出错：

- 随机数生成器的种子被复用（两次「不同」的执行产生同样的随机序列）；
- 依赖单调时间的缓存、租约、超时判断。

所以有一个专门的机制 —— **VMGenID**：一个 ACPI 设备，在 guest 内存里放一个 128 位代号。
代号变了就意味着「你被从快照恢复了」，guest 内核据此重新播种。

## 2. 一致性：为什么必须是同一瞬间

假设内存在 T1 保存，磁盘在 T2 保存（T1 < T2）。中间这段时间 guest 继续在跑。

恢复之后 guest 看到：**内存是 T1 的、磁盘是 T2 的**。

具体会怎样？guest 的文件系统在内存里维护着一堆状态：页缓存、inode 缓存、
未提交的日志事务。这些在 T1 被保存下来。而磁盘上的块已经走到了 T2。

于是可能出现：

- 文件系统日志里记着一笔已提交的事务，而内存里那个提交操作还没发生；
- 页缓存里的一个块，内容比磁盘上的**旧**（正常情况只可能更新）；
- 一个文件的 inode 说它有 10 个块，而磁盘上的分配位图说只有 8 个。

**guest 内核可能在恢复后直接报文件系统损坏**，也可能不报、只是静默地读到错的数据。

### 2.1 唯一的正确做法：一次暂停内完成

```
暂停虚机
  ├── 保存内存
  ├── 保存磁盘
  └── 保存 vCPU / 设备状态
恢复虚机
```

这样三者都是**同一瞬间**的镜像。guest 尚未刷盘的数据留在内存镜像里，位置完全正确 ——
恢复之后它会像什么都没发生一样把那些数据刷下去。

暂停的这段时间称为**冻结窗口**（freeze window）。它是快照**唯一对业务可见的代价** ——
业务感受到的是「卡了 N 毫秒」，而不是「这次调用花了 N 毫秒」。

> 这条约束在本方案里是不变量之一：
> **内存与磁盘必须在同一个暂停窗口内完成**（[第 14 篇 不变量 #5](14-failure-semantics.md#9-不变量清单)）。

## 3. 全量与增量

### 3.1 全量的问题

一次全量快照要写出整个 guest 内存。2 GB 的沙箱就是 2 GB 的写。
这决定了两件事：

- 冻结窗口与**虚机规格**成正比（除非把写移出窗口，那又带来一致性问题）；
- 存储占用是**每代 × 全量**。

### 3.2 增量的前提

增量快照只写「自上次以来变了的页」。它的前提是一个看似简单的问题：

> **怎么知道哪些页变了？**

宿主上的软件看不到 guest 的写 —— guest 直接在物理内存上跑。要知道哪些页被写过，
必须借助**硬件或内核**：

| 机制 | 原理 |
|---|---|
| 写保护 + 陷出 | 把页设成只读，第一次写时陷入内核，记一笔再放行 |
| 硬件标脏 | CPU 自己在页表更新时把地址记进一个缓冲区 |

两者的代价差两个数量级。这是[第 7 篇](07-dirty-page-tracking.md)的全部内容。

### 3.3 增量带来的新问题

有了增量，就有了**「一代」和「链」**的概念，也就有了新问题：

- 恢复到第 n 代，要不要把 1..n 代全部重放一遍？
- 删掉中间某一代会怎样？
- 回滚之后，比目标更新的那些代还有用吗？

这些是[第 8 篇](08-memory-diff-tree.md)的内容。剧透一下答案：
**不重放、按页寻址、历史是树不是链。**

## 4. 恢复的两种形态

**这是全书最重要的分野。**

### 4.1 重建：新建一个进程去加载

```
新建进程 → 建 KVM VM → 建 vCPU → 建中断控制器 → 建设备
        → 注册各种 fd → 建网卡 → 挂内存后端
        → 加载 vmstate → 恢复寄存器与设备状态 → 跑起来
        → guest 开始运行，逐页缺页把工作集换回内存
```

这是几乎所有现成实现的做法，包括上游 Firecracker 的 `PUT /snapshot/load`。

**成本 = 建一台虚机的固定开销 + 把工作集换回内存。** 后者与虚机规格成正比，
与「回退了多少」**完全无关**。

### 4.2 原地回写：往活着的进程里写

```
虚机暂停 → 把变了的那些页写回活着的内存映射
        → 把 vCPU / 设备状态写回既有对象 → 恢复运行
```

**一个宿主资源都不重建**：进程、KVM fd、中断控制器、设备、网卡、内存映射，
以及**已经在物理内存里的整个工作集**，全部原样保留。

**成本 = 变了多少就写多少。**

### 4.3 两者的对照

| | 重建 | 原地回写 |
|---|---|---|
| 成本正比于 | **虚机规格** | **回退跨度** |
| 沙箱身份 | 新进程（外部标识可以维持不变） | 同一个进程 |
| 网络、存储连接 | 全部重建 | 保留 |
| 恢复后的性能 | 一段时间内持续缺页 | **立刻满速** |
| 能处理「进程已死」吗 | **能** | 不能 |
| 能跨机器吗 | **能** | 不能 |
| 实现复杂度 | 低（构造函数保证对象自洽） | **高**（要让既有对象重新自洽） |

最后两行是代价。「原地回写」换来的速度，付出的是**适用范围**和**实现复杂度**：

- 适用范围：进程死了、要跨机器，它都做不了（[第 16 篇](16-lifecycle-and-portability.md)）；
- 复杂度：重建路线从零构造对象，天然自洽；原地路线要处理一类新问题 ——
  「从活对象里推导出来、又没进快照的状态」（[第 12 篇](12-rollback-pitfalls.md)）。

**本方案选的是原地回写。** 全书大半篇幅是在讲这个选择的后果。

## 5. 一个判断快照是否正确的好办法

怎么证明「恢复回来的确实是那个时刻」？

一个很强的判据：**杀掉一个进程，然后回滚，看它能不能复活。**

```
① 在 guest 里起一个后台进程，记下它的 PID 和启动时刻
② 打一个快照
③ kill -9 那个进程
④ 回滚到 ②
⑤ 检查：那个进程是不是回来了？PID 一样吗？启动时刻一样吗？
```

如果三个都对上了，说明恢复回来的是**完整的内存现场** ——
进程表、页表、文件描述符、内核里那个进程的全部结构，都回到了那一刻。

**这件事重放操作是做不到的。** 没有任何「反操作」能让一个被 `kill -9` 的进程
带着原来的 PID 和启动时刻回来。

> 本方案在 950 上的验收里包含这一项，结果是通过的
> （[第 17 篇 §4.1](17-observability-and-verification.md#41-950--hdbss-硬件标脏2026-08-29)）。
> 同一条测试还顺带证明了另一件事：三代快照之间那个进程的 PID 和启动时刻都没变 ——
> 说明**打快照的过程没有重启虚机**。

---

## 6. 小结

1. 「一台虚机的状态」有七项，其中**时间**和**外部世界对它的记忆**最容易被忽略，
   也最难排查。
2. **内存和磁盘必须取自同一瞬间**，否则 guest 会看到自相矛盾的文件系统状态 ——
   可能直接报损坏，也可能静默读到错数据。
3. 冻结窗口是快照**唯一对业务可见的代价**。
4. 增量的前提是「知道哪些页变了」，这必须借助硬件或内核，
   两种机制的代价差两个数量级。
5. 恢复有两种形态：**重建**（成本正比于虚机规格）和**原地回写**（成本正比于回退跨度）。
   本方案选后者，代价是适用范围变窄、实现复杂度上升。
6. 判断快照是否正确的强判据：**杀掉一个进程，回滚，看它能否带着原 PID 复活。**
   这件事重放操作做不到。
