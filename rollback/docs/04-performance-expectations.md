# 04 · 性能预期

> **这篇给谁看**：要估算 checkpoint / restore 在自己业务里花多少时间的客户开发者，以及要看达标结论的评审。
> **读完能做什么**：知道耗时由什么决定、当前在哪些改动量档位达标、有哪些已知的长尾。
> 本篇只写结论；**所有数字、拟合系数与原始出处都在 [25](25-results-and-compliance.md)**，测量口径在 [24](24-performance-methodology.md)。

---

## 1. 成本模型

checkpoint 与 restore 的耗时都是"固定开销 + 与改动量成正比的一项"，与虚机内存有多大基本无关：

```
checkpoint ≈ a₁ + b₁ × 自上一个点以来改过的数据量（内存脏页 + 磁盘写入）
restore    ≈ a₂ + b₂ × 回滚集大小（当前状态与目标之间，沿树路径所有被改过的页）
```

- 系数 a、b 随平台（脏页跟踪后端、存储介质）而不同，920B 上的拟合值见 [25](25-results-and-compliance.md)；
- **每个沙箱的第一次 checkpoint 是全量**，耗时正比于 guest 内存大小，每个沙箱（每一代）只付一次，不参与判定；
- restore 另有一项随沙箱磁盘视图里被写过的块数增长的开销（读各层的块清单），块数涨到上限也在毫秒以内；
  长跑中 restore 随时间变慢，主要来自同期变大的回滚量，不是块数本身（[25 §5](25-results-and-compliance.md#5-长跑与并发摘要)）；
- 与树的分支多少无关；"保留最新 N 个、删最旧的"用法下，耗时不随运行时间持续上涨（[02](02-semantics-and-limits.md) §4.2）。

对业务的直接含义：**改得少，回退就快**。在 Agent 的一步里只改了几十 MB 的沙箱，checkpoint 和 restore 都在几十毫秒量级；
一步改了几百 MB，耗时相应线性变长。

---

## 2. 判定口径（一句话）

客户参考指标是 **增量 checkpoint ≤ 200 ms、restore ≤ 100 ms**，按**客户端墙钟**判定，p50 判定、p99 并列，
按**每步改动量分档**（不按沙箱内存大小），全量根单列不判定；完整定义见 [24](24-performance-methodology.md)。

---

## 3. 判定结论

### 3.1 920B（kvm-wp 软件写保护）

条件：鲲鹏 920B 开发环境，`FC_TRACK_DIRTY_PAGES=true`（KVM 写保护跟踪脏页），模板 2 vCPU / 2 GB，
单沙箱串行、页缓存全热，代码为 [README](README.md) 所列的代码基准（2026-09-29）。

| 档位 | checkpoint（≤ 200 ms） | restore（≤ 100 ms） |
|---|---|---|
| 混合档（内存 : 文件 = 3 : 1），每步改动 0–256 MB 各档 | p50、p99 全部达标 | p50、p99 全部达标 |
| 纯内存档、纯文件档、只读触碰档 | 全部达标 | 全部达标 |
| 512 MB 极限档（拟合锚点，不是常规用法） | 达标 | **不达标**（p50、p99 都超线） |

按拟合外推，随着每步改动量增大，**restore 先于 checkpoint 碰线**；碰线点和逐档数字见 [25](25-results-and-compliance.md)。

以上结论以这一版代码的分档基准为准，逐档数据见 [25 §3](25-results-and-compliance.md#3-分档基准与判定)。

多沙箱并发时，单次操作比单沙箱串行慢：16 个沙箱持续并发、每沙箱上限 60 个 checkpoint 的 30 min 长跑里，
服务端 restore 的 p50 仍在 100 ms 线内，**p99 越过 100 ms**；不设上限、链深涨到几百的极限负载下，p99 接近 1 s。
并发负载不是客户判定口径的一部分，长跑与并发的数据见 [25 §5](25-results-and-compliance.md#5-长跑与并发摘要) 与 [25 §2.4](25-results-and-compliance.md#24-部署后回归rpm-部署版)。

### 3.2 950（HDBSS 硬件标脏）

**待补。** 本期代码尚未在 950 上跑分档基准。920B 的数字不能直接当作 950 的指标：两者的脏页跟踪后端不同
（HDBSS 由 CPU 记录脏页，省掉软件写保护在每个干净页第一次写入时的陷出），存储介质也不同。
950 的数据补齐后放在 [25](25-results-and-compliance.md)。

## 4. 已知的长尾

每条一句；数字与出处见 [25](25-results-and-compliance.md)，排障见 [08](08-troubleshooting.md)。

- **每个沙箱的第一次 checkpoint 是全量**，比增量慢一个数量级以上，正比于 guest 内存。这是树根的一次性代价。
- **delete 带同步合并，比不合并时慢**：删除的结尾会同步把可合并的隐藏节点合并（compact / fold）掉（每次最多若干个），delete 的中位耗时因此从几毫秒升到十几到二十几毫秒；p99 基本不变。
- **空闲一段时间后、不先 checkpoint 直接 restore 偏慢**：时间主要花在 Firecracker 回滚前的设备静默上；在 920B 上仍在 100 ms 线内。空闲后的 checkpoint 也比不空闲时慢。
- **多沙箱同时做首个增量 checkpoint，耗时偶发成两簇**：同一个二进制前后两次测量就可能分属不同的簇，稳定触发条件未找到。
- **restore 随回滚量增长**：guest 在后台持续写内存时，回滚集会真实变大，restore 随之变慢；这是真实工作量，不是缺陷。
- **宿主上连接数很多时，restore 的连接跟踪清理贴近关键路径**：后台清扫在大多数 restore 里被冻结窗口遮住，负载很重时会露出来。
- **宿主不跟踪脏页时每次都是全量**：功能正确，但每次都按全量付时间与空间，`mem_mode` 会一直是 `full`（[01](01-quickstart.md) §4）。
