# 02 · microVM 与 e2b 的沙箱模型

> 在讲怎么给一台机器打快照之前，得先讲清楚**被快照的那个东西是什么**。
> 本篇讲 microVM 与传统虚拟机、容器的差别，Firecracker 砍掉了什么，
> 以及 e2b 的一个沙箱在宿主上到底由哪些部件拼成。
>
> **读者**：不了解 e2b 或 Firecracker 的人。有 Linux 基础即可。
> **预备**：[第 1 篇](01-what-and-why.md)。
> **接下来**：[第 3 篇 · 虚拟机快照的基本原理](03-snapshot-fundamentals.md)。

## 0. 本篇要回答的问题

1. 容器、虚拟机、microVM 的隔离边界与启动代价分别是什么？
2. Firecracker 为了「小」砍掉了什么？这对快照意味着什么？
3. e2b 的 template / build / sandbox / envd / orchestrator 各是什么？
4. 一个沙箱在宿主上由哪些部件组成？
5. 为什么说「e2b 的用户沙箱从不冷启动」？

## 1. 三种隔离

要在一台机器上跑别人的代码，隔离方式大致三种：

| | 容器 | 传统虚拟机 | **microVM** |
|---|---|---|---|
| 隔离边界 | **共享宿主内核**（namespace + cgroup + seccomp） | 独立内核，硬件虚拟化 | 独立内核，硬件虚拟化 |
| 内核漏洞的影响 | 可能逃逸到宿主 | 被硬件边界挡住 | 被硬件边界挡住 |
| 启动时间 | 毫秒 | 秒～十几秒 | **~100 ms** |
| 内存开销 | 几 MB | 几百 MB | **几 MB** |
| 设备模型 | 无（用宿主的） | 完整仿真：BIOS、PCI、显卡、USB… | **极简**：几个 virtio 设备 |

跑**不受信任的任意代码**（AI Agent 生成的代码正是这种）时，共享内核的风险不可接受。
但传统虚拟机又太重。**microVM 就是为这个空隙设计的**：保留硬件隔离边界，
把设备模型砍到最小。

## 2. Firecracker

AWS 为 Lambda 和 Fargate 开发的 VMM（虚拟机监控器），Rust 写的，开源。
它砍掉的东西比保留的多：

| 砍掉 | 保留 |
|---|---|
| BIOS / UEFI | 直接加载 Linux 内核镜像 |
| PCI 总线 | **virtio-mmio**（更简单的设备发现方式） |
| 显卡、USB、声卡、软驱… | virtio-net、virtio-block、virtio-rng、串口 |
| 设备热插拔 | 启动时固定的设备集 |
| 大部分 CPU 特性仿真 | 直通 + 少量必要的处理 |

代码量因此只有 QEMU 的几十分之一，攻击面小得多，启动也快得多。

### 2.1 这对快照意味着什么

设备越少，「一台虚机的状态」就越简单。Firecracker 快照要保存的东西是：

| 类别 | 内容 |
|---|---|
| **guest 内存** | 通常是大头 —— 一个 2 GB 沙箱就是 2 GB |
| **vCPU 状态** | 每个 vCPU 的全部寄存器 |
| **中断控制器** | aarch64 上是 GIC 的状态 |
| **设备逻辑状态** | 每个 virtio 设备的队列位置、协商特性、中断状态 |

除了内存，其余加起来通常只有几十 KB。**这个悬殊的比例是后面所有优化的前提**：
优化内存那一项，就等于优化了整个快照。

### 2.2 Firecracker 已有的快照能力

上游 Firecracker 支持：

| 能力 | 说明 |
|---|---|
| Full 快照 | 写出完整的 guest 内存 + vmstate |
| **Diff 快照** | 只写自上次快照以来脏的页，写在各自的文件偏移上 |
| 脏页跟踪 | `track_dirty_pages`，靠 KVM 的写保护实现 |
| 加载 | `PUT /snapshot/load` —— **新建一个进程**去加载 |
| Pause / Resume | 暂停和恢复虚机 |

**注意最后两行**：上游只有「新建进程加载」这一条恢复路径。
本方案增加的核心能力就是**往活着的进程里写回**（[第 11 篇](11-in-place-rollback.md)）。

## 3. e2b 的对象模型

e2b 是一个把沙箱作为服务提供出来的平台。四个概念：

| 概念 | 是什么 |
|---|---|
| **Template** | 沙箱的「出厂状态」。用户定义（类似 Dockerfile），构建产出一份可以被反复加载的快照 |
| **Build** | 一次 template 构建的产物，有自己的 id。一个 template 可以有多个 build |
| **Sandbox** | 一个正在运行的沙箱实例，由某个 build 加载而来 |
| **envd** | 跑在 guest 里的守护进程，负责执行命令、读写文件、转发端口 |

### 3.1 一个 template 的产物

构建完成后，一个 build 由三份东西组成：

```
memfile     ← guest 内存镜像
rootfs      ← 根文件系统镜像
snapfile    ← vmstate：vCPU、GIC、设备状态
```

**这三份东西本身就是一个快照。** 也就是说：

> **e2b 的用户沙箱不是「启动」出来的，是「恢复」出来的。**

代码里这一点很清楚：`Factory` 有两个方法，

| 方法 | 谁用 | 内存后端 |
|---|---|---|
| `CreateSandbox` | **只有 template 构建流程用**（`internal/template/build/...`） | `uffd.NewNoopMemory(...)` —— 普通内存，冷启动 |
| `ResumeSandbox` | **所有用户沙箱** | 真正的 UFFD |

这个事实在后面反复用到。最重要的一处是[第 7 篇 §4.3](07-dirty-page-tracking.md#43-引导和加载两条路径都要武装)：
**脏页跟踪必须在「从快照加载」这条路径上武装**，只管冷启动等于完全没开。

### 3.2 内存是按需拉取的

一个 build 的 memfile 可能有几个 GB，而且**不在本地** —— 它在对象存储里。

如果每次起沙箱都要先把几个 GB 拉下来，启动时间就没法看了。e2b 的做法是
**userfaultfd（UFFD）**：

```
guest 访问一个还没有内容的内存页
    │
    ▼  缺页 → 内核不自己处理，转交给用户态
UFFD handler（orchestrator 里的一个组件）
    │
    ▼  从本地缓存取；没有就经 chunker 从对象存储按块拉
把这一页填进去，guest 继续跑
```

于是沙箱可以在 memfile 只拉了很小一部分的时候就跑起来，**用到哪拉到哪**。

> 这个机制对本方案有两处影响：
> ① 模板 memfile **本地不存在**，所以回滚路径不能依赖它 ——
>   这是[第 8 篇 §6.3](08-memory-diff-tree.md#63-全量根为什么是默认)「全量树根」的由来；
> ② 上游用 UFFD 的写保护位来判定脏页，而这条路径在 ARM 适配版上退化了 ——
>   见[第 7 篇 §5](07-dirty-page-tracking.md#5-脏页判据的三方差异)。

### 3.3 磁盘是分层的

rootfs 也不是直接给 guest 用的。它是**只读**的底座，上面盖一层写时复制（COW）的写层：

```
guest 的所有写  →  写层（一个稀疏文件 + mmap）
guest 的读      →  先查写层，没有再查底座
```

这样同一个 build 可以被成百上千个沙箱共享，每个沙箱只占自己写过的那部分。

这一层在[第 10 篇](10-disk-layering.md)展开 —— 本方案的磁盘增量就是在它上面做的。

## 4. 一个沙箱在宿主上的样子

```
┌─────────────────────── orchestrator 进程 ────────────────────────┐
│                                                                  │
│   沙箱表        代理（端口路由）        Checkpoint Service        │
│      │                                                           │
│      ├── Sandbox 对象                                            │
│      │      ├── process        → Firecracker 的 API socket       │
│      │      ├── Rootfs Provider → Overlay + NBD                  │
│      │      ├── Slot           → 网络命名空间、tap、IP           │
│      │      └── Template       → memfile / rootfs / snapfile     │
│      └── UFFD handler（每沙箱一个）                              │
└──────────────────────────────────────────────────────────────────┘
          │                    │                    │
          ▼                    ▼                    ▼
   Firecracker 进程       /dev/nbdX           tap 设备 + netns
          │
          ▼
    KVM（/dev/kvm）
```

| 部件 | 作用 |
|---|---|
| **orchestrator** | 宿主上的管理进程。管沙箱生命周期、网络、存储、代理 |
| **Firecracker 进程** | 每个沙箱一个。真正跑 guest 的 VMM |
| **UFFD handler** | 每个沙箱一个。按需填充 guest 内存页 |
| **NBD 设备** | 把宿主上的 Overlay 对象暴露成一个块设备给 guest |
| **网络槽位（Slot）** | 每个沙箱一个网络命名空间 + tap + IP，通过 NAT 出网 |
| **envd** | 在 guest 里，执行用户的命令 |

**「沙箱不能中断」这句话现在具体了**：一次中断意味着上面这些全部要重建 ——
新进程、新 KVM fd、新 tap、新 NBD 设备，以及把整个工作集重新缺页拉回内存。

## 5. 请求是怎么到达沙箱的

用户调 `sandbox.commands.run("ls")`，请求路径是：

```
SDK  →  沙箱的公开地址（形如 <port>-<sandbox-id>.<domain>）
     →  orchestrator 的代理
     →  解出 (sandboxID, port)
     →  转发进对应沙箱的对应端口
     →  guest 里的 envd 应答
```

本方案的 API 就是复用这条路径的 —— 只是**在最后一跳之前被截下来了**：
checkpoint 请求发给沙箱的 49984 端口，但由宿主直接应答，不进沙箱。

理由很直接：**打快照要暂停虚机，沙箱内的程序没法暂停自己。**
细节见[第 6 篇 §2](06-architecture.md#2-控制面请求发往沙箱却由宿主应答)。

## 6. 小结

1. **microVM** 保留硬件隔离边界，把设备模型砍到最小 —— 跑不受信任代码的合适选择。
2. Firecracker 砍掉了 BIOS、PCI、绝大部分仿真设备，只留几个 virtio 设备。
   **设备少 ⇒ 快照里除内存之外的部分只有几十 KB** ⇒ 优化内存就等于优化整个快照。
3. 上游 Firecracker 已有 Diff 快照和脏页跟踪，但**只有「新建进程加载」一条恢复路径**。
4. e2b 的 **template 产物本身就是一份快照**，用户沙箱一律由 `ResumeSandbox` 恢复而来，
   `CreateSandbox`（冷启动）只在构建 template 时使用。
5. 内存**按需从对象存储拉取**（UFFD + chunker）—— 这直接导致
   「模板 memfile 本地不存在」，是全量树根设计的由来。
6. 磁盘是**只读底座 + COW 写层**，本方案的磁盘增量就做在这一层上。
7. 「沙箱不能中断」的具体含义：进程、KVM fd、tap、NBD 设备、
   **以及已经在物理内存里的整个工作集**，中断一次全部要重建。
