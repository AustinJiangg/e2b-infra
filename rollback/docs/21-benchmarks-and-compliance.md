## 结论先行

### 成本模型

checkpoint 与 restore 的耗时都是"固定开销 + 与改动量成正比的一项"，与虚机内存有多大基本无关：

```
checkpoint ≈ a₁ + b₁ × 自上一个点以来改过的数据量（内存脏页 + 磁盘写入）
restore    ≈ a₂ + b₂ × 回滚集大小（当前状态与目标之间，沿树路径所有被改过的页）
```

为什么是这个形状：增量 checkpoint 只写出本代的脏页和本代封的磁盘层（[06](06-memory-diff-tree.md)、[07](07-disk-layering.md)），
restore 只回写回滚集里的页（[06](06-memory-diff-tree.md)、[09](09-in-place-rollback.md)），两者的工作量都与"改了多少"成正比；
固定开销是暂停与恢复虚机、Firecracker 的 API 往返、写位图侧车、换层、清连接跟踪表这些与改动量无关的步骤。

- 系数 a、b 随平台（脏页跟踪后端、存储介质）而不同。920B 上的拟合值见 §3.3：checkpoint ≈ 14.72 + 0.3228 × MB，restore ≈ 19.12 + 0.1876 × MB（客户端墙钟，ms）。
  直观地说，在 920B 上每多改 100 MB，checkpoint 多约 32 ms、restore 多约 19 ms；
- **每个沙箱的第一次 checkpoint 是全量**，耗时正比于 guest 内存大小，每个沙箱（每一代）只付一次，不参与判定（见下文"全量为什么单列"）；
- restore 另有一项随沙箱磁盘视图里被写过的块数增长的开销（读各层的块清单），块数涨到上界也在 1 ms 量级；
  长跑中 restore 随时间缓慢变慢，主要来自同期真实变大的回滚量，不是块数本身（[22 §4.9](22-long-run-and-concurrency.md#49-视图块数增长restore-随时间变慢)）；
- 与树的分支多少无关；"保留最新 N 个、删最旧的"用法下，树和磁盘都会走平，耗时不随运行时间持续上涨（[24 §4.2](24-semantics-and-limits.md#42-保留最新-n-个删最旧的会收敛)）。

对业务的直接含义：**改得少，回退就快**。在 Agent 的一步里只改了几十 MB 的沙箱，checkpoint 和 restore 都在几十毫秒量级；
一步改了几百 MB，耗时相应线性变长。

### 全量为什么单列

树根必须自包含，否则一条链没有可解析的底（[06 §8](06-memory-diff-tree.md#8-全量与增量怎么选)）。它的代价是写出整份 guest 内存：
920B 上 2 GB 模板服务端 433–445 ms、客户端墙钟 0.63–0.67 s，比 0 MB 档的增量（p50 14.9 ms）高一个数量级以上。

但它**每个沙箱只发生一次**：一个沙箱做 100 次 checkpoint，这约 0.65 s 摊下来每次约 6.5 ms，而且不在"回退到上一步"这个动作的路径上。
把它算进判定，得到的数字既不反映客户体验，也不反映实现质量。单列的另一个作用是当**分母**：没有这一行，"增量比全量快多少"这句话没法说。

### 判定口径（一句话）

客户参考指标是 **增量 checkpoint ≤ 200 ms、restore ≤ 100 ms**，按**客户端墙钟**判定，p50 判定、p99 并列，
按**每步改动量分档**（不按沙箱内存大小），全量根单列不判定；完整定义见 [20](20-performance-methodology.md)。

### 判定结论

**920B（kvm-wp 软件写保护）**。条件：`FC_TRACK_DIRTY_PAGES=true`（KVM 写保护跟踪脏页），模板 2 vCPU / 2 GB，单沙箱串行、页缓存全热：

| 档位 | checkpoint（≤ 200 ms） | restore（≤ 100 ms） |
|---|---|---|
| 混合档（内存 : 文件 = 3 : 1），每步改动 0–256 MB 各档 | p50、p99 全部达标 | p50、p99 全部达标 |
| 纯内存档、纯文件档、只读触碰档 | 全部达标 | 全部达标 |
| 512 MB 极限档（拟合锚点，不是常规用法） | 达标 | **不达标**（p50 108.2 ms、p99 113.0 ms） |

按拟合外推，随着每步改动量增大，**restore 先于 checkpoint 碰线**：restore 约在 431 MB、checkpoint 约在 574 MB。逐档数据见 §3。

多沙箱并发时，单次操作比单沙箱串行慢：16 个沙箱持续并发、每沙箱上限 60 个 checkpoint 的 30 min 长跑里，
服务端 restore 的 p50 88 ms 仍在 100 ms 线内，**p99 171 ms 越过 100 ms**；不设上限、链深涨到几百的极限负载下，p99 接近 1 s。
并发负载不是客户判定口径的一部分，数据与分析见 [22](22-long-run-and-concurrency.md)。

**950（Firecracker 自报 `hdbss`，2026-10-13）：已回传 perf。** 单沙箱串行的 12 档共 270 个增量样本，日志报告操作与现场检查异常 0。
混合档已测的 0 / 4 / 8 / 16 / 32 / 64 / 128 MiB，两项操作的墙钟 p50 与本轮 p99 都达标；256 MiB 的 checkpoint 达标，
restore p50 **105.6 ms** 超线；512 MiB 极限档两项都超线。纯内存 16 MiB、纯文件 16 MiB、只读 192 MiB 三档均达标。
另有同 checkpoint 串行 restore 100 次，墙钟 p50 / p99 / 最大为 **13.2 / 21.4 / 25.2 ms**。完整表与证据边界见 §6。
本轮 p99 在每档 10～30 个样本下等于最大值；缓存键是否齐全、被测提交、二进制 sha256 和存储介质尚未核实，不能据此宣称 HDBSS 比软件写保护快或慢。

**950 的 HDBSS 专项已归档默认 order 1。** 能力、自报、内核与 FC 日志相互印证；证据项与正式写密集基准共 69 次增量迭代，日志报告 MD5 不一致 0、非增量 0。

完整数据与负载含义见 §6.7；本次未扫描其他 order，也未做软件写保护对照。

**950 默认功能回归已通过（§2.5）。** `run.sh func` 为 **PASS 17 · FAIL 0 · SKIP 4**：16 个 crtest 用例共 863 条硬断言通过，SDK 异常语义另有 67 项通过。

### 对使用方式的含义

| 使用形态 | 本章的单次数字能不能直接用 | 说明 |
|---|---|---|
| 短生命周期沙箱，几十次 checkpoint 就销毁 | **能** | §3 的判定表就是这个形态 |
| 长期存活、"保留最新 N 个、删最旧" | **能，另加少量长跑开销** | 树、磁盘走平；restore 随回滚量和视图块数缓慢增长，滚动保留 10 的 1 h 长跑里服务端 p50 从 71 升到 84 ms（[22 §5.3](22-long-run-and-concurrency.md#53-滚动保留-10一小时与两小时)） |
| 长期存活、只拍不删、也不设上限 | **不能** | 链深与磁盘无界增长，restore 物化要走的链越来越长；应设 `CHECKPOINT_MAX_PER_SANDBOX` 或 `CHECKPOINT_MAX_BYTES_PER_SANDBOX`，或按"删最旧"管理（[27](27-configuration-and-capacity.md#43-数量上限怎么选)） |
| 一个节点上多个沙箱同时高频操作 | 看并发数据 | 共享的锁、宿主连接跟踪表和内存回收会把代价互相传递（[22](22-long-run-and-concurrency.md)） |

### 已知的长尾

每条一句；数字见 §7 与 [22 §6](22-long-run-and-concurrency.md#6-结论与剩余长尾)，排障见 [29](29-troubleshooting.md)。

- **每个沙箱的第一次 checkpoint 是全量**，比增量慢一个数量级以上，正比于 guest 内存。这是树根的一次性代价。
- **delete 带同步合并，比不合并时慢**：删除的结尾会同步把可合并的隐藏节点合并（compact / fold）掉（每次最多 8 个），delete 的中位耗时因此从几毫秒升到十几到二十几毫秒；p99 基本不变。
- **空闲一段时间后、不先 checkpoint 直接 restore 偏慢**：时间主要花在 Firecracker 回滚前的设备静默上；在 920B 上仍在 100 ms 线内。空闲后的 checkpoint 也比不空闲时慢（§4.2）。
- **多沙箱同时做首个增量 checkpoint，耗时偶发成两簇**：同一个二进制前后两次测量就可能分属不同的簇，稳定触发条件未找到。
- **restore 随回滚量增长**：guest 在后台持续写内存时，回滚集会真实变大，restore 随之变慢；这是真实工作量，不是缺陷。
- **宿主上连接数很多时，restore 的连接跟踪清理贴近关键路径**：后台清扫在大多数 restore 里被冻结窗口遮住，负载很重时会露出来。
- **宿主不跟踪脏页时每次都是全量**：功能正确，但每次都按全量付时间与空间，`mem_mode` 会一直是 `full`（[23 §4](23-quickstart.md#4-mem_mode这次是全量还是增量)）。

### 6.2 负载、样本与统计口径

每遍新建一个沙箱，先预热 `/dev/shm/sweep` 512 MiB、随机源 32 MiB 和根文件系统上的 `/bench-root/fsblob` 192 MiB，再建全量基点。
每个增量样本为：**从基点造规定量改动 → checkpoint 子节点 → restore 基点 → 校验现场 → 删除子节点**。
内存以 tmpfs 文件原地覆写模拟，根盘文件写后 `sync`；两遍按档位分摊样本，并非把下面的 n 再乘二。
这与连续建长链、再跨代恢复的 `checkpoint_bench_v2.py` 不同：这里的 restore 撤销本样本的改动，不能用目标 checkpoint 的标签混淆回滚量。

`analyze.log` 记录 **270 次迭代全部 `mem_mode=incremental`、异常记录 0**；另有两遍首次全量，合计 272 条操作记录。
“异常 0”只表示迭代记录中 create / restore / delete 没有报失败、没有记录到现场不一致，不证明全部功能用例已覆盖。

下表 p50 统一抄 `analyze.log` 的中位数；p99 为最近秩法。每档 n 为 10、20 或 30，故**本轮 p99 就是最大值**，合用一列，不能解释为长期尾延迟已充分采样。
`compliance.py` 用 `round(q × (n−1))` 选排序项，偶数 n 的 p50 不取中间两项平均，因此与 `analyze.log` 有小差异
（如混合 64 MiB 的 checkpoint 是 42.6 对 41.4 ms），不混抄；两份日志的超线档结论相同。
所有大小沿用脚本标签，计算按 1 MiB = 1048576 字节；耗时单位 ms。校验和造负载耗时不含在 SDK 调用墙钟内。

### 6.5 拟合是趋势，不是 p50 保证

`analyze.log` 在混合名义改动 ≤ 256 MiB 的 **210 条逐次迭代**上作普通最小二乘；小档样本多，拟合按迭代数加权，不是各档中位数拟合：

- checkpoint 墙钟 ≈ **17.47 + 0.4245 × MiB** ms（R² 0.9772）；
- restore 墙钟 ≈ **25.35 + 0.3050 × MiB** ms（R² 0.9513）。

反推 200 / 100 ms 得到的 430.0 / 244.7 MiB 只是**平均趋势线的交点**，不是实测 p50 达标上限，也没有置信区间；
430 MiB 更已超出拟合范围。模型对 512 MiB 的预测与该档实测 p50 相比，checkpoint 差 +0.2%、restore 差 +8.1%，
这是平均趋势预测与中位数的描述性对照，不能作为尾延迟误差界。判定仍以 §6.3 的已测档位为准。
“实际产物 MB”拟合的自变量是内存差分与盘层实占之和，与名义改动量定义不同，不混用其斜率。

日志还给出纯内存 / 纯文件各 n=50 的拟合，但各自只有 0 和 16 MiB 两个改动量位置（0 档 30 次、纯负载 20 次），
不足以验证跨改动量的线性关系；纯内存 checkpoint 冻结窗口的 R² 仅 0.1260，不采用它作为一般代价模型。
本节系数与 §3 的 920B 系数属于不同机器、样本与尚未补齐的部署条件，不能直接相减作为 HDBSS 收益。

且能力、自报、两侧启用日志和内容校验一致。冷/热耗时还受 cache、TLB、调度及后台活动影响；“冷 − 热”是本负载的额外首写耗时估计，
不能称为隔离测出的纯硬件成本。debugfs 计数覆盖该虚机在采集窗口中的全部 KVM 退出，不能全部归为 HDBSS buffer 溢出。
本轮未做同机软件写保护对照，因此不宣称实测减少了多少倍退出或获得了多少倍加速；也没有 order 之间的优劣结论。

#### 6.7.3 正式基准：连续页与随机散页

“脏页量”是 **4 KiB 页的覆盖量**，每页仅写 1 字节；不是连续复制这么多 MiB，也不是内存或磁盘写带宽。
`seq` 写 arena 开头连续 N 页；`rand` 在整个 1024 MiB arena 中无放回挑 N 页，再按随机顺序写。
表中的 1 / 2 写者是 guest 内常驻工作进程，分别尝试绑 vCPU，两个写者共同分摊总页数；宿主的 checkpoint / restore RPC 仍逐个执行。

每个样本为：回到基线 → 冷写 → 同页热写 → 记 MD5 → 拍增量 cpB → 将这些页改成另一值 → restore cpB → 校验 MD5 → restore 基线 → 删除 cpB。
表中的 restore 计的是**回到刚拍的 cpB**，随后回基线的耗时另记、不混入此列；§6.3 的混合分档则是拍 cpB 后直接回基线。
本专项主要写内存，二者的负载范围、页分布与回滚路径不同，不能拼成同一条按 MiB 的曲线。

#### 6.7.4 对性能和容量的含义

- **改动量还要结合页分布看。** 单写者 256 MiB 的 seq / rand，checkpoint 为 49.9 / 185.2 ms，restore 为 89.6 / 394.0 ms；
  512 MiB 时为 76.5 / 281.8 ms、165.2 / 613.2 ms。随机散页影响的不止 guest 写入，也影响后续快照与恢复。
  这与散页导致更多分散区间处理的机制相符，但本批没有内部区间数、I/O 调用或缓存分段记录，尚不能将全部差额归因到某一个阶段。
- **更大的档未必更慢。** rand 单写者从 512 到 1024 MiB，checkpoint 中位数反而从 281.8 降为 117.8 ms。
  当写满整个 arena 时，rand 和 seq 都覆盖所有页，只是顺序不同，已不再是相同稀疏程度；样本又只有 3 次。
  因而不作统一单调拟合，不据此认定越大越快或存在确定的代码缺陷。
- **双写者主要缩短 guest 写负载，不保证快照或恢复加速。** 例如连续写 256 MiB，冷写从 5.55 降到 2.77 ms，
  checkpoint 为 49.9 / 51.1 ms，restore 都是 89.6 ms；它不是两个 checkpoint RPC 的并发能力测试。
- **增量体积接近写脏覆盖量加本底。** 正式基准 0 档差分 18.5 MiB；连续单写者 16 / 64 / 256 / 512 / 1024 MiB 的差分为
  34.2 / 81.9 / 273.7 / 529.7 / 1042.2 MiB。随机单写者 1024 MiB 为 1076.8 MiB，其中可能含选页列表等程序活动带来的额外脏页；
  与连续方式的差额不是 HDBSS 误记的直接证明。该表只列内存产物，没有测根盘封层容量。

这轮可以作为默认 order 1 的启用、内容一致性与写密集性能证据；没有 order 扫描、同机软件写保护对照、长期运行或大样本尾延迟。
日志中的原始 JSON / JSONL 仍需保留在被测机上，以便后续追查精确分位数、内部阶段与异常。

## 本章要点

- checkpoint 与 restore 的耗时都是"固定开销 + 与改动量成正比"，与虚机内存大小基本无关；920B 上每多改 100 MB，checkpoint 多约 32 ms、restore 多约 19 ms。
- 每个沙箱的第一次 checkpoint 是全量（920B 的 2 GB 模板约 0.65 s 墙钟；950 本轮两次为 0.47 / 0.50 s），每个沙箱只付一次，单列不判定，同时作为"增量快多少"的分母。
- 920B（kvm-wp）单沙箱串行、热缓存：checkpoint 全部 18 档 p50 与 p99 达标；restore 除 512 MB 极限档外全部达标，按拟合约 430 MB 以内达标，restore 先于 checkpoint 碰线。
- 950（FC 自报 hdbss）：已归档 12 档 270 次增量的文本结果。混合已测档 0～128 MiB 两项达标，256 MiB 的 restore p50 105.6 ms 超线，512 MiB 两项超线；小样本 p99 等于最大值，不是长期尾延迟保证。
- 功能证据仍按平台区分：920B 的 smoke、func、T36 全规模、重启与注入类、FC 与 Go 单测通过；RPM 两次重装回归 smoke 5 / 5、func 17 / 0 / 4、`correctness.py` ALL PASS。950 默认 func 为 17 / 0 / 4，16 个用例共 863 条硬断言、SDK 67 项通过，四类重启 / 注入 / 配额专项跳过。950 的 2026-10-15 smoke 五项全过，预检 19 / 0 / 0、正确性 59 / 59；默认部署与功能验收通过不代替所有性能档位达标或小时级稳定性结论。
- 920B 串行 restore 5000 次 p50 / p99 为 9.58 / 18.2 ms；950 串行 100 次为 13.2 / 21.4 ms，全部成功且抽验一致。样本和部署条件不同，不合并、不据此归因；920B 空闲后 restore 偏慢的原因仍未查。
- HDBSS 默认 order 1 的专项已归档（§6.7），两任务共 69 次增量迭代、MD5 不一致 0、非增量 0；连续页与随机散页性能差别明显。冷/热比约 2.2 不能单独判定失效，需结合退出数与启用证据；尚无其他 order 的比较。
- 并发与长跑数字在 [22](22-long-run-and-concurrency.md)。950 原始样本、perf 轮二进制身份和缓存键覆盖率仍待补；HDBSS 专项已记录其当时的完整 sha256，但仍未建立源码 commit / RPM 对应，不能作为全部场景的完整验收。
