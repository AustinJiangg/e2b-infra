# 27 · 性能测试：三套方案的横向对照

> 同一台机器上有三套「快照」：进程级的 gsd / CRIU、本方案的 checkpoint / restore、
> e2b 原生 snapshot。它们在 SDK 上看起来几乎一样，但对「一份快照装什么」的定义完全不同 ——
> 而这个定义决定了负载该往哪里放、哪几列可以并排比、哪几列并排就是错的。
> 本篇讲这套对照怎么做才成立；数字在第 28 篇。
>
> **读者**：要做跨实现比较的工程师、要读对照表的评审。
> **预备**：[第 1 篇 §3](01-what-and-why.md#3-快照在四个层次上)、
> [第 4 篇](04-e2b-native-snapshot.md)、[第 20 篇](20-vs-native.md)、
> [第 26 篇](26-performance-methodology.md)。
> **代码**：`e2b-infra/rollback/scripts/acceptance/checkpoint_bench_v2.py`、`native_snapshot_bench.py`

## 0. 本篇要回答的问题

1. 三套方案的快照各自**覆盖什么**？为什么同一份负载在一套里是 200 MiB、在另一套里是零？
2. 为什么本方案的主力基准脚本之外还要养一份**对照组脚本**？它不是主力的升级版，那它多了什么、少了什么？
3. 三套的 Phase 2（恢复）语义各不相同 —— 哪些列可以逐行并排读，哪些列并排读就一定读错？
4. 造对照表时在 ARM 线上发现了什么？为什么那个发现对本方案没有影响？
5. 三张表摆在一起之前，要先过哪几条口径检查？

## 1. 三套方案摆在同一张图上

| | 进程级快照（gsd / CRIU） | 本方案 checkpoint / restore | e2b 原生 snapshot |
|---|---|---|---|
| **层次** | 进程级 | 虚机级，原地回滚 | 虚机级，重建 |
| **快照里装什么** | 选中进程的地址空间、打开的 fd、信号状态；文件那半由 overlayfs 的 upper 层管 | 整个 guest RAM 的按代差分 + rootfs 的封存写层 | guest RAM 的一份差分 + rootfs 写层的紧凑导出 |
| **产物落在哪** | 沙箱内 `/var/lib/gsd/snapshots/` | 宿主机 `/orchestrator/build/checkpoints/` | 宿主机导出缓存，再复制到模板存储 |
| **SDK 入口** | `sb.checkpoint.create` / `.restore` | `sb.checkpoint.create` / `.restore` | `sb.pause` + `Sandbox.connect`；`sb.create_snapshot` + `Sandbox.create` |
| **测试脚本** | `demo_checkpoint_perf.py` | `checkpoint_bench_v2.py` | `native_snapshot_bench.py` |

前两套在 SDK 上**完全同形**：同一个方法名、同一个 RPC 形状，差别全在服务端 —— 沙箱 5008 端口上
装的是哪个二进制。第三套走 SDK 自带的暂停与快照入口
（[第 4 篇 §1](04-e2b-native-snapshot.md#1-两个-rpc)）。

三者的差别不在快慢，在**覆盖范围**。有一句话贯穿全篇：

> **快照只能带回它覆盖范围内的东西。负载放在覆盖范围之外，测出来的既是零成本，也是假通过。**

这句话有两个方向的后果。往测量看，它决定了负载该往哪里放（[§3](#3-负载必须放在快照看得见的地方)）；
往语义看，它决定了「回滚」这个词在三套里指的不是同一件事（[§6](#6-定性结论)）。

## 2. 对照脚本为什么存在

### 2.1 主力基准与对照组

本方案有两份性能脚本，职责不同，不能互相替代。

| | `checkpoint_bench.py`（主力基准） | `checkpoint_bench_v2.py`（对照组） |
|---|---|---|
| 回答什么 | 增量的代价随「改了多少」怎么涨，以及**快照时机**值多少钱 | 在与进程级那套**完全可比**的档位表上，量本方案的端到端与服务端分段 |
| 结构来源 | 为回答时机成本从零设计的双段结构 | 照搬 `demo_checkpoint_perf.py` 的两阶段结构，刻意保持可比 |
| 可比对象 | 无，自成一套 | 进程级那套；再加同结构的 `native_snapshot_bench.py` |
| 命令行 | `--tiers` `--split` `--template` `--timeout` | 无参数，档位写死；只有一个诊断用环境变量 |
| 独占产出 | 时机成本（两段之差）、读盘字节数、按「撤销量」标注的 restore 曲线 | 内存 / 文件双代号校验、与另两套逐格对齐的表 |

**对照组不是主力的升级版**。主力脚本的设计与判定口径见
[第 26 篇 §3](26-performance-methodology.md#3-checkpoint_benchpy时机成本与直接量产物)；本篇只讲对照组，
以及它为了「可比」付出的代价 —— 档位写死、restore 的档位列换了含义、没有时机双段。

### 2.2 档位表逐格对齐

三份脚本共用一张档位表：总改动量 0 / 16 / 32 / 64 / 128 / 256 MiB，按 3:1 拆成内存与文件。

| 档 | 内存 MiB | 文件 MiB |
|---|---|---|
| 0 | 0 | 0 |
| 1 | 12 | 4 |
| 2 | 24 | 8 |
| 3 | 48 | 16 |
| 4 | 96 | 32 |
| 5 | 192 | 64 |

主力脚本的这张表是 `--tiers` 加 `--split` 算出来的，对照脚本把 `(mem_mb, file_mb)` 对写死在
`EXPERIMENTS` 里。**数值一致，来源不同** —— 写死是为了跟另一套的表一字不差地对齐，
改一个数就失去可比性。

### 2.3 原生那份的两个模式

`native_snapshot_bench.py` 要覆盖两个 SDK 入口，它们在服务端是同一段代码，差别只在「之后怎么起来」：

> `sb.pause()` 停机存快照，`Sandbox.connect(id)` 用同一个沙箱 ID 恢复。一次只能存一份、
> 只能回到最近那份 —— 它本来是给「闲置省资源」用的，不是给「多点回退」用的。所以这一模式
> 每档只能做 dirty → pause → resume → 验，**没有 Phase 2**。
>
> `sb.create_snapshot()` 存一份**持久**快照后沙箱继续跑，返回一个 snapshot_id（其实是 template id）。
> 之后任何时候 `Sandbox.create(template=snapshot_id)` 都能起一个处在那一刻的**新**沙箱。
> 多代快照可以并存、可以回到任何一代，这才是跟 checkpoint / restore 语义对得上的那条路。
>
> —— `native_snapshot_bench.py` 模块注释

「同 ID 但底下是新进程」这件事本身见
[第 20 篇 §1.2](20-vs-native.md#12-checkpoint快照--停--重新拉起)。

### 2.4 分段映射表

跨实现比较时最容易出错的一步是**把不同的阶段名当成同一件事**。对照组脚本在文件头里给了完整映射：

| 进程级（VM 内 gsd） | 本方案（宿主机 Firecracker + NBD） | e2b 原生 |
|---|---|---|
| `criu_dump_ms` | `snapshot`（内存那半） | 无分段 |
| `overlay_sink_ms` | `seal`（文件那半：封层） | 无分段 |
| `kill_ms + criu_restore_ms` | `save_live_bitmap + materialize + fc_rollback` | 无分段 |
| `overlay_restore_ms` | `assemble_view + reset_view` | 无分段 |
| `total_ms` | `frozen`（虚机真正停住的窗口） | 无分段 |
| `du -sh .../*_mem` | `mem_diff` / `mem_full` 的 `st_blocks` | 导出缓存里的 memfile 与 rootfs 文件 |
| （无对应） | 脏页后端 / 产物文件系统 / `mem_mode` 三项判据 | （无对应） |

两点要读出来：

**原生那一列整列是空的，不是漏测。** orchestrator 的 pause 路径只有 otel span，
不写 `timings.json`、也不打分段日志，所以那套只能拿到端到端与产物两类数
（`native_snapshot_bench.py` 模块注释）。这不影响对照 —— 它只是意味着**原生那一列没有「时间去哪了」
这一层**，三个时钟里少一个（[第 17 篇 §1](17-observability-and-verification.md#1-三个时钟)）。

**恢复那一行不能只取搬运那一步。** 差分树方案必须先把回滚集从各代差分里物化出来，
这一步常比搬运本身还贵，只算 `fc_rollback` 会让三分之一的冻结窗口对不上账
（对照组脚本 `RS_MEM` 的注释）。回滚集与物化见
[第 8 篇 §4](08-memory-diff-tree.md#4-回滚集)。

### 2.5 先证明测的是哪一套

前两套共用 SDK 入口，这带来一个真实的风险：**只看耗时数字分不出跑的是哪一套**。
判别只能看产物落点。

| | 本方案 | 进程级那套 |
|---|---|---|
| 宿主 `/orchestrator/build/checkpoints/<sbx>/` | 有 `ckpt_*/`、`index.json`、`layers/` | **不存在** |
| guest `/var/lib/gsd/snapshots/` | **空** | 有 `ckpt_*_mem/` |
| guest `journalctl -u gsd` | 无新记录 | 有 `overlay_sink_ms` / `total_ms` |

这是第 24 篇那条纪律的又一个实例：测试跑通不等于测的是你以为的那个东西
（[第 24 篇 §1](24-test-overview.md#1-为什么这套方案的测试要格外小心)）。跨实现对照多一层
「路由到哪个实现」的不确定性，所以每一轮开跑前先建一次快照、看产物落在哪，再开始计时。

## 3. 负载必须放在快照看得见的地方

造负载本身的三种失真（分配成本、写放大、放错层）与「预热 + 原地覆写」这个共同解法，
属于方法篇的内容，见 [第 26 篇 §2](26-performance-methodology.md#2-负载构造三种失真)。
本节只讲**同一个解法在三套上为什么落不到同一个地方**。

### 3.1 虚机级：tmpfs 就是内存

本方案与 e2b 原生都在宿主机上对整个 guest RAM 做快照。沙箱里的 `/dev/shm` 是 tmpfs，
tmpfs 的页就是 guest RAM 的页，而且它不落块设备。于是有一个很干净的分工：

- 往 `/dev/shm` 写 —— 脏的是内存，磁盘那半完全不动；
- 往根文件系统写 —— 脏的是磁盘写层，内存那半只多一份页缓存。

两半可以分别控制、分别验证，这就是两份虚机级脚本都把内存负载放在 `/dev/shm` 上一个文件、
文件负载放在根文件系统上另一个文件的原因。代价是文件那半会**同时**记进两列：
一次缓冲写既弄脏页缓存（算进内存增量）又落盘（算进文件增量）。这不是测量误差，是页缓存的本性，
两列如实摆出来即可。

### 3.2 进程级：只认进程地址空间

CRIU dump 的是进程。一个用 `dd` 写出来的 tmpfs 文件不在任何被 dump 进程的地址空间里，
它只是文件系统里的一个文件，CRIU 搬不走它。所以上一节那招在这里**直接不成立**：
同一份负载，在虚机级是满档脏页，在进程级是零。

进程级那套只能改成让进程自己持有一块内存、原地改它：沙箱里起一个常驻 Python 进程，
启动时分配一个 192 MiB 的 bytearray，按 4096 字节的步长逐页写一个字节把所有页碰实
（不碰实的话那些地址只是虚拟映射，既不驻留也不算脏），之后通过信号接收命令，
`dirty N` 就是用一个 1 MiB 的固定块把缓冲区前 N MiB 覆写 N 次。

这个设计里有两个乍看奇怪的细节，都是被判据本身逼出来的：

- **信号处理函数里不能调 `open()`。** Python 的 `open()` 会走内存分配器，可能向内核申请新映射，
  于是产生新的 VMA；CRIU dump 时遇到测量代码自己制造出来的 VMA，脏页账就对不上。
  脚本预先把命令文件和响应文件打开，处理函数里只对已有的 fd 做 `lseek` / `read` / `write`。
- **关掉透明大页。** 目的是把脏页粒度钉在 4 KiB。大页打开时一个 2 MiB 的 PMD 是一个整体，
  改其中一个字节整块都算脏，小档位会被放大。

第二条同时暴露了那套的判据：脚本末尾去 `dmesg` 里捞 `clear_refs` 的日志，
说明它的增量依赖内核的 soft-dirty 机制，而 soft-dirty 正是按 PTE 记的
（三套判据的并排见 [§5.3](#53-三套的脏页判据)）。

**测量代码本身必须留在判据之外** —— 这是跨实现对照里最容易被忽略的一条，因为它在每一套里长的样子都不同：
进程级要防自己造 VMA，虚机级要防预读把页填进来（[§5](#5-一个真实发现读也被算成脏)）。

### 3.3 文件那半的一处真实差异

内存那半三套各有办法，文件那半看起来都是「写一个文件」，写法却不同，读表时会咬人。

| | 本方案与原生的两份脚本 | 进程级那套 |
|---|---|---|
| 写法 | 预热撑到最大档，之后每档 `dd conv=notrunc` 覆写前 N MiB 再 `sync` | 每档用 SDK 的 `files.write` **重建**一个恰好 N MiB 的文件 |
| 文件大小 | 恒定 | 每档都在变 |
| 内容 | `/dev/urandom` | 单一字符 |
| 数据来源 | guest 内生成 | 从测试机经 HTTP 推进沙箱 |

后者有三处会让数字不可直接比较：文件是重建而不是覆写，**分配成本落进了档位**；
内容是单一字符，任何一层做压缩或去重都会让产物偏小；数据经 SDK 上传，
**端到端里多了一段网络**。

这不是说哪种写法错，而是说两张表并排时文件那一列的口径不同。要么各自只看趋势，
要么把写法统一之后再比。

### 3.4 校验也要放在能区分的地方

快照测试最危险的失败模式是假通过：数字很漂亮，但数据其实没回来，或者只回来一半。
三套脚本共用的思路是**写代号** —— 每建一代之前把这一代的名字写进沙箱，恢复之后读回来比。
关键是代号要写到能区分「哪一半回来了」的地方：

- 两份虚机级脚本把代号写两处。`/dev/shm/gen` 只有内存快照能带回来，根文件系统上的 `gen`
  只有换盘视图能带回来，两处分开判。只有单一代号的脚本，在「内存快照完全没生效、只有磁盘那半回滚了」
  的情况下照样打勾。
- 进程级那套的内存代号是常驻进程里的一个全局变量，通过信号读回来。这个设计更硬：
  能读到正确的变量值，就证明那个进程的地址空间真的被搬回来了，而不是进程被重启了。

**代号只有一页，不够。** 一个「层换对了但内容没回来」的缺陷能骗过它，所以两份虚机级脚本还比大文件的
md5：代号证明层换对了，md5 证明内容真的整片回来了。三重证据的完整讲法见
[第 25 篇 §1](25-functional-tests.md#1-什么叫回到那一刻)。

还有一个容易漏的点：**读回来验证时文件那半必须绕过 guest 页缓存**（`dd iflag=direct`）。
刚恢复的沙箱页缓存是空的，而基线那次是热的；不绕过的话读到的可能是缓存里的旧内容，
量到的耗时也完全不可比。封存写层丢失那个缺陷第一次验证时就是因为文件小、从页缓存读回来而假通过的
（[第 25 篇 §4](25-functional-tests.md#4-pause_verifypy一个自洽的静默损坏)）。

## 4. 恢复语义不同，所以有些列不能作差

### 4.1 两阶段结构，以及为什么必须分开

三份脚本的主体都是两阶段：**Phase 1 建代**（按档位表从小到大，每档先造负载再存一次快照，
记时间和产物大小），**Phase 2 恢复**（链建完之后逐代恢复，记时间并验数据）。前者回答「存快照多少钱」，
后者回答「回到某一代多少钱，以及回对了没有」。

为什么不建一代立刻恢复一代？因为**多代链本身是被测对象**。差分树里第六代的差分是相对第五代的，
恢复到第二代需要把第三到第六代全部撤销；只有先把链建完，才测得到这种跨多代的跳。

对照组脚本沿用了另一套的升序遍历，它自己的注释把这件事的后果写得很清楚：

> 升序遍历，与 `demo_checkpoint_perf.py` 相同 —— 那套每一代都是独立全量镜像，
> 恢复代价与顺序无关，所以它自然写成升序；这里照搬是为了两张表能逐行并排看。
>
> 但对差分树来说顺序有意义。……实际跳法是：第一跳从链尾回滚，要撤销后面所有代的并集，
> **整轮最贵**；往后每一跳都是前滚，只重放目标那一代自己的脏页。
>
> 一跳的代价取决于这一跳要撤销 / 重放的量，不是目标那一代自己有多大 —— 第一跳尤其如此，
> 它挂在某一行上却撤销了整条链。所以下面把 from → to 打出来，别照着档位那两列读。
>
> 还有一点：前滚命中的是目标那一代自己刚写完的差分文件（解析一跳到底、大概率还在页缓存里），
> 回滚要穿到链根的全量镜像上散读。同样的页数，两个方向的读放大不一样。
>
> —— `checkpoint_bench_v2.py`，Phase 2

于是同一个「restore」列，在三份表里的档位标签含义各不相同：

| | Phase 2 走法 | 档位列的含义 |
|---|---|---|
| 主力基准脚本 | 从链尾逐级 unwind 回链根 | **这一跳要撤销的量** |
| 对照组脚本 | 先大幅回退到链首，再一路前滚 | **目标那一代的负载**，不是这一跳的距离 |
| 进程级那套 | 逐代恢复，每代独立 | 目标那一代的负载（对它而言两者等价） |

**主力脚本与对照组脚本的 restore 列不能直接作差**，数字对不上是设计如此。

### 4.2 三种「恢复」

| | 恢复之后是什么 | 沙箱 ID | 多点回退 |
|---|---|---|---|
| 本方案 | **原地回滚**，同一个 Firecracker 进程、同一个沙箱 | 不变 | 支持，且能跨分支 |
| 原生 snapshot 模式 | 每一代是一个独立模板，恢复 = 用那个模板起一个**全新沙箱** | 换新 | 支持，各跳互不相关 |
| 原生 pause 模式 | 同一 ID 恢复，但只保留最近一份 | 不变 | **不支持** |
| 进程级那套 | `kill` 掉目标进程再由 CRIU 重新拉起，沙箱本身没停 | 不变 | 支持 |

「原地」与「重建」的成本模型差异是全书的核心分野
（[第 11 篇 §1](11-in-place-rollback.md#1-两种恢复形态)、
[第 20 篇 §3](20-vs-native.md#3-成本模型)）；恢复必须有活体沙箱这一约束见
[第 16 篇 §3.1](16-lifecycle-and-portability.md#31-恢复机制要求活体)。

对照表里的直接后果：**原生的 snapshot 模式每跳可以照档位读**（各跳独立），
**本方案的每跳不能**（代价取决于起点与终点之间差了多少），
**原生的 pause 模式没有 Phase 2 这一列**（只能每档存完立刻恢复）。

### 4.3 三个容易误会的名词

**`connect` 就是 resume。** e2b Python SDK 2.x 的 `Sandbox` 类上已经没有 `resume` 方法，
只有 `connect`；它打的是 `POST /sandboxes/{id}/connect`，该接口自己的文档写的是
「如果沙箱处于暂停状态，它会被恢复」。REST 层仍保留 resume 路由，生成的客户端里也还有对应模块，
但 SDK 的公开接口不再调用它。脚本用 `connect` 不是走了偏门。

**`upload` 是第二步落地。** 服务端存快照分两步：先把内存差分和 rootfs 导出写进宿主机的导出缓存目录，
再把它们连同几个元数据文件复制到模板存储 —— 后者就是 upload。本地部署时它是一次文件复制，
云上是真的往对象存储传。**两个入口对它的处理不同**：pause 把上传丢进后台就返回，
`create_snapshot` 会等上传完成才返回。所以脚本把 upload 单列一列，
也所以 `create_snapshot` 的端到端时间天然比 pause 大一截。

**`touch` 那一列必须有。** 原生恢复起来的沙箱，内存不是一次性搬回来的，而是按页懒加载：
guest 碰到某一页，宿主机才去把那一页填进来（[第 4 篇 §5](04-e2b-native-snapshot.md#5-恢复resumesandbox)）。
于是 resume 的端到端时间很短，但用户真正等到数据可用的时间不止这些。脚本的办法是：
存快照之前把负载整读一遍记一个基线，恢复之后再整读一遍，两者之差就是懒加载延后付的账。
本方案是把回滚集一次性搬回来，这笔账已经含在端到端里了。

> **两张表并排时必须把 touch 的差值加到原生那一边**，否则是拿「还没付的账」跟「已经付了的账」比。

### 4.4 产物落在什么介质上

这一条在两台测试机上都反直觉，而且它不是 e2b 的设计，是部署配置的结果：

| 路径 | 文件系统 | 实际介质 |
|---|---|---|
| `/orchestrator/build`（原生的导出缓存，本方案的产物根） | XFS on LVM | 真磁盘 |
| `/tmp/templates`（原生快照的最终产物） | tmpfs | **内存** |

环境变量 `LOCAL_TEMPLATE_STORAGE_BASE_PATH` 没有设置，走默认值 `/tmp/templates`，
而这两台机器的 `/tmp` 恰好是 tmpfs。也就是说，**当前部署下原生快照的最终产物放在内存里**：
不落盘、重启即失、占的是宿主机 RAM。本方案的产物在 `/orchestrator/build/checkpoints` 下面，
是真落盘的。

做对比时这一点必须写进条件标签：原生那套的 upload 一列是「磁盘读 + 内存写」，
换成磁盘存储会显著变大。这是**部署条件差异，不是实现差异** —— 换个部署，这一列的可比性就变了。

### 4.5 哪些列可以并排

| 列 | 可否逐行并排 | 理由 |
|---|---|---|
| checkpoint 端到端 | 可并排，需同段对齐 | 三套的档位表逐格相同；但对照组脚本默认不做落盘静默，对齐的是主力脚本「写完立刻拍」那一段 |
| checkpoint 产物量 | 可并排，**不可相减** | 覆盖范围不同：进程级只装那个进程的堆，虚机级还装页缓存与本底 |
| checkpoint 分段 | 仅两套 | 原生无分段 |
| restore 端到端 | **只可并列** | 档位列语义不同（撤销量 / 目标代负载），且恢复形态不同 |
| upload | 仅原生有 | 另两套产物就地可用 |
| touch | 仅原生非零 | 懒加载延后付的账 |
| 脏页后端 / `mem_mode` | 仅本方案有 | 另两套没有对应判据 |

一条通用规则：**范围不同的两个数不作差，只并列**。作差只在同一套实现的两段口径之间做
（例如主力脚本的时机成本），跨实现一律并列。

还有一条条件标签对三套的**影响不对称**，一定要跟着表走：脏页后端。软件写保护下每个干净页第一次被写
都要陷出一次虚机，这笔开销全部落在虚机级那两套身上，进程级那套走的是 soft-dirty，基本不受影响
（[第 7 篇 §6.1](07-dirty-page-tracking.md#61-软件写保护的代价模型)）。
**同一张对照表换到硬件标脏的机器上很可能变样**，所以一轮对照的结论只在它自己的后端上成立，
换后端要整轮重跑，不能只补一列。

## 5. 一个真实发现：读也被算成脏

造这套对照表时，在 950 上最值得看的一列不是时间，而是**原生 pause 的产物大小**：
名义脏内存从零档一路涨到最大档，导出的 memfile 几乎不动，始终停在同一量级；
对照之下本方案的内存差分随档位线性增长（数字见 [第 28 篇](28-results-and-compliance.md)）。

最初的怀疑是负载构造的伪影 —— 脚本在每次存快照之前会把负载整读一遍量 touch 基线
（[§4.3](#43-三个容易误会的名词)），读会把这些页填进来。查下去发现原因更具体，**而且不是伪影**。

### 5.1 链条的三步

1. **判据。** 原生 pause 路径向 Firecracker 要脏页位图，走的是 `get_dirty_memory`：
   先用 `mincore` 找出驻留的页，再读 `/proc/self/pagemap`，保留「驻留、且 userfaultfd 写保护位
   （第 57 位）是清的」那些页。代码注释写得很直白：present and write-protected bit cleared,
   indicating it was written to。
2. **前提。** 这个判据成立有一个前提：页被**读**进来的时候要带上写保护，只有真的被**写**过，
   写保护才会被解除。上游正是这么做的 —— 读缺页时给 `UFFDIO_COPY` 加上 `UFFDIO_COPY_MODE_WP`。
3. **前提在这条线上不成立。** ARM 适配补丁把那三行注释掉了（提交 `fbee6fcd1`，2026-06-08，
   提交信息 "patch: all patch for arm64"）。该改动也在对外交付的
   `0001-adapted-for-arm-architecture.patch` 里，两台测试机跑的都是含它的版本。

于是每一个被填进来的页，无论读进来还是写进来，写保护位都是清的，判据第二项恒真、塌缩成
`is_present()` —— 也就是 `mincore` 已经回答过的那个问题。机制层面的详细推导见
[第 7 篇 §5.1](07-dirty-page-tracking.md#51-退化是怎么发生的) 与
[§5.2](07-dirty-page-tracking.md#52-判据因此塌缩)。

### 5.2 两个结论

**其一，这条线上原生快照的「脏页集」实际上是「自上次 resume 以来被碰过的页集」，也就是工作集。**
增量只对从未被碰过的页成立；任何读过自己数据的工作负载，下一次快照就按工作集导出。
这也是 [第 20 篇 §3.2](20-vs-native.md#32-一个反直觉的现象) 说的那个「与改动量无关的下限」的来源，
而它是 **ARM 适配特有的**：x86 原生的增量本来就是精确的
（[第 20 篇 §6.3](20-vs-native.md#63-e2b-的增量快照有一个与改动量无关的下限)）。
这是一处**成本模型差异**，不是缺陷 —— 原生的成本本来就与虚机规格挂钩、与改动量关系不大
（[第 4 篇 §6](04-e2b-native-snapshot.md#6-成本模型总结)）。

**其二，这对本方案没有影响。** 本方案不走 uffd 这条判据，用的是 Firecracker 自带的差分快照，
脏位图来自 KVM 的写保护日志或 HDBSS 的硬件标脏，**读不算脏**
（[第 7 篇 §5.4](07-dirty-page-tracking.md#54-本方案怎么绕开)）。
同一台机器上、同一份负载下，本方案的内存差分随档位线性增长而原生的不增长，
正是这两条判据的差别在数据上的样子。

### 5.3 三套的脏页判据

| 方案 | 脏的判据 | 读算不算脏 |
|---|---|---|
| 进程级（gsd / CRIU） | 内核 soft-dirty，`clear_refs` 清、按 PTE 记 | 不算 |
| 本方案 | Firecracker 差分快照，位图来自 KVM 写保护或 HDBSS 写跟踪 | 不算 |
| e2b 原生（ARM 线，2026-09-11 前） | `mincore` 驻留 + pagemap 第 57 位未置 | **算** |
| e2b 原生（ARM 线，修复后） | Firecracker 写跟踪位图（KVM 写保护或 HDBSS），与本方案同源 | 不算 |

三种脏页跟踪机制本身的对比见 [第 7 篇 §2.4](07-dirty-page-tracking.md#24-三者对比)。

### 5.4 顺带一处脚本自身的修正

原生那份脚本开头会打印一行「脏页后端 HDBSS / kvm-wp」。这一行描述的是 **Firecracker 的写跟踪机制**，
它对本方案的 checkpoint 有意义，**原生 pause 路径根本不看它**。脚本早先版本在后端为 `off` 时提示
「memfile diff 会退化成整份内存，查 `FC_TRACK_DIRTY_PAGES`」—— 这句话对原生路径是错的，已改掉。

判据的条件标签必须跟着**那条路径**走，而不是跟着机器走。同一台机器上三套跑在三条判据上，
把机器级的条件标签套到不看它的那条路径上，就会得到一个自洽但无意义的解释。

> 修复之后这一段反过来了：原生 pause 路径**也**看那一行了，见 §5.5。脚本的提示已改为两版并存。

### 5.5 原生快照口径（修复后）

2026-09-11 起，infra-arm `jll` 分支（提交 `de25fe4d0`，一个提交、14 个文件、Firecracker 零改动）
把 ARM 线原生 pause / create_snapshot 的内存增量改成了精确的。读原生那一列之前先确认跑的是哪一版，
两版的口径完全不同。本节只讲**口径怎么变**；为什么修复前不精确、三层各改了什么、代价与边界，
见[第 21 篇](21-native-increment-diagnosis.md)、[第 22 篇](22-native-increment-fix.md)、[第 23 篇](23-native-increment-cost-and-verification.md)。

**改了三层，对应 §5.1 链条的三步之后再往下两步：**

1. **判据。** `Uffd.DiffMetadata` 不再走 `get_dirty_memory`（mincore + pagemap），改调
   `PUT /snapshot/save-dirty-bitmap` 取 Firecracker 的写跟踪位图 —— KVM 脏页日志（920B 上是写保护，
   950 上是 HDBSS）与 Firecracker 用户态位图的并集，**与本方案同一份位图**。读缺页填进来的页不在里面，
   这是对的：它们的内容已经在父代映射链里，不用再存。
2. **存。** 差分 header 的块大小从 2 MiB 降到 4 KiB；父代映射是字节区间、都是 2 MiB 对齐的，
   在 4 KiB 下仍然有效，不用重写。差分文件仍是「紧凑拼接 + header 指偏移」，只是步长变了。
3. **填。** guest 仍是 2 MiB 大页，uffd 一次缺页仍填 2 MiB。单个映射覆盖整页时零拷贝直接交
   `UFFDIO_COPY`（与修复前同一条路）；一个 2 MiB 页的 4 KiB 子页来自多代时，从映射链拼成一页再填，
   缓冲走池、用完归还。

**口径怎么变：**

| 列 | 修复前 | 修复后 |
|---|---|---|
| `memfile`（导出量） | 自上次 resume 以来**被碰过**的页（工作集），读也算，各档 ~400 MB | 这一代**写过**的 4 KiB 页之和 + 几 MB 系统本底，随写入量线性 |
| 与本方案的「内存产物量」 | 可并排，**不可相减**（口径不同） | **可并排也可相减**：两套读同一份位图，差别只剩差分文件的组织方式 |
| `touch`（恢复后首次整读） | 懒加载延后付的账 | 不变；拼接路径实测在噪声内（见第 28 篇表 3-J） |
| 脏页后端那一行 | 原生路径不看它 | 原生路径**也看它**：`FC_TRACK_DIRTY_PAGES` 关着时自动退回修复前口径并记日志 |
| 判别方法 | —— | cp0 行减去预热写入量后只剩几 MB 就是修复后 |

**两台机器的差别只剩供数机制。** 代码路径逐行相同，位图内容相同（950 上 `pb2.py` 只读 192 MB
那档 15.0 MB，920B 12.7 MB），差在运行期代价：920B 无 HDBSS，`FC_TRACK_DIRTY_PAGES=true` 意味着
KVM 写保护，每个干净页的第一次写陷出一次，**所有沙箱都付**；950 有 HDBSS，CPU 硬件记脏，不陷出，
而且 `fc/dirtytracking.go` 探到 KVM 能力 502 会默认开追踪。所以本方案的策略原样沿用到原生：
有 HDBSS 默认开、没有默认关；无 HDBSS 的机器上「精确增量」与「不开写保护」二选一，默认不开，
原生快照退回修复前口径，行为与修复前一致。

**对本方案的影响：无。** 本方案的导出走 Firecracker 进程内 `dump_dirty`、恢复走 `restore_dirty`，
不经过 memfile 差分链和 uffd；两边共用的只有 `save-dirty-bitmap` 这个非破坏性端点。
修复后的二进制上 `checkpoint_verify.py` 全过、`checkpoint_bench_v2.py` 六代全 `incremental`
（920B-0914，第 28 篇 §4）。

**探针脚本**（`e2b-infra/rollback/scripts/probes/`）：`pb2.py` 把 `/memory/dirty`、写跟踪位图、实际导出三列并排，
修复后后两列逐档相等；`pb5.py` 三代改同一个 2 MiB 块里的不同 4 KiB 页再各起新沙箱验 md5，
是「4 KiB 存、2 MiB 拼」的关键用例。

## 6. 定性结论

> **这不是同一件事的两种实现。三边快的地方不一样，原因是快照的范围不同。**

证据不在时间列里，在**产物量**里，而且对得很死：进程级那套最大档的 CRIU 产物≈那个常驻进程堆的脏量，
文件那 64 MiB **完全不在内存产物里**（由 overlayfs 单独管）；本方案同档的内存产物≈内存负载 +
那次文件写留在 guest 页缓存里的页 + 本底。两个数字都能从各自的覆盖范围推出来。

由此，两句话概括三边的成本结构：

- **进程级快在它拍的东西少** —— 不拍内核状态、不拍页缓存、不拍别的进程；
  沙箱里没有用户进程时，它的日志会直接打 `"no user processes, overlay-only checkpoint"`，
  checkpoint 退化成纯 overlay 切层。文件那半在它那边几乎免费（overlayfs 热切换只是一个 ioctl，
  数据早就在 upper 层里），本方案的 `seal` 要真的封 NBD 写层（[第 10 篇 §3](10-disk-layering.md#3-seal不搬运任何数据的换层)）。
- **本方案快在恢复时不用重建任何东西** —— 进程级恢复必须先 `kill` 掉目标进程再由 CRIU 整个重新拉起；
  原生恢复要建新的 Firecracker、vCPU、GIC、设备、tap 并重新缺页换入；本方案是把内存脏页搬回去、
  换盘视图，进程压根没停过。

比性能数字更要紧的是由此推出的两条**语义**差别：

1. **回滚范围。** 进程级只回滚它 dump 过的那组进程和 overlay 层；内核状态、页缓存、
   不在 dump 范围内的进程**不会回滚**。虚机级是整机回滚，guest 的一切都在内存镜像与磁盘视图里，
   包括它自己不知道的部分（[第 6 篇](06-architecture.md#在-guest-里跑一个-agentcriu-路线) 讲的正是这条）。
2. **失败面。** 进程级依赖 CRIU 能 dump / restore 目标进程 —— 进程用了 CRIU 不支持的特性
   （某些 fd 类型、特殊映射）就会失败；虚机级不看进程内部长什么样。

选哪一套是**按需要的回滚范围选**，不是按谁的某一列数字小选。

## 7. 三张表并排之前的口径检查表

1. **内存负载是否真的落在被快照覆盖的范围里。** CRIU 只认进程地址空间，虚机级认整个 guest RAM。
2. **分配成本是否已经挪进预热**，不落在任何档位上。
3. **名义档位和实测产物大小是否接近。** 差几倍就说明有放大，先查放大再读时间。
4. **文件那半的写法是否一致**：覆写还是重建、内容是否随机、是否经 SDK 上传。
5. **恢复后的验证是否绕过了 guest 页缓存**，两侧代号是否分开判。
6. **恢复时间是否已经把懒加载那笔（`touch`）算进来。**
7. **产物落在什么介质上**，tmpfs 还是真盘。
8. **Phase 2 的语义是原地回滚、另起新沙箱，还是根本没有 Phase 2**；档位列标的是撤销量还是目标代负载。

八条里有六条与时间无关 —— 跨实现对照的成败**主要不取决于计时精度**，取决于三张表的行是不是同一件事。
再加上 [§2.5](#25-先证明测的是哪一套) 的路由验证与[第 24 篇 §4](24-test-overview.md#4-测量纪律)
的条件标签，一轮对照才算口径齐全。

## 8. 小结

1. **三套快照的差别是覆盖范围，不是快慢。** 进程级装选中进程的地址空间与 overlay 层，
   虚机级装整个 guest RAM 与磁盘写层。负载放在覆盖范围之外，测出来既是零成本也是假通过。
2. **对照组脚本不是主力基准的升级版。** 它为「可比」写死档位、放弃时机双段、改了 restore
   的档位含义；主力脚本的时机成本、读盘字节数、按撤销量标注的 restore 曲线，它一列也没有。两个都要跑。
3. **同一份负载在三套里要用三种造法。** 虚机级写 tmpfs，进程级让进程自己持有一块 buffer 原地覆写；
   测量代码本身必须留在判据之外（不造 VMA、不预读把页填进来）。
4. **恢复语义不同的列不可作差。** 原地回滚 / 新沙箱 / 无 Phase 2，三种形态；作差只在同一套实现的两段口径之间做。
5. **原生那边要加两列才公平**：`upload`（pause 是后台上传，`create_snapshot` 等它完成）
   与 `touch`（懒加载延后付的账）。产物落在 tmpfs 还是真盘也要进条件标签。
6. **ARM 线上原生 pause 的脏页判据把读进来的页也算脏**，增量因此退化成工作集。
   这是判据差异带来的成本模型差异，且**对本方案无影响** —— 本方案的位图来自 KVM / HDBSS 的写跟踪，读不算脏。
   **2026-09-11 起已修复**（§5.5、[第 22 篇](22-native-increment-fix.md)）：原生也改读同一份位图、按 4 KiB 存差分，两套的内存产物量从此可相减；
   无 HDBSS 的机器上是否开写保护追踪，两套用同一条策略。
7. **定性结论是「快的地方不一样」**：进程级快在拍得少，本方案快在恢复不重建。
   两条语义差别（回滚范围、失败面）比任何一列数字都更能决定该选哪套。
8. **实测数字只在第 28 篇维护**，本篇给的是让那些数字能被正确阅读的口径。
