# 05 · 设计目标、约束与边界

> 一个系统的形状，是由它**明确不做什么**决定的，不亚于由它做什么决定。

## 1. 目标场景

一句话：**沙箱在执行任务时出错，需要退回到上一个已知良好的状态继续跑。**

三个特征（[第 1 篇 §1.2](01-what-and-why.md#12-这个需求的三个特征)）：

| 特征 | 具体含义 | 推出什么 |
|---|---|---|
| **高频** | 一个任务里十几次，不是一个沙箱一两次 | 单次成本必须低到可以随手用；固定开销不可接受 |
| **低延迟** | 发生在 Agent 的决策循环里 | 量化目标：**checkpoint ≤ 200 ms、restore ≤ 100 ms** |
| **沙箱不能中断** | 有 IP、端口映射、保持中的连接、外部持有的引用 | 排除一切「停掉再拉起」的路线 |

第三条最硬。它单独就排除了原生方案的整条路径 ——
`Pause` 和 `Checkpoint` 都要停掉沙箱（[第 4 篇](04-e2b-native-snapshot.md)）。

### 1.1 那两个数字约束的是什么

「≤ 200 ms / ≤ 100 ms」是客户给的上限，本身不是一个可测量的口径 —— 它没说谁的钟、
哪一次、哪个统计量。全书把它钉死成下面这一条，钉在**对我们最不利**的一侧：

| 操作 | 达标线 | 判定对象 | 不参与判定 |
|---|---|---|---|
| checkpoint | ≤ 200 ms | **增量** checkpoint（沙箱的第 2 代及以后），客户端墙钟 **p50**，p99 并列 | 树根全量 —— 每个沙箱一次性的成本，单列说明 |
| restore | ≤ 100 ms | **原地** restore（沙箱 ID 与 Firecracker 进程都不变），客户端墙钟 p50，浅集 / 深集分列 | 另起新沙箱的恢复形态，那是原生 snapshot 的路径 |

用客户端墙钟是因为它含网络往返与服务端全部工作，是三个钟里最大的一个，
也是客户在自己机器上唯一能复测的一个。完整的口径定义表见
[第 26 篇 §1.2](26-performance-methodology.md#12-口径定义表)，
逐档的判定结果见[第 28 篇 §5](28-results-and-compliance.md#5-对照客户指标的判定表)。

这条目标反过来规定了成本模型：达标线是一个**常数**，而增量的代价随本次改动量走
（[§5.1](#51-成本只与改动量挂钩)），所以性能表按**脏页量档位**给，不按沙箱内存大小给。

## 2. 硬约束

不可协商的，来自交付环境：

| # | 约束 | 后果 |
|---|---|---|
| 1 | **aarch64**（鲲鹏 920B / 950） | x86 上的方案不能照搬；ARM 适配版的既有问题要一起面对 |
| 2 | **产物盘是 ext4** | 整条数据路径**不得依赖 reflink**（[第 18 篇](18-ext4-vs-xfs.md)） |
| 3 | **不改动原生路径** | 两条路径必须并存，本方案是纯加法 |
| 4 | **沙箱内不装任何代理程序** | 全部动作在宿主侧完成（[第 6 篇 §2](06-architecture.md#2-控制面请求发往沙箱却由宿主应答)） |
| 5 | **交付形态是 patch + 二进制** | 单元测试不进交付物；orchestrator 与 Firecracker 成对交付 |

约束 2 的影响最深远：它直接否掉了「每代自足」这个更简单的设计
（[第 8 篇 §1.1](08-memory-diff-tree.md#11-reflink-是什么为什么-ext4-没有)），
是差分树存在的全部原因。

约束 3 意味着**不能为了本方案的方便去改动原生代码的行为**。
所有新增能力都是新路径、新端点、新字段。

## 3. 三条不复用原生的理由

### 3.1 它会中断沙箱

导出磁盘增量的路径必须先摘出写层、停掉沙箱、等 NBD 设备释放。
这不是实现细节 —— `ExportDiff` 的参数之一就是「关掉沙箱」这个回调
（[第 4 篇 §4.2](04-e2b-native-snapshot.md#42-必须停沙箱的硬证据)）。

**与特征三直接冲突。**

### 3.2 成本模型不对

恢复要新建 Firecracker 进程，再靠缺页把整个工作集换回内存 ——
代价取决于**虚机多大**，而不是**回退了多少**。

回退一个只改了 40 MiB 的沙箱，和回退一个改了 2 GiB 的沙箱，花的时间几乎一样。

**与特征一（高频）直接冲突**：高频意味着单次改动量通常很小，
而原生方案在这种情况下**省不下任何东西**。

### 3.3 ARM 适配版上增量已经退化

上游 x86 用 uffd 的写保护位区分读缺页与写缺页，增量是精确的。
移植到 aarch64 时那条写保护路径走不通，被注释掉了，判据退化成
「凡是被换入过的页都算脏」（[第 7 篇 §5](07-dirty-page-tracking.md#5-脏页判据的三方差异)）。

叠加「每次 snapshot 都重建沙箱、工作集必须重新换入」，得到一个反直觉的结果：

> **即使一次 snapshot 之间什么都没做，增量的下限也约等于整个常驻工作集。**

**必须说清楚**：这是 ARM 适配引入的退化，**不是 e2b 的设计问题**。
本方案修复它，也不构成「超越 x86 原生」。

> **2026-09-11 起已修复**（`KASandbox_0904` 提交 `c42d23e73`）：原生 pause 的判据换成 Firecracker 的写跟踪位图，差分按 4 KiB 存、按 2 MiB 页拼回。本段描述的是修复前的机制，仍是理解成本模型的依据；机理见[第 21 篇](21-native-increment-diagnosis.md)、改法见[第 22 篇](22-native-increment-fix.md)，修复后的口径与数据见[第 27 篇 §5.5](27-cross-implementation.md#55-原生快照口径修复后)、[第 28 篇 §3.3 表 3-J](28-results-and-compliance.md#表-3-j--native_snapshot_benchpy修复后920b-0914-native4k)。

## 4. 明确的非目标

**划界本身是设计的一部分。** 下面这些明确**不做**，交给原生 snapshot：

| 非目标 | 为什么划出去 |
|---|---|
| **宿主崩溃恢复** | 账本活在 orchestrator 进程内存里，进程一死就没了（[第 16 篇](16-lifecycle-and-portability.md)） |
| **跨节点迁移** | 产物是「相对模板的增量」，且路径绑定在本机 |
| **长期持久化** | 产物随沙箱生命周期回收 |
| **沙箱进程已死后的恢复** | 只有原地回滚一条路，它要求活体 |
| **虚机状态撕裂后的抢救** | 明确标记为死并要求重建 |
| **跨沙箱共享 checkpoint** | checkpoint id 只在所属沙箱的生命周期内有意义 |

### 4.1 划界带来的简化

把这些划出去，换来的不只是「少写点代码」，而是**整类问题不存在**：

| 不做什么 | 因此不用处理 |
|---|---|
| 产物不跨重启存活 | 陈旧条目回收、与已消失沙箱的对账、格式版本迁移 |
| 不跨节点 | 产物上传下载、一致性协议、跨节点的引用计数 |
| 没有兜底重建路线 | 两条恢复路径之间的语义对齐（但代价是失败必须分级，[§5.3](#53-宁可报错不可静默损坏)） |
| 只在活沙箱上工作 | 离线状态的加载、校验、修复 |

[第 15 篇 §1](15-state-and-concurrency.md#1-三类状态) 里那句「并发模型少了一整类问题」
就是这么来的。

### 4.2 划界的代价

诚实地说，代价是真实的：

- checkpoint **备份不走**（[第 16 篇 §2](16-lifecycle-and-portability.md#2-一个思想实验把目录完整拷走)）；
- orchestrator 重启、宿主重启，全部失效；
- 沙箱迁移到别的节点时 checkpoint 不跟随。

**这些不是缺陷，是这笔交易的另一半。** 换来的是零拷贝封存、原地回滚、
以及只随回退跨度增长的成本曲线。

## 5. 四条设计原则

从上面推出来，全书各篇都在实现它们。

### 5.1 成本只与改动量挂钩

**任何与虚机规格线性相关的固定开销都要消掉。**

体现在：

| 处 | 怎么做 |
|---|---|
| 内存产物 | 每代只存本代脏页，不克隆上一代（[第 8 篇](08-memory-diff-tree.md)） |
| 磁盘产物 | 封存是改名，零数据搬运（[第 10 篇](10-disk-layering.md)） |
| 封存的落盘 | 不做 msync，把 O(改动量) 变成 O(1)（[第 10 篇 §5](10-disk-layering.md#5-封存不等待落盘)） |
| 恢复 | 按页写回回滚集，不重建镜像（[第 11 篇](11-in-place-rollback.md)） |
| 内容解析 | 不合并链、不压平历史 —— 恢复成本与链深无关 |

唯一保留的固定开销是**全量树根**（每个沙箱的第一次 checkpoint），
而且它有开关（[第 8 篇 §6.3](08-memory-diff-tree.md#63-全量根为什么是默认)）。

### 5.2 不重建任何宿主资源

进程、KVM fd、eventfd、irqfd / ioeventfd 注册、tap、网络槽位、NBD 设备、内存映射 ——
**一个都不重建**。

这既是「快」的全部来源，也是「离不开活沙箱」的全部原因。同一件事的两面
（[第 16 篇 §3.4](16-lifecycle-and-portability.md#34-缺运行时环境)）。

### 5.3 宁可报错，不可静默损坏

这套系统操作的是**一台正在运行的虚拟机的内存**。一次错误的回滚不会让虚机崩溃 ——
它会让某几页内存的内容属于另一个时刻，然后虚机继续跑。

所以：

| 情形 | 处理 |
|---|---|
| 路径上缺侧车 | **报错**，不静默降级成全量回滚 |
| 链断了 | **拒绝恢复**，直到下一次全量 checkpoint |
| 账本与层栈不一致 | **标记污染并拒绝服务**，不留下一个看起来正常的错账本 |
| 拓扑不一致 | **拒绝**，不勉强写 |
| 纪元可能丢失 | 以**隐藏条目**保住它，宁可留垃圾也不留坏链 |

没有兜底重建路线，这条从「好习惯」变成了「硬要求」。
完整讨论见[第 14 篇](14-failure-semantics.md)。

### 5.4 能力随硬件自动降级，但要说出来

有 HDBSS 就用，没有就退回软件写保护；有 reflink 就克隆，没有就真拷贝。
**功能永远正确，只是代价不同。**

但降级**不能是静默的**：

| 手段 | 说明 |
|---|---|
| 启动时报告能力**和理由** | `track_dirty_pages_reason` |
| 每次调用回报 `memMode` | 第一个之后出现 `full` 就是有问题 |
| Firecracker 自报脏页后端 | `hdbss` / `kvm-wp` / `off` |
| `FC_HDBSS_REQUIRED` | 生产部署可以选择**宁可启动失败** |

见[第 17 篇 §2](17-observability-and-verification.md#2-让静默退化现形)。

## 6. 一句话总结这笔交易

> **用「绑定沙箱生命周期」换掉产物自足性与账本持久化，换来零拷贝封存、原地回滚、
> 以及只随回退跨度增长的成本曲线。**

两条路径并存，各管各的：

| | 原生 snapshot / resume | checkpoint / restore |
|---|---|---|
| 产物 | 自足，进对象存储 | 相对模板的增量，宿主本地 |
| 生存期 | 独立于沙箱 | 随沙箱回收 |
| 恢复 | 新建进程加载 | 活体原地回滚 |
| 适用 | 迁移、持久化、崩溃恢复 | 高频快速回退 |

---

## 7. 小结

1. 目标场景三个特征：**高频、低延迟、沙箱不能中断**。第三条单独就排除了原生方案的整条路径。
   低延迟的量化目标是 **checkpoint ≤ 200 ms、restore ≤ 100 ms**，只约束增量与原地 restore。
2. 五条硬约束，其中「**产物盘是 ext4**」影响最深远 —— 它否掉了「每代自足」这个更简单的设计。
3. 不复用原生的三条理由：**中断沙箱**、**成本模型不对**、**ARM 适配上增量已退化**。
   第三条是修复退化，不是超越上游。
4. **明确不做**六件事，换来的是整类问题不存在（陈旧条目、跨节点一致性、离线加载…）。
   代价也是真实的：产物备份不走、重启即失效。
5. 四条设计原则：**成本只与改动量挂钩**、**不重建任何宿主资源**、
   **宁可报错不可静默损坏**、**能力随硬件降级但要说出来**。
