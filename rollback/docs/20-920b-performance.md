# 20 · 920B 性能与平台差异

## 本章目标

920B 没有 HDBSS，脏页跟踪靠 KVM 写保护。这台平台承担了本方案的大部分开发验证，分档基准、原生精确增量的体积验证和长跑都先在这里完成。本章回答五个问题：

1. 软件写保护下，改动量与 checkpoint、restore 耗时是什么关系，碰线点在哪里；
2. 单沙箱连续 restore 和空闲之后 restore 的耗时如何；
3. 写保护的运行期代价由谁承担，920B 与 950 的差异在哪里；
4. checkpoint 与原生 pause 叠加时多了什么代价；
5. 原生快照的导出体积在修复前后怎样变化。

多沙箱并发和长跑的结果在[第 21 章](21-concurrency-and-longrun.md)，轮次明细和数据出处在[附录 B](B-920b-results.md)。

## 2. 分档基准与判定

### 2.1 负载与样本

条件为新 920B、`8ea5322bf`、单沙箱串行、页缓存全热。`bench_tiers.py` 全表跑 3 遍，共 1040 次迭代，每遍首个全量 checkpoint 单列。

| 项 | 结果 |
|---|---|
| 迭代模式 | 1040 次全部 `mem_mode=incremental` |
| 现场不一致 / 离群 | 0 / 0 |
| 三遍之间冻结窗口 p50 比值 | 0.95–1.05 |
| 缓存 | 1040 次 restore 的 `materialize_disk_read_mb` 与 `fc_rollback_disk_read_mb` 全为 0 |

数字是**客户端墙钟**（ms）。p99 取 `analyze.py` 的最近秩法，n < 100 的档取最大值，n = 100 的档取排序后第 99 项（[第 16 章 §3.3](16-test-methodology.md#33-分位数怎么算)）。负载构造见[第 16 章 §5](16-test-methodology.md#5-负载构造三种失真)。

判定线是 checkpoint ≤ 200 ms、restore ≤ 100 ms，按客户端墙钟判，只对增量操作判。

### 2.4 拟合与碰线点

混合档名义改动 ≤ 256 MB，以单次迭代为样本最小二乘（n = 780，客户端墙钟）：

- checkpoint ≈ **14.72 + 0.3228 × MB** ms（R² 0.9919）
- restore ≈ **19.12 + 0.1876 × MB** ms（R² 0.9810）

反推碰线：checkpoint 到 200 ms 约在 **573.9 MB**，restore 到 100 ms 约在 **431.0 MB**。用这两条线外推 512 MB 档，与实测 p50 相差 −1.8% / −6.1%。

拟合只描述 920B 上这张档位表的趋势，不是某个改动量下的 p50 保证。950 的系数在[第 18 章 §6](18-950-performance.md#6-拟合是趋势不是-p50-保证)，两者属于不同机器和样本。

### 2.5 判定

| 操作 | 结论（920B · kvm-wp · 单沙箱 · 热缓存） |
|---|---|
| 增量 checkpoint ≤ 200 ms | 全部 18 档 p50 与 p99 都达标，含 512 MB 极限档 |
| 原地 restore ≤ 100 ms | 除 512 MB 极限档外 17 档 p50 与 p99 都达标；512 MB 档 p50 108.2 ms 超线。按拟合，改动量约 430 MB 以内达标 |

这个判定只覆盖单沙箱串行和热缓存。多沙箱并发下的数字是另一种负载，按服务端计时，不能与这张表直接比较（[第 21 章 §1.5](21-concurrency-and-longrun.md#15-口径版本与机器)）。冷缓存路径没有测。

### 2.6 全量 checkpoint 单列

树根必须自包含，否则一条链没有可解析的底（[第 6 章 §8](06-memory-diff-tree.md#8-全量与增量怎么选)）。它的代价是写出整份 guest 内存：920B 上 2 GB 模板服务端 433–445 ms、客户端墙钟 0.63–0.67 s，比 0 MB 档的增量（p50 14.9 ms）高一个数量级以上。

它**每个沙箱只发生一次**：一个沙箱做 100 次 checkpoint，这约 0.65 s 摊下来每次约 6.5 ms，而且不在“回退到上一步”这个动作的路径上。把它算进判定，得到的数字既不反映使用体验，也不反映实现质量。单列的另一个作用是当分母：没有这一行，“增量比全量快多少”这句话没法说。

## 3. 单沙箱串行与空闲后 restore

本节是 920B 的专项结果。950 串行 100 次的记录见[第 18 章 §7](18-950-performance.md#7-同-checkpoint-串行-restore-100-次)。

### 3.1 串行 restore 5000 次

一个沙箱、一个调用方、同一个 checkpoint 连回 5000 次，现场内存 16 MB + 文件 4 MB，每 10 次抽验一次。

| 指标 | 值 |
|---|---|
| 客户端墙钟 p50 / p99 / 最大 / 最小 | 9.58 / 18.2 / 21.7 / 8.35 ms |
| 服务端 `frozen` p50 / p99 | 6.03 / 13.6 ms |
| 服务端 `total` p50 / p99 | 8.75 / 17.3 ms |
| 每 1000 次分段 p50 | 9.57 / 9.62 / 9.52 / 9.57 / 9.63 ms，无漂移 |
| 每 1000 次分段 p99 | 16.2–19.2 ms |
| 异常 | 0 |

同一台新 920B 上，修复前的部署件 `4af2872c6` 在 2026-09-22 跑过 n = 100 的串行：p50 12.5、p99 38.7、最大 40.1、最小 11.4 ms。两轮样本量不同，只作背景。

这个负载没有每次再制造一档新改动，回滚集很小，低延迟不能代替 [§2](#2-分档基准与判定) 的分档回滚成本。

### 3.2 空闲后 restore

同一沙箱串行，循环“空闲 T 秒 → checkpoint cpB → restore cpA → 删 cpB”（测法见[第 16 章 §7](16-test-methodology.md#7-空闲后-restore-与串口的专项测法)），客户端墙钟 ms。右两列是旧 920B 2026-09-21 的 `4af2872c6`（长跑修复前），跨机只看趋势。

| 臂 | n | restore p50 | > 100 ms | cpB checkpoint p50 | 旧机 p50 | 旧机 > 100 ms |
|---|---|---|---|---|---|---|
| 空闲 0 s | 30 | 15.4 | 0 / 30 | 10.6 | 40.4 | 0% |
| 空闲 0.5 s | 30 | 19.0 | 0 / 30 | 12.8 | 42.3 | 0% |
| 空闲 2 s | 30 | 23.2 | 0 / 30 | 75.9 | 50.9 | 17% |
| 空闲 5 s | 30 | 25.1 | 0 / 30 | 77.9 | 76.4 | 30% |
| 空闲 10 s | 20 | 29.1 | 0 / 20 | 66.8 | 99.2 | 50% |
| 空闲 2 s 后**不拍** cpB 直接 restore | 30 | 80.9 | 0 / 30 | —— | 61.6 | 30% |
| guest 内常驻忙循环 | 30 | 27.1 | 0 / 30 | 76.3 | 56.0 | 7% |

有两件事要分开读：

- **空闲后的第一次 checkpoint 更慢。** 空闲 ≥ 2 s 时 cpB 的 p50 是 66.8–77.9 ms，空闲 0 s 时是 10.6 ms。
- **空闲后不先 checkpoint 直接 restore 更慢。** “不拍 cpB”那一臂的服务端分段是 `total` 77.8、`frozen` 73.7、`fc_rollback` 52.1、`materialize` 5.8 ms，其中 FC 的 `fc_quiesce` 47.1 ms，其他臂 `fc_quiesce` 为 0。

时间主要花在 FC 的 quiesce，根因未查，当前只作记录（[第 28 章](28-troubleshooting.md)）。

### 3.3 串口

10 段 × 180 s 单沙箱负载，restore 7383 / 7383 成功且逐项一致。每段串口未卡死、无停顿、无 > 2 s 的串口行缺口，串口行间隔最大 1.595 s。这组结果同时计入长跑的 restore 总数，见[第 21 章 §5](21-concurrency-and-longrun.md#5-两天-15-组长跑731877-次-restore-逐项一致)。

## 4. 写保护的运行期代价与平台差异

### 4.1 位图由谁供数

原生精确增量的新判据不选后端，只读位图。位图由谁供数，是 Firecracker 启动时 `setup_dirty_tracking` 决定的（[第 5 章 §4](05-dirty-tracking-and-hdbss.md#4-hdbss-怎么被启用)）。

| | 950（HDBSS） | 920B（无 HDBSS） |
|---|---|---|
| 位图怎么来 | CPU 硬件记脏，guest 写页不陷出 | KVM 写保护，每个干净页第一次被写陷出一次 |
| 谁付这笔账 | 几乎没有 | **所有开了跟踪的沙箱**，不管做不做快照 |
| 默认是否开跟踪 | 开（探到 KVM 能力 502） | 关 |
| 原生快照口径 | 精确增量 | 默认驻留判据（修复前口径）；`FC_TRACK_DIRTY_PAGES=true` 才精确 |

这条策略与 checkpoint 完全一致，用的是同一个开关（[第 5 章 §4.7](05-dirty-tracking-and-hdbss.md#47-默认值为什么跟着硬件走)）：**有 HDBSS 时精确增量几乎零副作用；没有 HDBSS 的机器上，“精确增量”与“不让所有沙箱付写保护代价”二选一，默认选后者。**

920B 上 `FC_TRACK_DIRTY_PAGES=false` 的实测（2026-09-11，旧 920B）：pause 日志命中 `dirty tracking is off`，memfile 回到 172 / 178 MB 的工作集口径，内存与文件校验全过。

本方案的 checkpoint 也跟这个开关走。920B 不设变量时 checkpoint 照样能做，只是每次都是全量；本章和第 21 章的 920B 数据全部在 `FC_TRACK_DIRTY_PAGES=true` 下测得。

### 4.2 两台机器的共同点和差别

两台机器代码路径逐行相同，写跟踪位图的内容也一致：[§6.1](#61-pb2py-三列并排) 中列“只读 192 MiB”一步，950 上 15.0 MiB、920B 上 14.6 MiB，差的是模板本底。差别只在写保护这笔运行期代价。

### 4.3 这笔代价测到了多少

代价的模型是 [第 5 章 §6.1](05-dirty-tracking-and-hdbss.md#61-软件写保护的代价模型)：一个快照周期内被写的 D 页带来约 D 次 VM-Exit。它在 920B 上的量值有以下边界：

- **没有单独的量值。** 920B 上没有做过“同一负载开跟踪和关跟踪”的 guest 写性能对照，本章的耗时全部含这笔开销，拆不出来。
- **能看到的间接差异没有拆开。** [第 19 章 §4](19-native-pause-resume.md#4-920b-分档结果与对照) 里，开跟踪的一轮 resume 比关跟踪的对照慢 25.1～36.0 ms，恢复后内存读也慢约 84 ms（256 MiB 档）。但两轮除了跟踪开关，header 粒度和代码都不同，不能把这些差值当成写保护代价。
- **950 侧不做这个对照。** 950 的安排只量 HDBSS 自身，不做软件写保护对照，所以 920B 与 950 的差值不能归因于 HDBSS（[第 22 章 §7](22-acceptance.md#7-已知项与缺口)）。950 上 HDBSS 自身的额外首写代价见[第 18 章 §8](18-950-performance.md#8-hdbss-专项默认-order-1-的启用证据与写密集实测)。

## 5. 与 checkpoint 叠加的代价

[第 14 章 §9](14-native-precise-increment.md#9-与-checkpoint-叠加累积位图) 的累积位图在 checkpoint / restore 路径上加了记账，在原生 pause 路径上加了一次并集。代价如下。

| 位置 | 多做了什么 | 实测（旧 920B，2026-09-18） |
|---|---|---|
| 全量 checkpoint 的冻结窗口内 | 拍之前多导出一次活跃脏图（每 GiB guest 内存 32 KiB 的位图文件） | 计时键 `save_live_bitmap`：21 次全量 checkpoint 全都出现，2.01~4.95 ms，p50 约 2.2 ms；另一次单独测量 0.918 ms。增量 checkpoint 42 次都没有这一步 |
| 增量 checkpoint 之后、restore 期间 | 读一个位图文件，与集合做一次按位并 | 内存里的位运算，未单独计时；restore 本来就要导出活跃脏图（这一步不是新增的） |
| 原生 pause 时 | 集合并进写跟踪位图 | 同上 |

`save_live_bitmap` 这个计时键在 restore 路径上一直都有，全量 checkpoint 上是新增的。计时键的全表见[第 27 章](27-observability.md)。这组计时由哪个脚本产生，原始记录没有注明，推定见[附录 B §16](B-920b-results.md#16-数据出处)。

还有一项不是开销，而是正确结果本来的样子：做过 checkpoint 的沙箱，原生 pause 导出的是**这一代启动以来**写过的全部页，而不只是最近一段。T39 的服务端日志（[第 16 章 §12.4](16-test-methodology.md#124-与-checkpoint-叠加后导出完整证明累积位图)）里，写跟踪位图本身只有 2.6k~5.1k 页，导出却有 31k~34k 页，差出来的约 28k 页（约 110 MiB）正是 checkpoint 清掉、由集合补回的部分。这个量与“从不 checkpoint、同样负载”的沙箱导出量同一量级，不是额外负担。

## 6. 体积：修复前后

| A 刚建好 | 118.0 / 4.6 / 118.0 | 154 / 4.1 / 154 | 5.5 / 5.5 |

| C 空转 | 122.0 / 3.9 / 122.0 | 162 / 4.1 / 162 | 4.5 / 4.5 |

读法：

- 修复前左列与右列逐行相等：原生 pause 就是按它导出的。D 行“只读”比 C 行多了约 200 MiB，说明读被算成了脏（[附录 C §5.1](C-evolution-and-cases.md#51-改-12-mib导出-148-mib)）。
- 中列在两台机器、两种后端下形状一致，都是“写入量加几 MiB 本底”，说明写跟踪位图本身是精确的，与后端无关。

### 6.3 `native_snapshot_bench.py`：六档

旧 920B，同一份脚本、同一张档位表（名义脏内存 / 名义脏文件，单位 MB）。“修复前”列是同机同 Firecracker 的前一轮（09-11），“修复后”列是 09-14 那一轮。cp0 含预热写入的 192 + 64 MB，是本底。pause 模式下每一档都是一次 pause → resume，也就是一代新进程。

| 档 | 名义内存 / 文件 | memfile 修复前 | memfile 修复后 | pause ms（修复后） | resume ms（修复后） |
|---|---|---|---|---|---|
| cp0 | 0 / 0 | 442 | 281.7 | 519 | 271 |
| cp1 | 12 / 4 | 432 | **38.4** | 260 | 226 |
| cp2 | 24 / 8 | 434 | **54.2** | 289 | 211 |
| cp3 | 48 / 16 | 440 | **87.5** | 309 | 203 |
| cp4 | 96 / 32 | 442 | **153.1** | 496 | 289 |
| cp5 | 192 / 64 | 450 | **287.6** | 684 | 301 |

- 修复前 memfile 恒在 440 MB 上下：每档恢复后脚本都把 192 MB 负载读一遍验证内容，这些页每代都被换入、被判脏（[第 14 章 §3.2](14-native-precise-increment.md#32-两个放大叠在一起每代新进程换入即脏)）。
- 950（HDBSS）上同一脚本修复前的一轮（2026-09-09～10，负载同样按“预热 + 原地覆写”构造、档位相同）形状一样：cp0–cp5 的 memfile 为 406 / 394 / 402 / 398 / 404 / 410 MB，恒在 400 MB 上下；同一轮 resume 端到端约 90 ms，恢复后第一次把负载整读一遍另需约 165 ms，这是懒加载推迟付的账。950 上修复后的数据见[第 19 章 §3](19-native-pause-resume.md#3-950-分档结果)。
- 修复后 memfile 等于该档写入量加二三十 MB 本底，随写入量线性。
- snapshot 模式（每代持久快照、另起新沙箱恢复）的 memfile 与 pause 模式一致（38.6 / 56.2 / 87.5 / 152.9 / 286.1 MB），本地存储里的实占与导出缓存相等，说明上传路径没有改变布局。
- 上传时间（pause 返回到存储目录文件落齐）从修复前的约 200 ms 降到 50~150 ms（09-14 那一轮为 50~100 ms），这是导出量变小的直接收益。
- pause、resume 两列修复前后都在同一噪声带（pause 数百 ms，resume 200~300 ms，snapshot 模式恢复端到端 0.2~1.3 s），看不出系统性差别。这两列的抖动主要来自另起沙箱时的网络槽位配置，与快照无关。

这份脚本在同一沙箱里预热到最大档，导出量带着本底，耗时列也不适合按档比较。

### 6.4 `native_snapshot_tiers.py`：每档独立沙箱

为了得到按档可比的结果，2026-11-06 用 `benchmark/native_snapshot_tiers.py` 在新 920B 上重测，每档新建 3 个沙箱，只放本档负载，内存与文件 3:1。完整的 pause、resume、读取耗时、`create_snapshot()` 路径和条件在[第 19 章 §4](19-native-pause-resume.md#4-920b-分档结果与对照)。下表摘 `repeat` 的导出内存，每档 n = 15，单位 MiB。

| 档（总改动 MiB） | 0 | 16 | 32 | 64 | 128 | 256 |
|---|---|---|---|---|---|---|
| 精确增量（`kvm-wp`） | 16.1 | 39.3 | 58.8 | 93.0 | 159.6 | 292.2 |
| 对照（`off`，驻留判据） | 144.0 | 168.0 | 186.0 | 218.0 | 282.0 | 418.0 |

对照是不含本方案 checkpoint / restore、不含 4 KiB 写跟踪差分的另一份构建，不是纯上游。各档导出内存少约 122～129 MiB，这个差值基本恒定。它与 [§6.2](#62-pb4py只换判据的预测) 的归并地板是同一量级的现象，但两组数据的机器和负载都不同，不互相代入。

## 本章要点

- 920B 用 KVM 写保护，每个干净页第一次写陷出一次；950 用 HDBSS，硬件记脏。两边数字不相减、不算倍数。
- 新 920B、`8ea5322bf`、单沙箱热缓存下，18 档 checkpoint 全部达标，restore 只有 512 MB 极限档超线（p50 108.2 ms）。
- 混合档拟合为 checkpoint ≈ 14.72 + 0.3228 × MB、restore ≈ 19.12 + 0.1876 × MB，restore 约 431.0 MB 碰线。
- 同一 checkpoint 串行 restore 5000 次，客户端 p50 / p99 为 9.58 / 18.2 ms，无漂移。空闲 2 s 后不先 checkpoint 直接 restore，p50 80.9 ms，其中 `fc_quiesce` 47.1 ms，根因未查。
- 没有 HDBSS 的机器上，精确增量要显式打开跟踪，代价落在所有开了跟踪的沙箱上。这笔运行期代价在 920B 上没有单独量值。
- 累积位图在全量 checkpoint 冻结窗口里多一步 `save_live_bitmap`，p50 约 2.2 ms，增量 checkpoint 没有这一步。
- 修复后写跟踪位图与实际导出逐行相等：只读 192 MiB 从 358 MiB 降到 12.7 MiB，只改 12 MiB 从 176 MiB 降到 20.3 MiB。
