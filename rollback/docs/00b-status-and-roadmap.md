# 00b · 能力现状与后续方向

## 本章目标

读完本章，你应该能：

1. 判断当前 checkpoint / restore 的支持范围与设计边界；
2. 区分已知问题、待验证项与可选增强；
3. 找到每项限制或候选方向的详细分析、实现说明和验证证据。

本章是全书的功能与状态清单（Feature Ledger），汇总截至 **2026-10-15** 的手册记录。源码讲解基准、MR 交付基线及部署身份条件沿用 [README](README.md)；取得 MR 版或 RPM 时，仍须核对实际包含的能力。
已完成的修改与代表 commit 见 [00a](00a-post-mr-evolution.md)，本章集中回答当前能做什么、还有什么问题、以后可以做什么。

阅读时区分四类内容：

- **设计边界**：当前使用契约与明确的取舍，使用方需要按这个规则工作。
- **待修复问题**：已有异常或性能问题记录，处理状态可能是待定位、暂缓或运维处置；列入清单不表示已安排修复。
- **待验证项**：覆盖、证据或测量不足，不能写成已经通过，也不能仅凭缺少验证判为缺陷。
- **可选增强**：尚未实施的能力或优化候选，需要先明确需求、收益与实现前提。

候选方向没有承诺排期；表中顺序不表示优先级。判定性数字与原始证据继续在第 17、21、22 章维护，本章通过链接引用。

## 1. 当前能力与设计边界

| 能力或范围 | 当前状态与使用约束 | 详细说明 |
|---|---|---|
| 活沙箱原地回滚 | 已支持；内存、vCPU、中断控制器、设备逻辑状态、根盘及进程一起恢复，沙箱 ID、IP 和宿主资源保留 | [24 §1](24-semantics-and-limits.md#1-restore-回滚回什么)、[09](09-in-place-rollback.md) |
| 增量与树形历史 | 已支持 checkpoint / restore / list / delete，可在保留的分支间切换；不跟踪脏页时退回全量，空间与耗时增加 | [23](23-quickstart.md)、[06](06-memory-diff-tree.md)、[26](26-deployment-prerequisites.md) |
| 外部副作用 | 设计边界；外部数据库、API、消息与上传文件不会随 guest 回退，业务需自行幂等或去重 | [24 §2.1](24-semantics-and-limits.md#21-外部世界) |
| 连接与在途调用 | 设计边界；跨 restore 的 TCP 连接需要重连，在途命令和文件请求可能被中断，已发送响应头的流会截断 | [24 §2.2](24-semantics-and-limits.md#22-tcp-连接跨越-restore-的一律作废要重连)、[25 §5](25-errors-timeouts-concurrency.md#5-多个调用方与并发) |
| 时间与随机状态 | 设计边界；单调时钟倒退，墙钟在成功返回前校正，用户态缓存的随机状态会回退、需按业务需要重新初始化 | [24 §2.3](24-semantics-and-limits.md#23-时钟)、[24 §2.4](24-semantics-and-limits.md#24-随机数与被回滚这件事本身) |
| 生命周期与持久化 | 设计边界；checkpoint 仅在所属活沙箱当前这一代有效，不跨重启、迁移或原生 pause / resume；拷走目录也不能独立恢复。离场与持久化使用原生 snapshot | [24 §3](24-semantics-and-limits.md#3-checkpoint-什么时候失效)、[14](14-lifecycle-reasoning.md)、[18](18-native-and-checkpoint-together.md) |
| 并发调用 | 已支持跨沙箱并发；同沙箱 checkpoint / restore / delete 串行，等待与中断按接口契约处理 | [25 §5](25-errors-timeouts-concurrency.md#5-多个调用方与并发)、[22](22-long-run-and-concurrency.md) |
| 删除与空间回收 | 已支持隐藏、合并与回收；有依赖的数据删除后不立即释放。滚动保留的收敛依赖脏页跟踪、合并启用且处理跟得上；字节上限检查当前占用，不是严格空间预留 | [24 §4](24-semantics-and-limits.md#4-删除与空间回收用户视角)、[27 §4](27-configuration-and-capacity.md#4-容量规划) |
| 设备拓扑 | 设计边界；恢复要求快照与运行对象的拓扑一致，balloon / vsock / vhost-user block 明确拒绝 | [09 §4](09-in-place-rollback.md#4-validate_topology为什么必须一致) |
| restore 失败 | 按提交点分级；多数失败保持沙箱可用，提交点后发生“撕裂”时只能销毁重建 | [12](12-failure-semantics.md)、[25](25-errors-timeouts-concurrency.md) |

可导出 checkpoint 或跨重启账本加载属于 §3 的可选增强，当前使用仍遵循上述生命周期契约；单独补齐账本加载不能恢复已消失的虚机与设备资源。

## 2. 已知问题与验证缺口

本表汇总影响使用与后续判断的主要事项。完整现象、数字及历史轮次见 [21 §7](21-benchmarks-and-compliance.md#7-已知项与缺口)、[22 §6](22-long-run-and-concurrency.md#6-结论与剩余长尾)。其中的 920B 历史结果不自动适用于 950。

| 项目 | 类别与当前状态 | 影响、处理及证据入口 |
|---|---|---|
| delete 同步合并 | 待修复问题：性能优化暂缓 | 合并延长 delete 耗时；需要时可改后台异步合并，见 §3 及 [22 §6.2](22-long-run-and-concurrency.md#62-已知未解决) |
| conntrack 清扫长尾 | 待修复问题：已有方案，暂不实施 | 清扫成本受整张宿主表影响，可能进入冻结关键路径；按 ct mark 过滤的方案已设计，2026-09-30 决定暂不实施，见 [22 §4.6](22-long-run-and-concurrency.md#46-conntrack-清理占了冻结窗口) |
| 视图块数与装配成本增长 | 待验证项；相关优化为可选增强 | 长跑末尾块数尚未饱和，需要更长实测确认走势；区间编码候选见 §3。随真实回滚量增加的写回成本另行判断，见 [22 §6.2](22-long-run-and-concurrency.md#62-已知未解决) |
| 空闲后操作变慢、首个增量的两种耗时形态 | 待修复问题：触发条件或根因待定位 | 保留现象记录，需要针对负载复现；一次短测不能关闭概率项，见 [21 §7](21-benchmarks-and-compliance.md#7-已知项与缺口)、[22 §6.3](22-long-run-and-concurrency.md#63-到-950-上要重测什么) |
| netns 泄漏、客户端连接异常、偶发 GC 长暂停 | 待修复问题：分别为上游运维处置、客户端记录、未归因 | 各项影响范围与处理不同，不能归为同一个回滚缺陷，见 [22 §6.2](22-long-run-and-concurrency.md#62-已知未解决)、[29 §9](29-troubleshooting.md#9-网络槽位netns泄漏) |
| 950 长期运行与专项覆盖 | 待验证项 | 已有默认功能、短时并发与混合短稳态证据；小时级长跑、滚动保留、资源收敛以及重启 / 注入 / 配额等专项仍需按目标结论补测，见 [22 §6.3](22-long-run-and-concurrency.md#63-到-950-上要重测什么)、[21 §2.5](21-benchmarks-and-compliance.md#25-950-默认功能回归2026-10-13) |
| 950 部署身份、原始数据与 HDBSS 覆盖 | 待验证项 | 各轮身份与回传材料分别核对；默认 order 1 已有实测，其他 order 比较待补。HDBSS 与软件写保护对照已决定不做，见 [21 §7](21-benchmarks-and-compliance.md#7-已知项与缺口) |
| 跨树回滚与 HDBSS 武装时序 | 待验证项 | 前者已有单元测试，缺端到端用例；后者由调用点位置保证，缺断言，见 [21 §7](21-benchmarks-and-compliance.md#7-已知项与缺口) |
| 封层刷屏障与重复刷盘 | 待验证项：V1–V3 均未验证 | 先确认运行内核行为并测量耗时与读请求，再决定是否改代码；现状、源码依据和测法见 [B §5.1](B-extending.md#51-待验证项) |

## 3. 候选开发方向

本表承接原附录 B §5 的方向清单，统一维护候选项与状态。难度为原清单的粗估；实施前仍要验证收益、调用契约与失败语义。

| 方向 | 预期收益与前置条件 | 当前状态 / 难度 | 机制与证据入口 |
|---|---|---|---|
| 后台异步合并 | 减少 delete 同步等待；需要设计与 checkpoint / restore / delete 的并发及回收协调 | 可选增强；需要时再做 / 中 | [22 §4.10](22-long-run-and-concurrency.md#410-删除同步合并delete-变慢)、[06](06-memory-diff-tree.md) |
| conntrack 后台清扫再提速 | 降低宿主表规模对冻结窗口的影响；可先按生产数据评估单地址过滤阈值，进一步方案采用 ct mark 过滤 | 可选增强；ct mark 方案已设计、暂不实施 / 中 | [22 §4.6](22-long-run-and-concurrency.md#46-conntrack-清理占了冻结窗口) |
| 层侧车改为区间编码 | 减少逐块读取、解码成本；涉及 `.meta` 盘上格式变化，需处理格式兼容 | 可选增强；待评估 / 中 | [22 §6.2](22-long-run-and-concurrency.md#62-已知未解决)、[07](07-disk-layering.md) |
| 可导出的 checkpoint | 层栈压平并物化模板底座，提供独立导出接口；保留当前 checkpoint 默认路径 | 可选增强；待评估 / 中 | [14](14-lifecycle-reasoning.md)、[18](18-native-and-checkpoint-together.md) |
| 账本跨重启加载 | 补齐按事务顺序的 `fsync`、读取、陈旧条目回收及格式迁移；恢复账本之外还需处理虚机与设备生命周期 | 可选增强；待评估 / 中 | [13](13-state-concurrency-durability.md)、[14](14-lifecycle-reasoning.md) |
| 按沙箱按需武装脏页跟踪 | 将 orchestrator 统一配置细化到沙箱；需在创建时获知该沙箱是否使用 checkpoint | 可选增强；待评估 / 中 | [05](05-dirty-page-tracking-and-hdbss.md)、[26](26-deployment-prerequisites.md) |
| 层文件的全零块回收 | 当前恒等映射不剔除全零块；需区分“显式写零”与“沿用父层”，保持读取语义 | 可选增强；待评估 / 中 | [07](07-disk-layering.md) |
| 视图层列表改为引用父代 | 减少每条目完整记录全部层的记账成本；需保持历史合并与回收语义 | 可选增强；待评估 / 中 | [07](07-disk-layering.md)、[13](13-state-concurrency-durability.md) |
| 跨树回滚端到端验证、HDBSS 武装时序断言 | 补齐 §2 对应的验证缺口 | 待验证项；待补 / 低 | [19](19-testing-and-functional-verification.md)、[05](05-dirty-page-tracking-and-hdbss.md) |
| 跟上游合并 | 持续维护分叉；同步后重新生成部署补丁并验证组件配对 | 持续维护 / 持续 | [B §1](B-extending.md#1-代码在哪)、[源码开发与出包流程 §11](../../deploy-docs/08-源码开发与出包流程.md#11-checkpoint--restore-代码的来源是-deltabox-dev再生成走脚本) |

V1–V3 的具体测量任务保留在 [B §5.1](B-extending.md#51-待验证项)。实施任何候选改动前，按 [B §3](B-extending.md#3-改动自查清单) 检查不变量，按 [B §4](B-extending.md#4-怎么验证一次改动) 验证。

## 4. 如何维护本章

- 当前能力或边界变化时，先更新相应实现章节与第 24、25 章的使用契约，再同步 §1。
- 新发现问题或补齐验证时，在第 21、22 章记录条件、证据和结论，再同步 §2 的类别与状态；问题解决后可转到 [00a](00a-post-mr-evolution.md) 的演进入口。
- 候选方向的名称、前置条件与实施状态在 §3 维护。详细方案、测量和验证仍放在对应章节，其他章节通过链接引用本章。
- 未确定的优先级、负责人和目标版本不预填；只有明确安排后才补充，避免把候选清单当成交付承诺。

## 本章要点

- 当前能力与使用约束见 §1，详细契约仍在第 24、25 章。
- 已知问题与验证缺口见 §2；记录现象、缺少验证与确认缺陷需要分别判断。
- 候选方向统一在 §3 维护，尚未实施的方向不改变当前支持范围，也不代表已经排期。
