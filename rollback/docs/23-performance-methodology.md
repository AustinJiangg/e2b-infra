## 0. 本篇要回答的问题

1. 「checkpoint 200 ms」到底约束的是哪一次调用、哪个钟、哪个统计量？
2. 为什么判定按**脏页量**分档，而不是按沙箱内存大小？
3. 为什么全量 checkpoint 单列、不参与判定？
4. 造负载为什么是最容易做错的一步，三种失真各是什么、怎么消掉？
5. 四个脚本分别回答什么问题，为什么不能互相替代？

## 1. 指标口径

### 1.1 客户给的是一个上限，不是一个口径

「checkpoint ≤ 200 ms」这句话里缺六件东西：**谁的钟**（客户端还是服务端）、
**哪一次**（第一次还是第 n 次）、**哪个统计量**（平均、中位数还是最坏值）、
**什么负载**（改了多少）、**什么恢复形态**（原地回滚还是另起沙箱）、
**什么机器**。任何一项换一种取法，同一批数据都能得出相反的结论 ——
所以判定必须先把这六项钉死，而且钉在**对我们最不利**的那一侧。

下表是全书的判定口径。**第 25 篇的每一张判定表都按这张表读**，
本篇之后各节讲的都是「怎么把这张表测出来」。

### 1.2 口径定义表

| 维度 | 本书口径 | 为什么这么定 |
|---|---|---|
| **量什么钟** | **客户端墙钟**：SDK 调用发出到返回（用 `time.monotonic()` 夹住 `sbx.checkpoint.create()` / `sbx.checkpoint.restore()`），含网络往返、代理、服务端全部工作 | 三个钟里最大的一个，**最保守**；也是客户在自己机器上就能复测的唯一一个 —— 另外两个要读宿主机上的文件 |
| **对哪类操作 · checkpoint** | **增量 checkpoint**：一个沙箱的第 2 代及以后，服务端自报 `mem_mode=incremental` | 客户指标约束的是高频回退里的每一次；树根全量每个沙箱只发生一次 |
| **对哪类操作 · restore** | **原地 restore**：沙箱 ID 与 Firecracker 进程都不变。分**浅集**（回退一步）与**深集**（回到链根）两列分别判定 | 一跳的代价取决于起点与终点之间差了多少，不是目标那一代自己多大（[第 8 篇 §4.2](08-memory-diff-tree.md#42-定义)）。浅深两列把「回滚集大小」和「链深」拆开 |
| **统计量** | **p50 判定，p99 并列**；报告里同时给 p90 / max / n | p50 回答「通常多久」，p99 回答「最坏还能不能接受」。单次会抖，节点刚重启后的第一轮尤其明显 —— 见过同一档差 2~4 倍，所以任何单次数字都不作判定 |
| **分档变量** | **脏页量**：总改动量 0 / 16 / 32 / 64 / 128 / 256 MB，按 **3:1** 拆成内存份与文件份 | 增量的代价随「改了多少」走，不随沙箱内存大小走。「不同内存快照大小」在本方案里就翻译成这一列 |
| **样本构造** | 每档**一个全新沙箱**，链深一致地从 1 长到 33（预热 3 + 计入 30） | 链深是另一个会影响耗时的变量，每档各起一个沙箱才能让它在档与档之间**配平** |
| **全量 checkpoint** | **单列，不参与判定**。样本 = N 个全新沙箱各取第一次 checkpoint | 树根要自包含，等于写整份 guest RAM（[第 8 篇 §6.3](08-memory-diff-tree.md#63-全量根为什么是默认)），是**每个沙箱一次性**的成本，不落在高频回退的热路径上 |
| **冻结窗口** | **解释项**：列在判定表旁边，说明墙钟里有多少是虚机真停住的，**不用来判定** | 它比墙钟小（0 MB 档只占六成），拿它判定等于给自己放水；但它才是业务感受到的停顿（[第 00 篇 §5.1](00-design-overview.md#51-冻结窗口是唯一对业务可见的代价)），是解释「时间花在哪」的入口 |
| **条件标签** | 每个数字随身携带：机型 / 脏页后端（hdbss、kvm-wp、off）/ 产物文件系统与介质（真盘还是 loop）/ 模板规格 / 二进制版本 | 同样的代码在不同脏页后端上差好几倍。不带条件的数字没法跟另一次跑比，也不能跟别的机器上的数字相减 |
| **判据前提** | 该轮所有增量的 `mem_mode` 必须是 `incremental`；出现 `full` 整轮作废 | 这是本方案最典型的静默失效：脏页跟踪没开，每次悄悄整份拷内存，**测试全过但测的根本不是增量** |

达标线本身照抄客户：

| 操作 | 达标线 | 判定对象 | 不判定的部分 |
|---|---|---|---|
| checkpoint | ≤ 200 ms | 增量 checkpoint，客户端墙钟 p50（p99 并列） | 树根全量（单列说明） |
| restore | ≤ 100 ms | 原地 restore，客户端墙钟 p50（p99 并列），浅集与深集分列 | 另起新沙箱的恢复形态（那是原生 snapshot 的路径，见[第 20 篇](20-vs-native.md)） |

### 1.3 三个钟为什么只有一个能判定

[第 17 篇 §1](17-observability-and-verification.md#1-三个时钟) 讲了三个钟的分工：
客户端墙钟说「等多久」、冻结窗口说「业务感受到的停顿」、宿主分阶段说「时间去哪了」。
判定只用第一个，理由是**可复测性**加**保守性**：

- 冻结窗口要在 guest 里跑采样器才测得到，客户复现不了；而且它天然更小，
  用它判定是在挑一个对自己有利的口径。
- 宿主分阶段要读宿主机上的 `timings.json`，不在宿主机上跑就整列缺省。
  它回答的是「没达标该改哪」，不是「达没达标」。

三者的包含关系是固定的：**墙钟 ⊇ 冻结窗口 ⊇ 各分段之和**。所以墙钟达标，
另外两个必然达标；反过来不成立。第 25 篇的判定表把冻结窗口列在墙钟旁边，
角色是解释而不是判据 —— 例如 ext4 方案在 16 MB 以上各档，墙钟里 89–97% 都是冻结
（920B · kvm-wp · loop ext4 · 2 GB 模板），这句话说明的是
「这条路上没有『虚机还在跑』的部分可省，要更快只能让暂停窗口本身变短」。

### 1.4 为什么按脏页量分档

「不同内存快照大小下的性能」是一个自然的提法，但对本方案是问错了变量。
增量 checkpoint 写出的是**本代脏页**，成本模型是 O(本代脏页)，与虚机规格无关
（[第 8 篇 §7](08-memory-diff-tree.md#7-成本模型)）。一台 8 GB 沙箱只改了 4 MB，
它的 checkpoint 和一台 2 GB 沙箱改 4 MB 是一样的代价。
所以「内存快照大小」这个自变量在本方案里被翻译成**脏页量档位**，
判定表按档给 —— 这也是唯一能让客户按自己的负载对号入座的分法。

沙箱内存大小只影响两处，都不在判定范围内：树根全量的耗时（写整份 RAM），
和产物的逻辑体积（稀疏文件的表观大小恒等于整份 RAM）。

### 1.5 为什么全量单列

树根必须自包含，否则一条链没有可解析的底（[第 8 篇 §8](08-memory-diff-tree.md#8-全量与增量怎么选)）。
它的代价是写整份 guest RAM —— 920B 上 2 GB 模板实测 p50 1.511 s
（920B · kvm-wp · loop ext4 · 2 GB 模板），比任何增量档都高一个数量级。
但它**每个沙箱只发生一次**：一个沙箱做 100 次 checkpoint，
这 1.5 s 摊下来是 15 ms/次，而且不在「回退到上一步」这个动作的路径上。

把它算进判定会得到一个既不反映客户体验、也不反映实现质量的数字。
所以它单列一行，标注「一次性成本，不参与判定」，同时充当**增量数字的参照系** ——
没有这一行，「增量快 30 倍」这句话没有分母。

## 2. 负载构造：三种失真

判定表的第一列是「脏页 N MB」。要让这一列成立，**标签上的 N 必须等于服务端实际搬运的量**。
这是整套性能测试里最容易做错的一步，比调哪个 API 难得多。

### 2.1 失真一：分配成本混进档位

第一次申请并首次写一块新内存，内核要清零、要建页表。这笔开销跟「改」没关系，
但如果每档都重新分配容器，它就被算进了档位。

### 2.2 失真二：写放大

这一条在本项目里真实发生过。早期的内存负载是一句 shell：

```bash
eval "mem_X=\"$(head -c 192M /dev/zero | tr \\0 x)\""
```

命令替换先缓冲一份，`eval` 赋值再复制一份，缓冲区增长过程中 `realloc` 留下中间态，
内核给每块新映射清零，上一代释放之后重新缺页。**950 上实测放大约 5 倍**：
档位标 256 MB，量到的内存差分是 1087 MB。档位标签标的是「请求改多少」，
量到的是「实际脏多少」，两者差四倍，表就没法看了。

（这句 shell 来自跨实现对照那一侧的脚本，本方案的两份脚本从一开始就不这么造负载。
对照脚本为此重写了负载生成，见[第 24 篇 §2](24-cross-implementation.md#2-对照脚本为什么存在)。）

### 2.3 失真三：负载放错层

**快照只能带回它覆盖范围内的东西。负载放在覆盖范围之外，测出来的既是零成本，
也是假通过。** 本方案与原生都在宿主机上对整个 guest RAM 做快照，
于是有一个很干净的分工：

| 负载写在哪 | 脏的是什么 | 在哪一列出现 |
|---|---|---|
| `/dev/shm`（tmpfs） | **tmpfs 的页就是 guest RAM 的页**，且不落块设备 | 只进内存增量 |
| 根文件系统（`/bench-root`） | 磁盘写层（[第 10 篇 §3](10-disk-layering.md#3-seal不搬运任何数据的换层)） | 进文件增量，**同时**在内存里留一份页缓存 |

这就是两份脚本都把内存负载放在 `/dev/shm` 上一个文件、把文件负载放在根文件系统上
另一个文件的原因：两半可以分别控制、分别验证。
（进程级快照那一套只认进程地址空间，这一招在那边不成立 ——
属于[第 24 篇 §3](24-cross-implementation.md#3-负载必须放在快照看得见的地方)。）

### 2.4 解法：预热 + 原地覆写

两份脚本最后都收敛到同一个两步法。`checkpoint_bench.py` 的 `warm()` 与 `dirty()`
就是这两步，它的注释写得很直白：

> 把两个文件一次撑到各自的最大档位。这一代的成本（分配 + 首次写满）不计入任何档位。
>
> `conv=notrunc`：只覆写前 N 兆，不动文件大小 —— 体积在预热那一代就定死了，
> 这里量的才是「改了多少」而不是「分配了多少」。

`conv=notrunc` 是整件事的要害：没有它，`dd` 会先把文件截断成零字节再写 N MB，
于是文件大小每档都在变、每档都在重新分配，失真一原样回来。
用 `/dev/urandom` 而不是 `/dev/zero` 同样是有意的 —— 全零页会被稀疏文件、
去重、压缩各层特殊对待，随机数据量到的是最坏也是最诚实的情况。

预热那一代自己也建一个 checkpoint（`bench.snap("W", "warm", maxmb)`），
它承担全部分配成本，不属于任何档位。

### 2.5 文件那半故意不用 `O_DIRECT`

文件负载是**普通缓冲写 + sync**。脚本的 docstring 给了理由：

> 真实用户怎么写我们就怎么写：数据先进 guest 页缓存再刷到虚拟盘，所以一份文件写会
> **同时**出现在内存增量（页缓存那些页）和文件增量（落盘的块）里。这不是测量误差，
> 是页缓存的本性，实测两列会把它如实摆出来。

于是读表时有一个固定预期：**实测内存 ≈ 名义内存 + 名义文件，实测文件 ≈ 名义文件**。
偏离这个关系就说明负载构造出了问题，值得先查再读时间。

（验证阶段反过来：读回来比对内容时**必须**加 `iflag=direct` 绕过 guest 页缓存，
否则读到的可能是缓存里的旧内容。封存写层丢失那个 bug 第一次验证就是这样假通过的 ——
属于[第 22 篇](22-functional-tests.md)。）

### 2.6 3:1 从哪来

总改动量按内存:文件 = 3:1 拆分，理由写在 docstring 里：
「沙箱里跑代码的真实负载通常改内存远多于改文件」。
所以 256 MB 档实际是内存 192 MB + 文件 64 MB。这个比例可以用 `--split` 改，
但**判定表固定用 3:1** —— 换了比例的数据属于另一条曲线，不能和判定表混排。

## 3. `checkpoint_bench.py`：时机成本与直接量产物

交付态脚本，零依赖、可以单文件拷到目标机上跑。它回答两个别处不回答的问题：
**快照时机值多少钱**，以及**服务端到底写下了多少**。

### 3.1 一条链，三段

`Bench` 类的注释一句话概括了结构：「一个沙箱，一条检查点链：g0（全量树根）→ 预热 →
两遍档位 → 逐级退回」。全部代都长在同一条链上，最后从链尾一路退回 g0，
restore 的档位曲线顺带拿到。

### 3.2 两遍拍：① 减 ② 就是时机成本

同一套档位拍两遍，**唯一区别是什么时候拍**：

| 遍 | 做法 | 口径 |
|---|---|---|
| ① `now` | 写完立刻拍 | **最坏情况上界**。刚写的文件数据正被宿主内核往盘上刷，会和写 `mem_diff` 抢磁盘；NBD 管道里还有在途数据要排空 |
| ② `settle` | 写完先 `sync` + 歇 1 秒再拍 | **日常口径**，贴近「写完跑了一会儿才拍」 |

两段负载完全相同，所以 **① 减 ② 就是「写完立刻拍」这个时机的成本，
不是快照机制的成本**。`settle()` 的注释解释了为什么用主动 `sync` 而不是干等：
内核平时按自己的节奏刷（脏页过期约 30 秒），干等太慢，主动 `sync` 等价于
「已经过去了一会儿」，而且只刷脏页、无破坏性。

这是判定表之外的一个重要修饰：客户如果在写完的同一毫秒就 checkpoint，
拿到的是 ① 那一列；正常使用拿到的是 ② 那一列。

### 3.3 直接量服务端产物，不靠推断

`measure()` 与 `alloc()` 直接去产物目录上量：

- **内存**：这一代 `mem_diff` 的 `st_blocks × 512`。差分是稀疏文件，
  **表观大小是整个地址空间，实占才是真写下去的量**。
- **文件**：`layers/` 里这一代新出现的封层文件的实占之和。

这一列的价值是**把档位标签和服务端行为对上账**：名义 256 MB、实测 1087 MB
那种放大（§2.2）一眼就能看出来。每代存完整镜像的方案没有按代的 `mem_diff`，
那一格就空着 —— 脚本注释的原话是「空着比给一个错的数强」。

### 3.4 退一代的代价归上一行

`unwind()` 的注释是这条曲线的读法：

> **退一代的代价 = 这一跳要撤销的量**，也就是被退掉的那一代建之前弄脏的量 ——
> 不是目标那一代自己弄脏了多少。所以每一跳的档位标签取自被退掉的那一代。

每一跳还要读 `/dev/shm/gen` 的代号，确认真落到了目标代；
落错就记进 `bench.bad`，整轮返回非零。**耗时数字只有在落对了代的前提下才有意义。**

restore 表里另有一列「读盘」，取自 `timings.json` 的
`materialize_disk_read_mb` 与 `fc_rollback_disk_read_mb`
（服务端两个进程 `/proc/<pid>/io` 的 `read_bytes` 差值）。
它存在的理由值得单独记：

> 没有这一列，一次真读了盘的恢复和一次没读的长得一模一样，只是慢些，
> 「恢复成本与链深无关」也就分不清是结论还是「链正好还热着」。

### 3.5 它的定位：每档只测一次

这个脚本每档只跑一次，**不给分位数**。docstring 明确划了界：
「要分位数和分布，用 `rollback/test-950/bench-ckpt.py`」。
所以第 25 篇的判定表不由它产出 —— 它产出的是时机成本、产物实测、
以及一条能在客户机器上五分钟跑完的完整曲线。

## 4. `bench-ckpt.py`：分布、冻结窗口、连打

开发态脚本，两套方案通用。它和 `timing.py` 的分工写在 docstring 里：
`timing.py` 回答「对不对、是不是 O(脏页)」，这个脚本回答「到底多久」，
**给的是分布，能拿去对性能指标、能给客户看**。第 25 篇的判定表由它产出。

### 4.1 A：全量基线，每个样本一个新沙箱

> 每个沙箱的第一次 checkpoint 必然是全量（没有基线可增量）。开 N 个新沙箱各取一次，
> 得到全量的耗时与体积。**没有这条，增量的数字没有意义。**

为什么必须是 N 个新沙箱而不是同一个沙箱做 N 次：一个沙箱只有一次全量。
要拿到全量的分布，只能付 N 次建沙箱的代价。

### 4.2 B：每档一个新沙箱，把链深配平

> 每档**开一个新沙箱**，链深从 1 长到 reps，各档完全一致 ——
> 这样「链深」这个变量在档与档之间是配平的，档之间才可比。

默认 `--warmup 3 --reps 30`，前 3 次丢弃、后 30 次计入，链深固定长到 33。
`df` 基线取在预热之后：预热里必然有一次全量 2 GB，
「否则那 2 GB 会被摊进这一档的『每次新增物理空间』里」。

每档另做一次**漂移自查**：前 1/3 的 p50 对后 1/3 的 p50。链在变深、盘在变满，
这两个数偏离就说明这一档内部本身在漂，p50 不再代表整档。

### 4.3 C：冻结窗口怎么测

`freeze_probe.py` 是推进 guest 里跑的一个 ~2.5 kHz 单调时钟采样器。原理：

> 虚机被 checkpoint 暂停时，guest 里的一切都停住，包括这个采样器 ——
> 于是在它的时间序列里留下一个洞。洞的宽度就是**虚机真正被冻结的时长**。

采样率是权衡出来的：「再高就变成忙等，会跟被测负载抢 CPU；再低就分辨不出几毫秒的抖动」。
采样器自己只写一个预分配好的数组（几十 KB），不产生额外脏页、不刷盘 ——
否则它会污染低档位的脏页量。同理，探针**只启动一次**：
「python 解释器启动本身要弄脏十几 MB，放进窗口里会污染低档位的脏页量」。

这个测法自带分辨率下限，所以每档先跑一遍**底噪**：同样的弄脏节奏但**不做 checkpoint**，
取采样器观测到的最大间隔。判据是 `separated = min(冻结) > 2 × 底噪`，
报告里标成「可区分 ✓」或「⚠ 与底噪不可区分」。
**冻结值必须明显高于底噪才作数** —— 否则量到的是采样器自己的抖动。

一个读表时必须注意的点：C 这条主线跑的是**另一个沙箱、另一条更浅的链**
（一次 seed + `--freeze-reps` 次，默认 8 次），所以它那张表里的「客户端墙钟 p50」
和 B 段档位表里的墙钟**不是同一批样本**，两者不可混引。
920B 那轮 0 MB 档就差了一倍多（13.4 ms 对 29 ms，
920B · kvm-wp · loop ext4 · 2 GB 模板）—— 差的正是链深，见 §6。

### 4.4 restore：浅集与深集

每档建完链之后测两种跳：

| 跳法 | 做法 | 测的是什么 |
|---|---|---|
| **浅集** | tip ↔ tip−1 往返 ×10 | 路径恒为 1 个纪元，回滚集小；差异只在起点深度 |
| **深集** | tip ↔ root 往返 ×2 | 路径 33 个纪元，回滚集是全链并集 |

每跳都读回 `/dev/shm/mk` 的代号比对，不符就计进 `restore_mismatches`，
整轮判 `BENCH FAIL`。restore 的墙钟基本就等于停机时长
（整个虚机被换掉），所以这一条不另外测冻结窗口。

### 4.5 E：60 秒持续连打

**单次快不等于扛得住连打。** 这一段不停 checkpoint 60 秒（默认每次弄脏 32 MB），
报速率、p50/p99、以及**前 1/3 p50 对后 1/3 p50**。垫底那次全量单独剔出去，
「2 GB 的耗时和体积混进来会把整段统计带偏」。

920B 上这一段抓到了本方案目前最明确的一处劣化：ext4 方案 ×2.81、XFS 方案 ×1.7
（920B · kvm-wp · loop ext4 / loop xfs · 2 GB 模板）。
`degradation > 1.5` 时报告会自动写上「单次的数字不能直接外推到高频场景」。
数字与含义在[第 25 篇 §7](25-results-and-compliance.md#7-已知劣化与含义)。

## 5. `timing.py`：O(脏页) 与链深解耦

这个脚本不产出判定数字，产出的是**两条结构性结论**。

**A 段** 逐代 create，脏页 0 / 64 / 256 / 512 MB 各一代，
同时量 `df` 增量。它回答两件事：create 是不是 O(脏页)、
盘上是不是只多花了脏页那么多空间。后者在 XFS 方案上顺带检验 reflink 有没有生效 ——
克隆没生效就会变成整份复制，`df` 立刻暴露。

**B 段** 链深对照 5 / 20 / 50 代各一条链，**每代写脏不同的 4 MB**
（错开 `seek`），这是内容解析的最坏情况：没有任何后代覆盖它。
关键是它把「回滚集大小」和「链深」解耦：

| | 路径纪元数 | 变的是什么 |
|---|---|---|
| 深集 tip↔root | N 个 | 回滚集随链深一起涨，两个变量绑在一起 |
| 浅集 tip↔tip−1 ×5 | 恒为 1 个 | **只有目标所处的深度在变** —— 这才是链深本身的成本 |

实测 5 / 20 / 50 代**没有趋势**，原因在[第 8 篇 §7.1](08-memory-diff-tree.md#71-恢复为什么不随链深变慢)：
链深只影响位测试次数，真正的 I/O 只发生在命中的那一次。
所以本方案**不需要周期性压平历史**。

## 6. `probe-ramp.py`：一个判别式设计

§4.5 的连打劣化留下一个问题：爬升到底是「链变深」还是「写得多」？
在那个测法里两个变量同步增长，分不开。

判别式很简单：**做同样多次 checkpoint，但把每次的脏页量拉开**。

| 档 | 代数长得 | 字节写得 |
|---|---|---|
| 脏页 0 MB × 400 次 | 快 | 少 |
| 脏页 32 MB × 400 次 | 中 | 中 |
| 脏页 256 MB × 150 次 | 慢 | 多 |

> 如果爬升是**代数**驱动的，三条曲线按「第几代」对齐时应当重合；
> 如果是**写入量**驱动的，按「累计写了多少 GB」对齐时才重合。
> 两种归一化各算一遍斜率，看哪一种把三条曲线收拢，就是哪一个。

脚本把两种归一化的「三档之间相差几倍」都算出来，
`spread_per_gen < spread_per_gb / 2` 判 `depth`，反过来判 `bytes`，
都不成立判 `mixed` —— **判据写在脚本里，不靠人看图**。

920B 上的判定是 `depth`：按每代归一化三档只差 1.7 倍，按每 GB 归一化差 848 倍
（920B · kvm-wp · loop ext4 · 2 GB 模板）。**成本跟着代数走，跟写了多少字节几乎无关。**

脚本还顺手做了根因定位：杀沙箱之前把第 1 代与第 N 代的目录逐文件量下来
（`entry_breakdown()`），`manifest.json` 从 1 027 B 长到 85 268 B，
约 213 字节/代，其余文件基本不变。对应到实现，
`Entry.Rootfs.Layers` 是一个 `[]RootfsLayer{BuildID, Path}` 列表，
**每个 checkpoint 都把截止到自己的全部层完整记一遍** —— 单次 checkpoint 里
有一块 O(链深) 的记账，每次重做。

爬升还略微超线性，说明不止这一处，**没有继续深挖**，如实记在
[第 25 篇 §7](25-results-and-compliance.md#7-已知劣化与含义)。

## 7. 服务端分段：`timings.json` 读法

第三个钟。它不判定，它回答**没达标该改哪**。
产出机制、`PhaseTimings` 的接口与 `nil` 安全设计见
[第 17 篇 §1.1](17-observability-and-verification.md#11-phasetimings)；
两个脚本都直接读文件，不从日志里刮。

| 文件 | 落在哪 | 注意 |
|---|---|---|
| `timings.json` | `<store>/<sbx>/<ck>/` | 写一次就不动 |
| `last-restore-timings.json` | `<store>/<sbx>/` | **每次 restore 覆写一遍，必须紧接着读** |

字段与阶段的对应（`internal/sandbox/checkpoint.go`、`internal/checkpoint/service.go`）：

| 路径 | 字段 | 是什么 |
|---|---|---|
| create | `total` / `frozen` | 服务端全程 / 虚机真停住的那段 |
| create | `prepare`、`rootfs_header`、`checkpoint_to_files`、`append_layer`、`commit` | 服务端各步 |
| create | `pause`、`snapshot`、`seal`、`resume` | 冻结窗口内的四步（[第 10 篇 §3](10-disk-layering.md#3-seal不搬运任何数据的换层)） |
| restore | `save_live_bitmap`、`materialize`、`fc_rollback` | 内存那半：存活跃脏图 → 凑回滚集 → Firecracker 搬回去（[第 11 篇 §3](11-in-place-rollback.md#3-九个阶段)） |
| restore | `assemble_view`、`reset_view` | 磁盘那半：重建层栈 + 整体换视图（[第 10 篇 §7](10-disk-layering.md#7-resetview挂载不动整体换视图)） |
| restore | `conntrack`、`wait_envd`、`rollback_in_place` | 冲连接跟踪 / 等 envd 答话 / 回滚总段 |
| 两侧 | `fc_validate`、`fc_quiesce`、`fc_memory`、`fc_vcpus`、`fc_gic`、`fc_devices`、`fc_total` | Firecracker 自报，微秒精度（[第 11 篇 §7](11-in-place-rollback.md#7-计时与回报)） |
| restore | `materialize_disk_read_mb`、`fc_rollback_disk_read_mb` | 真从块层读回来的量，页缓存命中不计 |

分段给出的两条结论，是「要更快该往哪使劲」的答案（均为 920B · kvm-wp · loop ext4 · 2 GB 模板）：

- **create 的大头在 Firecracker 写内存那一步**：`snapshot` 占 `total` 的 87–98%，
  其余每一步都在 1 ms 以内且不随脏页量变化。**我们自己的代码在这条路上没有可优化的余地**，
  要更快只能让 Firecracker 写得更快 —— 950 上的 HDBSS 正是冲这个来的（[第 19 篇](19-kunpeng-platform.md)）。
- **restore 反过来，大头在我们自己这边**：`materialize`（沿差分树凑回滚集）
  是最大的一段且随脏页量线性涨，比 Firecracker 自己干的活还大一倍多；
  另有 `conntrack` 一笔约 7.5 ms 的固定税，完全不随脏页量变化 ——
  在 0 MB 档它占了整个停机时间的三分之一还多。
  **只算 `fc_rollback` 会让三分之一的冻结窗口对不上账。**

`fc_*` 与 orchestrator 侧同名段之差就是 RPC 开销。
某一档缺某个阶段（报告里显示 `—`）是正常的：两套方案的步骤本来就不完全一样
（[第 18 篇](18-ext4-vs-xfs.md)）。

## 8. 怎么读一份报告

`bench-ckpt.py` 每跑一轮写出 `bench.json`（全部原始样本）与 `报告.md`（渲染表）。
以 [`../test-950/reports/bench-ext4-20260824-200601/报告.md`](../test-950/reports/bench-ext4-20260824-200601/报告.md)
为例，六张表的角色：

| 表 | 回答什么 | 判定用它吗 |
|---|---|---|
| 一、全量 vs 增量 | 各档的创建 p50/p90/p99/max + 三种体积 | **是**（checkpoint 那半） |
| 二、虚机冻结窗口 | 冻结 p50/max、占墙钟比例、底噪 | 否，解释项 |
| 三、宿主分阶段 | 时间花在哪一段 | 否，定位用 |
| 四、restore | 浅集 p50/p99、深集 p50、内容校验 | **是**（restore 那半） |
| 五、持续 checkpoint | 速率与前后 1/3 劣化 | 否，但**限制单次数字的外推** |
| 六、漂移自查 | 每档前后 1/3 的 p50、`mem_mode` | 否，**判据**：这两条不过关整轮作废 |

三种体积口径必须分开读，报告里每次都重复一遍这段话：

- **逻辑体积** = `du --apparent-size`。两套都等于整份内存的大小 ——
  因为两套给出的都是一份完整的内存视图，不是「这次写了多少」。
- **du 实占** = 按 `st_blocks` 算。ext4 方案的差分是稀疏文件，这一列就是真实增量；
  XFS 方案是 reflink 克隆，共享的 extent 会在每个克隆里各算一遍，**这一列会虚高**。
- **新增物理空间** = 整档跑完 `df` 的净增量除以次数。
  **这一列才是盘上真正少掉的空间**，对两套都成立，**也是唯一可以横向比较的一列**。

两条必须先看、不过关就别读时间的检查：

1. **`mem_mode` 列必须全部是 `incremental`**。出现 `full` 说明脏页跟踪没生效，
   这一轮测的不是增量，脚本直接判 `BENCH FAIL`。
   需要注意的是这道判据本身也会失效 —— 某些 SDK 版本的 `CheckpointInfo`
   不带 `mem_mode` 字段，脚本会一律报 `?`（`benchmark/checkpoint-bench-对比.md` §5.1）。
   报 `?` 的那一轮，防静默退化的判据是**空的**，
   只能靠产物实测（内存那一列是否接近整份 guest RAM）当旁证。见
   [第 21 篇 §1](21-test-overview.md#1-为什么这套方案的测试要格外小心)。
2. **漂移自查两列要接近**。偏离就说明这一档内部在漂，p50 不代表整档。

最后，每个数字都要带回它的条件标签。上面这份报告的完整标签是
**920B（Kunpeng 920）· 脏页后端 kvm-wp · 产物在调优过的 loop ext4 上 · 模板 2 vCPU / 2 GB**，
其中 kvm-wp 意味着**每个干净页的第一次写都要陷出一次虚机，这笔开销全含在数字里**，
换到有 HDBSS 的机器上会消失。不同条件的数字**并列可以，相减不行**
（[第 21 篇 §4](21-test-overview.md#4-测量纪律)、
[第 25 篇 §1](25-results-and-compliance.md#1-条件标签)）。

## 9. 小结

1. **判定口径固定为：客户端墙钟、增量 checkpoint 与原地 restore、p50 判定 p99 并列、
   按脏页量分档、全量单列不判定、冻结窗口只作解释项。** 六项都钉在对自己最不利的一侧。
2. 「不同内存快照大小」在本方案里翻译成「**脏页量档位**」——
   增量的成本模型是 O(本代脏页)，与虚机规格无关。
3. **树根全量是每个沙箱一次性的成本**，不在高频回退的路径上，
   但必须列出来，否则「增量快多少倍」没有分母。
4. 负载构造有三种失真：分配成本、写放大（实测 5×）、放错层。
   解法是**预热 + 原地覆写**（`conv=notrunc`）、随机数据、
   内存负载放 tmpfs、文件负载放根文件系统。
5. 文件那半用普通缓冲写，**页缓存双计是本性不是误差**；
   验证读回时反而必须 `iflag=direct`。
6. 四个脚本不可互替：`checkpoint_bench.py` 给时机成本与产物实测（每档一次），
   `bench-ckpt.py` 给分布与冻结窗口（判定表由它产出），
   `timing.py` 把链深与回滚集大小解耦，`probe-ramp.py` 用判别式设计定性连打劣化。
7. 冻结窗口的测量自带分辨率下限，**底噪必须一起报**，不可区分的格子要标出来。
8. 服务端分段的结论是**方向性的**：create 的时间几乎全在 Firecracker 写内存，
   restore 的时间大头在 `materialize` 与一笔固定的 `conntrack`。
9. 读报告先看两条判据（`mem_mode` 全 `incremental`、漂移两列接近），
   再读时间；三种体积口径里**只有「新增物理空间」可以横向比较**。
