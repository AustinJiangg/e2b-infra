# 01 · 沙箱、microVM 与快照原理

## 本章目标

本章不要求写过虚拟化代码，有 Linux 基础即可。读完本章，你应当能够：

- 说清"把一台正在运行的机器退回过去某一刻"这个需求从哪来，为什么重做、应用层撤销都不行；
- 说清"快照"在文件系统、容器、进程、虚拟机四个层次上各捕获什么、看不见什么，以及为什么内存和磁盘必须一起退；
- 画出一个 e2b 沙箱在宿主上由哪些部件组成，并解释"e2b 的用户沙箱是恢复出来的，不是启动出来的"；
- 列出一台虚机的"状态"包括哪七项，说明为什么各部分必须取自同一瞬间；
- 区分恢复的两种形态 —— 重建与原地回写 —— 的成本模型，说出本方案选了哪一种、付出了什么。

上一章（[00](00-overview.md)，导读）给了全书的地图。本章从最基础的问题讲起：需求、被快照的对象、快照本身的原理。
下一章（[02](02-e2b-native-snapshot.md)）拿这些概念去看一个真实的实现 —— e2b 原生 snapshot。

## 1. 需求从哪来

### 1.1 一个具体的场景

一个 AI Agent 接到任务："把这个项目的测试跑通"。它在一个隔离环境（**沙箱**）里工作，步骤大致是：

```
① 拉代码
② 装依赖
③ 改配置
④ 跑构建
⑤ 构建失败，看日志
⑥ 装一个缺的系统库
⑦ 改另一个配置文件
⑧ 跑构建 —— 现在连步骤 ④ 原来能过的部分都过不了了
```

第 ⑦ 步把环境搞坏了。Agent 需要回到第 ⑥ 步结束时的状态，换个改法重试。

### 1.2 "重来一遍"为什么不行

最直观的办法是：扔掉这个沙箱，起一个新的，把 ①–⑥ 重做一遍。三个问题：

| 问题 | 说明 |
|---|---|
| **时间** | 装依赖可能要几分钟。Agent 一次任务里可能要退十几次，累计代价不可接受 |
| **外部副作用** | ①–⑥ 里可能有不可重复的动作：调用了一个 API、写了一个数据库、消耗了一个配额。重做会把它们再做一遍 |
| **不可复现** | 依赖源的内容会变、网络会抖、时间戳会不同。重做出来的环境**不保证**和原来一样 |

第三条最要命：如果重做的结果和原来不完全一样，这次"回退"就没有意义了 ——
Agent 面对的不再是"第 ⑥ 步之后的环境"，而是"一个大致像它的环境"。它基于第 ⑥ 步的观察做出的判断，在新环境里未必成立。

### 1.3 这个需求的三个特征

- **高频**：不是一天几次，是一个任务里十几次；
- **低延迟**：回退发生在 Agent 的决策循环里，几百毫秒和几秒是完全不同的产品体验；
- **不能中断**：沙箱有 IP、有端口映射、有正在保持的连接、有外部持有的引用。中断一次，这些全要重建。

这三条决定了后面所有的技术选择。第 [03](03-goals-and-design-choices.md) 章会把它们量化成设计目标。

## 2. 三种可选做法

### 2.1 重建沙箱

从头再来。上面已经讨论过 —— **慢、有副作用、不保证一致**。

### 2.2 应用层撤销

让每一步操作都记录一个"反操作"，出错时逆序执行。数据库的事务回滚就是这个思路。

问题在于**覆盖不全**。要撤销一次 `apt install`，得知道它装了哪些文件、改了哪些配置、跑了哪些 postinst 脚本、
往哪些数据库写了记录。而这只是一条命令。Agent 执行的是**任意**命令 —— 没有办法为"任意命令"写反操作。

还有一个更根本的问题：反操作本身也可能失败，而失败时状态比出错前更乱。

### 2.3 虚机级快照

**不关心做了什么，只记录状态是什么。**

把整台虚拟机某一时刻的完整状态（内存、CPU 寄存器、磁盘、设备）保存下来，需要时整体恢复。
它不需要理解 `apt install` 干了什么 —— 它保存的是那条命令执行完之后**整台机器的样子**。

| | 重建 | 应用层撤销 | 虚机快照 |
|---|---|---|---|
| 能回退什么 | 一切（但结果可能不同） | 只有被显式建模的操作 | **一切** |
| 依赖对操作的理解 | 是 | **是** | **否** |
| 外部副作用 | 会重复 | 需要单独处理 | 不重复，但也不撤销 |
| 结果确定性 | 不保证 | 取决于实现 | **逐字节一致** |
| 典型代价 | 分钟级 | 取决于操作 | 取决于实现 —— 这正是本书的主题 |

> **硬边界**：虚机快照能把机器内部退回去，**退不回外部世界**。已经发出的 HTTP 请求、
> 已经写进外部数据库的记录，任何快照方案都管不着。

## 3. "快照"在四个层次上

"快照"是个被复用得很厉害的词。四个常见层次捕获的东西完全不同：

| 层次 | 例子 | 捕获什么 | **看不见**什么 |
|---|---|---|---|
| 文件系统快照 | LVM、ZFS、Btrfs 的 snapshot | 某一时刻磁盘上的文件 | 内存里的一切：进程、页缓存、未落盘的写 |
| 容器镜像层 | Docker 的 layer / commit | 文件系统的**变更集** | 同上，而且不含运行中的进程 |
| 进程 checkpoint | CRIU | 一组进程的内存、寄存器、打开的文件、套接字 | 内核态的很多东西；**磁盘完全不管** |
| **虚拟机快照** | 本方案 | guest 的**全部**：内存、vCPU、设备、磁盘 | 外部世界（对端、宿主、网络） |

### 3.1 为什么层次很重要

拿开头那个场景说：

- **文件系统快照**能把 `/usr/lib` 退回去，但退不掉一个已经加载了旧版本库的进程；
- **容器镜像层**能记录"装了什么"，但退不掉进程和内存；
- **进程 checkpoint** 能把进程树退回去，但**磁盘还停在未来** —— 被退回的进程会读到它"还没写过"的文件；
- **虚机快照**能把这些一起退回去，因为它退的是**整台机器**。

第三条值得多想一下：**内存和磁盘必须一起退，否则 guest 会看到一个自相矛盾的世界**。
比如文件系统日志里记着一笔已提交的事务，而内存里那个提交操作还没发生。§6.2 会把这件事展开。

### 3.2 代价的层次也不同

大致的量级感受（不是精确数字）：

| 层次 | 单次快照的典型代价 | 恢复的典型代价 |
|---|---|---|
| 文件系统快照 | 元数据操作 | 元数据操作 |
| 容器镜像层 | 要打包、上传 | 要拉取、解压 |
| 进程 checkpoint | 与进程内存成正比 | 与进程内存成正比 |
| 虚机快照（朴素实现） | 与**虚机内存**成正比 | 与**虚机内存**成正比 |
| **虚机快照（本方案）** | 与**本次改动量**成正比 | 与**回退跨度**成正比 |

最后一行就是这本书要讲清楚的事：**怎么让虚机级快照的代价从"与规格挂钩"变成"与改动量挂钩"。**

一组实测数字能让这件事更具体。下面是开发早期在 920B 上量的一组（KVM 软件写保护、loop 设备上的 ext4、2 GB 模板，2026-08-25，当时的开发版本）：

| 操作 | 耗时 |
|---|---|
| 全量快照（第一次） | 1.549 s |
| 增量快照，改动量 0 MB | **0.022 s** |
| 增量快照，改动量 64 MB | 0.062 s |
| 增量快照，改动量 256 MB | 0.183 s |
| 恢复 | 几十毫秒量级 |

第二行最能说明问题：**什么都没改时，打一个快照几乎免费。** 朴素实现在这一行会付和第一行一样的 1.5 秒 ——因为它不知道"什么都没改"。
这组数只用来建立量级感：它来自早期版本、loop 设备上的盘，与当前代码不是同一套条件，不能拿来和后面的数字相减；当前代码的判定数字见 [21](21-benchmarks-and-compliance.md)，950 上的数字口径又不同（[20 §2](20-performance-methodology.md#2-条件标签)）。

### 3.3 本方案的位置

一句话：**虚机级、进程内、高频、宿主本地。**

| 特征 | 含义 |
|---|---|
| 虚机级 | 捕获 guest 的全部状态，包括内存和磁盘 |
| 进程内 | 恢复时**不重建**虚拟机进程，往活着的进程里写回差异 |
| 高频 | 单次代价低到一个任务里可以用十几次 |
| 宿主本地 | 产物不进对象存储，随沙箱生命周期回收 |

第二条是这套方案最核心的选择，也是它与几乎所有现成实现的分野。"进程内回滚"意味着：虚拟机的进程、它的 KVM 文件描述符、
网卡、块设备、以及**已经在物理内存里的整个工作集**，全部原样保留，恢复要做的只是"把变了的那些页改回去"（§6.4 展开）。

第四条是代价：产物离不开这个沙箱，所以**长期保存和跨机器迁移不归它管**，交给 e2b 原生 snapshot。
为什么"离不开"是推导出来的而不是偷懒，见 [14](14-lifecycle-reasoning.md)；两者怎么分工见 [18](18-native-and-checkpoint-together.md)。

## 4. microVM 与 Firecracker

在讲怎么给一台机器打快照之前，得先讲清楚**被快照的那个东西是什么**。

### 4.1 三种隔离

要在一台机器上跑别人的代码，隔离方式大致三种：

| | 容器 | 传统虚拟机 | microVM |
|---|---|---|---|
| 隔离边界 | **共享宿主内核**（namespace + cgroup + seccomp） | 独立内核，硬件虚拟化 | 独立内核，硬件虚拟化 |
| 内核漏洞的影响 | 可能逃逸到宿主 | 被硬件边界挡住 | 被硬件边界挡住 |
| 启动 | 最快 | 慢（要走固件、枚举设备） | 快（几乎只剩加载内核） |
| 每实例额外内存 | 很小 | 大（完整的设备模型） | 小 |
| 设备模型 | 无（用宿主的） | 完整仿真：BIOS、PCI、显卡、USB… | **极简**：几个 virtio 设备 |

跑**不受信任的任意代码**（AI Agent 生成的代码正是这种）时，共享内核的风险不可接受；但传统虚拟机又太重。
**microVM 就是为这个空隙设计的**：保留硬件隔离边界，把设备模型砍到最小。

### 4.2 Firecracker 砍掉了什么

Firecracker 是 AWS 为 Lambda 和 Fargate 开发的 VMM（虚拟机监控器，负责创建虚机、模拟设备的用户态进程），Rust 写的，开源。
它砍掉的东西比保留的多：

| 砍掉 | 保留 |
|---|---|
| BIOS / UEFI | 直接加载 Linux 内核镜像 |
| PCI 总线 | **virtio-mmio**（更简单的设备发现方式） |
| 显卡、USB、声卡、软驱… | virtio-net、virtio-block、virtio-rng、串口 |
| 设备热插拔 | 启动时固定的设备集 |
| 大部分 CPU 特性仿真 | 直通 + 少量必要的处理 |

代码量因此小得多，攻击面小，启动也快。

### 4.3 这对快照意味着什么

设备越少，"一台虚机的状态"就越简单。Firecracker 快照要保存的东西是：

| 类别 | 内容 |
|---|---|
| **guest 内存** | 通常是大头 —— 一个 2 GiB 的沙箱就是 2 GiB |
| **vCPU 状态** | 每个 vCPU 的全部寄存器 |
| **中断控制器** | aarch64 上是 GIC 的状态 |
| **设备逻辑状态** | 每个 virtio 设备的队列位置、协商特性、中断状态 |

除了内存，其余加起来通常只有几十 KB。**这个悬殊的比例是后面所有优化的前提**：优化内存那一项，就等于优化了整个快照。

### 4.4 Firecracker 已有的快照能力

上游 Firecracker 支持：

| 能力 | 说明 |
|---|---|
| Full 快照 | 写出完整的 guest 内存 + vmstate（vCPU、GIC、设备状态） |
| **Diff 快照** | 只写自上次快照以来脏的页，写在各自的文件偏移上 |
| 脏页跟踪 | `track_dirty_pages`，靠 KVM 的写保护实现（[05](05-dirty-page-tracking-and-hdbss.md)） |
| 加载 | `PUT /snapshot/load` —— **新建一个进程**去加载 |
| Pause / Resume | 暂停和恢复虚机 |

注意最后两行：上游只有"新建进程加载"这一条恢复路径。本方案增加的核心能力就是**往活着的进程里写回**
（[09](09-in-place-rollback.md)），接口扩展见 [08](08-firecracker-api-contract.md)。

## 5. e2b 的沙箱模型

e2b 是一个把沙箱作为服务提供出来的平台。

### 5.1 四个概念

| 概念 | 是什么 |
|---|---|
| **Template** | 沙箱的"出厂状态"。用户定义（类似 Dockerfile），构建产出一份可以被反复加载的快照 |
| **Build** | 一次 template 构建的产物，有自己的 id。一个 template 可以有多个 build |
| **Sandbox** | 一个正在运行的沙箱实例，由某个 build 加载而来 |
| **envd** | 跑在 guest 里的守护进程，负责执行命令、读写文件 |

### 5.2 用户沙箱是"恢复"出来的

一个 build 构建完成后由三份东西组成：

```
memfile     ← guest 内存镜像
rootfs      ← 根文件系统镜像
snapfile    ← vmstate：vCPU、GIC、设备状态
```

**这三份东西本身就是一个快照。** 也就是说：

> **e2b 的用户沙箱不是"启动"出来的，是"恢复"出来的。**

代码里这一点很清楚，`Factory`（`packages/orchestrator/internal/sandbox/sandbox.go`）有两个方法：

| 方法 | 谁用 | 内存后端 |
|---|---|---|
| `CreateSandbox`（:240） | **只有 template 构建流程用**（`internal/template/build/` 下） | `uffd.NewNoopMemory(...)`（:359）—— 普通内存，冷启动 |
| `ResumeSandbox`（:424） | **所有用户沙箱** | 真正的 UFFD（:473） |

这个事实后面反复用到。最重要的一处在 [05](05-dirty-page-tracking-and-hdbss.md)：**脏页跟踪必须在"从快照加载"这条路径上武装**，
只管冷启动路径等于完全没开。

### 5.3 内存是按需拉取的

一个 build 的 memfile 可能有几个 GB，而且**不在本地** —— 它在对象存储里。如果每次起沙箱都要先把几个 GB 拉下来，
启动时间就没法看了。e2b 的做法是 **userfaultfd（UFFD）**：Linux 提供的一种机制，让一段内存发生缺页时由用户态程序来填。

```
guest 访问一个还没有内容的内存页
    │
    ▼  缺页 → 内核不自己处理，转交给用户态
UFFD handler（orchestrator 里的一个组件，每沙箱一个）
    │
    ▼  从本地缓存取；没有就经 chunker 从对象存储按块拉
把这一页填进去，guest 继续跑
```

于是沙箱可以在 memfile 只拉了很小一部分的时候就跑起来，**用到哪拉到哪**。这个机制对本方案有两处影响：

1. 模板 memfile **本地不存在**，所以回滚路径不能依赖它 —— 这是差分树"全量根"默认开启的原因（[06](06-memory-diff-tree.md)）；
2. 上游用 UFFD 的写保护位来判定脏页，这条路径在 ARM 适配版上退化了（原生怎么判见 [02](02-e2b-native-snapshot.md)，
   退化的定义见 [05](05-dirty-page-tracking-and-hdbss.md)）。

### 5.4 磁盘是分层的

rootfs 也不是直接给 guest 用的。它是**只读**的底座，上面盖一层写时复制（COW，copy-on-write）的写层：

```
guest 的所有写  →  写层（一个稀疏文件 + mmap）
guest 的读      →  先查写层，没有再查底座
```

这样同一个 build 可以被许多沙箱共享，每个沙箱只占自己写过的那部分。本方案的磁盘增量就做在这一层上（[07](07-disk-layering.md)）。

### 5.5 一个沙箱在宿主上的样子

```
┌─────────────────────── orchestrator 进程 ────────────────────────┐
│                                                                  │
│   沙箱表        代理（端口路由）        Checkpoint Service        │
│      │                                                           │
│      ├── Sandbox 对象                                            │
│      │      ├── process         → Firecracker 的 API socket      │
│      │      ├── Rootfs Provider → Overlay + NBD                  │
│      │      ├── Slot            → 网络命名空间、tap、IP          │
│      │      └── Template        → memfile / rootfs / snapfile    │
│      └── UFFD handler（每沙箱一个）                              │
└──────────────────────────────────────────────────────────────────┘
          │                    │                    │
          ▼                    ▼                    ▼
   Firecracker 进程       /dev/nbdX           tap 设备 + netns
          │
          ▼
    KVM（/dev/kvm）
```

| 部件 | 作用 |
|---|---|
| **orchestrator** | 宿主上的管理进程。管沙箱生命周期、网络、存储、代理；本方案的 Checkpoint Service 也在里面 |
| **Firecracker 进程** | 每个沙箱一个，真正跑 guest 的 VMM |
| **UFFD handler** | 每个沙箱一个，按需填充 guest 内存页 |
| **NBD 设备** | 把宿主上的 Overlay 对象暴露成一个块设备给 guest |
| **网络槽位（Slot）** | 每个沙箱一个网络命名空间 + tap + IP，通过 NAT 出网 |
| **envd** | 在 guest 里，执行用户的命令 |

**"沙箱不能中断"这句话现在具体了**：一次中断意味着上面这些全部要重建 —— 新进程、新 KVM fd、新 tap、新 NBD 设备，
以及把整个工作集重新缺页拉回内存。

### 5.6 请求是怎么到达沙箱的

用户调 `sandbox.commands.run("ls")`，请求路径是：

```
SDK  →  沙箱的公开地址（Host 头里带着端口和沙箱 id）
     →  orchestrator 的代理
     →  解出 (sandboxID, port)
     →  转发进对应沙箱的对应端口
     →  guest 里的 envd 应答
```

本方案的 API 复用这条路径，只是**在最后一跳之前被截下来了**：checkpoint 请求发给沙箱的 49984 端口，但由宿主直接应答，不进沙箱。
理由很直接：**打快照要暂停虚机，沙箱内的程序没法暂停自己。** 细节见 [04](04-architecture.md)。

## 6. 虚拟机快照的基本原理

"保存一台机器的状态"这件事，难的不是保存，是**说清楚"状态"到底包括什么**，以及**怎么保证保存下来的各部分属于同一瞬间**。

### 6.1 "状态"包括七项

| # | 部分 | 大小量级 | 容易忽略吗 |
|---|---|---|---|
| 1 | guest 内存 | GB | 不会 |
| 2 | vCPU 寄存器 | 每 vCPU 几 KB | 不会 |
| 3 | 中断控制器（aarch64 上的 GIC） | 几 KB | 有点 |
| 4 | 设备逻辑状态（virtio 队列位置、协商特性、中断状态） | 几 KB | **是** |
| 5 | 磁盘 | GB | 不会 |
| 6 | **时间** | —— | **是** |
| 7 | **外部世界对它的记忆** | —— | **非常** |

前五项是"机器里的东西"，直觉上都想得到。后两项才是真正的坑。

**第 6 项：时间。** guest 里有两种时钟：

- **单调时钟**（`CLOCK_MONOTONIC`）：从某个起点单调递增，用于测量间隔；
- **墙钟**（`CLOCK_REALTIME`）：当前的年月日时分秒。

快照恢复之后，**单调时钟会倒退** —— 因为它来自 vCPU 的计时器寄存器，而那些寄存器被恢复成了快照时刻的值。
这违反了 POSIX 对 `CLOCK_MONOTONIC` 的承诺，但在快照语义下是唯一自洽的做法：guest 相信自己一直在那个时刻，
它的**所有**状态都与那个时刻一致。墙钟则不能留在过去（那会让所有时间戳都错），需要外部把它校回来。
这条直接决定了验收测试不能用时间做活性判据（[10](10-rollback-pitfalls.md)）。

**第 7 项：外部世界对它的记忆。** 这是最容易被忽略、也最难排查的一项。guest 被退回到十分钟前，但外部世界没有退：

| 外部记忆 | 退回后的后果 |
|---|---|
| 宿主内核的连接跟踪表（TCP 序号窗口） | guest 发出的包序号"倒退"，被内核判为非法直接丢弃 —— **连接挂死而不是报错** |
| TCP 对端 | 对端记得的序号和 guest 现在用的对不上 |
| 代理的连接池 | 池子里的连接对应的 guest 侧状态已经不存在了 |
| 已发出的 API 调用 / 已写入的外部数据库 | **无法撤销** |

前三项本方案会处理（[10](10-rollback-pitfalls.md)）；最后一项是任何快照方案的硬边界（用户视角见 [24](24-semantics-and-limits.md)）。

**还有一件事要告诉 guest。** 如果 guest 完全不知道自己被回滚了，某些东西会出错：随机数生成器的种子被复用
（两次"不同"的执行产生同样的随机序列），依赖单调时间的缓存、租约、超时判断也会出错。
所以有一个专门的机制 —— **VMGenID**：一个 ACPI 设备，在 guest 内存里放一个 128 位代号，代号变了就意味着
"你被从快照恢复了"，guest 内核据此重新播种。本方案原地回滚时何时改这个代号，见 [10](10-rollback-pitfalls.md)。

### 6.2 一致性：为什么必须是同一瞬间

假设内存在 T1 保存，磁盘在 T2 保存（T1 < T2），中间这段时间 guest 继续在跑。恢复之后 guest 看到：**内存是 T1 的、磁盘是 T2 的**。

具体会怎样？guest 的文件系统在内存里维护着一堆状态：页缓存、inode 缓存、未提交的日志事务。这些在 T1 被保存下来，
而磁盘上的块已经走到了 T2。于是可能出现：

- 文件系统日志里记着一笔已提交的事务，而内存里那个提交操作还没发生；
- 页缓存里的一个块，内容比磁盘上的**旧**（正常情况只可能更新）；
- 一个文件的 inode 说它有 10 个块，而磁盘上的分配位图说只有 8 个。

guest 内核可能在恢复后直接报文件系统损坏，也可能不报、只是**静默地读到错的数据**。唯一正确的做法是**一次暂停内完成**：

```
暂停虚机
  ├── 保存内存
  ├── 保存磁盘
  └── 保存 vCPU / 设备状态
恢复虚机
```

这样三者都是**同一瞬间**的镜像。guest 尚未刷盘的数据留在内存镜像里，位置完全正确 —— 恢复之后它会像什么都没发生一样把那些数据刷下去。

暂停的这段时间叫**冻结窗口**（freeze window）。它是快照**唯一对业务可见的代价**：业务感受到的是"卡了 N 毫秒"，
而不是"这次调用花了 N 毫秒"。所以全书在性能上反复区分"整个调用花了多久"和"虚机被冻住了多久"（[20](20-performance-methodology.md)）。
"内存与磁盘在同一个暂停窗口内完成"是本方案的不变量之一（[12](12-failure-semantics.md)）。

### 6.3 全量与增量

**全量的问题。** 一次全量快照要写出整个 guest 内存，2 GiB 的沙箱就是 2 GiB 的写。这决定了两件事：

- 冻结窗口与**虚机规格**成正比（除非把写移出窗口，那又带来 §6.2 的一致性问题）；
- 存储占用是**每代 × 全量**。

**增量的前提。** 增量快照只写"自上次以来变了的页"。它的前提是一个看似简单的问题：**怎么知道哪些页变了？**
宿主上的软件看不到 guest 的写 —— guest 直接在物理内存上跑，写内存不经过任何宿主代码。要知道哪些页被写过，必须借助**硬件或内核**：

| 机制 | 原理 |
|---|---|
| 写保护 + 陷出 | 把页设成只读，第一次写时陷入内核，记一笔再放行 |
| 硬件标脏 | CPU 自己在页表更新时把地址记进一个缓冲区 |

两者的代价差两个数量级：前者每个页的第一次写都要让虚机退出到宿主一次，后者几乎不打扰 guest。这是 [05](05-dirty-page-tracking-and-hdbss.md) 的全部内容。

**增量带来的新问题。** 有了增量，就有了"一代"和"链"的概念，也就有了新问题：

- 恢复到第 n 代，要不要把 1..n 代全部重放一遍？
- 删掉中间某一代会怎样？
- 回滚之后，比目标更新的那些代还有用吗？

这些是 [06](06-memory-diff-tree.md) 的内容。先说答案：**不重放、按页寻址、历史是树不是链。**

### 6.4 恢复的两种形态：重建与原地回写

**这是全书最重要的分野。**

**重建：新建一个进程去加载。**

```
新建进程 → 建 KVM VM → 建 vCPU → 建中断控制器 → 建设备
        → 注册各种 fd → 建网卡 → 挂内存后端
        → 加载 vmstate → 恢复寄存器与设备状态 → 跑起来
        → guest 开始运行，逐页缺页把工作集换回内存
```

这是几乎所有现成实现的做法，包括上游 Firecracker 的 `PUT /snapshot/load` 和 e2b 原生的 resume（[02](02-e2b-native-snapshot.md)）。
**成本 = 建一台虚机的固定开销 + 把工作集换回内存。** 后者与虚机规格成正比，与"回退了多少"**完全无关**。

**原地回写：往活着的进程里写。**

```
虚机暂停 → 把变了的那些页写回活着的内存映射
        → 把 vCPU / 设备状态写回既有对象 → 恢复运行
```

**一个宿主资源都不重建**：进程、KVM fd、中断控制器、设备、网卡、内存映射，以及**已经在物理内存里的整个工作集**，全部原样保留。
**成本 = 变了多少就写多少。**

| | 重建 | 原地回写 |
|---|---|---|
| 成本正比于 | **虚机规格** | **回退跨度** |
| 沙箱身份 | 新进程（外部标识可以维持不变） | 同一个进程 |
| 网络、存储连接 | 全部重建 | 保留 |
| 恢复后的性能 | 一段时间内持续缺页 | **立刻满速** |
| 能处理"进程已死"吗 | **能** | 不能 |
| 能跨机器吗 | **能** | 不能 |
| 实现复杂度 | 低（构造函数保证对象自洽） | **高**（要让既有对象重新自洽） |

最后三行是代价。"原地回写"换来的速度，付出的是**适用范围**和**实现复杂度**：

- 适用范围：进程死了、要跨机器，它都做不了（[14](14-lifecycle-reasoning.md)）；
- 复杂度：重建路线从零构造对象，天然自洽；原地路线要处理一类新问题 ——
  "从活对象里推导出来、又没进快照的状态"，例如网卡缓存的描述符、宿主的连接跟踪表（[10](10-rollback-pitfalls.md)）。

**本方案选的是原地回写。** 第二、三部分的大半篇幅是在讲这个选择的后果。

### 6.5 一个判断快照是否正确的强判据

怎么证明"恢复回来的确实是那个时刻"？一个很强的判据：**杀掉一个进程，然后回滚，看它能不能复活。**

```
① 在 guest 里起一个后台进程，记下它的 PID 和启动时刻
② 打一个快照
③ kill -9 那个进程
④ 回滚到 ②
⑤ 检查：那个进程是不是回来了？PID 一样吗？启动时刻一样吗？
```

如果三个都对上了，说明恢复回来的是**完整的内存现场** —— 进程表、页表、文件描述符、内核里那个进程的全部结构，都回到了那一刻。
**这件事重放操作做不到**：没有任何"反操作"能让一个被 `kill -9` 的进程带着原来的 PID 和启动时刻回来。

同一条测试还顺带证明另一件事：多代快照之间那个进程的 PID 和启动时刻都没变，说明**打快照的过程没有重启虚机**。
这项检查在正确性脚本里的写法见 [19](19-testing-and-functional-verification.md)，结果见 [21](21-benchmarks-and-compliance.md)。

## 本章要点

1. 需求来自"Agent 退回上一个已知良好的状态"，特征是**高频、低延迟、不能中断**；重做在时间、副作用、可复现性上都不行，
   应用层撤销没法为任意命令写反操作。
2. 虚机快照不需要理解做了什么，只记录状态是什么；它退不回外部世界。四个层次的"快照"里只有虚机快照同时覆盖内存和磁盘，
   而**内存和磁盘必须一起退**。
3. microVM 保留硬件隔离、砍掉设备模型；设备少使得内存以外的状态只有几十 KB，**优化内存就是优化整个快照**。
   上游 Firecracker 已有 Diff 快照与脏页跟踪，但只有"新建进程加载"一条恢复路径。
4. e2b 的 template 产物本身就是快照，用户沙箱一律由 `ResumeSandbox` 恢复而来；内存经 UFFD 按需从对象存储拉取，
   模板 memfile 本地不存在；磁盘是只读底座加 COW 写层。
5. 状态有七项，**时间**与**外部记忆**最容易被忽略；各部分必须在**一次暂停内**保存，冻结窗口是唯一对业务可见的代价。
6. 增量的前提是"知道哪些页变了"，只能靠硬件或内核；有了增量就要回答重放、删除、分支三个问题。
7. 恢复分**重建**（成本随规格）与**原地回写**（成本随回退跨度）；本方案选后者，代价是适用范围变窄、实现变复杂。
8. 强判据：被 `kill -9` 的进程回滚后带着原 PID 和启动时刻复活。
