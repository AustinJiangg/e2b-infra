# 两个环境变量，以及挖出来的四个坑

## 一、`FC_TRACK_DIRTY_PAGES` 与 `ORCHESTRATOR_BASE_PATH`

先把最容易混的一点摆清楚：**脏页这件事分两层，HDBSS 只是第二层。**

| 层 | 管什么 | 谁决定 | 什么时候定 | 开关 |
|---|---|---|---|---|
| ① | **要不要记脏页** | orchestrator，写进 Firecracker 的 boot config（`track_dirty_pages`） | **虚机启动那一刻** | `FC_TRACK_DIRTY_PAGES` |
| ② | **用什么方式记** | Firecracker 自己 | 运行时探测 | **没有开关**，KVM cap 502 能开就 HDBSS，不能就退回写保护 |

第二层是全自动的：`Vm::setup_dirty_tracking` 探一次 cap 502，成功用 HDBSS、失败退回
KVM 写保护，两者喂给上层的是同一个 `KVM_GET_DIRTY_LOG` 位图，语义一致，只差性能。
`GET /` 的 `dirty_tracking` 字段会自报选了哪个（`hdbss` / `kvm-wp` / `off`）。

**"脏页跟踪关着 → 退化成全量拷贝"说的是第一层，跟 HDBSS 无关。**
第一层关着时 Firecracker 根本不产生脏位图，checkpoint 算不出增量集合，
只能每次把整份 guest 内存抓走。不报错，测试照样"通过"，测的却不是增量。

### `FC_TRACK_DIRTY_PAGES`

- **我们加的**（上游 2026.09 里没有这个变量）
- **不设时跟着硬件走**（2026-08-25 起）：定义在
  `packages/orchestrator/internal/sandbox/fc/dirtytracking.go`
  ```go
  var trackDirtyPagesEnabled, trackDirtyPagesReason = resolveTrackDirtyPages()
  ```
  - 设了 → 按设的来（`"true"` 开，其它一律关），**env 永远是强制覆盖**
  - 没设 → `KVM_CHECK_EXTENSION(502)` 探一下 arm64 HDBSS：
    探到 → **默认开**（硬件标脏几乎不要钱）；探不到 → **默认关**
  - 探针是只读的：不建虚机、不启用任何能力，没有 `/dev/kvm` 的机器上也安全

  为什么探不到就关：没有硬件标脏时，内核要把每个干净页写保护起来，
  第一次写陷出一次 VM exit。对从头到尾不做 checkpoint 的沙箱是纯亏。

- **orchestrator 启动时会把结论和理由打出来**，配错不再是无声的：
  ```
  INFO  checkpoint capabilities  {"store": "...", "track_dirty_pages": false,
        "track_dirty_pages_reason": "no hardware dirty state tracking; ..."}
  WARN  dirty page tracking is off: every checkpoint will copy all of guest memory.
        Set FC_TRACK_DIRTY_PAGES=true to force it on.
  ```

**920B 上的情况**：内核没编 `CONFIG_ARM64_HDBSS`，cap 502 返回 0。
不设 env → 自动判定为**关**（实测：FC 自报 `dirty_tracking: off`，
第 2 次 checkpoint `mem_mode=full`、1.636 s）。
我们做测试时在 nomad job 里显式写 `FC_TRACK_DIRTY_PAGES=true` 强制打开。
phz 那套从来没设过，所以一直跑在关着的状态。

**950 上的情况**：cap 502 可用（`KVM_ENABLE_CAP(502, order=1) = 0`，
dmesg 里有 `Enable HDBSS success`），**所以什么都不用配，自动就是开的**。

四个用例都在 920B 上实测过：不设 env→关+WARN、`=true`→开、
XFS 套 store 在 XFS 上→`reflink: true`、XFS 套 store 指到 ext4→`reflink: false` + ERROR。

### `ORCHESTRATOR_BASE_PATH`

- **上游的变量**，不是我们加的（2026.09 里 9 个文件命中），生产默认 `/orchestrator`
- 它只决定 orchestrator 的数据（template / sandbox / build / checkpoints）落在哪个目录，
  也就是**落在哪个文件系统**上。跟脏页、跟 HDBSS 都无关。

两台机器正好相反：

| | 根盘 | ext4 套 | XFS 套 |
|---|---|---|---|
| 920B | **XFS** | 要造 loop **ext4** 卷，`ORCHESTRATOR_BASE_PATH=/mnt/ext4dev/orchestrator` | 用默认 `/orchestrator` 即可 |
| 950 | **ext4** | 用默认 `/orchestrator` 即可 | 要造 loop **XFS** 卷，指过去 |

所以在 950 上，只有 XFS 套需要设这个变量。它是部署选择而不是功能开关，
所以**已经写进 `xfs-reflink` 分支的 `e2b-deploy/dep/template-manager.hcl`**：

```
ORCHESTRATOR_BASE_PATH = "/mnt/xfsdev/orchestrator"
```

写的是字面路径而不是 `${ORCHESTRATOR_BASE_PATH}`，因为 `deploy.sh` 渲染 hcl 用的
`envsubst` 带一份显式变量白名单，没列进去的 `${...}` 会原样留在 job spec 里。
换挂载点就改这一行。`main` 分支不设，走默认的 `/orchestrator`（950 根盘就是 ext4）。

### 漏配的后果（两个都不报错）

| 漏配 | 现象 | 现在会怎样 |
|---|---|---|
| `FC_TRACK_DIRTY_PAGES` | 每次 checkpoint 都退化成全量拷贝，功能正常、数字失真 | 950 上不会再漏配（自动探测）；真关着时启动日志 **WARN** |
| XFS 套的 `ORCHESTRATOR_BASE_PATH` 落在 ext4 上 | reflink 克隆退化成整份拷贝，每次 checkpoint 变成一次 guest 内存大小的写 | 启动日志 **ERROR**，并指明该怎么改 |

两个都仍然**不会让部署失败**——这是有意的：功能是对的，只是慢。
但它们不再是无声的了，启动那几行日志就能看出来。

## 二、坑之一：改了 hcl 的 env，nomad 却拿不到（2026-08-25）

**这一条直接决定上面两个环境变量能不能生效，所以放在最前面。**

`/opt/e2b-infra` 下的 hcl 有**两份**，nomad 跑的是第二份：

```
e2b-deploy/dep/template-manager.hcl        仓库里的源
   └─(build.sh install_e2b 拷贝)→  /opt/e2b-infra/nomad/template-manager.hcl     ← 模板，带 ${...} 占位符
        └─(deploy.sh 用 envsubst 渲染)→  /opt/e2b-infra/rendered/template-manager.hcl  ← nomad 真正读的
```

`build.sh --nomad-job deploy template-manager` 里的 `nomad_job_deploy()` 是这样写的：

```bash
local rendered_dir="$E2B_DIR/rendered"
local hcl_file="$rendered_dir/${job}.hcl"
nomad job run -token "$token" "$hcl_file"
```

**它只读 `rendered/`，不重新渲染。** 所以只改 `nomad/` 里那份模板，改动永远到不了 nomad——
文件看着完全正确，`grep` 也能搜到你写的 env，但进程 `/proc/<pid>/environ` 里就是没有。

在 920B 上实测过一次：`03-switch.sh` 报"切换完成"，二进制确实换成了 XFS 套的，
但 `FC_TRACK_DIRTY_PAGES` 和 `ORCHESTRATOR_BASE_PATH` 都没生效——
store 落回默认的 `/orchestrator`，脏页跟踪是 `off`，**每次 checkpoint 都会静默退化成全量**。
测试照样能"跑通"，只是测的根本不是增量。

**`03-switch.sh` 现在两份都写**：模板保证以后重渲染不丢，渲染产物保证这次生效；
`03-switch.sh show` 会把两份的 env 分别打印出来，不一致一眼可见。

**手工改 env 时同理，两份都要改**，或者改完模板后跑一次完整的 `deploy.sh` 重渲染。

> 顺带：`rendered/` 那批文件在 920B 上的时间戳还是初次部署那天的。
> 也就是说，这套部署从装好那天起就没有重新渲染过——
> 谁要是这半年里改过 `nomad/` 里的东西，那些改动一次也没生效过。

**验证办法只有一个，别看文件，看进程**：

```bash
tr '\0' '\n' < /proc/$(pgrep -f '/usr/bin/template-manager' | head -1)/environ | grep -E 'FC_TRACK_DIRTY_PAGES|ORCHESTRATOR_BASE_PATH'
```

`04-verify-runtime.sh` 的第 2 步做的就是这件事。

## 三、坑之二：两个 60 秒撞在一起，真正的错误信息永远送不到（2026-08-25）

### 现象

跨分支回滚时 `restore` 卡住不返回，客户端最后抛的是：

```
httpcore.ReadTimeout: timed out
```

这句话什么也没说。实际发生的是：**Firecracker 那半边完整成功了，guest 没醒过来。**
从日志才看得出来：

```
07:48:50.955  PUT /snapshot/rollback   收到
07:48:50.980  rollback 200 OK，25110 us
07:48:50.993  resume vm 成功，eth0/rootfs/rng 全部 kick 到
              （之后什么都没有）
07:49:51.204  ERROR healthcheck failed        ← 正好 +60.2 秒
```

### 原因

| | 值 |
|---|---|
| 服务端 `envdRestoreTimeout`（等 guest 的 envd 回话） | 60 s |
| SDK 的默认 `REQUEST_TIMEOUT` | 60.0 s |

**两个预算完全相等**，客户端必然先放弃。服务端那句
`sandbox restored but envd did not come back` 永远写不进响应，
调用方只能看到一个裸的 `timed out`。**恰恰在最需要线索的时候没有线索。**

### 改法

服务端降到 **45 s**（infra-arm `jll@9f6cf6c42` / `jll-xfs@5b6826bd8`）。
正常一次 restore 的 `wait_envd` 是 **2 ms**，45 秒对 guest 完全不是约束，
它只决定**由谁来报这个错**。同时在这条路径上补了一条 ERROR 日志，
带沙箱 ID、检查点 ID 和分阶段耗时——即使客户端已经走了，也留得下痕迹。

### 触发条件仍未找到

那个"guest 醒不过来"的根因**没有定位**。三轮复现全部阴性，共约 1300 次 restore：

| 复现手段 | 次数 | 结果 |
|---|---|---|
| 专打跨分支 restore（`tmp/repro-fork-hang.py`） | 187 | 0 异常 |
| 整条循环 `correctness.py`（`tmp/loop-correctness.sh`） | 40 轮 ≈ 800 | 40 过 0 挂 |
| 回滚瞬间灌 8MB/次 制造在途 RX（`tmp/repro-rx-pressure.py`） | 315 | 0 异常 |

已排除的假设：
- **不是 FC 二进制不同**——挂死那次用的 `tmp/fc-versions/v1.13.1/firecracker`
  与现在 `bin/fc-ext4` 的 sha 完全一致（`9bfa37ab2a6b67fe`）
- **不是"跨分支"本身**——单独打 187 次打不出来
- **不是 correctness.py 那个序列本身**——整条跑 40 轮打不出来
- **不是服务端无限挂起**——超时机制存在且生效（那 60.2 秒就是它）

唯一的异常线索仍是当时的设备状态：`eth0 q0 avail=554 next_avail=554 next_used=326`，
有 228 个 RX 描述符在飞。KASandbox 的 `dbf3f6f`「原地回滚后重建 net 设备的 RX
描述符缓存」正是这块。但按这条线索加压 315 次也没打出来。

**结论：频率低于 1/1300，根因未知，但失败时的可诊断性已经修好。**
950 上如果再遇到，日志里会直接写明"rollback 成功、envd 没回来"，
并带上分阶段耗时——那时候的日志才有定位价值。

## 四、坑之三：`busybox_1.35_arm64` 在 2026.09 分支上是个 HTML 错误页

infra-arm 的 `2026.09` 分支里，

```
packages/orchestrator/internal/template/build/core/systeminit/busybox_1.35_arm64
```

是 **3611 字节的 HTML**（下载失败留下的错误页），不是二进制。
而同目录的 `busybox.go` 用 `//go:embed busybox_1.35_arm64` 把它嵌进 orchestrator，
在 arm64 上当作 guest 的 `/usr/bin/init`。

**症状**：建模板时 guest 内核直接 panic

```
Kernel panic - not syncing: Requested init usr/bin/init failed (error -8)
```

`-8` 是 `ENOEXEC`——内核在 exec 一个 HTML 文件。

**为什么 RPM 那条路没事**：`e2b-infra.spec` 第 30 行

```
cp %{SOURCE1} packages/orchestrator/internal/template/build/core/systeminit/
```

`Source1` 就是真的 2,028,568 字节 aarch64 静态 busybox，构建时覆盖掉占位文件。

**为什么我们踩到了**：我们把 `jll`/`jll-xfs` 从 `phz-demo` rebase 到 `2026.09`
（phz-demo 里提交了真的 busybox），直接 `go build` 时没有做 spec 那一步。

**处理**：构建脚本 `tmp/build-rebased.sh` 在 `go build` 前照抄 spec 的动作，
从 RPM 仓库拷真 busybox 进去，编完再 `git checkout --` 还原，分支保持干净，
0001 patch 不受影响。

## 五、坑之四：aarch64 的 seccomp 白名单漏了 `pread64`

**症状**：打开 `FC_TRACK_DIRTY_PAGES=true` 之后，建模板走到 pause-and-upload，
`GET /memory/dirty` 一调用，Firecracker 立刻退出，orchestrator 报

```
error waiting for fc process: exit status 148
failed to get memfile metadata: error getting dirty memory:
  Get "http://localhost/memory/dirty": dial unix /tmp/fc-....sock: connect: connection refused
```

`148` 是 Firecracker 的 `FcExitCode::BadSyscall`。FC 自己的日志里写得很清楚：

```
Shutting down VM after intercepting signal 31, code 1.
Shutting down VM after intercepting a bad syscall (67).
```

signal 31 = `SIGSYS`，aarch64 的 **67 号系统调用 = `pread64`**。

**根因**：`GET /memory/dirty` → `Vmm::get_dirty_memory` →
`PagemapReader::is_page_dirty`，后者在 `firecracker/src/vmm/src/utils/pagemap.rs:98`
直接 `libc::pread` 读 `/proc/self/pagemap`。而
`firecracker/resources/seccomp/aarch64-unknown-linux-musl.json` 的 `vmm` 线程
放行了这条路需要的 `openat`（开 pagemap）和 `mincore`（常驻页位图），**唯独漏了 `pread64`**。

**这不是我们改出来的**：`pagemap.rs` 在基线（`firecracker` 分支）里就是这样，
我们一行没动；基线的过滤器同样没有 `pread64`。以前没暴露，是因为这条路
只在 orchestrator 以 `track_dirty_pages` 启动虚机时才会走到，
而此前没有任何部署打开过这个开关。

**修复**：在 `vmm` 线程的过滤器里加一条 `pread64`
（KASandbox `jll` = `3863c76`，`jll-xfs` = `2b06bb0`）。

**对 950 的意义**：我们两套都要求 `FC_TRACK_DIRTY_PAGES=true`，
所以 950 上只要建模板就会撞上同一堵墙。**必须带上修好的 FC。**
