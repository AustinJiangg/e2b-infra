# 950 摸底结论

依据：`00-recon-950.sh` 在 slot6 上的完整输出，2026-08-24 14:12。
对照组：920B（hostname-tdi1m）同一脚本 2026-08-24 10:41 的输出。

**一句话**：HDBSS 确认可用；ext4 套开箱即用；XFS 套只能用 loop 镜像造卷；
另有三处与 920B 的差异会让现有脚本直接报错，已列在第 5 节。

---

## 1. HDBSS —— 可用，而且有硬证据

| 证据层 | 950 | 920B |
|---|---|---|
| 内核 | `CONFIG_ARM64_HDBSS=y` | **没有这个选项**（不是关闭，是压根没编） |
| KVM 能力查询 | `KVM_CHECK_EXTENSION(502) = 1`，per-VM 也是 1 | `= 0` |
| **真开一把** | `KVM_ENABLE_CAP(502, order=1) = 0` ✅ | `= -1` |
| 内核日志 | `kvm [1580278]: Enable HDBSS success, HDBSS buffer size: 1` | 无 |

最后那行 dmesg 是探针那次调用留下的，这是"能力启用"这一层最硬的证据——
不是"声称支持"，是内核确认开成功了。

**结论**：950 上 Firecracker 会自动选 HDBSS，**不需要配任何 env**。
920B 上没有 HDBSS，跑的是 KVM 写保护，所以 920B 验的是正确性，
性能数字要以 950 为准。

`FC_HDBSS_ORDER` 控制每 vCPU 的 buffer 大小，默认 1（8KiB）。
写密集负载下 buffer 溢出会吃掉收益，值得在 950 上用 1/2/4 各跑一轮
`timing.py` 对比。

## 3. 磁盘 —— XFS 卷只能用 loop 镜像

```
nvme0n1  7T
├─ p1  900M  vfat  /boot/efi
├─ p2    1G  ext4  /boot
└─ p3    7T  LVM2  → openeuler-root 1004G ext4 /
                   → openeuler-swap    4G swap
                   → openeuler-home  6144G ext4 /home
```

- **`vg_free = 0g`** —— LVM 已分完，切不出新逻辑卷
- 只有这一块盘，没有空闲裸盘、没有空闲分区
- ext4 上 `cp --reflink=always` 实测 **失败**（符合预期，ext4 不支持 reflink）
- `mkfs.xfs 6.6.0` 与 `xfs_info` 都在 ✅

**所以 XFS 套的卷只能是 loop 镜像。** 用 `02-prepare-loop-volume.sh --fs xfs`：
自动挑剩余空间最多的目录，950 上是 `/home`（3.4T 空闲），建 **300G 预分配**镜像。

**ext4 套不用造卷** —— 950 根盘本来就是 ext4，直接用，不设 `ORCHESTRATOR_BASE_PATH`。
这套是我们真正要交付的，它的数字必须来自真盘。

loop 的三项调优（脚本默认全开，跑完会自检打勾）：

1. `--direct-io=on` —— 绕开宿主页缓存，消掉双份缓存与双回写
2. `fallocate` 预分配 —— 消掉写路径上的 extent 分配与碎片
3. `-b 4096` —— 逻辑扇区对齐，消掉读改写

外加 `mkfs.xfs -K`：mkfs 默认对整个设备发一次 discard，loop 会把它翻译成对宿主镜像
打洞，预分配会被当场捅穿（920B 上实际踩到过，第一次建完 300G 只实占 1GB）。

即便调优过，loop 相对真盘仍有开销，**XFS 套的绝对耗时偏悲观**。
正确性和 reflink 省空间的效果不受影响 —— reflink 发生在镜像内部的 XFS 里。
要拿 XFS 套的产品级性能数，得单独配一块真盘走 `--device`。

## 5. e2b 部署现状 —— 三处差异会让脚本报错

| 差异 | 950 | 920B | 影响 |
|---|---|---|---|
| nomad job 名 | **`template-manager-system`** | `template-manager` | `03-switch.sh` / `04-verify-runtime.sh` 写死了 `template-manager`，**在 950 上会找不到 job** |
| `/fc-versions` | 有 `v1.12.1` 和 `v1.13.1` 两套 | 只有 `v1.13.1` | 见下方「fc-versions 的版本号对不上」 |
| `:3000` | **没有监听** | 监听中 | api 没起来，任何测试都跑不了，**得先修** |

### fc-versions 的版本号对不上（已知遗留问题，先不修）

950 上 `/fc-versions/` 有 `v1.12.1` 和 `v1.13.1` 两个目录，
**orchestrator 实际读的是 `v1.13.1`，而放在里面的 Firecracker 其实是 v1.12 那一版**。

这是最早做 ARM 适配时留下的：版本目录名和二进制的真实版本脱了钩。
不影响功能——目录名只是个查找键，读到的就是那个二进制。

**但换二进制时必须记住这一点**：要换的是 `v1.13.1/firecracker`，不是
`v1.12.1/firecracker`。换错了等于没换，而且不会有任何报错，
表现只是"改动没生效"。`04-verify-runtime.sh` 会把实际跑起来的 FC 的 sha 打出来，
换完对一眼就知道。

同理，`e2b-deploy/dep/init-client.sh` 把仓库里的 `firecracker.arm` 拷进
`/fc-versions/v<ver>/firecracker`，走的也是这个目录名。

**结论：先不修。** 修它要动版本号的来源，牵扯部署脚本和已有目录，
收益只是名字好看，风险大于收益。记在这里，以后一起清理。

其余观察：

- `/usr/bin/orchestrator` 与 `/usr/bin/template-manager` 是**同一个二进制**
  （sha `a886ec0d…`，95,854,232 B），来自 `e2b-infra-2026.09-3`。
  不含 gsd、不含 checkpoint —— 正是我们要替换的对象。
- `/opt/e2b-infra/bin/` 里**没有** `orchestrator.orig`
  → 950 是干净的 RPM 部署，没被手工替换过（920B 上则被换过）。
  这对我们是好事：走 RPM 重新部署即可，不用担心覆盖掉谁的手工改动。
- `/fc-versions/v1.12.1/firecracker-bak` 是 2,526,328 B，
  跟我们的 FC（2.6MB）一个量级，而同目录的 `firecracker` 是 8,648,752 B
  （= RPM 里那个 strip 过的官方构建）。看起来之前有人在这台机器上放过自编 FC。
- `client-proxy` 处于 `pending`（920B 上一度也是），不影响 checkpoint 测试。
- 模板/沙箱占用都很小：`/orchestrator` 共 17M，109 个 template 条目。

## 6. 要在 950 上先解决的事

1. **`:3000` 起不来**，必须先修，否则一切免谈。
   920B 上同样症状是三层连锁，可以照着排查：
   - `harbor-portal` 容器挂了 → nginx 起不来 → registry `:30443` 拒连 → api 拉不到镜像
   - `dnsmasq` 没起（`server=/consul/127.0.0.1#8600`）→ 容器解析不了 `redis.service.consul`
   - `nomad`/`consul` 因 SELinux 标签 `user_tmp_t` 报 `203/EXEC`
   排查顺序：`systemctl is-active nomad consul dnsmasq` →
   `docker ps -a | grep -E 'harbor|nginx'` → `nomad alloc status <api-alloc>`
2. **确认 python 环境**：跑脚本前 `conda activate jll-e2b`。
3. **模板存储位置**：`LOCAL_TEMPLATE_STORAGE_BASE_PATH` 不设时默认 `/tmp/templates`，
   而 950 的 `/tmp` 是 **tmpfs 566G** —— 意味着**每次重启模板对象全丢**，
   之后任何沙箱都建不出来。920B 今天就是栽在这里。
   建议在 950 上把这个变量显式指到磁盘路径（如 `/orchestrator/local-templates`），
   一劳永逸。
