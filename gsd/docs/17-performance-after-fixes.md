# 17 · 修复之后的性能：回退、收回与代价模型

## 本章目标

读完本章，你应当能回答：

1. 第一版修复为什么让 restore 慢了约 18 ms，这 18 ms 由哪三块组成，哪两块是 gsd 自己的、怎么收回的？
2. 一次"内核影响不超过 3 ms"的对照为什么是无效的，之后做内核性能对照要遵守哪几条规矩？
3. 剩下的那约 8.7 ms 是怎么一步步定位到"内核代码布局"的；既然有补丁能把它消掉，为什么最终决定不用？
4. 现在一次 create、一次 restore 的耗时由哪些项组成，各自随什么增长？
5. 读这套系统的性能数字时，多大的差别才算差别？

---

上一章（[16](16-restore-slowness-case.md)）讲的是交接时的 gsd 为什么慢。那一轮修完之后，gsd 的 restore 在新 920B 上稳定在 73～76 ms 这一档。
随后开始的是针对正确性的大规模修复：进程发现重写、杀整棵进程树、状态持久化、容量预检、鉴权，以及内核里切换与并发文件操作的互斥。
这些修复没有一项以性能为目标，但它们改变了 restore 路径上的每一步，于是性能也跟着变了。

本章是第二个案例，记录这次变化：先是一次回退，然后收回其中属于 gsd 的部分，再花了相当大的力气定位属于内核的那一部分，最后决定接受它。
末尾给出现在的代价模型。和上一章一样，本章按过程写，包括一次做错了的对照实验。

**关于本章的数字。** 本章的数字都来自新 920B（192.168.45.47），guest 为 2 vCPU、2048 MB，THP 为 never。每组数字都标明日期、代码版本和口径。
它们是在修复过程中的不同模板、不同内核上测的，放在一起只为说明原因和趋势；**不同组之间不能相减，判定值见 [20](20-results-and-gaps.md)**。

---

## 结论先行

- 第一版修复让 restore 的 `total_ms` p50 从约 76 涨到约 94。多出来的约 18 ms 分三块：每次操作多调两次 `systemctl show`（约 9 ms），
  杀进程从"直接杀"改成"先冻结再杀"（约 +1.5～2.5 ms），`criu_restore` 本身变慢（约 +6～10 ms）。
- 前两块是 gsd 引入的，已经收回：进程发现的耗时从 9.0 ms 降到 0.7 ms（`verify_gsd` 8 次 restore 的 p50，见 §2.4），杀进程回到修复前的水平。
- 第三块不在 gsd，在 guest 内核，而且与内核修复的代码内容无关：它是内核代码段整体挪了位置之后，缺页与拷贝路径上的代码落到了一个不利的地址相位上。
  交接时那份内核的布局恰好落在有利的相位，是"碰巧快"。
- 有一个只含填充的补丁可以把相位调回去、消掉这约 8.7 ms，现场验证有效。**最终没有采用**：它是针对这一颗 CPU 和这一版代码的调参，
  之后内核里任何一处改动都要重新复核；我们决定接受普通布局下的性能，不把它入库。
- 现在的单树 restore 约等于 `criu_restore` 加 `kill` 再加不到 1 ms 的其余各项；多树时各项随树的数量线性增长。

## 1. 回退：第一版修复之后慢了 18 ms

第一版修复（21 个提交）在 2026-09-30 第一次上机。功能验证基本通过，但部署自检的 restore 耗时明显变了。
口径：`verify_gsd`，一个持有 192 MiB 匿名内存的进程，同一沙箱里连续 8 次 restore，取各分段的 p50，单位 ms。

| 组合 | `total_ms` | `criu_restore_ms` | `kill_ms` | `find_pids_ms` |
|---|---|---|---|---|
| 修复前（2026-09-23） | 73.1 | | | |
| 修复前（2026-09-30，更换二进制之前） | 75.9 | | | |
| 修复前的 gsd，修复前建的模板 | 75.6 | 64.0 | 11.1 | 不单独计时 |
| 第一版修复，新建的模板（两次） | 93.8 / 94.5 | 70.4 | 13.6 | 9.0 |

六档负载的性能脚本（`demo_checkpoint_perf`，三轮）给出同样的图景：restore 各档慢 18～22 ms，create 各档慢 8～13 ms；
每档都多出约 9 ms 的 `find_pids`，`kill` 从 11.4 涨到 13.0。18 次 restore 的文件与内存校验全部正确，所以这是纯粹的性能问题。

把差值按分段拆开，是三块：

1. **`find_pids` 约 9 ms。** 修复前这一步不单独计时，耗时也可以忽略；修复后每次 create 和 restore 都稳定多出 9 ms。
2. **`kill` 多约 1.5～2.5 ms。**
3. **`criu_restore` 多约 6～10 ms**（`verify_gsd` 里是 64.0 对 70.4，性能脚本各档是 8～10）。

前两块的原因读代码就能确定，第三块在当时是个谜：gsd 调用 criu 的方式几乎没有变。

## 2. 收回属于 gsd 的两块

### 2.1 `find_pids`：两次 `systemctl show`

第一版修复重写了用户进程的发现逻辑。为了把 envd 和 gsd 自己从"要 dump、要杀"的集合里排除出去，每次扫描都调用两次 `systemctl show` 去查这两个服务的主进程号。
在 guest 里单独量，一次 `systemctl show` 的 p50 是 4.0 ms。两次就是 8 ms，再加上逐个读 `/proc/<pid>/stat` 和 `status` 的时间，合起来就是那 9 ms 的量级。

修法有三处，都在同一个提交里（"make process discovery cheap again"，`9c8035627`）：

- **不再为自己查。** gsd 的进程号直接取自身的 pid。
- **envd 的主进程号缓存起来，用 starttime 校验。** 缓存的 pid 在这次扫描里还在、它的启动时间也没变，就是同一个 envd 进程，直接用；
  pid 不在了或启动时间变了（envd 重启过、pid 被复用），才重新查一次（`envdPID`，`ckpt/pid.go:207`）。
  gsd 启动时在后台先查好（`warmEnvdPID`，`ckpt/pid.go:232`，由 `Handle` 在 `ckpt/service.go:140` 触发），所以第一次 create 也不付这笔钱。
  查不到 envd 仍然不算错误（[12](12-failure-semantics.md)）。
- **扫描时整批跳过内核线程。** guest 里 74 个 pid 中有 60 个是内核线程，逐个读它们的 `stat` 和 `status` 是扫描的大头。
  现在先读一次 kthreadd 的子线程名单，名单里的整个跳过；名单之外的照常读 `stat`，标志位表明是内核线程的不读 `status`（`kernelThreads`，`ckpt/pid.go:131`；`scanProcs`，`ckpt/pid.go:83`）。
  名单读不了时不跳过，行为与之前一样，只是慢一些。

用缓存而不是彻底不查，是因为 envd 的进程号确实可能变，而把 envd 误当成用户进程 dump 或杀掉的后果很严重。
用 starttime 校验而不是定时刷新，是因为它没有"刷新间隔内恰好重启"的窗口：pid 和启动时间都对得上的，一定是同一个进程。

### 2.2 一次操作只扫一次 `/proc`

第一版修复里，一次 create 要扫三遍 `/proc`：找进程树的根一遍，记录每个进程 dump 前的状态一遍，容量预检再一遍并且逐个读 `status`。
现在合成一次带 `status` 的扫描，三个用途共用它的结果（`scanUsers`，`ckpt/pid.go:305`；调用处 `ckpt/service.go:180`，预检用 `estimateDumpIn`，`ckpt/service.go:209`）。
create 的 `precheck_ms` 因此从 0.9 降到 0.04。dump 之后枚举被停住的进程仍然要重新扫描，因为 dump 期间可能有新进程被 fork 出来。

restore 这边，扫描被挪到了准备好层目录之后、紧挨着杀进程的位置，并且这次扫描的结果直接当作杀进程的第一轮输入（`ckpt/service.go:504-506`、`:524`），省掉一次重复扫描。
之后每一轮冻结仍然重新扫描，"最后一轮扫描没有发现新进程才算冻结完成"这个条件没有变，所以第一次扫描之后才 fork 出来的子进程照样会被找到并杀掉。

### 2.3 `kill`：先冻结再杀的代价

修复前只对进程树的根发 SIGKILL。这是错的：子进程会被 PID 1 收养后继续运行，占着 pid，导致随后的 `criu restore` 失败（[08](08-process-trees.md)）。
现在是先对整棵树发 SIGSTOP 冻住、反复扫描直到没有新进程、再整体 SIGKILL。多出来的是冻结阶段的扫描和信号。
这一块是正确性的必要代价，不能省；能省的只有上一小节说的那次重复扫描。收回之后，`kill` 的耗时里几乎全是"等被杀进程退出"，
日志里新增的细分项（`freeze_rounds`、`proc_scans`、`scan_ms`、`signal_ms`、`wait_exit_ms`）可以直接看到这一点，各项的定义在 [24](24-configuration-and-observability.md)。

### 2.4 收回之后

口径：新 920B，2026-09-30。

| 指标 | 第一版修复 | 收回之后 | 口径 |
|---|---|---|---|
| `find_pids_ms` | 9.0 | 0.7 | `verify_gsd`，8 次 restore 的 p50；两次用的是各自新建的模板 |
| `kill_ms` | 13.6 | 11.5 | 同上 |
| `criu_restore_ms` | 70.4 | 72.3 | 同上 |
| `total_ms` | 93.8 | 84.7 | 同上 |
| 同一模板上热换 gsd 二进制，restore `total_ms` p50 | 93.1 | 84.1（修复前的 gsd 为 82.7） | 3 轮，每轮每个变体一个新沙箱，各 7 次 |
| 同上，create `total_ms` p50 | 28.3 | 16.1 | 同上 |

当轮的结果汇总把进程发现和杀进程这两项记为 9.1 → 0.6 ms 与 13.1 → 11.5 ms（未注明口径，与上表前两行是同一件事的另一次读数）。

最后两行是最干净的对照：同一个模板、同一个内核，只换 gsd 的二进制。收回之后新旧 gsd 相差约 1.4 ms，大致就是"先冻结再杀"和其他正确性检查的净代价。

但 `verify_gsd` 的 84.7 仍然比修复前的 73～76 高出约 9 ms，而且高出来的部分全在 `criu_restore` 里。

当时在 gsd 这一侧把能想到的候选都试了一遍，每个变体与默认做法逐一对照：把切层之后立即启动的后台回收推迟到 criu 之后，或者干脆不做；
让 criu 的输出直连标准错误，或者用它自己的参数写文件，而不是经管道转发；跳过恢复之前的镜像检查。各变体的 `criu_restore` 在 70.7～75.5 之间，
与默认做法的差别都在沙箱之间的正常波动（约 ±3 ms）以内。结论是这部分时间不在 gsd。同一轮里还有一个更直接的线索：
**同一个修复前的 gsd，在修复前建的模板上 `criu_restore` 是 65.5～66.9，在新建的模板上是 70.7～71.5。** 差别跟着模板走，不跟着 gsd 走。

## 3. 一次失效的对照，以及由此定下的规矩

### 3.1 错在哪

在怀疑内核之前，其实已经做过一次"新旧 gsd × 新旧内核"的 2×2 对照，结论是"内核对 restore 的影响不超过约 3 ms，回退来自 gsd"。这个结论后来被撤销了，因为实验本身是无效的。

实验的做法是：保持模板不变，把宿主上 orchestrator 使用的内核目录从一份切到另一份，然后起沙箱测量。实验者以为这样就换了 guest 的内核。实际上没有。

原因在 [05](05-guest-boot-and-injection.md) 讲过：**模板是一份快照，里面固化了建模板那一刻正在运行的内核。** 沙箱从模板快照恢复出来，不经过重新开机，
宿主上的内核文件在这个过程中根本不被读取。所以切换宿主的内核目录，对已有模板恢复出的沙箱毫无影响；只有此后新建的模板才会用上新内核。

戳破这一点的是在沙箱里读 `/proc/version`：旧模板里的内核构建时间是 9 月 23 日，两个新模板里的都是 9 月 30 日，与当时宿主上"切"到了哪份内核无关。
于是那张 2×2 表的"内核"一维其实从头到尾没有变过，它测到的只是同一份内核上两组测量之间的差别，"不超过 3 ms"说明不了内核的影响。

这同时解释了上一节末尾的线索："差别跟着模板走"的真实含义是"差别跟着模板里固化的内核走"。

### 3.2 重新归因

把实验改对之后只需要一组数据。同一个收回之后的 gsd，分别在两份内核下各建一个模板（新 920B，2026-09-30，`verify_gsd` 口径）：

| 模板里的内核 | `criu_restore_ms` p50 | `total_ms` p50 |
|---|---|---|
| 修复前的内核 | 63.6 | 75.7 |
| 带当时全部内核修复的内核 | 72.3 | 84.8 |

**内核修复让 `criu_restore` 慢了约 8.7 ms。** 而在修复前的内核上，新 gsd 的 `total_ms` 是 75.7，与修复前的 73～76 已经持平。
至此回退的三块全部归位：两块在 gsd，已收回；一块在内核，约 8.7 ms。

### 3.3 之后的规矩

从这次失误里定下了内核性能对照的四条做法，之后所有的内核 A/B 都照此执行（脚本是随手册附带的 `scripts/probes/exp_gsd_swap.py`）：

1. **每个内核各建自己的模板。** 建之前先把宿主切到对应的内核并确认生效。不存在"换内核不换模板"的对照。
2. **在每个沙箱里读 `/proc/version` 核对**，确认它跑的确实是预期的那份内核（`scripts/probes/probe_tpl_env.py` 一次列出模板里的内核、THP、挂载等环境）。
3. **变体逐轮交错，每轮每个变体一个新沙箱。** 机器的整体状态会随时间漂移（同一天里同一个内核的绝对值前后能差 2 ms），
   交错之后漂移对各变体的影响相同，同批之内的差值才可信。
4. **同一个内核建两个模板一起测。** 两个模板之间的差就是"模板间噪声"的直接度量；不同内核之间的差要明显大于它才算数。

第 4 条给出了这套环境里"多大的差别才算差别"的经验值：同一内核的两个模板之间，`criu_restore` 的 p50 相差 0.1～1.1 ms 是常态，偶尔到 1.5～3 ms；
单个沙箱还可能整体离群（一次交错对照里某一轮是 98.9 ms，其余各轮在 71～77）。所以验收时对逐轮交错的对照采用 ±3 ms 的判据（[26](26-acceptance-runbook.md)），
小于这个幅度的差别不解释。

## 4. 那 8.7 ms：从二分到代码布局

### 4.1 二分：全部来自一个"不相干"的提交

当时的内核修复是若干个顺序提交。按提交逐个编出内核、各建模板、交错测量。
口径：新 920B，2026-09-30，192 MiB 的进程，一个 checkpoint 之后连续 8 次 restore 并去掉第 1 次，每轮新沙箱，共三批；表中是 `criu_restore_ms`，单位 ms。

| 内核 | 各轮 p50 的中位数（两个模板） | 全样本 p50 |
|---|---|---|
| 修复前的内核（2026-09-23 构建） | 64.0 / 63.9 | 64.8 / 64.4 |
| 同一份源码，用后来的编译配置重编 | 63.6 / 63.6 | 63.9 / 63.6 |
| 加上第一个修复提交 | 73.2 / 71.5 | 72.7 / 71.7 |
| 再加上第二个修复提交 | 71.8 | 72.2 |
| 加到当时的第一批修复为止 | 74.2 / 73.1 | 74.2 / 72.7 |
| 再加上切换与并发操作互斥的修复 | 72.9 / 72.5 | 73.7 / 72.5 |

第二行是一个必要的对照：它排除了"两份内核的编译环境或配置不同"这种解释。结果很清楚，**约 8.5～9 ms 全部在第一个修复提交处出现，之后的提交不再增加。**
同一内核的两个模板相差 0.1～1.1 ms，不同内核之间相差约 9 ms，信号远大于噪声。

问题在于这个提交做的事：调整切换 ioctl 内部几个步骤的先后顺序，删掉调试打印，删掉 `fs/proc/task_mmu.c` 里的调试计数器。
它没有碰内存管理，没有碰缺页处理，没有碰任何拷贝路径；而 ioctl 本身在一次 restore 里只占不到 1 ms。从代码上看，它不可能让 criu 慢 9 ms。

### 4.2 先看 criu 把时间花在哪

对两份内核各取一份 `criu restore -v4` 的日志对齐：差别集中在"把 49800 个页读回内存"那一段，快的内核 58.2 ms，慢的内核 64.3 ms；其余阶段相同。
这是单次样本，只用来确定方向：变慢的是读回页面的阶段，而不是 fork、cgroup 迁移或文件校验。

### 4.3 排除两个"合理"的解释

**调试打印。** 第一个修复提交删掉了 ioctl 开头和结尾的两行打印，所以快的内核每次 restore 会往内核日志里写两行，慢的内核不写。
打印本身只会让事情变慢，但它有一个副作用：写日志会唤醒日志守护进程，可能让 CPU 没有机会进入深度空闲状态，从而让紧随其后的 criu 跑得更快。

**空闲唤醒。** 这是上一条的一般形式：也许慢的内核只是让 CPU 更容易睡着。

两者用同一个实验排除：在慢的内核的沙箱里起一个后台进程，要么每 10 ms 往 `/dev/kmsg` 写一行，要么以最低优先级空转，然后量 restore。
`criu_restore` 仍是 74.6 和 78.0，与不加后台进程时的 76.3 没有区别，离快的内核的 62.8 很远。

### 4.4 脱离 criu 复现

如果变慢的是"读回页面"，就应该能不靠 criu 复现。在 guest 里写一个微基准，把这个阶段拆成几种基本操作分别计时，各做 192 MiB：

| 操作 | 快的内核 | 慢的内核 |
|---|---|---|
| 只触发匿名内存的缺页 | 67～69 | 67～69 |
| 只读文件 | 15～16 | 15～16 |
| 把文件读进已经缺过页的内存 | 约 15 | 约 15 |
| 从 tmpfs 文件 `preadv` 进**尚未缺页**的匿名内存 | 77～78 | 86～88 |

单位 ms。前三种在两份内核上相同，只有最后一种差约 9 ms，与 `criu_restore` 的差值吻合。最后一种正是 criu 恢复内存的做法：它把镜像文件的内容直接读进一段刚映射、还没有物理页的地址空间，
于是缺页发生在**内核态向用户内存拷贝的途中**。单独的缺页不慢，单独的拷贝不慢，慢的是"拷贝当中缺页"这条路径，折算下来每页约 180 ns。

有了这个微基准，后面的实验就不必每次都跑完整的 restore。

### 4.5 惰性填充实验：与代码内容无关

对比两份内核的符号表发现，缺页和拷贝路径上的几个关键函数（向用户内存拷贝、清零页面等）在两份内核里的地址整体平移了，各自的 64 字节对齐并没有变。
第一个修复提交改变了它所在文件的代码长度，位于它之后的内核代码因此都挪了位置。

于是做了一组不改任何逻辑、只改位置的实验：在快的内核里，往一个与缺页路径毫不相干的位置（`fs/proc` 的代码段里）插入一段永远不会被执行的填充，
让它后面的代码整体后移，然后量同一个微基准。口径：新 920B，2026-09-30，guest 内 192 MiB，中位数，单位 ms。

| 内核 | 微基准 |
|---|---|
| 快的内核（基准） | 77.0 |
| 加上第一个修复提交 | 84.1 |
| 快的内核 + 64 字节填充 | 86.2 |
| 快的内核 + 4 KiB 填充 | 85.7 |
| 快的内核 + 16 KiB 填充 | 83.8 |
| 快的内核 + 64 KiB 填充 | 84.2 |
| 快的内核 + 128 KiB 填充 | 77.9 |
| 快的内核 + 2 MiB 填充 | 80.6 |
| 快的内核，编译时让所有函数按 64 字节对齐 | 84.6 |
| 慢的内核，同上 | 89.1 |

这张表说明了三件事：

1. **只挪 64 个字节就足以让它变慢。** 这段填充不含任何会被执行的指令，语义上是零改动。所以变慢与第一个修复提交"改了什么"无关，只与"后面的代码被挪到了哪里"有关。
2. **挪 128 KiB 又回到快的水平。** 效应是周期性的，周期是 128 KiB：决定快慢的是某一组代码（内核里的库函数、驱动和体系结构相关的库函数那几段）相对缺页路径的地址，以 128 KiB 为模的余数，即"相位"。
3. **快是少数，慢是多数。** 试过的各种位移里，只有恰好保持原相位的那一种是快的；强制函数对齐也不能改善。
   也就是说，修复前那份内核的布局是恰好落在了有利相位上的特例，它是**碰巧快**，其余绝大多数布局都在慢的那一档。

第三点改变了问题的性质。此前的问法是"修复引入了什么让它变慢"，答案是什么也没有引入：任何一个增删了代码的改动，都有很大的概率把布局从那个特例挪走。
由此可以推断，即使不做任何修复，内核里别处的增删（例如跟进上游的小版本）同样可能让这约 8.7 ms 出现；这一点没有专门验证。

为什么相位会影响这条路径的速度，没有继续往下查，要坐实需要在 guest 里用性能计数器做剖析，当时没有做。
对于做决定来说，知道"它由布局相位决定、与代码内容无关"已经足够。

### 4.6 可以用填充消掉

既然是相位问题，就可以用填充把相位调回去。做法是在内核那几段库代码的最前面加两个只含填充的目标文件，把它们的起始地址钉回修复前的相位，代价是约 117 KiB 的内核代码段。
这当中还排除了两种更简单的做法：把入口代码对齐（微基准 77.1，说明入口代码的位置无关紧要）；用 128 KiB 的对齐指令（会把整个代码段的起点后移 64 KiB，微基准 83.7～84.3，说明整体平移同样变慢）。

带上这个填充补丁之后（新 920B，2026-09-30）：

| 内核 | 微基准中位数 | `criu_restore_ms` 全样本 p50（内核对照） |
|---|---|---|
| 修复前的内核，同源码重编 | 77.4 | 65.3 / 65.7（两个模板，各 9 轮） |
| 修复到此为止，不带填充 | 84.7 | 73.6～74.0（两份不带填充的内核各一个模板，各 6 轮） |
| 修复到此为止，带填充 | 77.2 | 65.5 / 64.5（两个模板，各 9 轮） |

带填充的内核与修复前的内核持平（差 −1.2～+0.2 ms），比不带填充的快约 8.5 ms。同一天的 `verify_gsd` 上，`total_ms` p50 从 87.0 降到 80.7。
技术上，这约 8.7 ms 是可以完全追回来的。

### 4.7 为什么最终不处理

2026-10-08 整理内核补丁时，这个填充补丁被拿掉了。它没有进入 `0003-overlayfs-hot-switch-fixes.patch`，仓库里不存在。理由如下。

**它修的不是一个缺陷，而是一次调参。** 这约 8.7 ms 完全由代码布局的相位造成，不对应内核里任何一处写得不好的代码。
填充补丁所做的，是针对"这一颗 CPU"和"这一版内核代码"，把布局手工拨回到那个有利的相位。它不含任何逻辑，功能上没有风险；但它的正确性只在这两个前提同时成立时才成立。

**之后的任何改动都要重新复核。** 填充的大小是按当时各段代码的长度算出来的。当时给出的容忍范围是：文件系统部分的代码量变化在大约 ±32 KiB 以内不受影响；
排在文件系统之前的代码（内存管理、调度、体系结构相关代码）或排在那几段库代码之后的代码有改动，或者文件系统部分的变化超出这个范围，都需要按符号表重新核对相位，必要时重算填充。
换句话说，带着这个补丁，以后每一次改内核、每一次跟进上游的小版本，都要多做一道"检查布局相位并重新调参"的工序，而且这道工序只有理解本章内容的人才做得了。
不做的后果并不严重，只是性能悄悄回到普通布局的水平；但那样一来补丁就成了一段不起作用、却没有人敢删的填充。
而内核修复在那之后并没有停：回收被换下的层、修 rename 与 restore 的竞争、修 work 目录相关的两处缓存，每一轮都在改文件系统部分的代码。

**换一个平台，它没有任何依据。** 相位效应是在这一台机器的这一颗 CPU 上测出来的。在别的 CPU 上，有利的相位是否相同、效应是否存在，都没有数据。
把一个只对单一 CPU 有效的布局写死在内核补丁里，对其他平台可能没有作用，也可能有反作用。

**被放弃的基准本身只是巧合。** 修复前那份内核快，不是因为它做对了什么，而是它的布局碰巧落在了有利的相位上。
把"碰巧快"的那个数当作应当维持的基准，再用持续的人工调参去追它，是把一次巧合当成了承诺。更诚实的基准是普通布局下的性能，它才是这套代码在一般情况下的表现。

所以决定是：**接受普通布局，不把填充补丁入库。** 这约 8.7 ms 不计为回退，而是计为"修复前的基准偏乐观"。它作为设计取舍记在 [03](03-goals-and-tradeoffs.md)。
如果将来某个部署确实需要追回这几毫秒，并且愿意为固定的硬件和固定的内核版本承担复核的工作，做法和复核判据在 [附录 B](B-extending.md)。

### 4.8 拿掉之后的确认

拿掉填充补丁、加上后续修复的内核，与此前几份内核再做一次交错对照。口径：新 920B，2026-10-08，192 MiB，每沙箱 8 次 restore 去掉第 1 次，6 轮，单位 ms。

| 内核 | `criu_restore_ms` 各轮 p50 的中位数 | 切换 ioctl 的 p50 |
|---|---|---|
| 不带填充的旧一轮内核 | 72.8 | 0.337 |
| 带填充的内核 | 66.0 | 0.342 |
| 拿掉填充、加上回收修复（两个模板） | 73.0 / 75.8 | 0.399 / 0.382 |

拿掉之后回到了不带填充时的那一档，比带填充的慢约 8 ms，符合预期。这一批只有 6 轮；其中一个模板比不带填充的旧一轮内核高约 3 ms，是否全是模板间波动，没有再加样本确认。
同一张表还给出了另一个数：回收逻辑让 restore 的切换 ioctl 多了 0.04～0.06 ms，这是后续内核修复在性能上唯一可测的直接代价。

再之后的内核修复（work 目录相关的两处缓存、rmdir 的竞争）在逐轮交错对照里没有带来可测的变化：8 轮，restore `total_ms` p50 为 84.76 对 84.97（2026-10-08）。

## 5. 现状的代价模型

这一节把现在一次操作的耗时拆成各项，并说明每一项随什么增长。举的数字都标了口径，用来建立量级感；判定值见 [20](20-results-and-gaps.md)。

### 5.1 单树 restore

单树 restore 的 `total_ms` 约等于 `criu_restore_ms` 加 `kill_ms`，再加不到 1 ms 的其余各项。
以 2026-10-08 在 `259f1a25c` 上的部署自检为例（`verify_gsd`，192 MiB，8 次 restore 的 p50）：`total_ms` 83.3，其中 `criu_restore_ms` 71.0、`kill_ms` 11.1、`find_pids_ms` 0.7、`precheck_ms` 0.1。

| 项 | 随什么增长 | 说明 |
|---|---|---|
| `criu_restore_ms` | 被恢复进程的内存总量（整条增量链合起来的页数，而不是最后一次增量的大小） | 主体是把页面读回并缺页映射。THP 为 never 使这一项比开大页时高，原因与不能更改的理由见第 6 节 |
| `kill_ms` | 被杀进程的内存总量 | 几乎全是等进程退出、内核归还它的页。64 MiB 的进程约 5 ms，192 MiB 的约 11～12 ms |
| `find_pids_ms` | guest 里的用户进程数 | 不到 1 ms |
| `precheck_ms` | 目标 checkpoint 的树数与增量链的深度 | 检查镜像可读、建好目录，约 0.1 ms |
| `overlay_restore_ms` | 基本恒定 | 一次 ioctl，约 0.3～0.4 ms；其中回收逻辑占 0.04～0.06 ms |

restore 的耗时与"回滚掉了多少改动"几乎无关：它总是杀掉全部进程、恢复全部内存。这是进程级回滚与整机级回滚在成本模型上的根本差别，对照见 [18](18-process-vs-machine-level.md)。

### 5.2 单树 create

create 的 `total_ms` 约等于 `criu_dump_ms` 加 1～2 ms。`criu_dump_ms` 随**本次要写出的页数**增长：全量时是进程的全部匿名内存，增量时只是上次以来的脏页。
同一口径下的三种情形（新 920B，2026-10-08，一棵 64 MiB 的树，8 轮的 p50）：不改内存的增量 dump 约 10 ms，全部改写后的增量 dump 约 43 ms，全量 dump 约 50 ms。
前者是 dump 的固定开销（冻结进程、遍历页表、写元数据），后两者的差别不大，说明页面写出的速度是主要因素。

`stopped_ms`（进程被停住的时长）在单树时只有 0.7～2.4 ms：它从 dump 结束算起，只包含沉下 upper 和清 soft-dirty。dump 本身期间进程也是冻结的，那段时间计在 `criu_dump_ms` 里。

### 5.3 多棵树：线性增长

每棵树各做一次 dump 和一次 restore，串行执行，所以各项随树的数量线性增长。口径：新 920B，2026-10-08，每棵 64 MiB，8 轮的 p50，单位 ms。

| 树数 | 增量 create：`criu_dump` / `stopped` / `total` | 全量 create：`criu_dump` / `stopped` | restore：`criu_restore` / `kill` / `total` |
|---|---|---|---|
| 1 | 10.18 / 0.66 / 11.63 | 49.66 / 2.43 | 27.20 / 5.21 / 33.63 |
| 2 | 20.71 / 11.40 / 22.67 | 92.02 / 45.48 | 56.07 / 6.18 / 63.77 |
| 3 | 33.50 / 23.75 / 36.94 | 138.87 / 91.82 | 83.53 / 10.02 / 94.79 |

从表里可以读出每多一棵 64 MiB 的树的边际代价：restore 约 +28 ms，增量 dump 约 +11 ms，全量 dump 约 +45 ms。

多树时要特别留意 `stopped_ms`。它从**第一棵**树 dump 完算起，而先 dump 完的树要一直停到最后一棵 dump 完，所以它约等于"其余各棵的 dump 时间之和"：
三棵树全量时，最先 dump 的那棵要多停约 92 ms，而单树时只有 2.4 ms。对停顿敏感的负载，应当尽量让需要一起保存的进程成为一棵树（[22](22-semantics-and-limits.md)）。

多树独有的预检（查树间共享的管道和 socket）开销很小：`precheck_ms` 从单树的 0.04 涨到三棵树的 0.13。

串行是有意的选择，理由和并行化时要注意的问题在 [10](10-restore.md)。

### 5.4 可写打开的文件：沉下 upper 时的拷贝

一般情况下沉下 upper 很快（约 0.5 ms，一次改名加一次 ioctl）。例外是 checkpoint 时有文件正以写方式打开着，或被共享可写映射着：
内核要把这种文件留在新的 upper 里，并在沉下去的层里放一份拷贝，拷贝在切换的写锁内完成（[07](07-overlay-concurrency-and-fixes.md)）。

实测（新 920B，2026-09-30，被一个进程以读写方式持有的单个文件）：没有持有时 `overlay_sink_ms` 为 1.7，16 MiB 时 12.9，64 MiB 时 48.0，128 MiB 时 101.5，
折合每 MiB 约 0.8 ms（2026-10-08 在加入回收之后的内核上复测，三档为 12.7、47.5、98.7，同一档；判定值见 [20](20-results-and-gaps.md)）。这段时间里用户进程是停着的，而且所有访问 overlay 的操作都被写锁挡住。
guest 里常驻的、以写方式打开的大文件只有系统日志，它不在 overlay 的层里，不产生这项开销；需要留意的是用户自己长期开着的大文件，例如数据库文件。
这一行为可以用内核模块参数 `overlay.ckpt_move_open` 调整（[24](24-configuration-and-observability.md)），限制见 [15](15-known-limits.md)。

### 5.5 每个请求的固定开销

- **鉴权**：每个 RPC 读一次 MMDS，约 0.63 ms（新 920B，2026-09-30 的修复验证；2026-10-08 确认验证按 secure / 非 secure 分开测的判定值见 [20](20-results-and-gaps.md)）。不缓存的理由在 [04](04-architecture.md)。它不计在 gsd 自报的 `total_ms` 里。
- **经代理的往返**：SDK 测到的端到端时间比 gsd 自报的 `total_ms` 多出的部分，量级是 2 ms 上下。
- **新沙箱的第一个请求**偶尔会有约 5 秒的延迟，发生在宿主一侧，与 gsd 无关，原因未查，见 [15](15-known-limits.md)。测性能时要去掉每个沙箱的第一次请求，本章各口径都是这样做的。

### 5.6 读数时的注意事项

- 两次测量之间差 3 ms 以内不要解释（第 3.3 节）。
- 六档负载的性能脚本三轮之间可能整体漂移一二十毫秒，尤其是同一台机器上还有别的沙箱在跑的时候。它适合看各档之间的相对形状，不适合比较两个版本；比较版本用逐轮交错的对照。
- 压测脚本记录的是脚本一侧的墙钟时间，受并发 worker 数量的影响，不是 gsd 的耗时，不作为性能依据。
- 调试内核（开了内存与锁的检查）上的耗时是发布版的数倍，只用于查正确性，不能读性能。

## 6. THP 为 never 的代价

`criu_restore_ms` 这一项里，有一部分是 THP 关闭带来的：恢复时往全新的地址空间填入全部内存，用 4 KiB 页比用 2 MiB 大页多出许多次缺页。
上一章在旧 920B 上直接量过这个差别（[16](16-restore-slowness-case.md) 的"把 THP 打开"一节）。新 920B 上没有重做这组对照，这里不给数字。

这是性能上最大的一项"明知可以更快而不去做"的代价，理由不是性能上的权衡，而是正确性上的前提：增量 dump 靠 soft-dirty 位，而一个大页只有一个位，
THP 开着时零散的写入会让每次增量都退化成全量。原理和实测在 [02](02-criu-and-incremental-memory.md)。
所以 THP 为 never 不在可调项之列：开机脚本在切换根文件系统之前设置它，gsd 启动时再检查一次并兜底（`ensureTHPNever`，`main.go:196`）。
如果在部署里看到增量 checkpoint 忽然变得和全量一样大，首先要查的就是 THP 是不是被改回去了（[25](25-troubleshooting.md)）。

## 本章要点

1. 第一版修复让 restore 慢了约 18 ms，分三块：两次 `systemctl show`（约 9 ms）、先冻结再杀（约 2 ms）、`criu_restore` 变慢（约 6～10 ms）。前两块在 gsd，已收回。
2. 收回的办法是缓存 envd 的主进程号并用 starttime 校验、一次操作只扫一次 `/proc`、扫描时跳过内核线程；进程发现从 9.0 ms 降到 0.7 ms。
3. 模板固化了建模板时的内核，切换宿主的内核目录不会改变已有模板。一次忽略了这一点的对照得出了错误的"内核影响不超过 3 ms"。
   此后内核对照一律每个内核各建模板、在沙箱里核对内核版本、变体逐轮交错、同一内核建两个模板以度量噪声。
4. 剩下的约 8.7 ms 经二分落在一个只改 ioctl 内部顺序的提交上；排除调试打印和空闲唤醒之后，用微基准复现为"内核向尚未缺页的用户内存拷贝"这条路径变慢。
5. 惰性填充实验证明它只取决于内核代码的布局相位（周期 128 KiB），与代码内容无关；修复前的布局是碰巧落在有利相位上的特例。
6. 填充补丁可以把这约 8.7 ms 完全追回，但它是针对单一 CPU 和单一代码版本的调参，之后任何改动都要重新复核。决定是接受普通布局，不把它入库。
7. 现状：单树 restore 约等于 `criu_restore` 加 `kill` 加不到 1 ms；每多一棵 64 MiB 的树，restore 约 +28 ms、增量 dump 约 +11 ms、全量 dump 约 +45 ms；多树时先 dump 的树要多停"其余各棵的 dump 时间之和"。
8. 另有三项按量计费的代价：可写打开的文件在 checkpoint 时每 MiB 约 0.8 ms；鉴权每个请求约 0.6 ms（判定值见 [20](20-results-and-gaps.md)）；回收逻辑让 restore 的 ioctl 多 0.04～0.06 ms。THP 为 never 的代价不可免除。
