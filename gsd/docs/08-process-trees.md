# 08 · 用户进程树与多树

## 本章目标

读完本章，你应当能够：

- 说出 gsd 怎样从一次 `/proc` 扫描里找出"用户进程"，以及为什么要按**树**来组织它们；
- 给出"根"的精确定义，并对一个具体的进程列表判断它有几棵树；
- 解释"同一棵树"是怎么认定的，它为什么是按树做增量的前提；
- 说清多棵树时的预检拒绝什么、不拒绝什么、检查不出什么，以及为什么选择拒绝而不是放宽；
- 说明 dump 之后放开哪些进程、restore 之前怎么把进程杀干净。

前两章（[06](06-overlay-hot-switch.md)、[07](07-overlay-concurrency-and-fixes.md)）讲的是文件系统这一半。本章转到进程这一半，只讲"对象是谁"：哪些进程、怎么分组、组与组之间有什么限制。
拿这些树去做什么，是后面两章的内容——[09](09-checkpoint.md) 讲 dump，[10](10-restore.md) 讲 restore。本章定义的"用户进程树"和"根"两个术语全书通用。

主要代码：`ckpt/pid.go`（扫描与找根）、`ckpt/shared.go`（多树预检）、`ckpt/criu.go` 的 `killTrees`。

---

## 1. 为什么是"树"

沙箱里与用户有关的进程都是 envd 以 uid 1000 拉起来的：SDK 的每一次 `commands.run` 在 guest 里是 envd 的一个子进程，它自己可能再派生出一串子孙。

CRIU 的 dump 以**一棵进程树**为单位：给它一个根进程号（`--tree`），它保存这个进程和它的全部子孙，恢复时按原来的父子关系和进程号重建。
它不接受"一组互不相干的进程"。所以 gsd 必须回答两个问题：当前有哪几棵树要保存，每棵树的根是谁。

交接前的实现只取"按目录名排序遇到的第一个 uid 1000 的进程"当作唯一的根。`/proc` 的目录名是字符串，`"1203"` 排在 `"850"` 前面，
取到的可能是某棵树中间的一个子进程，也可能只是好几棵树里的一棵——其余的树既不保存也不恢复。现在的实现对当前**全部**用户进程树各做一次 dump、各做一次 restore。

## 2. 一次扫描

### 2.1 读什么

`scanProcs`（`ckpt/pid.go:83`）遍历 `/proc` 下所有数字命名的目录，对每个进程读两个文件：

| 文件 | 取哪些列 | 用途 |
|---|---|---|
| `/proc/<pid>/stat` | 状态、父进程号、标志位、启动时间 | 建父子关系；记录 dump 前的状态；认内核线程；认"同一个进程" |
| `/proc/<pid>/status` | 真实 uid、`RssAnon`、`RssShmem`（都没有时退回 `VmRSS`） | 判断是不是用户进程；容量预检（[13](13-state-concurrency-capacity.md)） |

结果是一张"进程号 → 快照"的表（`procTable`，`pid.go:33`）。扫描过程中退出的进程直接跳过；只有 `/proc` 本身读不了才算错误。
这个错误会让 Create 或 Restore 直接失败（`Internal`），而不是当作"没有用户进程"继续——后者会让 create 返回成功却没有保存任何进程（[12](12-failure-semantics.md)）。

### 2.2 `stat` 的解析

`stat` 的格式是 `进程号 (命令名) 状态 父进程号 …`。命令名可以包含空格和右括号——终端复用器的服务端进程、改过进程标题的工作进程都是现实例子——所以不能按空格切。
`parseStat`（`pid.go:52`）找到**最后一个** `)`，从它之后按空格切分：第 0 列是状态，第 1 列是父进程号，第 6 列是标志位，第 19 列是启动时间。
后两列缺失或解析不了时取 0，不算错误：标志位只用来少读几个文件，启动时间为 0 的后果是"认不出同一棵树，做全量"，都是安全的退化。

### 2.3 跳过内核线程

一个典型的 guest 里有七十多个进程号，其中六十个是内核线程。它们既不是用户进程，也不可能是用户进程的子孙（父进程都是 2 号进程 kthreadd），逐个读它们的两个文件占了扫描的大头。
`kernelThreads`（`pid.go:131`）先读一次 `/proc/2/task/2/children` 拿到 kthreadd 的全部子进程，扫描时整批跳过；不在这份名单里的（kthreadd 自己，或者读名单之后才出现的）照常读 `stat`，
标志位带 `PF_KTHREAD` 的不再读 `status`、不进表。名单读不了（内核没开对应选项）时不跳过，行为与没有这项优化时相同。

代码注释记录的效果是一次扫描从约 2.3 ms 降到约 0.4 ms。这项优化是为了收回修复过程中引入的一次性能回退，来龙去脉见 [17](17-performance-after-fixes.md)。

### 2.4 一次操作只扫一次

`scanUsers`（`pid.go:305`）做一次带 `status` 的扫描，同时算好排除集合，返回一个 `userScan`。之后：

- Create 用**同一次**扫描找根、记录每个进程 dump 前的状态、做多树预检的进程列表、做容量预检的内存估算；
- Restore 用它列出要杀的进程，并且直接把它当作杀进程的第一轮扫描（§6.2）。

用户进程**不缓存**，每次操作都重新扫描：缓存的进程会退出，进程号会被复用，而 restore 需要看到的是此刻的全部用户进程（`ckpt/service.go:67-68` 的注释）。

## 3. 谁是用户进程，谁是根

### 3.1 排除集合

`systemPIDs`（`pid.go:184`）给出三个永远不碰的进程：

- **PID 1**；
- **gsd 自己**（`os.Getpid()`）；
- **envd**：取 systemd 记录的 `envd.service` 主进程号。

后两个其实只是双保险——它们以 root 运行，本来就不会被 uid 过滤选中。

envd 的主进程号要通过 `systemctl show` 查询，在 guest 里一次约 4 ms，比整次扫描还贵一个数量级。所以 `envdPID`（`pid.go:207`）把它缓存起来，
并且每次使用前用本次扫描里的启动时间校验：缓存的进程号在表里还在、启动时间也没变，就是同一个 envd 进程，直接用；否则（第一次、envd 重启过、进程号被复用）才重新查。
gsd 启动时另有一个后台协程把它预先查好（`warmEnvdPID`，`pid.go:232`），第一次 create 或 restore 就不用付这 4 ms。

**查不到 envd 不是错误**，照常按 uid 扫描。envd 正在重启、服务没在跑、`systemctl` 失败都属于这种情况。交接前的实现在这里会整个报错，
连带让 create 静默地降级成"只有文件系统的 checkpoint"，而用户进程明明还在。

### 3.2 用户进程

uid 等于 1000（`userUID`，`pid.go:17`）、且不在排除集合里的进程（`userPIDsIn`，`pid.go:242`）。1000 是 envd 拉起用户命令时使用的 uid，在代码里是常量。

以 root 身份运行的东西——包括用 SDK 以 root 用户执行的命令、系统服务——**不是**用户进程，不被保存也不被杀掉。这条边界是 [01](01-problem-and-scope.md) 里"回滚范围"的进程那一半。

### 3.3 根

`userRootsIn`（`pid.go:259`）的定义分两步：

1. **候选根**：自己是用户进程，而父进程不是用户进程。父进程通常是 envd；被收养之后是 PID 1。
2. **根**：候选根里，祖先链上没有别的候选根的那些（`hasAncestorIn`，`pid.go:282`）。

第二步处理的是嵌套：用户进程 → `sudo`（uid 0）→ 用户进程。最里面那个进程的父进程是 `sudo`，不是用户进程，所以它满足第一步；但它其实在外面那棵树里——
一棵树的成员是"根和它的**全部子孙，不看 uid**"（`subtree`，`pid.go:151`），CRIU 的 `--tree` 也是这样取的。如果把它再当成一棵树单独 dump 一次，
restore 时同一个进程号要被创建两次，后一次必然失败，而那时进程已经被杀掉了。所以它不算根，跟着外面那棵树一起保存、一起恢复。

根按进程号**数值**升序排列，依次编号 `t0`、`t1`……这个顺序就是 dump 的顺序、镜像子目录的名字，也是 restore 的顺序。

### 3.4 数一数

| 沙箱里的情况 | 树的棵数 |
|---|---|
| 空闲，没有任何用户命令在跑 | 0 |
| 一个 `commands.run(..., background=True)` | 1（根是 envd 的那个子进程） |
| 两个后台命令 | 2 |
| 再加一个在某条命令里用 `nohup … &` 起、之后被 PID 1 收养的进程 | 3 |
| 一个后台命令里 `sudo` 再切回用户身份起的进程 | 仍是 1（属于外面那棵） |

前四行是 2026-10-08 的确认验证里用探针脚本在沙箱里实际数过的形状（[19](19-testing-and-debug-kernel.md)）。0 棵树时 create 做的是只有文件系统的 checkpoint（[09](09-checkpoint.md)）。

## 4. "同一棵树"

增量 dump 只写上次 dump 以来被改过的页，所以它必须有一个明确的"上次"——**同一棵树**上一次的镜像。多棵树时不能按序号对应：上次的 `t1` 这次可能已经退出，原来的 `t2` 就成了 `t1`。

gsd 的认定标准是**根进程的进程号和启动时间都没变**（`incrementalParent`，`ckpt/service.go:396`）。启动时间是 `stat` 里的那一列，单位是开机以来的时钟滴答；
进程号可能被复用，但复用它的新进程启动时间不同，所以这两样合起来在一次开机期间唯一确定一个进程。

`Service.lastTrees` 为当前活着的每棵树记着这四样：根进程号、根的启动时间、镜像所属的 checkpoint、镜像目录。下一次 create 对每个根去查：

- 查到了，而且那个 checkpoint 还在条目池里——以它的镜像目录为父做增量；
- 查不到（新起的树、根的进程号被复用）——全量；
- 启动时间读出来是 0——全量；
- 查到了但所属的 checkpoint 已经不在条目池里（不应发生）——全量并告警。父镜像必须属于某个条目，删除逻辑才知道它还被依赖（[13](13-state-concurrency-capacity.md)）。

确认验证里有一个例子正好说明"按根认、不按序号认"：一个有三棵树的 checkpoint 之后退出了一棵，下一个 checkpoint 剩下两棵，其中新编号为 `t1` 的那棵，
父镜像是上一个 checkpoint 的 `t2` 目录。

有一处要特别注意：restore 恢复出来的进程虽然进程号与 dump 时相同，却是**新进程**，启动时间变了。所以 restore 成功后 gsd 用恢复出来的根进程的启动时间重建 `lastTrees`（[10](10-restore.md)）。

## 5. 多棵树之间的预检

### 5.1 问题：每棵树各自 dump，树之间的连接接不回去

每棵树由一次独立的 CRIU 运行保存，再由一次独立的 CRIU 运行恢复。CRIU 只看得见它正在处理的那棵树。如果两棵树之间有一条"连接"，分开保存再分开恢复之后会怎样？
`ckpt/shared.go` 的文件头注释把三种情况分开讲了：

| 树之间的连接 | CRIU 的行为 | 结果 |
|---|---|---|
| 一端在树外的 unix socket 连接 | dump 时自己报错（外部 socket） | create 失败，明确 |
| 匿名管道，一棵树写、另一棵树读 | **照常 dump 成功**；restore 时给只有一端的管道新建一条 | 恢复出两条互不相干的管道，读的一方再也读不到写的一方的数据；create 和 restore 都报成功 |
| 两棵树持有同一个 socket（例如都继承了同一个监听 socket） | 各 dump 一份 | 恢复出两个独立的 socket，"共用"没有了；还可能在 restore 时因地址冲突失败，而那时进程已经杀了 |

第二行是关键。它不是推测：2026-10-08 的确认验证里手工做过——只有一端在树里的匿名管道，两棵树各自 `criu dump` 都返回 0，各自 restore 也成功，
但恢复之后读端的 `cat` 立刻读到文件结束并退出，输出文件不再增长。**两边都报成功，数据通路却静默地断了。** 这是预检存在的前提：
如果 CRIU 会报错，gsd 把错误转出去就够了；正因为它不报，gsd 必须自己在 dump 之前查。

### 5.2 查什么

`crossTreeShared`（`shared.go:49`）只在有两棵或更多树时运行（一棵树没有"树间"，因此单树不付任何代价）。它对每棵树的每个进程读 `/proc/<pid>/fd` 下每个符号链接的目标：
管道是 `pipe:[<inode 号>]`，socket 是 `socket:[<inode 号>]`，同一个内核对象的 inode 号相同。把持有者按对象归组之后：

- **socket**：只要有两个持有者分属不同的树，就算共享。
- **管道**：要进一步看方向。读 `/proc/<pid>/fdinfo/<fd>` 里的 `flags`，取访问模式（`fdAccess`，`shared.go:123`）；只有"一棵树里有写端、另一棵树里有读端"才算共享。

找到第一个就返回（按对象名排序，保证结果确定）。Create 随即返回 `FailedPrecondition`，错误信息由 `describe`（`shared.go:149`）拼出，写明是哪两棵树、各自的根进程号、
哪条管道或哪个 socket、哪个进程的哪个描述符在写或读，并附一句处置建议：把相互连接的进程用同一条命令启动，让它们成为一棵树。此时**什么都没动**——没有 dump，没有切换，没有进程被停过。

### 5.3 不拒绝什么

管道为什么要看方向？因为有一种极常见的"共用管道"并不是树间通信：同一个 shell 派生出几个进程，之后各自被 PID 1 收养成了几棵树，它们的标准输出都是当初那条**通向 envd** 的管道。
几棵树都只持有写端，读端在 envd 手里。这条管道在 restore 之后本来就接不回 envd——单树时也一样——树与树之间并不靠它通信。所以它不算。

确认验证里的对照组就是这个形状：三棵树共用通向 envd 的标准输出，create 不被拒绝。

### 5.4 检查不出什么

- **连接两棵树的 unix socket**：连接的两端是两个不同的 inode，按 inode 归组查不出来。它由 CRIU 在 dump 时报"使用了外部 socket"，gsd 返回 `Internal`，
  错误信息写明是哪棵树并附 `criu-dump.log` 的尾部；在它之前已经 dump 完的树被放开，这次的镜像全部删掉（[09](09-checkpoint.md)）。结果仍然是明确的失败，只是发生得晚一些。
- **树之间共享的匿名共享内存**（`MAP_SHARED|MAP_ANONYMOUS`，只可能来自共同的祖先）：查不出来，CRIU 也不报。restore 之后每棵树各有一份，不再共享（[15](15-known-limits.md)）。
- **读不了的描述符**（进程刚好退出等）：跳过。预检是尽力而为的。

### 5.5 为什么是拒绝，而不是放宽

CRIU 有一些选项可以让它"容忍"外部资源，例如把某个外部 socket 声明为外部的。gsd 一个都没加，理由来自上面那个实测：
这类放宽的效果是让 dump 不再报错，但被声明为外部的连接在 restore 后并不会被接回到另一棵树上——它只是把一个**明确的失败**变成一个**静默的断开**。
对一个承诺"回到那一刻"的功能来说，静默断开比失败更糟：调用方拿到成功的返回，进程也都在，只是互相再也说不上话。

所以策略是：能在 dump 之前查出来的，在什么都没动的时候拒绝；查不出来但 CRIU 会报的，转成明确的失败；两者都不行的（匿名共享内存），写进已知限制。
给使用者的建议始终是同一条——需要相互通信、需要严格一致的进程，用一条命令启动成一棵树（[22](22-semantics-and-limits.md)）。

预检的开销很小：2026-10-08 的验证里，Create 的 `precheck_ms` 在 1、2、3 棵树时的中位数分别是 0.04、0.10、0.13 ms（新 920B，每棵 64 MiB，该项包含容量估算；判定值见 [20](20-results-and-gaps.md)）。

## 6. 停与杀

### 6.1 dump 之后放开谁

dump 之后每棵树都被 CRIU 留在停止状态（原因见 [09](09-checkpoint.md)），最后要由 gsd 发 `SIGCONT` 放开。但不能无差别地放开：
用户自己按 Ctrl-Z 或用 `kill -STOP` 停住的进程，在 dump 之前就是停止状态，checkpoint 不应该替用户把它们唤醒。

所以 Create 在**第一棵树 dump 之前**一次记全所有树里每个进程的状态（`states`，`pid.go:323`）。要在最前面记全，是因为后面的树 dump 时前面的树已经被停住了，那时再看状态就分不清是谁停的。
全部 dump 完之后，`resumable`（`pid.go:414`）从要放开的名单里去掉"dump 前就是 `T`"的进程；dump 前的扫描里还不存在的进程（扫描与 CRIU 冻结之间新派生的）照常放开。

这依赖 CRIU 的一条语义：它开始接管时已经处于停止状态的任务，在镜像里记为停止，restore 之后仍是停止的。因此被用户停住的进程在 create 之后、在 restore 之后都保持停止；
确认验证里把预先停住的进程分别放在 `t0` 和 `t1` 两个位置各测过一遍。这条语义同时也是 gsd **不能**在 dump 之前自己发 `SIGSTOP` 来冻结所有树的原因（[09](09-checkpoint.md)）。

### 6.2 restore 之前怎么杀干净

restore 要求当前用户进程一个不剩（原因在 [10](10-restore.md)）。难点是进程在被杀的过程中还会派生新进程。

只对根发 `SIGKILL` 是不够的：子进程被 PID 1 收养后继续运行，占着进程号——CRIU 要按原进程号重建整棵树，会报 `Can't fork … File exists`——
还会带着 checkpoint 之后的状态继续写文件系统。逐个发 `SIGKILL` 也不够：扫描到杀掉之间新派生的子进程会漏网。

`killTrees`（`ckpt/criu.go:215`）的做法是**先冻住，再清点，最后一起杀**：

1. 取种子进程（全部用户进程）和它们的全部子孙——子孙不看 uid。
2. 对其中还没冻过的进程逐个发 `SIGSTOP`。被冻住的进程不会再派生。
3. 重新扫描 `/proc`，回到第 1 步，直到某一轮扫描**没有发现新进程**。这时名单是完整的：名单里的都停着，不可能再长出新的。
   轮数上限是 10（`maxFreezeRounds`，`criu.go:188`），正常一两轮收敛，上限只为防止病态情况下的死循环；到上限仍在增长时记一条错误，继续往下杀。
4. 对名单里的全部进程发 `SIGKILL`。
5. 在总共 3 秒的时限内（`killWaitTimeout`，`criu.go:184`）逐个等它们退出并让出进程号。

第一轮直接使用调用方刚做的那次扫描，省一次 `/proc` 遍历；之后每一轮都重新扫描，所以"最后一轮没有新进程"这个收敛条件不变——第一轮里漏掉的会在第二轮被找到。
函数永远跳过 PID 1 和 gsd 自己。

等待退出用的是 `waitForProcessExit`（`criu.go:298`）：先用进程文件描述符等退出事件（进程一退出就返回，微秒级），再确认 `/proc/<pid>` 消失。
gsd 通常不是被杀进程的父进程——envd 拉起的由 envd 回收，restore 恢复出来的由 PID 1 回收——所以它只能等别人回收之后进程号被释放，自己是父进程时才顺手回收。
交接前这里是每 10 ms 轮询一次，杀进程的耗时因此总是 10 的整数倍（[16](16-restore-slowness-case.md)）。

`killTrees` 返回实际发过信号的进程号，以及一组细分统计（冻结轮数、扫描次数、扫描耗时、发信号耗时、等退出耗时），Restore 把它们打进日志，是排查 `kill_ms` 异常的入口（[25](25-troubleshooting.md)）。

## 本章要点

1. CRIU 以树为单位，所以 gsd 以树为单位：当前全部用户进程树各 dump 一次、各 restore 一次，按根进程号升序编号 `t0`、`t1`……
2. 用户进程是 uid 1000 且不是 PID 1、gsd、envd 的进程；根是"父进程不是用户进程、且祖先里没有别的根"的用户进程；一棵树包含根的全部子孙，不看 uid。
3. 一次操作只扫一次 `/proc`，跳过内核线程，envd 的主进程号缓存并用启动时间校验；查不到 envd 不是错误，读不了 `/proc` 才是。
4. "同一棵树"按根的进程号加启动时间认定，这是按树做增量的依据；restore 恢复出的进程启动时间变了，要重新记。
5. 多棵树时，一条管道的读写两端分在两棵树里、或两棵树持有同一个 socket，create 在什么都没动的时候被拒绝；只是被多棵树继承、另一端在 envd 的管道不算。
6. 选择拒绝而不放宽，是因为实测表明只有一端在树里的管道 dump 和 restore 都成功却静默断开；树间的 unix socket 连接由 CRIU 报错，树间的匿名共享内存检查不出来。
7. dump 后只放开 dump 前不是停止状态的进程；restore 前先冻住、反复扫描到没有新进程、再整体杀掉并等进程号释放。
