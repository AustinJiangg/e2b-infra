# 01 · 进程级回滚：问题与定位

## 本章目标

读完本章，你应当能够：

- 说清 gsd 面向的场景，以及这个场景里"值得回滚的状态"为什么只有用户进程和文件；
- 列出一次 restore 会回滚什么、不会回滚什么，并说出每一项不回滚的原因；
- 比较"整机快照"和"进程快照"两条路线：各自保存什么、恢复时做什么、代价大致落在哪里；
- 说清 gsd 是一个什么样的程序：跑在哪、以什么身份、对外提供哪几个接口；
- 理解"范围内 / 范围外"这条分界线，它是后面很多设计和限制的来源。

上一章（[00](00-overview.md)）给了全书的地图。本章从问题本身讲起，把"进程级"三个字的含义钉死：
后面每一章说到"被回滚的""不被回滚的"，指的都是本章 §2 的那两张表。下一章（[02](02-criu-and-incremental-memory.md)）
讲进程那一半所依赖的 CRIU 和增量内存原理。

## 1. 场景

### 1.1 Agent 想退回上一步

一个 AI Agent 在沙箱里执行任务，典型的过程是一连串步骤：克隆代码、装依赖、起一个开发服务器、改几个文件、跑测试。
任何一步都可能把环境弄坏：装错了版本、删错了目录、把一个长时间运行的进程改崩了。它需要的是：

> 回到上一步结束时的样子，换个做法再试一次。

这里的"样子"由两样东西组成：

- **文件**：代码、配置、装进系统的包、临时文件；
- **正在运行的用户进程**：例如那个开发服务器、一个打开着的解释器、一个跑到一半的后台任务，连同它们内存里的状态。

只回滚文件是不够的。假设开发服务器在内存里缓存了某个配置文件的内容，文件退回去了、进程没退，
两者就对不上；反过来只回滚进程也不行。所以文件和进程必须**一起**回到同一时刻。

### 1.2 什么不需要回滚

同一个沙箱里还有很多别的状态：内核自己的数据结构、页缓存、网络协议栈、`systemd` 和它管理的系统服务、
负责执行 SDK 命令的 envd。对"退回上一步"这个需求来说，它们大多不是任务的一部分：

- 任务不关心内核的调度队列长什么样、页缓存里缓存了哪些块；
- envd 是 SDK 与沙箱之间的通道，把它也退回去意味着 SDK 手里的连接、正在等待结果的调用全部失效；
- 系统服务（日志、时间同步）的状态退回去没有意义，日志反而是希望保留下来的东西。

于是出现了一个选择：是把整台虚拟机当成一个整体退回去，还是只退回任务真正关心的那部分。
gsd 选的是后者，这就是"进程级"的含义。

## 2. 回滚什么，不回滚什么

这两张表是全书的基准。面向使用者的展开版本（带例子和建议）在 [22](22-semantics-and-limits.md)。

### 2.1 被回滚的

| 对象 | 具体指什么 | 由谁完成 |
|---|---|---|
| 用户进程树 | uid 为 1000 的进程，连同它们的全部子孙。envd 启动用户命令时默认用的就是这个 uid | CRIU（[02](02-criu-and-incremental-memory.md)、[09](09-checkpoint.md)、[10](10-restore.md)） |
| overlay 根文件系统 | guest 的 `/` 上的一切：`/etc`、`/home`、`/opt`、`/usr`、`/var` 的大部分，以及 `/tmp` | overlayfs 热切层（[06](06-overlay-hot-switch.md)） |

关于"用户进程树"需要先说明四点，完整定义在 [08](08-process-trees.md)：

- **用 uid 划界**。gsd 不靠进程名、不靠 cgroup，只看 uid 是不是 1000（`userUID`，`ckpt/pid.go:17`）。
  一个 uid 为 1000 的进程，如果它的父进程不是 uid 1000（通常是 envd，被收养之后是 PID 1），它就是一棵树的**根**。
- **一棵树包含根的全部子孙，子孙不看 uid**。用户进程里用 `sudo` 起的子进程虽然是 root 身份，也属于这棵树，跟着一起保存和恢复。
- **直接以 root 身份起的命令不在范围内**。SDK 允许指定用 root 执行命令，这样起的进程不是 uid 1000，
  gsd 不保存它、restore 时也不杀它，它属于 §2.2 的"root 起的其他服务"那一类。
- **可以有很多棵树，也可以一棵都没有**。SDK 每起一个后台命令就是一棵树；空闲的沙箱里没有用户进程，
  这时 checkpoint 只保存文件系统，restore 也只回滚文件系统。

关于文件系统也有一点要强调：`/tmp` **在回滚范围内**。它是 overlay 根的一部分，不是单独挂载的内存文件系统。
这样安排是因为用户进程经常在 `/tmp` 里开着文件，如果进程回到了过去而 `/tmp` 没有，CRIU 恢复进程时可能因为文件已经被删掉或改了大小而失败
（`/tmp` 的处理细节见 [05](05-guest-boot-and-injection.md)）。

### 2.2 不被回滚的

| 对象 | 为什么不回滚 | restore 之后是什么样 |
|---|---|---|
| PID 1（`systemd`） | 它是所有进程的祖先，杀不得也重建不得 | 一直在运行，不受影响 |
| envd | SDK 的通道；以 root 运行，本来也不会被 uid 选中 | 一直在运行。SDK 经 envd 执行命令、读写文件的能力不受 restore 影响 |
| gsd 自己 | 执行回滚的人不能回滚自己 | 一直在运行；它记录的 checkpoint 列表不随 restore 变化 |
| root 起的其他服务 | 不是 uid 1000，不在范围内 | 一直在运行，但它们看到的文件系统在脚下被换掉了（见 §5） |
| 内核状态 | CRIU 只保存用户进程；内核态（页缓存、网络栈、时钟、内核线程）不属于任何一棵用户进程树 | 不变。时钟不会倒退，内核的缓存照常 |
| `/run`、`/dev/shm` | 是独立挂载的内存文件系统，不在 overlay 上 | 保持 restore 那一刻的内容 |
| checkpoint 的镜像目录 | 镜像放在一个独立挂载的 2 GiB 内存文件系统里（`/var/lib/gsd/snapshots`）；它要是被回滚，较新的 checkpoint 就没了 | 不变 |
| `/var/log`、`/var/lib/systemd`、`/var/lib/chrony` | 开机时从底层的 ext4 直接绑定进来，绕过了 overlay | 保持 restore 那一刻的内容。日志因此不会被回滚掉 |
| overlay 的层目录（`/overlay`）和基础镜像（`/mnt/lower`） | 它们是 overlay 的"原料"，同样从 ext4 绑定进来 | 由 gsd 管理，不属于被回滚的内容 |
| 沙箱之外的一切 | 已经发出去的请求、写进外部数据库的数据 | 任何快照都退不回来 |

这张表里有两类"不回滚"，性质不同：

- 一类是**有意划出去的**：PID 1、envd、gsd、系统服务、内核。它们不属于"任务的状态"。
- 另一类是**根文件系统搭建方式的结果**：`/run`、`/dev/shm`、`/var/log` 等目录不在 overlay 上，所以切层切不到它们。
  这一类会带来一个需要知道的限制：被恢复的进程如果在 checkpoint 时开着 `/dev/shm` 或 `/run` 里的文件，
  而这个文件后来被删掉或改了大小，CRIU 恢复它时可能失败（[15](15-known-limits.md)）。

哪些目录在 overlay 上、哪些不在，是开机脚本 `overlay-init` 决定的。它的文件头注释列出了完整的划分，
逐步的挂载过程见 [05](05-guest-boot-and-injection.md)。

## 3. 两条路线

要把一个运行中的沙箱退回过去，有两条技术路线。它们保存的东西不一样，恢复的方式也不一样。

### 3.1 整机快照

把虚拟机当成一个黑盒：保存全部 guest 内存、vCPU 寄存器、设备状态和磁盘。保存和恢复都在虚拟机**外面**做，
由 Firecracker 和宿主上的编排程序完成，guest 里什么都不需要装。

- **保存什么**：整台机器。用户进程、内核、页缓存、系统服务，全在里面。
- **怎么恢复**：把内存和设备状态放回去。guest 里的每一个进程，包括内核自己，都"回到了过去"，没有任何进程被杀掉或重建。
- **代价落在哪**：增量保存时要知道整个 guest 内存里哪些页被改过，这需要宿主侧的脏页跟踪；
  保存的量包含了内核和页缓存的改动，不只是用户进程的。恢复时写回的量与"退回去多远"成正比。
- **边界**：因为连内核一起退，跨越回滚的网络连接会失效，guest 的单调时钟会倒退。

同一个仓库里的整机级 checkpoint / restore 走的就是这条路线，它有自己的手册。

### 3.2 进程快照

打开黑盒，只保存里面的一部分：选定的一组用户进程，加上文件系统。保存和恢复都在虚拟机**里面**做，
由 guest 内的一个守护进程调用 CRIU 完成。

- **保存什么**：选定进程的内存、寄存器、打开的文件等；文件系统单独处理。内核状态和别的进程不保存。
- **怎么恢复**：进程没有办法"原地退回"，只能把现在的进程杀掉，再按镜像重新创建：重新 fork 出同样 PID 的进程、
  重新映射内存、把页面内容读回来、重新打开文件。
- **代价落在哪**：保存的量只是这组进程改过的页，比整机少；但恢复是重建，要把进程的**全部**内存读回来，
  代价取决于进程有多大，与这一步改了多少基本无关。此外杀进程本身也要时间。
- **边界**：范围外的东西不回滚（§2.2）；被保存的进程必须是 CRIU 能处理的；恢复期间有一段时间用户进程是不存在的。

gsd 走的是这条路线。

### 3.3 一个建立直觉的例子

两条路线"拍下的东西不一样"，从产物的大小上看得最清楚。下面这组数来自一次早期的对照：
同一个负载（一个常驻的用户进程改写 192 MB 内存，同时往磁盘写 64 MB 文件），两套各拍一个增量 checkpoint。

| | 内存那一半的产物 | 包含了什么 |
|---|---|---|
| 进程级 | 约 194 MB | 那个用户进程改过的页。写文件的 64 MB **不在里面**，文件由 overlay 的层单独承担 |
| 整机级 | 约 276.5 MB | 用户进程改过的页，加上那次写文件留在 guest 页缓存里的页，再加内核自己的少量改动 |

> 条件：旧 920B（已退役），2026-09-08，交接时的代码，两套各跑一次，单位照原记录写作 MB。
> 这组数只用来说明"范围不同"，不是当前代码的性能数据；判定值见 [20](20-results-and-gaps.md)。

这张表说明了三件事。第一，进程级拍得少，是因为它不拍内核状态和页缓存。第二，在进程级这里，
内存和文件是两种不同的东西，由两种不同的机制负责；在整机级那里，文件写入的一部分也表现为内存的改动。
第三，不能脱离范围去比较两套的耗时——它们做的不是同一件事。完整的对照在 [18](18-process-vs-machine-level.md)。

### 3.4 为什么两条路线都存在

进程快照不是整机快照的"轻量版"，整机快照也不是进程快照的"完整版"。它们在一个问题上取了相反的答案：
**要不要让范围之外的东西保持不动。**

- 整机级的答案是"不要"：一切都回去，语义最简单（沙箱整体回到那一刻），代价是范围外的连接和时钟也一起回去；
- 进程级的答案是"要"：只有用户进程和文件回去，envd、系统服务、内核照常运行，
  代价是出现了一条"范围内 / 范围外"的分界线，分界线两侧的东西在 restore 之后不再属于同一时刻（§5）。

哪一种合适取决于任务。本书只讲进程级怎么做、做到了什么程度；选型的讨论集中在 [18](18-process-vs-machine-level.md)。

## 4. gsd 是什么

gsd 的全称是 Guest Sandbox Daemon。它是一个用 Go 写的守护进程，静态编译成单个可执行文件。

| 属性 | 值 | 说明 |
|---|---|---|
| 运行位置 | 每个沙箱（Firecracker 虚拟机）内部 | 由 systemd 以 `gsd.service` 管理，崩溃后自动重启 |
| 身份 | root | 它要读所有进程的 `/proc`、给用户进程发信号、调用 CRIU、对根文件系统发 ioctl |
| 监听 | `0.0.0.0:49984`（`defaultPort`，`packages/gsd/main.go:28`） | SDK 的请求经宿主的代理转进来 |
| 接口 | Connect RPC 服务 `checkpoint.Checkpoint` 的四个方法，加一个 `/health` | 见下表 |
| 鉴权 | 除 `/health` 外，每个请求都要带沙箱的 access token | 与 envd 用同一个 token（[04](04-architecture.md)） |
| 依赖 | guest 里的 CRIU（固定路径 `/usr/sbin/criu`）；打了补丁的 guest 内核 | [03](03-goals-and-tradeoffs.md) |

四个 RPC（定义在 `packages/gsd/spec/checkpoint/checkpoint.proto`）：

| RPC | 做什么 | 实现 |
|---|---|---|
| `CreateCheckpoint` | 保存当前全部用户进程树和文件系统，返回 checkpoint ID 和各阶段耗时 | `CreateCheckpoint`（`ckpt/service.go:163`），详见 [09](09-checkpoint.md) |
| `RestoreCheckpoint` | 杀掉当前全部用户进程，把文件系统切回目标 checkpoint，再恢复当时的进程 | `RestoreCheckpoint`（`ckpt/service.go:463`），详见 [10](10-restore.md) |
| `ListCheckpoints` | 列出本沙箱现有的 checkpoint | `ListCheckpoints`（`ckpt/service.go:745`） |
| `DeleteCheckpoint` | 删除一个 checkpoint；如果别的 checkpoint 的增量还依赖它，先隐藏、稍后回收 | `DeleteCheckpoint`（`ckpt/service.go:764`），详见 [13](13-state-concurrency-capacity.md) |

`GET /health` 不需要 token，正常时返回 `{"status":"ok"}`，gsd 处于降级状态时返回 `degraded` 和原因，两种情况都是 HTTP 200
（降级的三种来源见 [12](12-failure-semantics.md)）。

gsd 不是用户自己装进沙箱的。orchestrator 在**构建模板**的时候把 gsd 的可执行文件、它的 systemd 单元和开机脚本 `overlay-init`
一起放进模板，并把模板的启动入口换成 `overlay-init`；之后从这个模板创建的每个沙箱里都有一个已经在运行的 gsd。
这个过程和它的开关见 [05](05-guest-boot-and-injection.md)。

需要记住 gsd 的两个特点，它们在后面多次出现：

- **它只在沙箱内部工作，宿主看不见它的状态。** checkpoint 的列表、镜像、层，全都在沙箱里。
  宿主上的 orchestrator 在运行期不参与 checkpoint / restore，只是把请求转进来（[04](04-architecture.md)）。
- **它管得住的只有 uid 1000 的进程。** 它可以让用户进程停下来、杀掉它们、重建它们；
  但它没有办法让 PID 1、envd 或别的 root 服务在层切换的那一刻停止访问文件系统。

## 5. 范围内与范围外：一条分界线

把回滚范围限定在"用户进程 + overlay 根文件系统"，换来的是保存量小、范围外的东西不受打扰。
但这条分界线也带来三个后果，后面的章节都在处理它们。

**后果一：范围外的进程会跨越切换继续运行。** checkpoint 或 restore 把 overlay 的层换掉的那一刻，
root 的服务和 envd 的文件接口可能正在读目录、写文件、重命名。内核必须保证这种并发不会让系统崩溃，
这是 [07](07-overlay-concurrency-and-fixes.md) 的主题。即使不崩溃，这些进程在 restore 之后手里拿着的目录和文件
也可能属于一条已经被丢弃的历史，本书把它叫作"被丢弃的时间线"；它们会看到什么、哪些操作会返回错误，
属于语义问题，在 [22](22-semantics-and-limits.md) 说明。

**后果二：范围内的进程与范围外的状态可能对不上。** 一个被恢复的用户进程回到了 checkpoint 那一刻，
但它连着的 envd、它在 `/run` 里留下的文件、它依赖的某个系统服务都停留在现在。
进程如果与范围外的东西保持着联系（管道、socket、内存文件系统里的文件），恢复之后这些联系可能已经失效。
最常见的一种——用户进程的标准输出是一条通向 envd 的管道——在 [08](08-process-trees.md) 讨论。

**后果三：范围内部也不是一个不可分的整体。** 多棵用户进程树是一棵一棵分别保存、分别恢复的。
它们的文件系统是同一时刻的，但两棵树之间存在很短的先后差；如果两棵树用管道或 socket 直接相连，
分别恢复之后就接不回去，所以这种情况下 checkpoint 会被拒绝（[08](08-process-trees.md)、[09](09-checkpoint.md)）。

这三条都不是实现上的疏漏，而是"只回滚一部分"这个选择的必然结果。[03](03-goals-and-tradeoffs.md) 把它们作为取舍逐条列出，
[15](15-known-limits.md) 把由此而来的限制汇总成表。

## 6. 先认识几个词

下面几个词从下一章起会不加解释地使用，完整的术语表在 [A](A-glossary-and-code-map.md)。

| 词 | 含义 |
|---|---|
| checkpoint | 既指"保存"这个动作，也指保存下来的那个点。一个 checkpoint 由若干棵树的 CRIU 镜像和一个层栈组成 |
| restore / 回滚 | 把用户进程和根文件系统放回某个 checkpoint 那一刻 |
| 进程级 / 整机级 | 本书讲的这一套 / 另一本手册讲的那一套 |
| 用户进程树、根 | 见 §2.1；严格定义在 [08](08-process-trees.md) |
| 层、upper、work、层栈 | overlay 的只读层、当前可写层、overlay 自己用的工作目录、从上到下的全部只读层（[06](06-overlay-hot-switch.md)） |
| 切换 | 一次热切层 ioctl。checkpoint 做一次（把 upper 沉下去），restore 做一次（把层栈换回去） |
| 镜像 | CRIU 保存一棵进程树得到的一组文件，放在一个目录里（[02](02-criu-and-incremental-memory.md)） |
| 时间线 | 沙箱文件系统的一段历史。restore 之后，从目标 checkpoint 到 restore 之前的那一段称为"被丢弃的时间线" |

## 本章要点

1. gsd 面向的需求是"退回上一步"，而这一步里值得回滚的状态是**用户进程**和**文件**，两者必须回到同一时刻。
2. 被回滚的：uid 1000 的用户进程树（含全部子孙）和 overlay 根文件系统（含 `/tmp`）。
   不被回滚的：PID 1、envd、gsd、root 的其他服务、内核状态，以及不在 overlay 上的 `/run`、`/dev/shm`、`/var/log` 等目录和镜像目录。
3. 整机快照在虚拟机外面把整台机器放回去，没有进程被重建；进程快照在虚拟机里面只保存选定的进程，恢复时必须杀掉并重建它们。
   前者的恢复代价随"退多远"变化，后者随"进程有多大"变化。
4. gsd 是沙箱内以 root 运行的守护进程，监听 49984，提供 Create / Restore / List / Delete 四个 RPC 和一个免鉴权的 `/health`；
   它由 orchestrator 在构建模板时装进去，运行期宿主不参与。
5. "只回滚一部分"带来一条范围内外的分界线：范围外的进程跨越切换继续运行、范围内外的状态可能对不上、多棵树之间不是一个整体。
   这三点是后面许多设计和限制的来源。
6. 两套方案不是同一件事的两种实现，不能脱离范围比较耗时；对比和选型只在 [18](18-process-vs-machine-level.md)。
