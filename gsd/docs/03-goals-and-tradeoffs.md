# 03 · 设计目标、约束与取舍

## 本章目标

一套系统的形状，一半由它要做什么决定，另一半由它**明确不做什么、明确接受什么代价**决定。读完本章，你应当能够：

- 说出 gsd 的三个设计目标，以及"改动面"被限定在哪四个地方；
- 列出七条硬约束，说明每一条是从哪里来的、违反了会怎样；
- 复述四项取舍，各自换来了什么、付出了什么，对应的限制在哪一章；
- 列出明确的非目标；
- 在读后面各章时，认出某个设计细节是在落实本章的哪一条。

前两章给了原料：[01](01-problem-and-scope.md) 划定了回滚范围，[02](02-criu-and-incremental-memory.md) 讲了进程那一半的原理和它带来的两条约束。
本章把目标、约束、取舍收在一处。第二部分从下一章（[04](04-architecture.md)）开始进入实现，那里的每一个设计决定都能在本章找到出处；
[15](15-known-limits.md) 里标为"设计如此"的每一项限制，也都对应本章的某一条取舍。

## 1. 目标

### 1.1 三个目标

| 目标 | 具体含义 | 推出什么 |
|---|---|---|
| **不停机** | checkpoint 和 restore 期间虚拟机一直在运行，不暂停 vCPU、不重建沙箱 | 只能在 guest 内部动手；停下来的只能是被保存的那些用户进程，而不是整台机器 |
| **不改 Firecracker** | 虚拟机监控器保持原样 | 不能依赖宿主侧的脏页跟踪和内存快照接口；脏页信息要在 guest 内核里自己取（soft-dirty，[02](02-criu-and-incremental-memory.md)） |
| **改动面可控** | 只动四个地方：guest 内核、guest 里的守护进程、模板构建流程、SDK | 宿主上的运行期路径（创建沙箱、转发请求、暂停与恢复沙箱）不增加逻辑 |

三条合起来，就是 [01](01-problem-and-scope.md) 里"进程快照"那条路线：在虚拟机里面，只保存选定的用户进程和文件系统。

### 1.2 改动面的四个地方

| 位置 | 做了什么 | 在哪一章 |
|---|---|---|
| guest 内核 | 两个补丁：`0002-overlayfs-hot-switch-checkpoint.patch`（热切层 ioctl 与 arm64 的 soft-dirty）和 `0003-overlayfs-hot-switch-fixes.patch`（在它之上的全部修复） | [06](06-overlay-hot-switch.md)、[07](07-overlay-concurrency-and-fixes.md) |
| guest 守护进程 | gsd 本身：进程发现、调用 CRIU、驱动层切换、状态管理 | [08](08-process-trees.md)–[13](13-state-concurrency-capacity.md) |
| 模板构建 | orchestrator 建模板时把 gsd、它的 systemd 单元和开机脚本放进模板，换掉启动入口，并做一次自检 | [05](05-guest-boot-and-injection.md) |
| SDK | `sandbox.checkpoint` 的四个方法、连接配置、错误映射 | [21](21-quickstart.md)、[12](12-failure-semantics.md) |

值得注意的是 orchestrator 的参与**只在建模板的时候**。沙箱运行期间，宿主对 checkpoint / restore 一无所知，
它只是像转发其他端口一样把发往 49984 的请求送进沙箱（[04](04-architecture.md)）。
这个注入可以整体关掉：把 orchestrator 的环境变量 `HOST_GSD_PATH` 设成小写的 `off`，建模板的流程就与没有 gsd 时完全一样
（`GSDEnabled`，`packages/orchestrator/internal/cfg/model.go:39`）。

### 1.3 没有写进目标的东西

本书没有把某个耗时数字列为设计目标。原因是进程级 restore 的耗时主要由"被恢复的进程有多大"决定（[02](02-criu-and-incremental-memory.md)），
它随业务而变，不是一个可以用常数概括的指标。性能方面本书做的是两件事：把交接时不该有的开销找出来去掉（[16](16-restore-slowness-case.md)），
以及给出修复后的代价模型，让使用者能估算自己的场景（[17](17-performance-after-fixes.md)）。实测数字只在 [20](20-results-and-gaps.md)。

## 2. 硬约束

下面七条不是可以调的参数，而是这套方案成立的前提。任何一条不满足，要么功能不可用，要么结果不可信。

| # | 约束 | 从哪里来 | 不满足会怎样 |
|---|---|---|---|
| 1 | guest 内核必须打 `0002`、`0003` 两个补丁 | 热切层的 ioctl 和 arm64 的 soft-dirty 都在补丁里；`0003` 修掉了会导致内核崩溃和数据错误的问题 | 没有 `0002`：ioctl 不存在，gsd 的 overlay 管理无法工作。只有 `0002` 没有 `0003`：能跑通主路径，但并发场景下不安全（[07](07-overlay-concurrency-and-fixes.md)） |
| 2 | 内核配置打开 `CONFIG_CHECKPOINT_RESTORE` 与 `CONFIG_MEM_SOFT_DIRTY` | 前者是 CRIU 的前提，后者是增量的前提 | CRIU 无法运行，或者每次都是全量 |
| 3 | **只支持 arm64 的 guest** | 见 §2.1 | x86_64 的 guest 里 CRIU 跑不起来 |
| 4 | 透明大页必须是 `never` | soft-dirty 的粒度（[02](02-criu-and-incremental-memory.md)） | 增量几乎每次都退化成全量 |
| 5 | CRIU 4.x，位于 `/usr/sbin/criu` | gsd 写死了这个路径；基础镜像里带的是源码编译的 4.2.1 | 建模板时的自检失败，模板建不出来 |
| 6 | 镜像放在 guest 内一个 2 GiB 的内存文件系统里 | 见 §2.2 | —（这是一条容量约束，不是开关） |
| 7 | overlay 的所有层在同一个文件系统上 | 见 §2.3 | ioctl 拒绝切换 |

### 2.1 为什么只支持 arm64

有两个各自独立的原因，任何一个都足以排除 x86_64：

- **x86_64 的 guest 内核配置没有打开 `CONFIG_CHECKPOINT_RESTORE`**（`fc-kernels/configs/x86_64/6.1.158.config:220`；
  arm64 的那份是打开的，`fc-kernels/configs/arm64/6.1.158.config:196`）。没有它 CRIU 不能工作，soft-dirty 也选不上。
- **补丁里的 soft-dirty 只做了 arm64。** `0002` 在 `arch/arm64/` 下补上了这个架构原本缺的实现（[02](02-criu-and-incremental-memory.md)），
  整套方案的开发和验证也都只在 arm64 上进行。

x86_64 上游内核本身是有 soft-dirty 的，所以把配置打开、在 x86_64 上把整套验证重做一遍，原则上是可行的；
但这件事没有做，本书不对 x86_64 上的行为作任何保证。

### 2.2 镜像为什么放在 guest 的内存里

CRIU 的镜像写在 `/var/lib/gsd/snapshots`，这是开机脚本挂的一个上限 2 GiB 的内存文件系统。放在内存而不是根盘上，有两个理由：

- **它不能在 overlay 上。** 镜像目录如果是根文件系统的一部分，restore 把根文件系统切回过去时，较新的 checkpoint 的镜像就跟着消失了。
- **它的生命周期要和内核里的层栈一致。** gsd 的状态文件也放在这里。内存文件系统在 guest 重启时清空，
  而 overlay 的层栈在 guest 重启时也回到初始状态，两者同生共死，gsd 启动时用"状态文件在不在"就能判断这是不是开机后的第一次启动
  （[13](13-state-concurrency-capacity.md)）。

代价是直接的：**镜像占的是 guest 自己的内存**。一个 2 GiB 内存的沙箱里，用户进程占得越多，留给镜像的就越少；
而镜像的大小又正比于用户进程的内存。两者此消彼长，所以 gsd 在每次保存之前做容量预检，估算放不下就拒绝，
而不是写到一半把内存耗尽（估算方法见 [13](13-state-concurrency-capacity.md)）。这也是使用上"要定期删除不用的 checkpoint"的原因（[22](22-semantics-and-limits.md)）。

与此相对，文件那一半（overlay 的层）占的是 guest 的根盘，不占内存。

### 2.3 层为什么必须在同一个文件系统上

overlay 在挂载时会探测可写层所在文件系统的一系列能力（是否支持某些重命名方式、扩展属性、文件名长度等），之后一直沿用探测结果。
热切层不重新探测，所以新的可写层必须还在原来那个文件系统上，探测结果才继续成立。
修复后的 ioctl 明确检查这一点，不满足时返回 `-EXDEV`（`0003-overlayfs-hot-switch-fixes.patch` 的 `ovl_do_ioctl_checkpoint`）；
同一个函数还拒绝带 index 目录的挂载（`-EOPNOTSUPP`），因为 index 不随切换更新。

gsd 的部署形态天然满足这条约束：所有的层目录都在 `/overlay` 下，而 `/overlay` 和基础镜像 `/mnt/lower` 都来自同一个 ext4 根盘
（[05](05-guest-boot-and-injection.md)）。把它列为硬约束，是提醒改部署形态的人：不要把层目录挪到另一块盘上。

还有一条相关的容量约束：ioctl 的参数是一个选项字符串，里面要列出每一个只读层的路径，而它的长度上限是一个内存页（4 KiB，`maxOverlayOptionsLen`，`ckpt/overlay.go:31`）。
层栈因此有深度上限。现场连续做 checkpoint，前 190 次成功，第 191 次被 gsd 拒绝并给出原因
（新 920B，2026-09-30，提交 `a35ce1993`；判定值见 [20](20-results-and-gaps.md)，预检的做法见 [13](13-state-concurrency-capacity.md)）。

## 3. 取舍一：状态全在 guest 里

**选择。** gsd 的全部状态——有哪些 checkpoint、每个 checkpoint 由哪些层和哪些镜像组成、当前的层栈、下一次增量的父镜像——
都在 guest 内部：一份在 gsd 进程的内存里，一份持久化在内存文件系统上的 `state.json`。宿主上没有任何账本。

**换来了什么。**

- 宿主的运行期路径完全不用改，orchestrator 不需要理解 checkpoint；
- 没有"宿主账本与 guest 实际状态不一致"这一类问题：状态和它描述的对象在同一台虚拟机里；
- 沙箱删除时什么都不用清理，镜像和层随沙箱的内存和磁盘一起消失；
- gsd 崩溃重启后能从状态文件恢复，与内核里的层栈重新对上（[13](13-state-concurrency-capacity.md)）。

**付出了什么。**

- **宿主看不见。** 宿主无法列出某个沙箱有哪些 checkpoint，无法统计占用，也无法替沙箱回收。容量管理只能由沙箱内的预检和使用者自己的删除来完成。
- **与这台虚拟机共存亡。** guest 重启，checkpoint 全部丢失；checkpoint 不能拿到另一个沙箱上用，也不能离开沙箱保存。
- **占的是沙箱自己的资源。** 镜像占内存，层占根盘（§2.2）。
- **依赖 guest 没有被破坏。** 如果 guest 里有人以 root 身份删掉了镜像目录或层目录，gsd 只能在 restore 之前的检查里发现并拒绝（[10](10-restore.md)）。

沙箱被暂停再恢复（宿主对虚拟机做快照再加载）时，gsd 进程连同它的内存、内存文件系统上的文件、内核里的层栈是作为一个整体被冻结和恢复的，
按设计 checkpoint 仍然可用，状态不需要重新加载（`ckpt/state.go` 的文件头注释）。这一点目前**未验证**：没有专门的现场结果（[20](20-results-and-gaps.md) 的缺口表）。

## 4. 取舍二：每棵树一次 CRIU，串行

**背景。** 沙箱里常常不止一棵用户进程树：SDK 每起一个后台命令就是一棵。而 CRIU 的一次 dump 只能保存一棵树（[02](02-criu-and-incremental-memory.md)）。

**选择。** 有几棵树就调用几次 CRIU，一棵接一棵地做；restore 也是按同样的顺序一棵接一棵地恢复。每棵树有自己的镜像目录和自己的增量链。

**换来了什么。**

- **实现简单。** 每次 CRIU 调用互不相干，镜像目录互不相干，增量的父子关系按树各管各的。
- **失败语义清楚。** 保存时任何一棵失败，整个 checkpoint 失败：已经保存完的树被放开，这次的镜像全部丢弃，沙箱回到原状。
  恢复时某一棵失败，错误信息里写明哪几棵已经恢复、哪一棵失败、哪几棵还没有尝试（[12](12-failure-semantics.md)）。
- **不需要给 CRIU 放宽条件。** gsd 没有使用任何让 CRIU 忽略"树外连接"的选项，CRIU 报错就是错。

**付出了什么。**

- **耗时随树的数量线性增长。** 下面是一组说明趋势的数（每棵树 64 MiB，1、2、3 棵树）：restore 的总耗时是 32.9、60.4、93.3 ms，
  checkpoint 的总耗时是 11.2、21.8、33.5 ms。

  > 条件：新 920B，2026-10-08，提交 `259f1a25c`，多棵树验证脚本的性能用例，gsd 侧 `total_ms` 的中位数，checkpoint 是内存没有改动时的增量。
  > 判定值与口径见 [20](20-results-and-gaps.md)。

- **树与树之间不是原子的。** 后保存的树在先保存的树已经停住之后还多运行了一小段时间（大约是前面那些树的保存时间）。
  文件系统是一致的——所有树都停住之后才切层——但两棵互相协作的树，恢复之后看到的对方状态可能比自己旧这么一小段（[09](09-checkpoint.md)）。
- **树间直接相连的不支持。** 分开恢复的两棵树，它们之间的管道和共用的 socket 接不回去。更糟的是，对管道来说 CRIU 不会报错：
  保存和恢复都成功，只是连接静默地断了。所以 gsd 在保存之前自己检查，发现两棵树共用管道或 socket 就拒绝（[08](08-process-trees.md)）。

**为什么不并行恢复。** 各棵树之间没有依赖，原则上可以同时恢复。没有这样做的原因写在 `RestoreCheckpoint` 的注释里（`ckpt/service.go:463` 的函数体内）：
每个 CRIU 恢复都要把进程迁回原来的 cgroup、按指定的 PID 建进程，并发时对内核里相关锁的争用没有实测过；一棵失败时其余几棵的收尾也更复杂。
先保证正确和可解释，并行留给以后（[B](B-extending.md)）。

**给使用者的含义。** 需要严格一致、或者彼此用管道相连的一组进程，应当由同一个命令启动，使它们成为一棵树（[22](22-semantics-and-limits.md)）。

## 5. 取舍三：范围外的进程，保证安全，不保证一致

**背景。** [01](01-problem-and-scope.md) 已经说过，gsd 只管得住 uid 1000 的进程。层切换的那一刻，PID 1、envd、其他 root 服务都在正常运行，
它们可能正在访问文件系统，也可能手里一直拿着某个目录（当前工作目录）或某个打开的文件。

**为什么不干脆把它们也停住。** 停住解决不了问题。一个被停住的进程，手里的目录和文件引用并不会消失，等它继续运行时，
这些引用指向的仍然是切换之前的对象。要让它们"干净"，只有杀掉重启——而 envd 承载着 SDK 的连接，PID 1 根本杀不得。
所以这些进程必然会带着切换之前的引用活到切换之后，内核必须正面处理这种情况。

**选择。** 分成两个层次的保证：

- **安全是必须的。** 无论范围外的进程在切换的瞬间做什么文件操作，内核都不能崩溃、不能损坏数据、不能卡死。
  做法是用一把读写锁把"切换"和"所有会读取文件后端状态的 overlay 操作"隔开，切换时把内核缓存里的每个文件和目录对象都按计划改写一遍。
  这是交接后投入最多的部分，整整一章（[07](07-overlay-concurrency-and-fixes.md)）。
- **一致的视图不保证。** restore 之后，范围外的进程手里的旧引用可能属于被丢弃的时间线。内核对它们的处理是有明确规则的，但不是"一切如常"：
  - 手里拿着一个目录、而这个目录在目标时间线里仍然存在：目录被"复活"，之后经过它看到的是目标时间线的内容；
  - 手里拿着一个打开的文件：它继续看到旧时间线里的那份内容，与新打开同一路径看到的不是同一个东西；
  - 以一个已经不属于当前时间线的目录为起点做修改：返回 `ESTALE`（"文件句柄已过期"）。

**换来了什么。** envd、SDK 的连接、系统服务在 restore 前后一直可用，不需要重连，也不需要重启。

**付出了什么。** 范围外的长期运行进程如果把当前工作目录放在会被回滚的路径下，或者长期开着会被回滚的文件，
restore 之后可能遇到 `ESTALE` 或者读到旧内容。这些情形的完整描述和建议在 [22](22-semantics-and-limits.md)，限制条目在 [15](15-known-limits.md)。
此外，`/proc/mounts` 里显示的 overlay 选项一直是开机时的那一组，不反映当前的层栈，也是这一类"只保证工作、不保证看起来一致"的遗留。

## 6. 取舍四：性能上接受普通的代码布局

这一条是在修复过程中做出的决定，放在这里是因为它确定了"性能做到哪里为止"。

修复内核侧的问题之后，在逐轮交错的内核对照里，restore 中 CRIU 那一段比用修复前的内核时慢了约 8 到 9 ms
（新 920B，2026-09-30，gsd 侧 `criu_restore_ms` 的中位数；完整数据见 [17](17-performance-after-fixes.md)，判定值见 [20](20-results-and-gaps.md)）。追查的结果是：这段差距与新增代码的内容无关，
而是内核代码段的**布局**变了——新增的代码把后面的函数整体往后推，某些热点函数相对于内存页边界的位置随之改变，
在这台机器的处理器上恰好落在一个较慢的位置。实验表明，只要在代码段里塞一段不执行任何功能的填充、把布局调回原来的相位，
这段差距就消失了。

可以把这段填充留在补丁里。最终没有这样做，理由是：

- 那是针对**这一款处理器**和**当前这一版代码**的调参。以后任何一处内核改动、换一款处理器，都可能让它失效，需要重新测量和调整；
- 交接时的布局并不是特意调过的，只是碰巧落在了快的位置上。把"碰巧"固化成依赖是不合适的；
- 不带填充的后果只是性能回到普通布局的水平，不影响正确性。

所以结论是接受普通布局，并把来龙去脉记录下来。完整的定位过程和数据在 [17](17-performance-after-fixes.md)；
如果将来确实需要把这几毫秒追回来，做法和复核的判据在 [B](B-extending.md)。

这条取舍的一般含义是：本书对性能的态度是去掉不该有的开销，而不是为某一个测试数字做不可维护的优化。

## 7. 非目标

下面这些明确**不做**。有的是别的机制的职责，有的是当前范围之外。

| 非目标 | 为什么划出去 |
|---|---|
| **跨沙箱使用 checkpoint、迁移** | 状态、镜像和层都在这台虚拟机内部，并且与它的内核层栈绑定（§3） |
| **把 checkpoint 持久化到宿主** | 同上。需要离开沙箱保存状态时，用宿主侧对整个沙箱的快照 |
| **回滚内核状态** | CRIU 只保存用户进程。需要连内核一起回滚时用整机级（[18](18-process-vs-machine-level.md)） |
| **x86 的 guest** | §2.1 |
| **保存树与树之间共用的管道、socket** | 每棵树单独保存和恢复，接不回去；gsd 在保存前拒绝（§4） |
| **回滚不在 overlay 上的目录** | `/run`、`/dev/shm`、`/var/log` 等（[01](01-problem-and-scope.md)） |
| **兼容 CRIU 保存不了的进程** | gsd 不为此给 CRIU 加放宽的选项；保存失败时如实报错，带上日志尾部。本书没有整理 CRIU 不支持特性的清单（[20](20-results-and-gaps.md) 的缺口表） |

把这些划出去换来的是：不需要宿主侧的存储和回收、不需要跨节点的一致性、不需要离线加载和格式迁移。
代价在 §3 已经列过：checkpoint 走不出这台虚拟机。

## 8. 这些取舍怎样落到实现上

上面的目标和取舍，在实现里表现为三条反复出现的做法。读后面各章时可以对照。

**先检查，后动手；不可逆的步骤只有一个。** checkpoint 没有不可逆的步骤：任何一步失败都退回原状。
restore 唯一不可逆的步骤是杀进程，所以所有能做的检查和准备都排在它之前（镜像和父链是否可读、切层用的目录能否建好、选项字符串是否放得下）。
于是失败被清楚地分成两类："什么都没动"和"进程已经没了"（[10](10-restore.md)、[12](12-failure-semantics.md)）。

**宁可拒绝，不静默降级。** 因为状态在 guest 里、宿主看不见（§3），一次"报了成功但其实没做全"的操作很难被发现。
所以扫描进程失败时不会退化成"只保存文件系统"，overlay 初始化失败时不会"照常返回成功但不切文件系统"，
镜像放不下、层栈太深、树间有共用管道，都在动手之前明确拒绝并说明原因（[12](12-failure-semantics.md)）。

**停住的只是必须停住的。** "不停机"落到实现上，是把停顿限制在被保存的用户进程身上，并且只在必须的那一段：
从一棵树保存完，到层切换和 soft-dirty 清零完成（[02](02-criu-and-incremental-memory.md)、[09](09-checkpoint.md)）。
范围外的进程从不被停住，内核侧用锁保证它们与切换互不破坏（§5）。

## 本章要点

1. 三个目标：**不停机**、**不改 Firecracker**、**改动面限定在 guest 内核、guest 守护进程、模板构建和 SDK**。宿主只在建模板时参与，运行期不参与。
2. 七条硬约束里最要记住的三条：**只支持 arm64 的 guest**；**透明大页必须是 `never`**；**镜像放在 guest 的 2 GiB 内存文件系统里，占的是沙箱自己的内存**。
3. 取舍一：状态全在 guest 内。换来宿主零改动和没有账本不一致；代价是宿主看不见、checkpoint 走不出这台虚拟机、容量靠沙箱自己管。
4. 取舍二：每棵进程树各做一次 CRIU，串行。换来简单的实现和清楚的失败语义；代价是耗时随树数线性增长、树之间不是原子的、树间直连的管道和 socket 不支持。
5. 取舍三：对范围外的进程，切换**保证安全**但**不保证一致的视图**。换来 envd 和系统服务不受打扰；代价是陈旧目录出发的写会返回 `ESTALE` 等语义上的边角。
6. 取舍四：接受普通的内核代码布局，不为单一处理器做布局调参；代价是比交接时那个碰巧较快的布局慢几毫秒。
7. 实现上的三条做法——先检查后动手、宁可拒绝不静默降级、只停必须停的——都是从上面的目标和取舍推出来的。
