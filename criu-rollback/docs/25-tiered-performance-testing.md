# 25 · 分档性能测试：怎么测、怎么比

## 本章目标

- 分清三类测试：开发阶段的功能测试、开发阶段的性能测试、开发完成之后的对外评测，以及它们对负载的要求有什么不同。
- 说清两套快照回滚现在的分档性能测试各是怎么测的，950 上 2026-11-18 测出了什么。
- 说清现在的测法拿来比较两套为什么不合理。
- 给出两次分析得出的测试设计：第一次（§5）和第二次（§6），以及第二次分析时发现的可以改核心逻辑的地方（§7）。

这一章是测试设计的工作稿，会随讨论多次修改。每次修改保留前一次的结论和理由，只在后面追加，方便对照为什么改。

本章引用的实测数字都标明了平台和日期，出处在 [22](22-950-results.md)、[24](24-vs-sandbox-level.md) 和沙箱级手册[第 18 章](../../rollback/docs/18-950-performance.md)。

## 1. 三类测试

两套快照回滚的测试按目的分成三类。前两类在开发阶段，第三类在开发完成之后。

### 1.1 开发阶段的功能测试

**回答的问题：** 功能对不对。checkpoint 之后 restore，内存、文件、进程是否都回到那一刻；失败时是否按约定失败；并发、容量、长跑下是否仍然对。

**怎么用：** 不对就修 bug，修完重跑。判据是 PASS / FAIL，没有“快慢”。

**现有的脚本：** 进程级的 `verify_*.py`、四组压测（[18](18-testing-and-debug-kernel.md)）；沙箱级的 crtest 功能回归、smoke 正确性验收（沙箱级手册[第 16、17 章](../../rollback/docs/16-test-methodology.md)）。

### 1.2 开发阶段的性能测试

**回答的问题：** 功能都对了，但是哪里慢、慢在哪一段、改了之后有没有变快。

**怎么用：** 找到瓶颈，改核心逻辑，用同一个测试比较改前改后。

**对负载的要求：** 要能**归因**。所以负载可以是人为的、极端的：只改一个量、其余固定；故意取最坏情况把代价放大；配合服务端分段计时、CRIU 统计、对照组。负载像不像真实使用不重要，重要的是能把时间对应到代码里的某一步。附录 [D](D-restore-slowness-case.md)、[E](E-regression-case.md) 的归因过程就是这一类。

前两类测试基本都由 AI 编写、运行和解读，修改的对象是快照回滚的核心逻辑。功能都对、性能达标之后，开发阶段结束。

### 1.3 开发完成之后：对外评测

开发结束之后的性能测试，本书称为**对外评测**。“评测”说的是它不判对错，只测量和说明；“对外”说的是它的读者是项目之外的人：要看懂两套方案有多快、为什么快、各自好在哪里，并据此选型。

**回答的问题：**

1. 每一套方案有多快，能不能达到客户的参考线（checkpoint ≤ 200 ms、restore ≤ 100 ms，客户端墙钟）。
2. 为什么是这个速度：耗时由哪几项组成，每一项多少。
3. 两套方案相比，在什么负载下哪一套更快、快多少。

**对负载的要求：** 与开发阶段相反，负载要能对应真实使用；条件要写全、能被别人复现；比较两套时要公平。开发阶段那种“故意取最坏情况”的负载可以出现在评测里，但必须标明是最坏情况，不能当作典型值。

| | 开发阶段功能测试 | 开发阶段性能测试 | 对外评测 |
|---|---|---|---|
| 读者 | 开发者 | 开发者 | 客户、评审、选型的人 |
| 判据 | PASS / FAIL | 改前改后的差，能否归因 | 不判对错，给数字和解释 |
| 负载 | 覆盖各种语义情形 | 单因素、可取极端 | 对应真实使用，标明最坏情况 |
| 结果之后 | 修 bug | 改核心逻辑 | 写进手册与汇报 |
| 什么时候跑 | 每次改动 | 每次性能相关改动 | 开发完成后、每个交付版本 |

对外评测的脚本就是两套的**分档性能测试脚本**。本章其余部分都在讨论它应该怎么设计。

## 2. 现在是怎么测的

### 2.1 四个脚本

| 脚本 | 测哪一套 | 内存负载 | 文件负载 | 档位 |
|---|---|---|---|---|
| `bench_tiers.py`（沙箱级 `run.sh perf`） | 沙箱级 | 覆写 `/dev/shm` 里预热好的 tmpfs 文件 | 覆写根盘上的大文件，然后 `sync` | 混合档按内存 3 : 文件 1；另有纯内存、纯文件、只读档 |
| `demo_checkpoint_perf.py`（进程级验收） | 进程级 | 常驻 Python 进程里本档大小的 `bytearray` | SDK 写一个本档大小的文件，然后 `sync` | 混合 3 : 1，进程大小随档位一起变 |

### 2.2 950 上的结果（2026-11-18）

这次在 950 上两套都跑了两种分档测试：各自的混合分档用来看每一套能不能达到参考线；同负载对比用两套跑同一个脚本、同样的负载，只换快照回滚的实现。**判断哪一套更快，以同负载对比为准。** 下面所有数都是 2026-11-18、宿主没有配置 UB 时跑的。

**一、各自的混合分档（内存 : 文件 = 3 : 1）。** 两边都取服务端耗时的 p50，单位 ms。沙箱级是 perf-full 的 `total`，每档 n = 60～100；进程级是 extended 里验收测试三轮的中位数，每档 n = 3。

| 总改动 MiB | 沙箱级 checkpoint | 进程级 checkpoint | 沙箱级 restore | 进程级 restore |
|---:|---:|---:|---:|---:|
| 0 | 14.5 | 7.9 | 17.9 | 8.6 |
| 16 | 18.7 | 14.0 | 22.4 | 13.9 |
| 32 | 24.2 | 19.9 | 27.0 | 18.1 |
| 64 | 36.2 | 28.5 | 36.0 | 28.1 |
| 128 | 64.9 | 47.5 | 53.0 | 44.6 |
| 256 | 117.5 | 86.3 | 97.9 | 81.3 |

表面上每一档都是进程级更低，但这张表**不能用来比较两套的快慢**（§3）。它的用处是看各自能不能达标：沙箱级混合档 p50 与 p99 全部达标的最高档是 128 MiB；192 MiB 档 restore 的 p99 是 109 ms，超线；256 MiB 档 restore 的 p50 是 99.8 ms，正好压在 100 ms 线上；512 MiB 档两项都超线。

**二、同负载对比（判断快慢以这组为准）。** guest 里一个常驻进程预分配 P MiB 内存，每次改其中 d MiB；文件负载是根盘上一个 f MiB 的文件。客户端墙钟 p50，单位 ms，每个测点 n = 20。

① 只改内存（进程固定 256 MiB）：

| 改动 d MiB | 沙箱级 checkpoint | 进程级 checkpoint | 沙箱级 restore | 进程级 restore |
|---:|---:|---:|---:|---:|
| 0 | **7.0** | 19.6 | **20.4** | 94.5 |
| 16 | **14.9** | 24.4 | **24.2** | 97.8 |
| 64 | **20.2** | 41.2 | **41.3** | 102.5 |
| 128 | **27.9** | 57.1 | **59.7** | 95.9 |
| 256 | **41.0** | 93.2 | **89.1** | 98.9 |

② 进程大小变化（每次改 16 MiB）：

| 进程 P MiB | 沙箱级 checkpoint | 进程级 checkpoint | 沙箱级 restore | 进程级 restore |
|---:|---:|---:|---:|---:|
| 32 | **13.4** | 16.6 | 23.4 | **22.8** |
| 64 | **15.0** | 19.4 | **27.3** | 36.9 |
| 128 | **14.6** | 19.1 | **25.4** | 60.0 |
| 256 | **15.5** | 24.3 | **26.7** | 123.3 |
| 384 | **15.3** | 26.8 | **27.5** | 164.0 |

③ 只写文件（进程 16 MiB，内存不改）：

| 文件 f MiB | 沙箱级 checkpoint | 进程级 checkpoint | 沙箱级 restore | 进程级 restore |
|---:|---:|---:|---:|---:|
| 16 | 34.2 | **11.2** | 31.1 | **19.2** |
| 64 | 106.2 | **12.2** | 51.9 | **22.5** |

④ 第一次全量 checkpoint：沙箱级 254～433 ms，与进程大小无关，因为它保存的是整台 guest 的内存；进程级 36～206 ms，随进程大小增长。每个测点都是进程级更低。

⑤ 16 个沙箱同时做：两侧服务端耗时基本不变。checkpoint 是 14.6 对 17.2 ms，restore 是 27.5 对 36.8 ms，都是沙箱级在前。

**三、按负载的构成看谁更快。**

| 负载的构成 | 谁更快 | 原因 |
|---|---|---|
| 改内存的 checkpoint | 沙箱级 | 一页不改时 7.0 对 19.6 ms；每多改 1 MiB 多 0.11 对 0.29 ms。沙箱级在宿主上直接写差分；进程级要冻结进程、扫描整个进程的页表，并且只能在 guest 的 2 个 vCPU 上写 |
| 进程较大时的 restore | 沙箱级 | 沙箱级只写回改过的页，每 MiB 回滚量约 0.27 ms；进程级每次重建整个进程，每 MiB 进程大小约 0.40 ms，和改了多少无关 |
| 很小的进程 | 接近 | 32 MiB 进程的 restore 是 23.4 对 22.8 ms |
| 写文件 | 进程级 | 进程级只做一次层切换，不搬数据。沙箱级要在 vCPU 暂停期间，把宿主上还没写回的磁盘数据经 NBD 推进写层，每 MiB 约 1.3～1.5 ms。测试是写完立刻 checkpoint，所以这是最坏情况（§6.2） |
| 第一次全量 | 进程级 | 进程级只保存用户进程，沙箱级要保存整台 guest |

粗算的分界（950，p50）：restore 方面，每次改 16 MiB 时，进程小于约 35 MiB，进程级才不比沙箱级慢；即使整个进程都被改写，进程也要小于约 75 MiB 进程级才占优。checkpoint 方面，内存改 64 MiB 的同时，写的文件超过约 16 MiB，进程级的 checkpoint 就更低。

2026-11-17 那一轮各自的混合分档得出过“六档都是进程级更低”。那一轮宿主还配置着 UB；混合档里 1/4 是文件，进程级一侧的进程又小，这两点都偏向进程级。负载换成相同、内存改动为主以后，950 上是沙箱级更低。

## 3. 现在的测法有什么问题

**用各自的混合分档比较两套，不合理：**

1. **两套的代价由不同的量决定。** 沙箱级的 checkpoint 主要看文件写入量，每 MiB 1.3～1.5 ms；进程级的文件写入几乎不花时间，但它的 restore 要看进程有多大，每 MiB 0.40 ms。3 : 1 这个比例和进程大小怎么取，直接决定结果是哪一套更快。
2. **两侧的内存负载不是同一种东西。** 沙箱级改的是 `/dev/shm` 里的 tmpfs 文件，它不属于任何进程，CRIU 不保存它；进程级改的是一个进程自己的 `bytearray`，而且进程大小随档位一起变，256 档的进程只有约 205 MiB。
3. **样本量差很多。** 一边 60～100 次，一边 3 次。

混合分档用来看单一套方案自己能不能达到客户的参考线，仍然有用。

**同负载对比解决了“同一负载”，但还有局限**（[24](24-vs-sandbox-level.md) §5.7）：文件写完立刻 checkpoint；内存改写只有连续页；只有一棵进程树；每个测点 n = 20；没有真实负载的比例。

## 4. 写文件的代价与 O_DIRECT：测试要模拟到哪一层

讨论测试设计之前先回答一个问题：沙箱级写文件慢，是因为 Firecracker 打开磁盘时没有用 `O_DIRECT` 吗？真实使用时会打开吗？测试要不要打开它？

**`O_DIRECT` 不是沙箱用户能选的东西。** 沙箱里的程序照常读写文件，它只经过 guest 自己的页缓存。`O_DIRECT` 说的是宿主上的 Firecracker 怎样打开根盘背后的块设备，这是平台的部署配置。Firecracker 的 virtio-blk 根本没有这个选项：`DiskProperties::open_file` 只设读写；能配的只有 `cache_type`（`Unsafe` / `Writeback`）和 IO 引擎。orchestrator 配根盘时什么都没设（`setRootfsDrive`），用的是默认的 `Unsafe`。所以测试环境和生产环境用的就是同一种打开方式，测试在这一点上已经是真实的，不需要、也没有办法“打开 `O_DIRECT`”。

**慢的直接原因不是“没开 `O_DIRECT`”，而是 checkpoint 时数据还没进写层。** 沙箱级要求写层与内存快照对应同一时刻，所以 checkpoint 在暂停窗口里把宿主块设备页缓存中还没写回的数据经 NBD 推进写层（沙箱级手册[第 18 章 §5.4](../../rollback/docs/18-950-performance.md#54-写文件的代价由什么决定)）。不开 `O_DIRECT` 决定的是这些数据**在什么时候**推进去：

- 现在（缓冲写入）：guest 写回很快返回，数据先停在宿主页缓存里，由宿主内核在约 30 s 后自行写回；如果在这之前 checkpoint，就由 checkpoint 在暂停窗口里推。
- 假如改成直写（`O_DIRECT`，或 `cache_type = Writeback` 让 guest 的 `fsync` 传到宿主）：数据在 guest 写回或 `fsync` 的那一刻就经 NBD 送走，checkpoint 时不用再推；但这部分时间加到了沙箱里程序的写盘上。

推送的总量一样，变的只是由谁、在什么时候付。所以“没开 `O_DIRECT` 所以慢”这个说法不准确，准确的说法是：**分档测试在数据刚进宿主页缓存的那一刻做 checkpoint，正好让 checkpoint 付了全部推送的代价。**

**真实使用里，checkpoint 时数据在哪，取决于用户的行为。** 920B 上的实验（沙箱级手册第 18 章 §5.4）对同一个 64 MiB 文件改变两件事：写完是否 `fsync`，写完之后多久 checkpoint。

新 920B（`kvm-wp`，沙箱级栈），同一个 64 MiB 文件，每组 5 次，p50，单位 ms：

| 写法与时机 | checkpoint 时数据在哪 | checkpoint 期间经 NBD 推送 | 冻结窗口 | 墙钟 |
|---|---|---|---|---|
| 不写文件（对照） | —— | 0 | 8.9 | 10.5 |
| 只 `write`，立刻 checkpoint | guest 页缓存 | 0 | 13.8 | 15.4 |
| `fsync` + `sync`，立刻 checkpoint（现在分档测试的做法） | 宿主页缓存 | 64.2 MiB | 70.8 | 72.8 |
| 同上，但 checkpoint 前先在宿主上 `sync`（46.8 ms） | 写层 | 0 | 23.8 | 25.7 |
| `fsync` + `sync`，等 40 s | 写层 | 0 | 44.2 | 49.6 |
| 只 `write`，等 75 s | 写层 | 0 | 37.7 | 41.2 |

等待的两组还带着 guest 里 ext4 后台清零 inode 表多写的约 60 MiB（§7 的 O-5），所以冻结窗口比“只 `write`，立刻”高；扣掉这部分，文件本身在 checkpoint 时已经不用付推送的代价。同一个文件，checkpoint 墙钟从 15 ms 到 73 ms，取决于写法和时机，与平台配置无关。

**结论：** 平台的打开方式不用改，也不该为测试去改；测试要模拟的是用户行为里决定这件事的两个量：**写完之后是否 `fsync` / `sync`**，以及**写完之后多久做 checkpoint**。现在的分档测试把这两个量都固定在最贵的取值上（`sync` 且立刻 checkpoint）。这是合法的最坏情况，但不能当成典型值来和进程级比较。

## 5. 第一次分析的建议（2026-11-18）

**应该分开测。** 每次只改变一个量，其他固定，分别量出每一项的代价。同负载对比已经是这样做的。

**写文件必然写页缓存，这个不用去掉。** 页缓存就是写文件的一部分真实代价，测“纯文件”时把它算在文件头上就对了。要控制的是另外两件事：

1. **写完到 checkpoint 隔多久。** 要加一组：写完等 0 / 10 / 40 秒再 checkpoint。
2. **要不要 `sync`。** 不 `sync` 时数据还在 guest 的页缓存里：沙箱级把它算作内存改动；进程级的文件已经在 overlay 的上层，不受影响。两种情况各测一组。

**两套之间公平比较，分三层：**

1. **单项测量。** 在同一台机器、同一时段，两侧交替跑同一个脚本：
   - 内存：同一个进程的匿名内存，进程固定，改动量从 0 到 256 MiB，连续页和随机散页各一组。随机散页在沙箱级上 256 MiB 要 171 ms，连续只要 35 ms，差别很大。
   - 进程大小：改动量固定，进程从 32 MiB 到 1 GiB。
   - 文件：写入量从 0 到 256 MiB，按上面的写回时机和 `sync` 分组。
   - 进程数、线程数：进程级的耗时随进程树数增长。
   - 第一次全量单列。
   - 每个测点 n ≥ 100，记 p50 和 p99，并记录 UB 等条件。
2. **验证能否相加。** 挑几个混合点（如 1 : 3、1 : 1、3 : 1），用第 1 层的单项代价相加去预测，再看和实测差多少。
3. **用真实负载代替拍脑袋的比例。** 在几类典型的 agent 任务上（装依赖、跑测试、编译、处理数据）每一步都 checkpoint，从两套各自记录的产物大小里统计出每一步的内存改动量、文件写入量和进程大小。把这些数代入第 1 层得到的代价，就能估出两套各要多少时间；再挑几段真实过程整段重放，实测核对。

这样得到的结论是“在什么样的负载下，哪一套更快、快多少”，可以直接用客户自己负载的数据来查。

## 6. 第二次分析（2026-11-18）

第一次的建议回答了“怎样比得公平”，但它是一份开发阶段性能测试的方案：单因素、可归因。按 §1 的分类重新看，对外评测还要回答另外两件事：结果要能对应真实使用；要让读者一眼看出每套好在哪里。第二次分析在第一次的基础上改了四处。

### 6.1 对外评测由三张表组成，各回答一个问题

| 表 | 回答 | 负载 | 谁来跑 |
|---|---|---|---|
| **A 代价分解表** | 为什么是这个速度 | 单因素（第一次分析的第 1 层），两套同一个脚本 | 两套各跑，交替 |
| **B 场景表** | 在真实使用里各有多快、谁更快 | 按真实任务画像构造的几类场景（§6.3） | 两套各跑，交替 |
| **C 达标表** | 每一套能不能达到客户参考线 | 各套自己的分档，按场景的组成分档（§6.4） | 各跑各的，不并列比较 |

现在的混合分档只对应 C，而且被拿去当成了 B 用。三张表分开以后，比较两套只看 A 和 B，C 只看各自。

### 6.2 “真实”落在用户行为上，不落在平台配置上

§4 已经说明：平台的配置（Firecracker 打开磁盘的方式、guest 内核、模板）就按部署的样子测，不为测试调整。要模拟真实的是用户行为。对 checkpoint / restore 的耗时有影响的用户行为有这些：

| 用户行为 | 影响哪一套、怎么影响 | 现在的测法 |
|---|---|---|
| 两次 checkpoint 之间改了多少内存 | 两套都是主要变量 | 有 |
| 改的内存是连续还是分散 | 沙箱级 256 MiB 散页比连续慢 4.6 倍（checkpoint）；进程级未测 | 只有连续 |
| 进程有多大 | 进程级 restore 由它决定；沙箱级几乎不受影响 | 同负载对比有 |
| 写了多少文件 | 沙箱级 checkpoint 的主要变量；进程级几乎不受影响 | 有 |
| 写完是否 `fsync` / `sync` | 决定文件数据 checkpoint 时在 guest 页缓存还是宿主页缓存（§4） | 固定为 `sync` |
| 写完到 checkpoint 隔多久 | 同上；隔得越久，沙箱级 checkpoint 越不用推数据 | 固定为 0 s |
| 进程、线程有多少 | 进程级随进程树数线性增长 | 没有 |
| 多久 checkpoint 一次、多久 restore 一次 | 决定每次的改动量；restore 频率决定 restore 耗时有多重要 | 没有 |

后面四行目前都缺。其中“是否 `fsync`”和“隔多久”在测试里是两个开关；“多久 checkpoint 一次”决定了每一步的改动量和写完到 checkpoint 的间隔，要从真实任务里量。

### 6.3 场景先量后定，而不是先定比例

第一次分析的第 3 层是“最后用真实负载核对”。第二次分析把它提到最前面：**先量真实任务的画像，再据此定场景和档位**，因为 3 : 1 这样的比例、“立刻 checkpoint”这样的时机，都是在没有画像时临时定的。

**量什么。** 选几类典型的 agent 任务（安装依赖、跑单元测试、编译、数据处理、交互式改代码），每一步结束时 checkpoint，记录：

- 这一步的内存改动量：沙箱级取内存差分大小减本底；进程级取镜像大小；
- 文件写入量：沙箱级取盘层大小；进程级取 overlay 上层大小；
- 进程大小与进程树数：guest 里 `/proc` 统计；
- 写完到 checkpoint 的间隔、这一步里是否有 `fsync`：guest 里用 `strace -c` 或 `/proc/<pid>/io` 统计，或在任务脚本里埋点；
- 两次 checkpoint 之间隔多久、多久 restore 一次：由 agent 的调用记录给出。

**怎么定场景。** 按画像把步骤归成三四类，每类取中位数和 p90 作为两个档，例如：

| 场景（示意，数值待量） | 内存改动 | 页分布 | 进程大小 | 文件写入 | `fsync` | 写完到 checkpoint |
|---|---|---|---|---|---|---|
| 交互式小步 | 小 | 分散 | 中 | 小 | 偶尔 | 几秒 |
| 装依赖 / 编译 | 中 | 连续为主 | 小到中 | 大 | 多 | 立刻 |
| 跑测试 / 数据处理 | 大 | 分散 | 大 | 中 | 少 | 立刻到几秒 |

表里的方向只是示意，没有实测依据，定场景必须用量出来的数。

**场景用合成负载重放。** 场景表（B）用一个两套共用的负载生成脚本按画像重放：常驻进程改指定量、指定分布的内存；写指定量的文件、按指定方式落盘；等指定时间再 checkpoint。合成重放可以重复、可以交替两套跑；真实任务整段回放只作核对，不作主表，因为真实任务每次的改动量不同，样本之间不可比。

### 6.4 分档仍然保留，但档位按场景的组成来分

客户的参考线是按“改动量”说的，所以达标表（C）仍按改动量分档。区别是每个档位的组成取自场景画像，而不是固定的 3 : 1；同一个改动量下可以有“内存为主”“文件为主”两条档线。写完到 checkpoint 的间隔取场景的典型值，另外保留一条“写完立刻 checkpoint”的档线，标明是最坏情况。

### 6.5 公平比较的规则

| 规则 | 理由 |
|---|---|
| 两套用同一个负载脚本、同一种内存负载（进程的匿名内存，不用 tmpfs） | tmpfs 不属于任何进程，进程级不保存它（§3） |
| 同一台机器、同一时段、两套交替跑，每轮切栈 | 宿主状态（UB、页缓存、残留 netns）随时间变 |
| 两侧样本量相同，每个测点 n ≥ 100，报 p50、p90、p99，写明 p99 的取法 | 现在一边 3 次、一边 100 次；n = 60 时 p99 就是最大值 |
| 报客户端墙钟和服务端分段，两侧的分段对齐到“冻结窗口、写数据、恢复数据” | 读者要看为什么 |
| 第一次全量单列 | 两套保存的范围不同，不进增量比较 |
| 每轮开头记录宿主条件：UB、`numactl -H`、`kernel.numa_balancing`、脏页后端、二进制 sha256 | 11-17 与 11-18 两轮的差别说不清，就是因为没记 |
| 两套各自的模板与 guest 内核照部署的样子用，写明差别 | 两套的模板和 guest 内核本来就不同（进程级的 guest 内核带补丁），这是方案的一部分，不是变量 |

## 7. 第二次分析发现的可改核心逻辑之处

本阶段不改快照回滚的核心逻辑；下面几处是在分析测试时看到的，列出来供决定是否修改。都未实施。O-5 严格说不在快照回滚的核心逻辑里，在模板构建上，但它直接改变 checkpoint 的工作量，一并列出。

| 编号 | 所在 | 现象 | 可能的改法 | 收益与代价 |
|---|---|---|---|---|
| O-1 | 沙箱级 checkpoint | 暂停窗口里要把宿主块设备页缓存中的根盘数据经 NBD 推进写层，64 MiB 约 47 ms（920B，`snapshot` 段） | 暂停 vCPU **之前**先对根盘块设备做一次 `fsync`（预刷），暂停后 Firecracker 的 `sync_all` 只推剩下的一点 | 冻结窗口大幅缩短（920B 实验：先在宿主上 `sync` 再 checkpoint，frozen 从 70.8 ms 降到 23.8 ms）；API 调用的总墙钟不变，因为预刷的时间还在调用里；预刷期间 guest 继续运行，新写入的数据由暂停后的那次推送处理，正确性不变 |
| O-2 | 沙箱级运行期 | 同上，数据要等宿主内核约 30 s 后写回 | orchestrator 在后台按脏数据量或时间间隔对根盘块设备做 `fsync`，让数据提前进写层 | 典型使用下 checkpoint 时已无数据可推，墙钟也降下来；代价是同一块反复写时会多推几次，宿主后台多一些 I/O |
| O-3 | 沙箱级 `seal` | `seal` 随本代盘层大小增长：920B 上 64 MiB 约 9 ms、约 124 MiB 约 19 ms；950 纯文件 64 MiB 11.1 ms | 先在 `seal` 里拆开计时（`BLKFLSBUF`、`fsync`、新写层创建、`AppendLayer`）再定；如果主要是 `BLKFLSBUF` 丢弃块设备页缓存的开销，封层时可以只 `fsync` 不丢缓存（封层不改磁盘内容，缓存仍然有效，丢缓存只在 restore 换视图时需要） | 未验证，需要先加分段 |
| O-5 | 模板构建（两套都受影响，沙箱级最明显） | 模板快照拍下时，guest 的 ext4 还没做完 inode 表的后台清零（lazy itable init，根盘 8 个块组都没有 `ITABLE_ZEROED`）。从模板新建的沙箱启动几秒后会多写约 60 MiB 根盘数据；沙箱级 restore 到清零完成之前拍的 checkpoint，每次都会重做这次清零（920B 实测：restore 回基点约 4 s 后写出 60.5 MiB，Firecracker 把它写进根盘块设备） | 模板构建时等 lazy init 完成（`ext4lazyinit` 线程退出）再拍模板快照；或者在构建根盘镜像时用 `mkfs.ext4 -E lazy_itable_init=0` 直接清零 | 每个新沙箱少写约 60 MiB；沙箱级新沙箱的第一次增量 checkpoint 少推约 60 MiB（920B 上约 50 ms）、少一份 60 MiB 盘层。代价是模板构建多等几秒，或镜像构建多写一次 inode 表。上游 e2b 的模板构建是同样的流程，需要先确认这个改动放在哪一层 |
| O-4 | 进程级 restore | 每次重建整个进程，耗时由进程大小决定，与改了多少无关（950：384 MiB 进程改 16 MiB 时 restore 164 ms） | 方向是只恢复改过的页而不是重建整个进程，例如复用现有进程的页、或 CRIU 的延迟页恢复（restore 先返回，页在首次访问时再填） | 改动大，后者把代价挪到 restore 之后；未评估 |

`O_DIRECT` 和 `cache_type = Writeback` 不在这张表里：它们把推送的代价挪到沙箱里程序的写盘上（§4），对用户可见，不建议作为默认值。

O-5 是在追查 §4 实验里一个异常时发现的：“`fsync` + `sync` 后等 10 s 再 checkpoint”那一组，checkpoint 期间经 NBD 推送了 124.7 MiB，而文件只有 64 MiB。用 ftrace 的 `writeback_dirty_folio` 看到多出来的页都是 Firecracker 在写完后第 2 秒写进根盘块设备的，落在设备开头约 60 MiB；guest 侧的块设备计数显示，restore 回基点约 4 s 后、没有任何用户操作时写出了 60.5 MiB，之后 `ext4lazyinit` 线程消失。950 的 perf-full 不受影响：它的基点在预热之后才拍，各档盘层与名义文件量一致（沙箱级手册[第 18 章 §5.2](../../rollback/docs/18-950-performance.md#52-产物)）。

## 本章要点

1. 测试分三类：开发阶段的功能测试（对不对）、开发阶段的性能测试（慢在哪、改了是否变快，负载可以极端、要能归因）、开发完成后的对外评测（有多快、为什么、两套各好在哪，负载要对应真实使用、比较要公平）。分档性能测试属于第三类。
2. 各自的混合分档（3 : 1）只能说明每一套自己能否达标，不能用来比较两套：两侧内存负载不同、进程级的进程大小随档位变、1/4 的文件正好是沙箱级最贵的部分。比较以同负载对比为准。
3. 950 同负载对比的结论：改内存的 checkpoint、进程较大时的 restore 沙箱级更快；写文件、第一次全量进程级更快；很小的进程两侧 restore 接近。
4. 沙箱级写文件慢，不是因为“没开 `O_DIRECT`”这一配置本身：`O_DIRECT` 是平台的打开方式，用户选不了，Firecracker 也不支持。决定代价落在 checkpoint 里的是用户行为：写完是否 `fsync`、写完多久 checkpoint。现在的测试把这两项固定在最贵的取值。
5. 第二次分析：对外评测拆成代价分解表、场景表、达标表三张；场景和档位先量真实任务的画像再定；两套同脚本、同机交替、同样本量；画像采集是下一步的第一件事。
6. 可改之处（都未实施）：沙箱级 checkpoint 暂停前预刷根盘、运行期后台推送、`seal` 分段后再定；进程级 restore 不重建整个进程的方向；模板构建等 ext4 lazy init 完成再拍快照（每个新沙箱少写约 60 MiB）。
