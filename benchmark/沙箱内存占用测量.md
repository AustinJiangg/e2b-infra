# 空闲沙箱内存占用：原理与测量

> 问题：基于 `build_template.py` 构建的 2U2G 模板（`cpu_count=2, memory_mb=2048`）起一个沙箱、
> 什么也不干，宿主机实际要付出多少内存？和模板规格是什么关系？
>
> 配套脚本：`mem_snap.sh`（内存快照）、`idle_sandbox.py`（起空闲沙箱）、
> `measure_idle_mem.sh`（一键测量 + 报告）。
>
> **实测结果与结论见 [`空闲沙箱内存实测分析.md`](空闲沙箱内存实测分析.md)**。本篇讲原理和测法。

---

## 1. 沙箱的内存去了哪

一个沙箱在宿主机上就是一个 firecracker 进程（orchestrator fork 出来，跑在 Nomad task cgroup 里），
它的内存分成下面几块，**第一块是大头，而且它不在常规统计里**：

| | 内容 | 记在哪 | `top`/`free`/cgroup 能看到吗 |
|---|---|---|---|
| ① 客户机内存 | VM 里内核、envd、进程、page cache 用到的物理内存 | firecracker 映射的 **hugetlb（2 MiB 大页）**，`/proc/<fc>/smaps` 的 `Private_Hugetlb` | **看不到**：hugetlb 不进 RSS，也不进 cgroup memory（`deploy-docs/12` §0） |
| ② VMM 开销 | firecracker 自己的堆、线程栈、设备模拟缓冲 | 普通页，firecracker 的 RSS/PSS | 能 |
| ③ orchestrator 侧 | UFFD 缺页处理、NBD/rootfs overlay、网络等每沙箱状态 | `template-manager` 进程 RSS 的增量 | 能 |
| ④ 内核与缓存 | KVM/网络/NBD 等内核对象，读模板 memfile/rootfs 产生的 page cache | `/proc/meminfo` 的 Slab、PageTables、Cached 等，只能从 `MemTotal-MemAvailable` 的变化整体看到 | 能，但很难逐项归到某个沙箱 |

> 更正：本篇初版把 `/mnt/snapshot-cache` 当成模板缓存，这是错的。模板 memfile/rootfs 的本地缓存在
> `/orchestrator/build`（磁盘，读取时进 page cache），`/mnt/snapshot-cache` 是暂停/快照用的 tmpfs，
> 起空闲沙箱时不会变（`deploy-docs/10` §1；2026-11-10 两次实测它都是 0）。

所以：

```
大页池里   每个沙箱 = ① 客户机大页
普通内存里 每个沙箱 ≈ ② firecracker PSS + ③ orchestrator RSS 增量 + ④ 内核与缓存
           （②③④ 合起来就是 MemTotal-MemAvailable 的增量；大页池开机就扣掉了，不影响这一项）
```

`mem_snap.sh` 就是把这几项分别读出来；`measure_idle_mem.sh` 在起沙箱前后各采一次做差，再除以沙箱数。

### 1.1 为什么客户机内存不是 2G

沙箱不是冷启动，而是**从模板快照恢复**：

1. 模板构建时，VM 按 `memory_mb=2048` 启动、跑完 provision，然后打快照，内存内容存成 `memfile`。
2. 创建沙箱时，firecracker 按 2048 MiB **映射**一段大页地址空间，但不立刻分配物理页；
   这段内存注册到 userfaultfd（UFFD）。
3. 客户机访问到哪一页，触发缺页，orchestrator 才从 memfile 把对应内容拷进去（`UFFDIO_COPY`），
   此时宿主机才真正分配一个 2 MiB 大页。

因此宿主机付出的是**"恢复之后客户机实际摸过的页"**，按 2 MiB 取整，而不是 `memory_mb`。
`memory_mb` 只是**上限**：客户机最多能用到 2G，宿主机最多为它付出 2G + 少量开销。

## 2. 和模板规格的关系

| 规格项 | 对空闲内存的影响 |
|---|---|
| `memory_mb` | **上限**，不是占用。间接影响：客户机内核的 `struct page` 数组约占内存的 1.5%（2G → 约 32 MiB），这部分恢复后会被碰到；客户机里内存越大，page cache 越"舍得"不回收，长时间运行后占用会往上限靠 |
| `cpu_count` | 几乎无影响：每个 vCPU 只多一个线程栈和少量 per-CPU 内核数据（KB~MB 级） |
| 镜像内容 | **主要因素**：快照那一刻常驻的进程（envd、systemd 等服务）和内核数据，恢复后都会被重新碰到 |
| 大页粒度 | 客户机碰 4 KiB，宿主机就分 2 MiB。访问越分散，放大越明显（本仓库固定用 `hugepages-2048kB` 池，见 `start-client.sh`） |

## 3. 大概多少

2026-11-10 实测（base 模板，2U2G，详见 [`空闲沙箱内存实测分析.md`](空闲沙箱内存实测分析.md)）：
每多一个空闲沙箱，**大页池多用 158 MiB**（不是 2048），**普通内存多用约 180 MiB**，
其中 ② firecracker 约 2.5 MiB，③ orchestrator 约 81 MiB，其余约 97 MiB 还没归因。
初版估计的"③ 几 MiB"偏低了一个数量级。

决定这个值的因素：

1. **恢复后的工作集**：客户机内核 + 常驻进程 + 恢复后发生的 page cache。镜像里预装/自启的东西越多越大。
2. **运行时长**：没有 balloon，客户机摸过的页**不会还给宿主机**。哪怕"什么都不干"，内核定时任务、
   日志、envd 心跳也会慢慢摸新页，所以要对比 T1（30s）和 T2（5min）。在里面跑过程序之后，
   占用会接近程序峰值内存 + 它产生的 page cache，最坏到 `memory_mb`。
3. **大页放大**：见上表。
4. **一次性开销**：第一个沙箱会带来模板缓存读入、orchestrator 内部结构初始化等一次性开销，
   后面同模板的沙箱不再付。所以单测 1 个沙箱会高估，要用 N=1 和 N=10 两次做差求边际值。

### 3.1 "占用"之外还要看"预留"

报告里有一行 `大页 Rsvd`。如果 firecracker 映射客户机内存时没有带 `MAP_NORESERVE`，内核会在映射时
就把整段 2G 大页**预留**掉（还没分配物理页，但其他进程也拿不走）。这时：

- 实际占用（`大页已用`）仍是一两百 MiB；
- 但**并发上限**按 `memory_mb` 计算，即 `可用大页 / 2048 MiB`（`deploy-docs/11` §3.2 的算法）。

测一次看 `Rsvd` 增量就知道：约等于 `N × 2048 - ①` 说明是满额预留；接近 0 说明是按需。

## 4. 测量步骤

在服务器上用 root、在 `benchmark/` 目录下执行（`idle_sandbox.py` 读这里的 `.env`，和 `sandbox.py` 一样）。
测量时尽量不要有其他沙箱或模板构建在跑。

```bash
cd /path/to/e2b-infra/benchmark
git pull
```

**只看当前状态**（随时可用，不起沙箱）：

```bash
bash mem_snap.sh
```

**一键测 1 个空闲沙箱**（基线 → 起沙箱 → 30s、300s 各采一次 → 关闭沙箱 → 60s 后再采一次 → 报告）：

```bash
bash measure_idle_mem.sh 1
```

**测 10 个，求边际值**：

```bash
bash measure_idle_mem.sh 10
```

参数：`measure_idle_mem.sh [N] [T1秒] [T2秒] [T3秒]`，默认 `1 30 300 60`（T3 从关闭沙箱算起）；
环境变量 `TEMPLATE`（默认 `base`）、`PYTHON`（默认 `python`）。

结果在 `mem_runs/<时间戳>_n<N>/`：

| 文件 | 内容 |
|---|---|
| `report.txt` | 汇总表 + 每个沙箱独占估算 + T2 明细 + 客户机 `free -m` |
| `before.*` / `t1.*` / `t2.*` / `t3.*` | 四个时刻的快照（`.txt` 人读，`.kv` 机读；t3 是关闭后） |
| `sandbox.log` | `idle_sandbox.py` 输出 |

> 采基线前脚本会 `echo 1 > /proc/sys/vm/drop_caches` 清一次宿主机 page cache，
> 让 `MemTotal-MemAvailable` 一行干净些；对大页各项没有影响。

### 4.1 读报告

```
   before        T1        T2        T3 | T1-before T2-before |      T2/N | T3-before | (MiB；T3=关闭后残留)
      ...                                                                         | ① 客户机内存(fc 大页)
      ...                                                                         | ② firecracker 进程 RSS
      ...
```

- **每个沙箱**：报告末尾给出三个数——大页 ①/N；可归因合计 (①+②PSS+③)/N；宿主机总口径 (①+④)/N。
- **orchestrator cgroup**：`memory.current` 的增量是记在 Nomad task cgroup 账上的部分，
  要和 `memory.max`（现值 32 GiB）比，这决定了普通内存侧能撑多少沙箱。
- **关闭后残留**：`T3-before` 列。大页应回到 0；普通内存若残留明显，说明有缓存或泄漏。
- **边际值**：`(n10 的 T2 增量 − n1 的 T2 增量) / 9`，扣掉了模板缓存等一次性开销，适合用来估并发容量。
- **空闲增长**：T2 − T1，说明"什么都不干"时内存每分钟涨多少。
- **核对**：`大页已用` 增量应约等于 ①；如果明显更大，说明期间有别的沙箱/构建在用大页。
- **客户机视角**：`sandbox.log` 里的 `free -m`。宿主机 ① 大致等于客户机的 used + buff/cache
  再按 2 MiB 取整（客户机里 free 的页如果曾经被用过，宿主机也已经付出了）。

### 4.2 手动方式

不想用一键脚本时：

```bash
bash mem_snap.sh > /root/before.txt
```

另一个终端起沙箱并保持（`Ctrl-C` 或到时间自动关闭）：

```bash
python idle_sandbox.py --count 1 --hold 600
```

等 30 秒后：

```bash
bash mem_snap.sh > /root/after.txt; diff /root/before.txt /root/after.txt
```
