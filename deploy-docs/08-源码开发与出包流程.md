# 08 源码开发与出包流程

本篇讲**改 E2B 的 Go 源码**这条链路上你每天怎么操作。03 篇讲的是 RPM 怎么从
"源码 + 补丁 + 离线二进制"构建出来（供应链视角），两篇配套看。

## 0. 两条开发线，频率差一个量级

先分清你在改什么——这决定了要不要出包：

| | 改什么 | 频率 | 怎么生效 |
|---|---|---|---|
| **部署线** | 仓库A 的 `e2b-deploy/`、`e2b-infra.spec`、各种 Source 二进制 | 低。装机流程定型后基本不动 | 必须重打 `e2b-deploy.tar.gz` / 重出 RPM（03 篇 §4、§6） |
| **源码线** | 上游 Go 源码（orchestrator / api / envd …） | **高，这是主要工作** | **编出二进制直接替换正在跑的那个，不出包**（§4） |

源码线的日常循环是 **改码 → 编译 → 换二进制 → 验证**，一轮几分钟，
`rpmbuild` 一次都不用跑。只有一个功能做完、要把改动固化下来时，才走一次
"生成 patch → 出 RPM"（§5）——那是**阶段收尾**，不是每次改动都做的事。

> 为什么能直接换：RPM 的作用只是把编译产物摆到 `/usr/bin`、`/opt/e2b-infra/bin`、
> `/fc-envd` 这几个位置。你手工把同一个文件拷到同一个位置，效果完全一样。
> RPM 的价值在**可复制地装到一台新机器**，而不是在你自己这台机器上迭代。

下面的流程在 openEuler 24.03 aarch64 上完整跑通过：搭树 → 打 patch → 重新生成的 patch
与仓库里那份逐字节相同 → orchestrator 编出全部 5 个产物。照着走就行；
真遇到报错，翻 §8 的速查表。

> 仓库只有**一个** patch：`0001-adapted-for-arm-architecture.patch`。
> 早期曾把 FC 启动优化拆成 `0002-fc-launch-dedicated-helper.patch`，那个拆分对下游开发
> 只有负担没有收益（详见 §9），已合并进 0001，spec 里的 `Patch2:` 声明也已删除。

## 1. 先建立心智模型：两个仓库 + 一份 Go SDK

整套流程最关键的一点，就是分清这三者各自是什么、产物流向哪里。想清楚这张图，后面就不会乱：

```
┌─ 仓库A:交付仓库 = projects/e2b-infra ──────────────────────────┐
│  内容:0001 patch、e2b-infra.spec、各种 tarball                  │
│        (源码包、e2b-deploy、tools-arm64 = Go SDK …)             │
│  角色:你 push 到远端、别人拿去 rpmbuild 的东西                  │
│        ⚠️ 它【不含】展开的 Go 源码                              │
│  变量:$E2B_PKG                                                  │
└────────────────────────────────────────────────────────────────┘
        ▲ 只回收一样东西:重新生成的 0001.patch
        │
┌─ 仓库B:源码工作树 = projects/e2b-src ──────────────────────────┐
│  内容:上游源码解开 + 建 git 基线 + 打上 0001                    │
│  角色:你平时写代码的地方。纯本地工具,【不 push 任何地方】      │
│        唯一产物 = 新的 0001.patch                               │
│  变量:$E2B_SRC                                                  │
└────────────────────────────────────────────────────────────────┘
        ▲ 编译时借用
        │
┌─ Go SDK = /usr/local/go(系统级安装)───────────────────────────┐
│  角色:只是编译器。装一次,全局可用                              │
│  ⚠️ 既不放进仓库A的源码,也不放进仓库B的工作树(会污染 git)     │
└────────────────────────────────────────────────────────────────┘
```

**为什么需要仓库B**：仓库A 里只有 patch，没有可编译的源码。而 patch 文件是**不能手改**的
（行号/上下文一错就 `Hunk FAILED`）。所以要有一棵"展开并打好补丁"的源码树：你在里面正常写代码，
最后用 `git diff` 让 git 帮你重新生成 patch。仓库B 的 git 只为这一件事存在，永远不推到远端。

### 源码树的三个结构特点

这三条决定了后面所有命令的形状，先记住：

| 特点 | 影响 |
|---|---|
| **多模块**：根目录没有 `go.mod`，是 `go.work` 工作区 + 13 个子模块 | `vendor/` 在 `packages/<模块>/vendor/`，根目录没有；编译要进模块目录 `make build` |
| **tarball 自带 `.git`**：一份 grafted 浅仓库，HEAD 游离在 tag `2026.09`（上游提交 `4853232`），没有本地分支 | 搭树时是"在现成仓库上补基线"，不是从零 `git init`；要先 `git switch -c dev` |
| **vendor 和 `go.work.sum` 是打包时另外塞进去的**，不在上游 git 历史里 | 基线必须自己打 `upstream` tag（含 vendor），不能拿现成的 `2026.09` tag 当下界 |

## 2. 关于 Go SDK：用系统装的，不用包里那份

`tools-arm64.tar.gz` 就是**官方 Go 1.25.4 ARM64 SDK**（解开是标准 `go/` 目录，即 GOROOT）；
`tools-amd64.tar.gz` 是它的 x86_64 版。它们存在的唯一目的是**给 rpmbuild 用**：spec 的
`%prep` 按架构解压到 `BUILD/go-toolchain/`，`%build` 把 `GOROOT` 指过去——这样构建机
不需要预装 Go、也不需要联网（`BuildRequires` 里只有 `make gcc`）。详见 03 篇 §3.2。

**日常开发用系统装的那份就行：**

```bash
wget --no-check-certificate https://mirrors.aliyun.com/golang/go1.25.4.linux-arm64.tar.gz
rm -rf /usr/local/go && tar -C /usr/local -xzf go1.25.4.linux-arm64.tar.gz
export PATH=$PATH:/usr/local/go/bin          # 写进 ~/.bashrc
```

`GOROOT` 不用配（go 二进制自己按路径推断），`GOPATH` 默认 `~/go` 即可（走 vendor 模式，用不到）。

<details>
<summary>为什么 <code>tools-arm64.tar.gz</code> 和官网下载的 sha256 对不上（点开）</summary>

内容完全相同，只是解开后用不同压缩参数重新打了一次包：

| | 大小 | sha256 |
|---|---|---|
| 官网 `go1.25.4.linux-arm64.tar.gz` | 57268847 | `a68e86d4…9ff0` |
| 仓库 `tools-arm64.tar.gz` | 57033990 | `b8450631…c782` |

依据：`go/VERSION` 的官方构建时间戳 `2025-10-31T13:24:27Z` 一字不差；全部 16092 个文件
mtime 都是官方构建日；gzip 头部 MTIME 字段被清零（`gzip -n` 这类可复现构建手法，官方原件
不会全 0）；`tools-amd64.tar.gz` 的 gzip 头前 16 字节与之完全一致，说明是同一套流程批量重打的。

所以差的 ~235 KB 纯粹是 deflate 输出不同。**不必追求 sha256 一致**——验证它可信，
看 `go/VERSION` 时间戳 + `go version` 输出就够了。
</details>

## 3. 一次性准备

### 3.1 环境脚本 `source-e2b.sh`

放在你自己的家目录（不要写进多人共用的 `~/.bashrc`）。它只放项目特有的东西，
Go 的 PATH 交给 `~/.bashrc` 管：

```bash
# /home/<你>/source-e2b.sh —— 每次开发前 source 一下

export E2B_PKG=/home/<你>/projects/e2b-infra   # 仓库A：patch + spec + tarball
export E2B_SRC=/home/<你>/projects/e2b-src     # 仓库B：改代码的地方

export GOFLAGS=-mod=vendor    # 只用 vendor 里的依赖，绝不联网
export GOTOOLCHAIN=local      # 禁止 go 因 go.mod 版本声明而联网换工具链
export GOWORK=off             # 忽略 go.work（与 -mod=vendor 冲突），但不动文件

echo "[e2b] E2B_PKG=$E2B_PKG"
echo "[e2b] E2B_SRC=$E2B_SRC"
echo "[e2b] go: $(go version 2>/dev/null || echo '未找到 go，检查 ~/.bashrc 的 PATH')"
```

三个环境变量各自解决一件事：

- **`GOFLAGS=-mod=vendor`** —— 离线编译的前提，依赖只从 `vendor/` 取。
- **`GOTOOLCHAIN=local`** —— Go 1.21+ 发现 `go.mod` 声明的版本高于本机时会自动联网下载工具链，
  离线机上会卡住；`local` 强制只用本机这套。
- **`GOWORK=off`** —— 根目录 `go.work` 让 go 进入 workspace 模式，与 `-mod=vendor` 冲突。
  spec 的 `%build` 是直接 `rm -f go.work`，但**本地别删文件**（删了会被 `git add -A` 记成删除、
  混进 patch）。`GOWORK=off` 效果等价而不动工作树：

  ```
  有 go.work 时     go env GOWORK → /path/to/go.work   # workspace 模式
  GOWORK=off 时     go env GOWORK → off                # 不在 workspace 模式
  删掉 go.work 后   go env GOWORK → (空)               # 同样不在 workspace 模式
  ```

**还要确认本机有 C 编译器**：`packages/orchestrator` 主程序是 `CGO_ENABLED=1` 编的，
且最后一行要用 `$(CC)` 编 `fc-launch-c`。

```bash
cc --version || gcc --version
```

### 3.2 搭源码树（直接粘这段）

从零搭一棵树、换机器、或想丢掉一堆试验性提交重来，都跑这一段。
每步在做什么见 §3.3。

```bash
source /home/<你>/source-e2b.sh

# ── 0) 旧树改名留底，不要直接 rm ────────────────────────────────────────
cd "$E2B_SRC"
[ -d e2b-infra-2026.09 ] && mv e2b-infra-2026.09 "e2b-infra-2026.09.bak-$(date +%Y%m%d-%H%M)"

# ── 1) 解开源码（先确认不是 134 字节的 git-lfs 指针）────────────────────
ls -l "$E2B_PKG/e2b-infra-2026.09.tar.gz"
mkdir -p "$E2B_SRC"
tar -xzf "$E2B_PKG/e2b-infra-2026.09.tar.gz" -C "$E2B_SRC"
cd "$E2B_SRC/e2b-infra-2026.09"

# ── 2) vendor 自检：5 个模块都要 ✅ ─────────────────────────────────────
for d in packages/api packages/client-proxy packages/db packages/envd packages/orchestrator; do
    printf '%-30s %s\n' "$d/vendor" "$([ -d "$d/vendor" ] && echo ✅ || echo '❌ 缺')"
done

# ── 3) 补 ARM busybox（必须在建基线之前）────────────────────────────────
cp "$E2B_PKG/busybox_1.35_arm64" \
   packages/orchestrator/internal/template/build/core/systeminit/

# ── 4) 挡住 packages/db 的编译产物（该模块没有 .gitignore）──────────────
cat >> .git/info/exclude <<'EOF'
packages/db/bin/
packages/db/scripts/seed/postgres/seed-db
EOF

# ── 5) git 身份 + 落到分支 + 建基线 ─────────────────────────────────────
git config user.name  "你的名字"
git config user.email "you@example.com"
git switch -c dev
git add -A && git commit -qm base            # 会刷一屏 CRLF warning，正常，见 §3.4
git tag upstream

# ── 6) 打 patch ─────────────────────────────────────────────────────────
patch -p1 < "$E2B_PKG/0001-adapted-for-arm-architecture.patch"
git add -A && git commit -qm patched

# ── 7) 自检四连 ─────────────────────────────────────────────────────────
diff <(grep -v '^index ' "$E2B_PKG/0001-adapted-for-arm-architecture.patch") \
     <(git diff upstream HEAD | grep -v '^index ') \
  && echo "✅ 重生成的 patch 与仓库A 一致"
git diff upstream HEAD | grep -c "GIT binary patch"    # 必须是 0
find . -name '*.rej' -o -name '*.orig' | head          # 必须没输出
git log --oneline --decorate -3 && git status

# ── 8) 冒烟编译 ─────────────────────────────────────────────────────────
cd packages/orchestrator && make build && ls -lh bin/
```

八步全绿之后删掉备份：

```bash
rm -rf "$E2B_SRC"/e2b-infra-2026.09.bak-*
```

### 3.3 这几步各自在解决什么

| 步骤 | 为什么必须这么做 |
|---|---|
| **2** vendor 逐模块查 | 多模块布局，`vendor/` 在 `packages/<模块>/vendor/`。根目录 `ls vendor` 查不到是正常的，别据此以为源码包坏了。`shared`/`auth` 等不需要自己的 vendor——它们通过 `replace … => ../shared` 被 `go mod vendor` 复制进了上面 5 个模块里。<br>（旁证：上游纯源码约 14 MB，而这个 tarball 有 143 MB，多出来的十倍就是 vendor——它不是 GitHub 上那份 `archive/refs/tags/2026.09.tar.gz`，是补过 vendor 的定制包。） |
| **3** 补 busybox，且必须在建基线**之前** | patch 给 `systeminit/busybox.go` 加了 `//go:embed busybox_1.35_arm64`，但这个二进制**不在源码包也不在 patch 里**——二进制进 patch 会变成 GNU `patch` 应用不了的 `GIT binary patch`，所以它只能是 spec 的 `Source1`，由 `%prep` 的 `cp %{SOURCE1} …` 拷进构建树。手工搭的树没有这一步，漏了 orchestrator 编不过。<br>放在建基线之前拷，它就进了 `upstream` 基线：两个 commit 里都有、没变化，于是 `git diff upstream HEAD` 永远看不到它，既不污染 patch 也不用配 ignore。这样 `upstream` tag 的含义正好等于"`%prep` 打 patch **之前**的状态"。<br>（全树扫过 `//go:embed`，只有这一个引用的文件源码包里没有。） |
| **4** 排除 db 的编译产物 | `orchestrator`/`api`/`client-proxy`/`envd` 各自的 `.gitignore` 都有 `bin`，**只有 `packages/db` 没有 `.gitignore`**。它的 `bin/migrator` 和 `scripts/seed/postgres/seed-db` 一旦编出来就会被 `git add -A` 收走，patch 里出现 `GIT binary patch`，而这个错误要到别人 `rpmbuild` 时才暴露。写 `.git/info/exclude` 而不是 `.gitignore`——后者自己会进 patch。 |
| **5** 先 `git switch -c dev` | tarball 自带的 `.git` 是游离 HEAD 且没有任何本地分支，在上面提交完再 `git checkout` 别处，这两个 commit 就悬空了。先落到分支上。<br>（`git config` 那两行也别省：全新仓库没配身份的话，第一条 `git commit` 直接失败。） |
| **5** 自己打 `upstream` tag | **别拿现成的 `2026.09` tag 当基线。** 那个提交里不含 vendor（vendor 在 git 眼里是 untracked），拿它当下界会把整棵 vendor 树算成"新增文件"，patch 从 1 万行涨到几十万行。 |
| **7** 自检四连 | 此刻一行代码都没改，所以重生成的 patch 必须与仓库A 里那份等价——这一条过了，就证明"以后 `git diff upstream HEAD` 生成的 patch = 部署机上跑的那份"。 |
| **8** 零改动冒烟编译 | 把工具链问题和代码问题分开。这一条同时验证 `GOWORK=off` 生效、vendor 完整、busybox 已补、gcc 可用。 |

### 3.4 建完之后应该长这样

```
$ git log --oneline --decorate -3
b0b40ac4 (HEAD -> dev) patched
516002f5 (tag: upstream) base
4853232b (grafted, tag: 2026.09) Fix load current env in set-env (#2002)

$ git status
On branch dev
nothing to commit, working tree clean

$ ls -lh packages/orchestrator/bin/
orchestrator  111M    clean-nfs-cache  21M    fc-launch  2.9M
fc-netns-exec 2.3M    fc-launch-c      71K
```

编译过程里这两行**不是报错**，忽略即可：

- `cat: ../../.last_used_env: No such file or directory` —— Makefile 第 1 行
  `ENV := $(shell cat ../../.last_used_env || echo "not-set")` 取上游 dev 环境名，取不到就回落。
- `git add -A` 刷屏的二十几条 `CRLF will be replaced by LF` —— 来自上游自带的 `.gitattributes`
  （`* text=auto`），不是你的 `core.autocrlf` 设错了。git 只在**索引里**归一，工作区不动；
  被 warn 的全是 `vendor/` 里的 LICENSE / README / .txt 等非编译产物，而 `.gitattributes` 又把
  `*.go`/`*.mod`/`*.sum` 钉成 `eol=lf`。提交完 `git status` 是 clean 就说明没事，
  `git diff upstream HEAD` 比的是两个都已归一的 commit，patch 不受影响。

做完这些，`$E2B_SRC/e2b-infra-2026.09` 就是你**长期的开发目录**，以后不用再重建。

## 4. 日常循环：改码 → 编译 → 换二进制（不出包）

这是你 95% 时间在做的事。一轮几分钟，**不碰 patch、不碰 rpmbuild**。

```bash
source /home/<你>/source-e2b.sh
cd "$E2B_SRC/e2b-infra-2026.09"
```

### ① 改代码

想改哪个文件改哪个，**不用再想"属于哪一层"**——这是只保留单一 patch 的最大红利。

### ② 编译

```bash
cd packages/orchestrator && make build      # 改哪个模块编哪个；编不过就别往下走
```

> `packages/db` 的 `make build` **只编 `migrator`**。`seed-db` 不在里面——spec 是单独
> `pushd packages/db/scripts/seed/postgres && go build -o seed-db seed-db.go` 编的。
> 改了 seed-db 就照这条命令自己编一遍。

### ③ 替换二进制、让它跑起来

**关键：不同模块的运行形态不同，替换方式也不同。** 先对号入座：

| 你改了 | 运行形态 | 二进制落在哪 | 怎么生效 |
|---|---|---|---|
| **orchestrator / template-manager** | nomad `raw_exec`（job `template-manager-system`，task `start`） | `/usr/bin/orchestrator` 和 `/usr/bin/template-manager`——**同一个二进制两个名字**（`start-client.sh:16-17`），job 起的是后者 | 覆盖两个文件 → 重跑 job |
| **fc-launch / fc-netns-exec / fc-launch-c** | orchestrator 起沙箱时 fork 的助手 | `/opt/e2b-infra/bin/`（`fc/mode.go` 里硬编码，可用 `E2B_FC_{LAUNCH,NETNS_EXEC,LAUNCH_C}_HELPER` 覆盖路径） | 只覆盖文件即可，**不用重启 orchestrator**——下一个沙箱就用新的 |
| **api / client-proxy(edge)** | nomad `docker` | harbor 镜像 `$REGISTRY_URL/{api,client-proxy}`，由 `deploy.sh` 从 `/opt/e2b-infra/bin/<name>.Dockerfile` 构建 | 拷二进制 → 重建并推镜像 → 重跑 job |
| **envd** | 注入沙箱 rootfs 的 guest 侧代理 | `/fc-envd/envd`，模板构建时写进 rootfs | 覆盖文件 → **重新构建模板**，已有模板不受影响 |
| **seed-db / migrator** | 一次性工具 | `/opt/e2b-infra/bin/` | 覆盖文件，下次用到时自然是新的 |

**改 orchestrator（最常见）：**

```bash
SRC="$E2B_SRC/e2b-infra-2026.09/packages/orchestrator/bin/orchestrator"

# rm -f 再 cp：正在跑的进程占着这个二进制，直接 cp 会 ETXTBSY（Text file busy）。
# unlink 是允许的——老进程继续用旧 inode，新文件落到新 inode。
rm -f /usr/bin/orchestrator /usr/bin/template-manager
cp "$SRC" /usr/bin/orchestrator
cp "$SRC" /usr/bin/template-manager
chmod +x /usr/bin/orchestrator /usr/bin/template-manager

cd /opt/e2b-infra && bash build.sh -r template-manager   # 只重跑这一个 job，跳过镜像构建
```

⚠️ 重跑 `template-manager-system` 会**杀掉当前所有运行中的沙箱**（orchestrator 就是它们的父进程）。
调试期无所谓，跑着压测的时候注意。

**改 fc-launch 系列助手：**

```bash
cd "$E2B_SRC/e2b-infra-2026.09/packages/orchestrator"
for b in fc-launch fc-netns-exec fc-launch-c; do
    rm -f "/opt/e2b-infra/bin/$b"
    cp "bin/$b" "/opt/e2b-infra/bin/$b"
done
chmod +x /opt/e2b-infra/bin/fc-*
# 不用重启任何服务，下一个沙箱就走新的助手
```

**改 api / client-proxy：**

```bash
cp "$E2B_SRC/e2b-infra-2026.09/packages/api/bin/api" /opt/e2b-infra/bin/api

source /opt/e2b-infra/dep/.env          # 取 REGISTRY_URL
cd /opt/e2b-infra/bin
DOCKER_BUILDKIT=0 docker build -t "$REGISTRY_URL/api" -f api.Dockerfile .
docker push "$REGISTRY_URL/api"

cd /opt/e2b-infra && bash build.sh -r api
```

（`api.Dockerfile` 就是 `COPY api /api` 一行，构建上下文是 `bin/`，所以只要把新二进制拷进去
就够了。`build.sh -r` 走 `deploy.sh --only`，**会跳过镜像构建**，所以 build/push 得自己来。）

**改 envd：**

```bash
rm -f /fc-envd/envd
cp "$E2B_SRC/e2b-infra-2026.09/packages/envd/bin/envd" /fc-envd/envd
chmod 755 /fc-envd/envd
cd benchmark && python build_template.py     # envd 是构建模板时写进 rootfs 的，必须重建模板
```

### ④ 验证

```bash
# 确认跑的确实是刚编的那个
md5sum /usr/bin/template-manager \
       "$E2B_SRC/e2b-infra-2026.09/packages/orchestrator/bin/orchestrator"

# 看日志
tail -f /data/nomad/alloc/*/alloc/logs/start.stdout.0
```

然后回到 ①。**这一圈里 git 都不用碰**——想留存档点就正常 `git commit`，
但 patch 和 RPM 都等做完一个阶段再说。

## 5. 阶段收尾：把改动固化回仓库A

一个功能做完、想让别人也能装上（或者自己想留个可复现的版本）时，才走这一节。

### ① 提交到仓库B

```bash
cd "$E2B_SRC/e2b-infra-2026.09"
git status                          # 应该只有你改的源码文件
git add -A && git commit -m "描述这次改动"
```

### ② 重新生成 patch

```bash
git diff upstream HEAD | grep -c "GIT binary patch"      # 保险：必须是 0
git diff upstream HEAD > "$E2B_PKG/0001-adapted-for-arm-architecture.patch"
wc -l "$E2B_PKG/0001-adapted-for-arm-architecture.patch" # 基线 9814 行 + 你的改动
```

零歧义、不可能打崩别的 patch。文件名不变，直接覆盖仓库A 里的旧 patch。

那条 `grep -c` 不是走过场：一旦有二进制被 `git add -A` 收进去，它就变成非 0，
而这个错误本来要到别人 `rpmbuild` 时才暴露。

### ③ 验证 patch + 出包 + 提交

```bash
# 验证 patch 能在纯净源码上干净应用（20 秒）
rm -rf /tmp/verify && mkdir -p /tmp/verify
tar -xzf "$E2B_PKG/e2b-infra-2026.09.tar.gz" -C /tmp/verify
cd /tmp/verify/e2b-infra-2026.09
patch -p1 --dry-run < "$E2B_PKG/0001-adapted-for-arm-architecture.patch" \
  && echo "✅ patch 可干净应用"

# 出 RPM（须在 aarch64 机器上；_sourcedir 里要有 tools-arm64.tar.gz 等全部 Source）
cd "$E2B_PKG"
rpmbuild -bb e2b-infra.spec --define "_sourcedir $PWD"

# 装到部署机：Release 一直不动，同名同版本，必须带 --force
rpm -Uvh --force ~/rpmbuild/RPMS/aarch64/e2b-infra-2026.09-3.aarch64.rpm

# 提交交付仓库（改了 e2b-deploy/ 的话还要重打 e2b-deploy.tar.gz，见 03 篇 §4）
git add 0001-adapted-for-arm-architecture.patch
git commit -m "..." && git push -u origin <你的分支>
```

**`Release` 保持不动。** 每次改版本号既没意义又要连带改一堆引用。
代价只有一个：`rpm -q` 看不出装的是哪一次构建，所以**别靠版本号判断部署机上跑的是不是最新的**，
用 §4④ 那个 `md5sum` 对比。

> 装完 RPM 之后必须**重放 dep overlay**（`build.sh -i` 会用 `dep/` 版覆盖顶层脚本），
> 否则 `/opt/e2b-infra/init-client.sh` 等会退回上游版本。见 03 篇 §6 和
> `single-node-offline-deploy.md` §5。
>
> 注意 `rpm -Uvh` 会把 `/usr/bin/template-manager` 之外的东西也刷回 RPM 里的版本，
> 所以**装包之后要重新跑一遍 `build.sh -s`**（或至少 `start-client.sh` + `-r` 各 job），
> 让部署机回到"由包决定"的状态——而不是停留在你手工拷的那份。

## 6. 流程速查卡

```
一次性:  写好 source-e2b.sh (GOFLAGS / GOTOOLCHAIN / GOWORK)
         §3.2 那八步一把梭：解包 → 查 vendor → 补 busybox → exclude db 产物
                            → 分支+基线+tag upstream → patch -p1 → 自检 → 冒烟编译

日常(高频，不出包):
         ① 改代码
         ② cd packages/<模块> && make build
         ③ 换二进制：
              orchestrator  rm -f + cp → /usr/bin/{orchestrator,template-manager}
                            → build.sh -r template-manager
              fc-* 助手     rm -f + cp → /opt/e2b-infra/bin/   (不用重启)
              api/edge      cp → bin/ → docker build+push → build.sh -r api
              envd          cp → /fc-envd/envd → 重建模板
         ④ md5sum 对一下 + 看日志 → 回 ①

收尾(低频，做完一个阶段):
         ① git add -A && git commit
         ② grep -c "GIT binary patch" == 0
            git diff upstream HEAD > $E2B_PKG/0001-adapted-for-arm-architecture.patch
         ③ patch --dry-run → rpmbuild (Release 不动) → rpm -Uvh --force
            → 重放 dep overlay / build.sh -s → push 仓库A
```

## 7. 两件必须知道的事

### 7.1 `go.work` 别混进 patch

`source-e2b.sh` 里的 `GOWORK=off` 已经解决了它，**不要用 `rm -f go.work` 那种做法**：
`go.work` 是被 git 跟踪的，删了之后一个 `git add -A` 就把删除提交进去，patch 里于是
多出一段删 `go.work` 的 diff——而 spec 的 `%build` 本来就会 `rm -f go.work`，纯属噪音。

万一手滑删了，`git status` 会显示 `deleted: go.work`，恢复它：

```bash
git checkout -- go.work            # ✅ 只写 go.work，别带 go.work.sum（原因见 §8 表）
```

### 7.2 加了新依赖必须重做 vendor

`vendor/` 是把第三方依赖源码原样复制进项目的一份副本，配合 `-mod=vendor` 让编译完全不联网
——**这是整套离线构建的命脉**（另一半是 Go SDK 随包自带）。

如果你的改动动了某个模块的 `go.mod`（引入了新的第三方库），那个模块的 `vendor/` 里不会自动有它，
离线编译会报 `cannot find module providing package …`。这时必须到**有网机器**上、
**进到那个模块目录**执行：

```bash
cd packages/orchestrator   # ← 改了哪个模块的 go.mod 就进哪个
go mod vendor
```

改动跨模块（比如 shared 加了新依赖，api 和 orchestrator 都用到）就每个受影响的模块各跑一遍。
补全后的 `vendor/` 会一起进 patch（patch 变大属正常）。日常只改现有逻辑则不涉及这步。

## 8. 常见报错速查

| 报错 | 原因 / 处置 |
|---|---|
| `Bad source: ...tar.gz`，或 tar 报不是 gzip | 忘了 `git lfs pull`，源码包还是 134 字节的 LFS 指针 |
| 根目录 `ls vendor` 找不到 | 正常：多模块布局，vendor 在 `packages/<模块>/vendor/`，用 §3.2 第 2 步的循环查 |
| `pattern busybox_1.35_arm64: no matching files found` | 漏了 §3.2 第 3 步。已经建完基线才发现的话，拷进去后把这个路径追加进 `.git/info/exclude`，别让它进 commit |
| `cannot find module providing package ...` | 该模块 vendor 不全，见 §7.2（**进到那个模块目录**跑 `go mod vendor`） |
| `go: downloading go1.x.y ...` 卡住 | 没设 `GOTOOLCHAIN=local`，go 在联网找工具链 |
| `-mod=vendor` 与 workspace 冲突 / 其它 `go.work` 报错 | 没设 `GOWORK=off`（§3.1） |
| `make build` 报 `cc: command not found` / cgo 相关 | 没装 gcc。orchestrator 是 `CGO_ENABLED=1` 编的，还要用 `$(CC)` 编 `fc-launch-c`（§3.1） |
| `cat: ../../.last_used_env: No such file or directory` | 不是错误，忽略（§3.4） |
| 换二进制时 `cp: ... Text file busy` | 目标正被运行中的进程执行（ETXTBSY），内核不许写。先 `rm -f` 再 `cp`——unlink 是允许的（§4③） |
| 换完二进制行为没变 | 只拷文件不够：orchestrator 要 `build.sh -r template-manager` 重跑 job，api/edge 要重建推镜像后 `build.sh -r api`，envd 要重建模板。对照 §4③ 那张表 |
| `git commit` 报 `unable to auto-detect email address` | 没配 git 身份，见 §3.2 第 5 步 |
| `error: pathspec 'go.work.sum' did not match any file(s)` | `go.work.sum` 在磁盘上有，但被上游 `.gitignore` 第 14 行忽略、git 从没跟踪它。git 遇到匹配不上的 pathspec 会**整条命令失败、一个文件都不恢复**，所以恢复只写 `git checkout -- go.work` |
| 生成的 patch 突然涨到几十万行 | 基线用错了：拿 tarball 自带的 `2026.09` tag 当下界，把 vendor 整棵树算成新增。用自己打的 `upstream` tag |
| patch 里出现 `GIT binary patch`，别人 `%prep` 打不上 | 有二进制被 `git add -A` 收进去了（多半是 `packages/db` 的编译产物，见 §3.2 第 4 步）。`git diff upstream HEAD --stat \| grep Bin` 定位，`git rm --cached` 后补进 `.git/info/exclude` |
| `%prep` 阶段 `Hunk #N FAILED` | patch 与源码不匹配。多半是手改了 patch，或 patch 不是从 `upstream` 基线 diff 出来的。按 §3.2 重搭树 + §5② 重新生成 |
| 安装时 `package ... is already installed` | 预期内：`Release` 一直不动，每次都是同名同版本。用 `rpm -Uvh --force`（§5③） |
| 安装时 `file ... conflicts with file from package ...` | RPMS 目录里旧 Release 的包被通配符一起装了；写明确文件名 |

## 9. 附：为什么只保留一个 patch

拆成多个 patch 的唯一价值是"想单独应用/单独关掉其中一个"，或"它们来自不同上游"。
本仓库两条都不满足：`%autosetup -p1` 每次都是固定顺序全部一起打，从没单独用过其中一个；
两个 patch 也都是同一个上游 tag（2026.09）上的自家下游改动。

而多 patch 的代价是实打实的——每次改代码都要先回答一串问题：
"我的改动属于哪一层？该 `diff upstream` 还是 `diff patch1`？改了 patch1 会不会把 patch2 打崩？"
合并成一个之后，这一整类问题全部消失，重新生成 patch 塌缩成 §5② 那一条命令。

失去的只有一样：FC 启动优化不再是一个自包含、一眼可见的独立改动集。
但这种"逻辑归属"本来就该记在 git 提交和 `benchmark/FC启动优化-*.md` 文档里，
而不是靠 patch 文件的物理拆分来保存——patch 是"当前差异快照"，不是"历史账本"。

> **但 patch 机制本身要保留，别改成把源码整个 fork 进仓库。** patch 的真正价值是让
> 相对上游的改动小而可见，并且将来上游出新版（2027.xx）时，你能把这份 patch 尝试
> rebase 上去。fork 整棵源码树会同时失去"与纯上游一键对比"和"跟随上游升级"两个好处。
>
> 最佳组合就是本篇描述的：**保留 patch 模型，但只留一个 patch，并长期维护一棵
> 打好补丁的源码工作树**。
