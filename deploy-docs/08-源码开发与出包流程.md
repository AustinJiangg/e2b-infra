# 08 源码开发与出包流程

本篇回答一个问题：**我要改 E2B 的 Go 源码，从"改第一行代码"到"新 RPM 装上部署机"，
完整流程该怎么走。**

03 篇讲的是 RPM 怎么从"源码 + 补丁 + 离线二进制"构建出来（供应链视角）；
本篇讲的是**你作为开发者每天怎么操作**（工作流视角）。两篇配套看。

> **前提**：本篇假设仓库只有**一个** patch（`0001-adapted-for-arm-architecture.patch`）。
> 早期曾把 FC 启动优化拆成 `0002-fc-launch-dedicated-helper.patch`，那个拆分对下游开发
> 只有负担没有收益（详见 §7），已合并进 0001、spec 里的 `Patch2:` 声明也已删除。

## 1. 先建立心智模型：两个仓库 + 一份 Go SDK

整套流程最关键的一点，就是分清这三者各自是什么、产物流向哪里。想清楚这张图，后面就不会乱：

```
┌─ 仓库A:交付仓库 = projects/e2b-infra ──────────────────────────┐
│  内容:0001 patch、e2b-infra.spec、各种 tarball                  │
│        (源码包、e2b-deploy、tools-arm64 = Go SDK …)             │
│  角色:你 push 到远端、别人拿去 rpmbuild 的东西                  │
│        ⚠️ 它【不含】展开的 Go 源码                              │
│  变量:$E2B_PKG                                                  │
└────────────────────────────────────────────────────────────────┘
        ▲ 只回收一样东西:重新生成的 0001.patch
        │
┌─ 仓库B:源码工作树 = projects/e2b-src ──────────────────────────┐
│  内容:上游源码解开 + git init + 打上 0001                       │
│  角色:你平时写代码的地方。纯本地工具,【不 push 任何地方】      │
│        唯一产物 = 新的 0001.patch                               │
│  变量:$E2B_SRC                                                  │
└────────────────────────────────────────────────────────────────┘
        ▲ 编译时借用
        │
┌─ Go SDK = /usr/local/go(系统级安装)───────────────────────────┐
│  角色:只是编译器。装一次,全局可用                              │
│  ⚠️ 既不放进仓库A的源码,也不放进仓库B的工作树(会污染 git)     │
└────────────────────────────────────────────────────────────────┘
```

**为什么需要仓库B**：仓库A 里只有 patch，没有可编译的源码。而 patch 文件是**不能手改**的
（行号/上下文一错就 `Hunk FAILED`）。所以要有一棵"展开并打好补丁"的源码树：你在里面正常写代码，
最后用 `git diff` 让 git 帮你重新生成 patch。仓库B 的 git 只为这一件事存在，永远不推到远端。

## 2. 关于 Go SDK：用系统装的，不用包里那份

### 2.1 `tools-arm64.tar.gz` 是什么

它就是**官方 Go 1.25.4 ARM64 SDK**，解开是标准的 `go/` 目录（`bin/go`、`src/`、`pkg/` …），
也就是 GOROOT。仓库里还有 `tools-amd64.tar.gz`，同一套东西的 x86_64 版。

它存在的唯一目的是 **给 rpmbuild 用**：spec 的 `%prep` 会按架构把它解压到
`BUILD/go-toolchain/`，`%build` 再把 `GOROOT` 指过去——这样**构建机不需要预装 Go**
（`BuildRequires` 里只有 `make gcc`），也不需要联网。详见 03 篇 §3.2。

### 2.2 为什么它和官网下载的 sha256 对不上

这是个常见困惑。实测对比：

| | 大小 | sha256 |
|---|---|---|
| 官网 `go1.25.4.linux-arm64.tar.gz` | 57268847 | `a68e86d4b72c2c2fecf7dfed667680b6c2a071221bbdb6913cf83ce3f80d9ff0` |
| 仓库 `tools-arm64.tar.gz` | 57033990 | `b84506318d627fee963bfa9920ebd4a36fc2feebb40c0821c54084662282c782` |

**结论：内容完全相同，只是被解开后用不同的压缩参数重新打了一次包。** 取证依据：

- `go/VERSION` = `go1.25.4` + `time 2025-10-31T13:24:27Z`，是**官方构建时间戳**，一字不差；
- `go/bin/go` 是 ELF aarch64 可执行文件，内嵌版本串 `go1.25.4`；
- 全部 16092 个文件的 mtime 都是 2025-10-31（官方构建日），内容没被动过；
- **gzip 头部的 MTIME 字段被清零**（`00 00 00 00`）——这是"可复现构建"的典型手法
  （`gzip -n` 或 Go 的 `archive/gzip` 等），官方原件不会是全 0；
- 旁证：`tools-amd64.tar.gz` 的 gzip 头前 16 字节与 arm64 完全一致，说明两个包是
  同一套流程批量重打的，不是分别从官网下载的原件。

所以大小差 ~235KB 纯粹是 deflate 输出不同造成的，sha256 自然不同。
**不必追求让两者 sha256 一致**——那需要还原原始打包参数，没有意义。
要验证它可信，看 `go/VERSION` 的官方时间戳 + `go version` 输出就够了。

### 2.3 因此：日常开发用 `/usr/local/go`

既然两者等价，**优先用系统装好的那份**：

```bash
wget --no-check-certificate https://mirrors.aliyun.com/golang/go1.25.4.linux-arm64.tar.gz
rm -rf /usr/local/go && tar -C /usr/local -xzf go1.25.4.linux-arm64.tar.gz
# 在 ~/.bashrc 里配 PATH（root 多人共用时，这样谁登录都能用）
export PATH=$PATH:/usr/local/go/bin
```

理由：已经装好了省事；仓库里那份的使命是构建时给 rpmbuild 用，和日常开发编译无关；
少一份解压副本少一个混淆源。

**GOROOT / GOPATH 都不用手配**：

- `GOROOT` —— go 二进制会自己推断（`/usr/local/go/bin/go` → `/usr/local/go`）。
  只有要用仓库里那份 SDK 时才需要显式 export，而我们不用它。
- `GOPATH` —— 默认 `~/go` 即可。本项目走 vendor 模式，依赖全在 `vendor/` 里，基本不碰它。

## 3. 一次性准备（每台开发机只做一遍）

### 3.1 写环境脚本 `source-e2b.sh`

放在你自己的家目录（不要写进多人共用的 `~/.bashrc`）。它**只放项目特有的东西**，
Go 的 PATH 交给 `~/.bashrc` 管，两者不重复、不冲突：

```bash
# /home/<你>/source-e2b.sh
# 用法：每次开发 e2b 前先 `source /home/<你>/source-e2b.sh`

# —— 两个仓库 ——
export E2B_PKG=/home/<你>/projects/e2b-infra   # 交付仓库：patch + spec + tarball
export E2B_SRC=/home/<你>/projects/e2b-src     # 源码工作树：改代码的地方

# —— 离线编译开关（本项目必需）——
export GOFLAGS=-mod=vendor    # 只用 vendor 目录的依赖，绝不联网
export GOTOOLCHAIN=local      # 禁止 go 因 go.mod 版本声明而联网自动换工具链

echo "[e2b] E2B_PKG=$E2B_PKG"
echo "[e2b] E2B_SRC=$E2B_SRC"
echo "[e2b] go: $(go version 2>/dev/null || echo '未找到 go，检查 ~/.bashrc 的 PATH')"
```

> `GOTOOLCHAIN=local` 很重要：Go 1.21+ 发现 `go.mod` 声明的版本高于本机时，
> 会**自动联网下载**对应工具链。离线机器上这会卡住或报错，`local` 强制它只用本机这套。

### 3.2 解开源码，搭出仓库B

用 `$E2B_PKG/e2b-infra-2026.09.tar.gz`——它就是 spec 用的同一份源码（`Source0`），最准确。

```bash
source /home/<你>/source-e2b.sh

# ⚠️ 先确认它是真文件，不是 git-lfs 指针（134 字节的就是指针，需要先 git lfs pull）
ls -l "$E2B_PKG/e2b-infra-2026.09.tar.gz"

mkdir -p "$E2B_SRC"
tar -xzf "$E2B_PKG/e2b-infra-2026.09.tar.gz" -C "$E2B_SRC"
cd "$E2B_SRC/e2b-infra-2026.09"                 # ← 这就是你以后的开发目录

# 命脉检查：vendor 在不在（离线编译全靠它，见 §6.2）
ls vendor >/dev/null 2>&1 && echo "✅ vendor 就位" || echo "❌ 缺 vendor，离线编译会失败"
```

### 3.3 建 git 基线 + 打 patch

```bash
cd "$E2B_SRC/e2b-infra-2026.09"
git init -q
git add -A && git commit -qm base
git tag upstream                    # ← 钉死"纯上游"基线，以后永不变动

patch -p1 < "$E2B_PKG/0001-adapted-for-arm-architecture.patch"
git add -A && git commit -qm patched   # 当前状态 = 部署机上跑的源码
```

`upstream` 这个 tag 是重新生成 patch 时的"下界"，是整个流程的锚点。做完这三步，
`$E2B_SRC/e2b-infra-2026.09` 就是你**长期的开发目录**，以后不用再重建。

## 4. 日常开发循环（每次改动就这 5 步）

```bash
source /home/<你>/source-e2b.sh
cd "$E2B_SRC/e2b-infra-2026.09"
```

### ① 改代码

想改哪个文件改哪个，**不用再想"属于哪一层"**——这是只保留单一 patch 的最大红利。

### ② 编译验证

```bash
[ -f go.work ] && rm -f go.work go.work.sum     # 与 -mod=vendor 冲突，编译前临时删（见 §6.1）

cd packages/orchestrator && make build && cd -  # 改哪个模块编哪个；编不过就别往下走
```

各模块与产物的对应关系见 03 篇 §3.3（orchestrator 会额外产出 `fc-launch`、`fc-netns-exec`）。

### ③ 提交

```bash
git status                          # ⚠️ 确认没有 "deleted: go.work"（见 §6.1）
git add -A && git commit -m "描述这次改动"
```

### ④ 重新生成 patch —— 一条命令

```bash
git diff upstream HEAD > "$E2B_PKG/0001-adapted-for-arm-architecture.patch"
```

零歧义、不可能打崩别的 patch。文件名不变，直接覆盖仓库A 里的旧 patch。

### ⑤ 验证 + 出包 + 提交

```bash
# 验证 patch 能在纯净源码上干净应用（建议每次都做，20 秒的事）
rm -rf /tmp/verify && mkdir -p /tmp/verify
tar -xzf "$E2B_PKG/e2b-infra-2026.09.tar.gz" -C /tmp/verify
cd /tmp/verify/e2b-infra-2026.09
patch -p1 --dry-run < "$E2B_PKG/0001-adapted-for-arm-architecture.patch" \
  && echo "✅ patch 可干净应用"

# 出 RPM（须在 aarch64 机器上）
cd "$E2B_PKG"
rpmbuild -bb e2b-infra.spec --define "_sourcedir $PWD"
# 产物：~/rpmbuild/RPMS/aarch64/e2b-infra-2026.09-<Release>.aarch64.rpm

# 提交交付仓库
git add 0001-adapted-for-arm-architecture.patch
git commit -m "..." && git push -u origin <你的分支>
```

装到部署机、以及装完之后必须做的"重放 dep overlay"，见 03 篇 §6 和
`single-node-offline-deploy.md` §5。

## 5. 流程速查卡

```
一次性:  写好 source-e2b.sh
         tar 解源码到 $E2B_SRC
         git init && git tag upstream && patch -p1 < 0001

每次改:  cd $E2B_SRC/e2b-infra-2026.09
         ① 改代码
         ② rm go.work; make build                (编不过就停)
         ③ git checkout -- go.work; git add -A && git commit
         ④ git diff upstream HEAD > $E2B_PKG/0001-adapted-for-arm-architecture.patch
         ⑤ patch --dry-run 验证 → rpmbuild → push 仓库A
```

## 6. 两个必须记住的坑

### 6.1 `go.work` 别混进 patch

第 ② 步为了编译删掉了 `go.work`，但它**不能进 patch**——spec 的 `%build` 本来就会
`rm -f go.work`，patch 里再删一遍是多余噪音。所以第 ③ 步 `git status` 若看到
`deleted: go.work`，先恢复再提交：

```bash
git checkout -- go.work go.work.sum
```

### 6.2 加了新依赖必须重做 vendor

`vendor/` 是把所有第三方依赖的源码原样复制进项目的一份副本，配合 `GOFLAGS=-mod=vendor`
让编译完全不联网——**这是整套离线构建的命脉**（另一半是 Go SDK 随包自带）。

如果你的改动动了 `go.mod`（引入了新的第三方库），`vendor/` 里不会自动有它，
离线编译会报 `cannot find module providing package ...`。这时必须到**有网机器**上：

```bash
go mod vendor      # 补全 vendor/
```

补全后的 `vendor/` 也会一起进 patch（patch 会变大，属正常）。日常只改现有逻辑、
不加新依赖则不涉及这步。

### 6.3 常见报错速查

| 报错 | 原因 / 处置 |
|---|---|
| `Bad source: ...tar.gz`，或 tar 报不是 gzip | 忘了 `git lfs pull`，源码包还是 134 字节的 LFS 指针 |
| `%prep` 阶段 `Hunk #N FAILED` | patch 与源码不匹配。多半是手改了 patch，或 patch 不是从 `upstream` 基线 diff 出来的。按 §3.3 + §4④ 重新生成 |
| `cannot find module providing package ...` | vendor 不全，见 §6.2 |
| `go: downloading go1.x.y ...` 卡住 | 没设 `GOTOOLCHAIN=local`，go 在联网找工具链 |
| `go.work` 相关报错 | 编译前没删 `go.work`（spec 的 `%build` 会自己删，本地要手动） |
| 安装时 `file ... conflicts with file from package ...` | RPMS 目录里旧 Release 的包被通配符一起装了；写明确文件名 |
| 安装时 `package ... is already installed` | 同 Release 重装，用 `rpm -Uvh --force` |

## 7. 附：为什么只保留一个 patch

拆成多个 patch 的唯一价值是"想单独应用/单独关掉其中一个"，或"它们来自不同上游"。
本仓库两条都不满足：`%autosetup -p1` 每次都是固定顺序全部一起打，从没单独用过其中一个；
两个 patch 也都是同一个上游 tag（2026.09）上的自家下游改动。

而多 patch 的代价是实打实的——每次改代码都要先回答一串问题：
"我的改动属于哪一层？该 `diff upstream` 还是 `diff patch1`？改了 patch1 会不会把 patch2 打崩？"
合并成一个之后，这一整类问题全部消失，重新生成 patch 塌缩成 §4④ 那一条命令。

失去的只有一样：FC 启动优化不再是一个自包含、一眼可见的独立改动集。
但这种"逻辑归属"本来就该记在 git 提交和 `benchmark/FC启动优化-*.md` 文档里，
而不是靠 patch 文件的物理拆分来保存——patch 是"当前差异快照"，不是"历史账本"。

> **但 patch 机制本身要保留，别改成把源码整个 fork 进仓库。** patch 的真正价值是让
> 相对上游的改动小而可见，并且将来上游出新版（2027.xx）时，你能把这份 patch 尝试
> rebase 上去。fork 整棵源码树会同时失去"与纯上游一键对比"和"跟随上游升级"两个好处。
>
> 最佳组合就是本篇描述的：**保留 patch 模型，但只留一个 patch，并长期维护一棵
> 打好补丁的源码工作树**。
