# 模板与快照到底存在哪里（STORAGE_PROVIDER 全梳理）

> 起因：`.env` 里明明写着 `STORAGE_PROVIDER=MinioBucket`，但快照产物看起来在本地磁盘上。
> 本文把「模板/快照存储」这条链路从 Go 代码到部署脚本全部理一遍：存在哪、谁决定、
> 为什么 MinIO 没生效、想真用 MinIO 怎么改。
>
> 配套：[`09-增量快照实现与ARM实测分析.md`](09-增量快照实现与ARM实测分析.md)（快照内部怎么算增量）、
> `benchmark/snapshot.py`（打快照的脚本）。

---

## 0. 结论速查

1. **要先分清两件事**：
   - **本地缓存**：`/orchestrator/build`、`/orchestrator/template`、`/mnt/snapshot-cache`
     —— **不管 provider 是什么都有**，是运行期的缓存，orchestrator 重启还会被清空；
   - **持久化存储**：由 `STORAGE_PROVIDER` 决定，Local 就是本地目录，MinioBucket 就是桶。
2. 本仓库 **nomad 单机部署里持久化 provider 实际是 `Local`**，模板/快照的持久化目录是
   `/tmp/templates`（构建层缓存是 `/tmp/build-cache`），都是代码默认值，本仓库没有覆盖。
   openEuler 上 `/tmp` 是 tmpfs ⇒ **宿主重启后模板全部丢失，要重新建模板**（§7.1）。
3. **MinIO 在这套 nomad 单机部署里没有被任何组件用来存模板/快照**：`.env` 的
   `STORAGE_PROVIDER=MinioBucket` 没有任何被提交的 job 会消费它。
4. 原因是一行硬编码：`e2b-deploy/dep/template-manager.hcl` 里写死了
   `STORAGE_PROVIDER = "Local"`，而 `build.sh -s` 会用这份文件**覆盖** RPM 装进去的那份
   （RPM 那份写的是 `${STORAGE_PROVIDER}`，会被 `.env` 渲染成 MinioBucket）。

> **一处更正**：我此前说过「你在 `/orchestrator/build` 看到 memfile，说明 provider 是 Local」——
> 这个推断不成立。那两个目录是**本地缓存**，MinIO 模式下同样会有。真正的判据是
> 进程的环境变量 + `/tmp/templates` 里有没有东西（见第 5 节）。结论（provider 确实是 Local）
> 没变，但依据要换成第 4 节那条硬编码。

| 层 | 路径 | 谁写 | 生命周期 | 代码 |
|---|---|---|---|---|
| 沙箱运行态 | `/orchestrator/sandbox`（`SANDBOX_CACHE_DIR`） | orchestrator | 沙箱销毁即清 | `shared/pkg/storage/sandbox.go:21` |
| 本地缓存 · 模板元文件 | `/orchestrator/template/<buildID>/cache/<uuid>/{snapfile,metadata.json}` | orchestrator | TTL 25h，缓存项关闭即 `RemoveAll` | `storage/template_cache.go:50`、`sandbox/template/cache.go:30` |
| 本地缓存 · diff 数据 | `/orchestrator/build/<buildID>-memfile-<rand>`、`<buildID>-rootfs.ext4-<rand>` | orchestrator | TTL 25h + 容量驱逐；**进程启动时整目录清空** | `sandbox/build/diff.go:77`、`sandbox/template/cache.go:78-90` |
| 本地缓存 · 快照 tmpfs | `/mnt/snapshot-cache`（`SNAPSHOT_CACHE_DIR`，tmpfs 65G） | orchestrator | 重启即空 | `storage/sandbox.go:22`、`e2b-deploy/dep/init-client.sh:76-78` |

最能说明「`/orchestrator/build` 是缓存不是家」的一行代码，在模板缓存初始化里：

```go
// packages/orchestrator/internal/sandbox/template/cache.go:78
err := cleanDir(config.DefaultCacheDir)      // DefaultCacheDir = ${ORCHESTRATOR_BASE_PATH}/build
```

**orchestrator 一重启，`/orchestrator/build` 就被清空。** 持久化的东西不可能放在这里。

相关默认值（`packages/orchestrator/internal/cfg/model.go:22-27`、`storage/sandbox.go:21-23`）：

| 环境变量 | 默认值 | 含义 |
|---|---|---|
| `ORCHESTRATOR_BASE_PATH` | `/orchestrator` | 下面几个的基准目录 |

## 2. 持久化：provider 怎么选、路径/键是什么

`packages/shared/pkg/storage/storage.go:97-135`，两个入口各建一个 provider：

```go
func GetTemplateStorageProvider(...) (StorageProvider, error) {
    provider := Provider(env.GetEnv("STORAGE_PROVIDER", string(DefaultStorageProvider)))

    if provider == LocalStorageProvider {                                  // "Local"
        basePath := env.GetEnv("LOCAL_TEMPLATE_STORAGE_BASE_PATH", "/tmp/templates")
        return newFileSystemStorage(basePath), nil                         // 就是本地目录
    }

    bucketName := utils.RequiredEnv("TEMPLATE_BUCKET_NAME", ...)           // 桶模式才需要
    switch provider {
    case AWSStorageProvider:   return newAWSStorage(ctx, bucketName)
    case GCPStorageProvider:   return NewGCP(ctx, bucketName, limiter)
    case MINIOStorageProvider: return NewMinioBucketStorageProvider(ctx, bucketName)  // ← ARM patch 新增
    }
}
```

`GetBuildCacheStorageProvider` 同构，只是换成 `LOCAL_BUILD_CACHE_STORAGE_BASE_PATH`
（默认 `/tmp/build-cache`）和 `BUILD_CACHE_BUCKET_NAME`。

| provider 值 | 模板/快照落点 | 构建层缓存落点 | 需要的环境变量 |
|---|---|---|---|
| `Local` | `LOCAL_TEMPLATE_STORAGE_BASE_PATH`，默认 **`/tmp/templates`** | `LOCAL_BUILD_CACHE_STORAGE_BASE_PATH`，默认 **`/tmp/build-cache`** | 无（桶名都不需要） |
| `MinioBucket` | 桶 `TEMPLATE_BUCKET_NAME` | 桶 `BUILD_CACHE_BUCKET_NAME` | `MINIO_ENDPOINT` / `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` |
| `GCPBucket` / `AWSBucket` | 对应云厂商的桶 | 同上 | 云凭据 |

**对象键在所有 provider 下是一样的**（`shared/pkg/storage/template.go:10-52`），前缀是 build ID：

```
<buildID>/snapfile
<buildID>/memfile            <buildID>/memfile.header
<buildID>/rootfs.ext4        <buildID>/rootfs.ext4.header
<buildID>/metadata.json
```

落到不同 provider 上就是：

- **Local**：`/tmp/templates/<buildID>/memfile`（`fsStorage` 直接按路径建目录写文件，`storage_fs.go:59-76`）
- **MinIO**：桶 `e2b-dev-fc-templates` 里的对象 `<buildID>/memfile`；MinIO 自己在磁盘上摊成
  `/root/data/minio/e2b-dev-fc-templates/<buildID>/memfile/xl.meta`

ARM patch 对这一块只做了两件事（`packages/shared/pkg/storage/storage.go`）：

```diff
-	GCPStorageProvider   Provider = "GCPBucket"
-	AWSStorageProvider   Provider = "AWSBucket"
-	LocalStorageProvider Provider = "Local"
-
-	DefaultStorageProvider Provider = GCPStorageProvider
+	GCPStorageProvider     Provider = "GCPBucket"
+	AWSStorageProvider     Provider = "AWSBucket"
+	LocalStorageProvider   Provider = "Local"
+	MINIOStorageProvider   Provider = "MinioBucket"
+	DefaultStorageProvider Provider = MINIOStorageProvider
...
+	case MINIOStorageProvider:
+		return NewMinioBucketStorageProvider(ctx, bucketName)
```

新增的 `storage_minio.go` 有两个细节要记住：

- `useSSL = false` 是**硬编码**的常量 ⇒ `MINIO_ENDPOINT` 必须是 `host:port`（不带 `http://`），且走明文 HTTP；
- `NewMinioBucketStorageProvider` **只建 client，不建桶** ⇒ 桶必须事先存在。

## 3. 谁会去读写持久化存储

全仓库只有两个地方构造 provider：

| 调用点 | 用途 |
|---|---|
| `packages/orchestrator/main.go:297` `GetTemplateStorageProvider` | 模板/快照的读写（恢复沙箱、上传快照） |
| `packages/orchestrator/internal/template/server/main.go:92` `GetBuildCacheStorageProvider` | 模板构建的层缓存 |

（另外 `cmd/create-build`、`cmd/resume-build` 两个离线工具也会调，不参与线上流程。）

**`packages/api` 完全不 import 存储包**（`grep -rn "pkg/storage" packages/api/` 为空）。
所以：

- API 不直接碰模板文件；删模板/删快照是 API 通过 gRPC 让 template-manager 去做，
  最终落到 `packages/orchestrator/internal/template/template/main.go:21`
  的 `DeleteObjectsWithPrefix(buildID)`——**用的是 template-manager 自己的 provider**；
- 换句话说，**api job 上设不设 `STORAGE_PROVIDER` 都无所谓**。

本部署里 orchestrator 与 template-manager 是**同一个进程**
（`dep/template-manager.hcl`: `ORCHESTRATOR_SERVICES = "orchestrator,template-manager"`），
所以「这台机器的模板存哪」完全由这一个进程的环境变量决定。

## 4. 为什么 `.env` 写了 MinioBucket 却没生效

完整链路，四步：

**① RPM 安装期**（`e2b-infra.spec:64-67`）

```bash
install -d %{buildroot}/opt/e2b-infra/nomad
for hcl in iac/provider-gcp/nomad/jobs/*.hcl; do
    install -D -m 644 "$hcl" %{buildroot}/opt/e2b-infra/nomad/$(basename "$hcl")
done
```

这批 hcl 里（含 ARM patch 改过的 `template-manager.hcl`、`orchestrator.hcl`）写的是：

```hcl
STORAGE_PROVIDER = "${STORAGE_PROVIDER}"      # 会被 .env 渲染成 MinioBucket
```

**② `build.sh -s` 覆盖**（`e2b-deploy/build.sh:268`）

```bash
cp -fv "$DEP_DIR/template-manager.hcl" "$E2B_DIR/nomad/template-manager.hcl"
```

`e2b-deploy/dep/template-manager.hcl` 里是**字面量**：

```hcl
ORCHESTRATOR_SERVICES = "orchestrator,template-manager"
STORAGE_PROVIDER      = "Local"                 # ← 关键的一行，写死了
MINIO_ENDPOINT        = "${MINIO_ENDPOINT}"     # 传了，但 provider 不是 Minio，用不上
TEMPLATE_BUCKET_NAME  = "${TEMPLATE_BUCKET_NAME}"
```

**③ `deploy.sh` 渲染**（`dep/deploy.sh:3-4,26-33,128-141`）

```bash
cd "$SCRIPT_DIR"          # /opt/e2b-infra
source .env               # STORAGE_PROVIDER=MinioBucket 在这里被 export
for hcl in nomad/*.hcl; do
    envsubst '... $STORAGE_PROVIDER ...' < "$hcl" > rendered/$(basename "$hcl")
done
```

`envsubst` 只替换 `${VAR}` 形式，**字面量 `"Local"` 原样保留**。

**④ 只提交 4 个 job**（`dep/deploy.sh:143-160`）

```bash
JOBS=(redis template-manager edge api)
```

`orchestrator.hcl`（里面才是 `${STORAGE_PROVIDER}`）**根本没被提交**——orchestrator 是跑在
`template-manager` 这个 system job 里的。

**所以**：`.env` 的 `STORAGE_PROVIDER=MinioBucket` 在 nomad 单机路径上没有任何 job 会消费它，
唯一读这个变量的进程拿到的是硬编码的 `Local`。

> k8s/helm 路径是另一回事：`helm/templates/orchestrator.yaml`、`template-manager.yaml` 用的是
> `storageProvider: ${STORAGE_PROVIDER}`（patch:1165,1704,1865），那条路上 MinIO 是真生效的。
> 也就是说 `.env` 里那行是给 helm 路径和「本来的设计意图」留的。

**顺带一问：这台机器上 MinIO 还被谁用？**

- 模板/快照：不用（本文主题）；
- Loki：用的是 `storage_config.filesystem`（`iac/.../loki.hcl`），不走 S3；
- ClickHouse 备份：`CLICKHOUSE_BACKUPS_BUCKET_NAME=` 是空的。

⇒ **nomad 单机部署里 MinIO 基本是「装了没用」**，`build.sh -i` 装它、健康检查它，
但没有组件往里写东西。桶 `e2b-dev-fc-templates` / `e2b-dev-fc-cache` 也没有建（核对见 §7.1）。

## 6. 想真的用 MinIO，怎么改

> 先想清楚要不要改：单机场景下 Local 更快（少一跳网络 + 少一份拷贝），MinIO 的价值在
> **多节点共享模板**和**独立于节点生命周期的持久化**。单机想要「不丢」，把 Local 的
> base path 指到持久盘（第 7 节）成本更低。

**步骤**

1. **建桶**（代码不会自动建）：

   ```bash
   # 控制台 http://<SERVER_IP>:9001 (minioadmin/minioadmin) 手工建，或用 mc：
   mc alias set local http://127.0.0.1:9000 minioadmin minioadmin
   mc mb local/e2b-dev-fc-templates
   mc mb local/e2b-dev-fc-cache
   ```

2. **改那行硬编码**——注意要改**源头**，否则下次 `build.sh -s` 又被覆盖回去：

   ```bash
   # 源头（仓库里，会被打进 e2b-deploy.tar.gz）
   e2b-deploy/dep/template-manager.hcl:  STORAGE_PROVIDER = "Local"
                                      →  STORAGE_PROVIDER = "${STORAGE_PROVIDER}"
   # 机器上当前生效的那份（想先试一把就只改这个）
   /opt/e2b-infra/nomad/template-manager.hcl
   ```

3. **确认 `.env`**（`/opt/e2b-infra/.env`）：

   ```bash
   STORAGE_PROVIDER=MinioBucket
   MINIO_ENDPOINT="<SERVER_IP>:9000"     # 不能带 http://，useSSL 在代码里硬编码为 false
   MINIO_ACCESS_KEY="minioadmin"
   MINIO_SECRET_KEY="minioadmin"
   TEMPLATE_BUCKET_NAME=e2b-dev-fc-templates
   BUILD_CACHE_BUCKET_NAME=e2b-dev-fc-cache
   ```

4. **迁移已有数据**（不迁的话旧模板会「对象不存在」，建沙箱直接失败）：

   ```bash
   mc cp --recursive /tmp/templates/    local/e2b-dev-fc-templates/
   mc cp --recursive /tmp/build-cache/  local/e2b-dev-fc-cache/
   # 目录结构必须保持 <buildID>/<文件名>，不要多套一层
   mc ls local/e2b-dev-fc-templates | head
   ```

5. **只重跑这一个 job**（不必整套 `-s`）：

   ```bash
   bash /path/to/e2b-deploy/build.sh -r template-manager     # = deploy.sh --only template-manager
   grep -n STORAGE_PROVIDER /opt/e2b-infra/rendered/template-manager.hcl   # 应该是 MinioBucket
   ```

6. **验证**：

   ```bash
   cd benchmark && python snapshot.py --mode diff --keep-snapshot --blob-mb 20
   mc ls local/e2b-dev-fc-templates | tail -5      # 应出现新的 <buildID>/ 前缀
   nomad alloc logs -stderr -job template-manager-system start | grep -i 'minio\|storage' | tail
   ```

7. **回滚**：把第 2 步改回 `"Local"`，`build.sh -r template-manager`；
   `/tmp/templates` 里的老数据还在（前提是没被清理）。

**常见坑**

| 现象 | 原因 |
|---|---|
| 起 job 就报 `Bucket for storing template files` 相关的 required env 报错 | `TEMPLATE_BUCKET_NAME` / `BUILD_CACHE_BUCKET_NAME` 没渲染进去（`utils.RequiredEnv`，桶模式必填） |
| 建沙箱报「对象不存在」 | 桶没建、或旧模板没迁移 |
| 连不上 MinIO / TLS 报错 | `MINIO_ENDPOINT` 带了 `http://`，或想走 HTTPS——`useSSL=false` 是硬编码的，要 HTTPS 得改 `storage_minio.go` 重新出包 |
| 改完没效果 | 只改了 `/opt/e2b-infra/nomad/…` 但又跑了一次 `build.sh -s`，被 `dep/` 那份覆盖了 |

## 7. Local 模式的运维注意点

### 7.1 模板放在 tmpfs 上：宿主重启即丢

以下在新 920B（openEuler 24.03 LTS-SP4，2026-09-23）上逐条核对过。

| 事实 | 依据 |
|---|---|
| 生效的 provider 是 `Local` | 仓库 `e2b-deploy/dep/template-manager.hcl:78` 写死 `STORAGE_PROVIDER = "Local"`，渲染后是 `/opt/e2b-infra/rendered/template-manager.hcl:79`；`template-manager` 进程环境里是 `STORAGE_PROVIDER=Local` |
| `.env` 的 `MinioBucket` 不生效 | `/opt/e2b-infra/.env:140` `export STORAGE_PROVIDER=MinioBucket` 只渲染进了 `/opt/e2b-infra/rendered/orchestrator.hcl:76`；`e2b-deploy/dep/deploy.sh:143-148` 的 `JOBS` 只有 `redis` / `template-manager` / `edge` / `api`，orchestrator job 从不提交（§4） |
| 模板根目录 `/tmp/templates`，构建层缓存 `/tmp/build-cache` | 代码默认值：`packages/shared/pkg/storage/storage.go:131-135`（`LOCAL_TEMPLATE_STORAGE_BASE_PATH`）、`:159-163`（`LOCAL_BUILD_CACHE_STORAGE_BASE_PATH`），源码 `KASandbox_0904` `deltabox-dev`@`4af2872c6`；部署没有设这两个变量（`rendered/template-manager.hcl` 与进程环境里都没有） |
| 每个 build 一个目录 `/tmp/templates/<buildID>/`，六个文件 | `memfile`、`memfile.header`、`rootfs.ext4`、`rootfs.ext4.header`、`snapfile`、`metadata.json`（原生 pause / snapshot 的产物也按同样的键写在这里，§2） |
| `/tmp` 是 tmpfs | `findmnt /tmp` 的 FSTYPE 为 `tmpfs`；由系统自带的 `/usr/lib/systemd/system/tmp.mount` 挂载（`local-fs.target.wants/` 下有它的链接），不是部署脚本加的 |
| MinIO 在跑，但没有建桶、不存模板 | `systemctl is-active minio` 为 `active`；`/root/data/minio/` 下只有 `.minio.sys`，没有任何桶目录 |

**后果**

- **宿主重启后 `/tmp/templates` 为空，模板（以及写在里面的原生 pause / snapshot 产物）全部丢失，需要重新建模板**
  （`benchmark/build_template.py`；若报 `Alias base already used`，按
  [`../single-node-offline-deploy.md`](../single-node-offline-deploy.md) §6.7 先删掉占着别名的那条）。
  重启后的整套恢复动作见 [`06-日常运维手册.md`](06-日常运维手册.md) §8.4。
- 不重启也会被清：`/usr/lib/tmpfiles.d/tmp.conf` 里有 `q /tmp 1777 root root 10d`，
  `systemd-tmpfiles-clean.timer` 为 active（`systemctl list-timers` 显示每天触发一次）；
  按 `tmpfiles.d(5)` 的 age 语义，`/tmp` 下超过 10 天既没被访问也没被修改的文件会被删掉。

**核对命令**

```bash
grep -n STORAGE_PROVIDER /opt/e2b-infra/rendered/template-manager.hcl /opt/e2b-infra/rendered/orchestrator.hcl
tr '\0' '\n' < /proc/$(pgrep -f '^/usr/bin/template-manager' | head -1)/environ \
  | grep -E 'STORAGE_PROVIDER|LOCAL_.*_BASE_PATH'
#   期望：STORAGE_PROVIDER=Local，没有 LOCAL_*_BASE_PATH 行
findmnt /tmp                                     # FSTYPE = tmpfs
ls /tmp/templates | wc -l                        # 模板/快照 build 数
ls /tmp/templates/*/ | grep -v -e '^/' -e '^$' | sort | uniq -c   # 六个文件名各出现 build 数次
find /root/data/minio -mindepth 1 -maxdepth 1    # 只有 /root/data/minio/.minio.sys
```

**可选做法：落到真盘**（当前部署没有这样做）

在 `e2b-deploy/dep/template-manager.hcl` 的 `env {}` 里加两行，指到真盘上的目录
（下面的路径只是示例，换成机器上实际的持久盘目录）：

```hcl
LOCAL_TEMPLATE_STORAGE_BASE_PATH    = "/data/e2b/templates"
LOCAL_BUILD_CACHE_STORAGE_BASE_PATH = "/data/e2b/build-cache"
```

要改源头 `dep/` 这份，否则下次 `build.sh -s` 会用它覆盖 `/opt/e2b-infra/nomad/template-manager.hcl`（§4 ②）。
改完把 `/tmp/templates`、`/tmp/build-cache` 里的老数据 `mv` 过去，再 `build.sh -r template-manager`。
另一条路是换成 MinIO（§6）。

### 7.2 磁盘占用分两处看

- `/tmp/templates`：持久化存储层，只有删模板/删快照才会回收
  （`python snapshot.py --mode cleanup` 或 SDK 的 `delete_snapshot`）；它在 tmpfs 上，占的是内存（§7.1）；
- `/orchestrator/build`：缓存，TTL 25h + 容量驱逐 + **orchestrator 重启清空**，
  不用手工管；看着大不代表泄漏。

## 8. Q & A

**Q：我在 `/orchestrator/build` 看到 200 MB 的 memfile，这不就是快照存本地了吗？**
A：那是**缓存**。MinIO 模式下同样会先写到这里再上传。判断 provider 要看进程环境变量（第 5 节①）。

**Q：`delete_snapshot` 之后 `/orchestrator/build` 里的文件还在？**
A：正常。删的是持久化对象（`/tmp/templates/<buildID>/`），缓存靠 TTL/重启回收。

**Q：那 `.env` 里的 `TEMPLATE_BUCKET_NAME` / `MINIO_*` 现在完全没用？**
A：在当前 nomad 单机路径下，对模板存储没用（provider 是 Local，桶名和 MinIO 凭据都不会被读）。
它们会被渲染进 `template-manager.hcl` 的 env，但代码里那条分支走不到。helm/k8s 路径下有用。

**Q：`api` job 要不要设 `STORAGE_PROVIDER`？**
A：不需要，`packages/api` 根本不 import 存储包。

**Q：换成 MinIO 之后，快照的增量语义会变吗？**
A：不会。增量是在 orchestrator 侧算好再写出去的，provider 只负责存字节流。
详见 [`09-增量快照实现与ARM实测分析.md`](09-增量快照实现与ARM实测分析.md)。
