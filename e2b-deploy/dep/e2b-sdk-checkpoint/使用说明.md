# checkpoint / restore：Python SDK 使用说明

给沙箱做**状态快照**并**回滚**：内存、vCPU、设备状态、磁盘一次性存下来，
之后可以把沙箱原样放回那一刻。

适用版本：`e2b==2.20.0` + 本仓库 `e2b-deploy/dep/e2b-sdk-checkpoint/` 覆盖层。

---

## 1. 它装在哪、怎么装

部署时由 `build.sh` 的 `install_e2b` 自动完成，顺序是：

```
pip install e2b==2.20.0
  → dep/e2b-sdk-checkpoint/install.py     ← checkpoint 能力铺进 site-packages
  → patch_e2b.py                          ← 内网明文（https→http）
```

**顺序不能反**：`patch_e2b.py` 会对 `connection_config.py` 做全局 https→http 替换，
覆盖层排在它后面会把替换结果又盖回去。

手工操作（排查时用）：

```bash
python3 /opt/e2b-infra/dep/e2b-sdk-checkpoint/install.py --check      # 看状态
python3 /opt/e2b-infra/dep/e2b-sdk-checkpoint/install.py             # 装
python3 /opt/e2b-infra/dep/e2b-sdk-checkpoint/install.py --uninstall # 还原
```

安装是**整文件覆盖**、版本锁死的：装之前核对 `e2b` 的版本，不是 `2.20.0` 就停，
不会悄悄装出一个半吊子。覆盖层一共 **21 个文件**：12 个是新增文件，9 个覆盖上游既有文件
（其中 `e2b_connect/client.py` 不在 `e2b/` 下，是 site-packages 顶层的另一个包）。
被覆盖的 9 个上游文件都留一份 `.orig`，`--uninstall` 能还原。
装完会另开一个干净解释器自检一遍（属性、方法、proto 字段、端口、异常族、
不重放、超时都验），不过就报错退出。

## 2. 最小例子

```python
import os
from e2b import Sandbox

os.environ["E2B_API_URL"]  = "http://<服务器IP>:3000"
os.environ["E2B_API_KEY"]  = "<你的 key>"
os.environ["E2B_DOMAIN"]   = "e2b.app"
os.environ["E2B_HTTP_SSL"] = "false"      # 内网明文部署必须设

sbx = Sandbox.create(template="base", timeout=600)

sbx.commands.run("echo 第一版 > /work/state.txt")
ck = sbx.checkpoint.create(name="第一版")
print(ck.checkpoint_id, ck.mem_mode)

sbx.commands.run("echo 第二版 > /work/state.txt")
print(sbx.commands.run("cat /work/state.txt").stdout)     # 第二版

sbx.checkpoint.restore(ck.checkpoint_id)
print(sbx.commands.run("cat /work/state.txt").stdout)     # 第一版 —— 回来了

sbx.kill()
```

异步用法完全一样，方法前面加 `await`：

```python
from e2b import AsyncSandbox
sbx = await AsyncSandbox.create(template="base", timeout=600)
ck = await sbx.checkpoint.create(name="第一版")
await sbx.checkpoint.restore(ck.checkpoint_id)
```

## 3. 接口

全部挂在 `sandbox.checkpoint` 下。

| 方法 | 返回 | 说明 |
|---|---|---|
| `create(name=None, request_timeout=None)` | `CheckpointInfo` | 做一次 checkpoint。`name` 只是给人看的标签，不要求唯一。默认超时 300 s |
| `restore(checkpoint_id, request_timeout=None)` | `bool` | 回滚到指定 checkpoint。默认超时 300 s。**只会返回 `True`**，失败一律抛异常，不要拿返回值分支 |
| `list(request_timeout=None)` | `List[CheckpointInfo]` | 列出本沙箱的全部 checkpoint，按时间从旧到新。默认超时 60 s |
| `delete(checkpoint_id, request_timeout=None)` | `bool` | 删除一个 checkpoint。默认超时 300 s。同样只会返回 `True`，失败抛异常 |
| `is_available(request_timeout=None)` | `bool` | checkpoint 接口是否应答 |
| `is_running(request_timeout=None)` | `bool` | 同上，旧名字，为兼容保留 |

### `CheckpointInfo`

| 字段 | 类型 | 说明 |
|---|---|---|
| `checkpoint_id` | `str` | 唯一 ID，`restore` / `delete` 用它 |
| `name` | `Optional[str]` | 做 checkpoint 时给的名字 |
| `created_at` | `Optional[int]` | Unix 秒 |
| `mem_mode` | `Optional[str]` | `"incremental"` / `"full"`，**见下节** |

## 4. `mem_mode`：这次 checkpoint 是增量还是全量

`"incremental"` = 这次只写了自上次 checkpoint 以来被改动的内存页。
`"full"` = 把整份 guest 内存都拷了一遍。

沙箱的**第一次** checkpoint 没有基线可比，必然是 `"full"`，这是正常的。
之后是哪一种，取决于宿主的 orchestrator 有没有打开脏页跟踪：开着是 `"incremental"`，关着每次都是 `"full"`。
两种情况功能都正确、都不报错，差别只在耗时和占用空间，所以只能从这个字段看出来。
量级参考（920B 开发环境实测，2GB 内存沙箱，KVM 写保护跟踪）：全量约 **1.5 秒 / 2048 MB**，
增量（脏页 32MB）约 **0.05 秒 / 40 MB**。

**按平台：**

- **鲲鹏 950（带 HDBSS，本产品的目标平台）**：什么都不用配。orchestrator 启动时探测到硬件脏状态跟踪
  （`KVM_CHECK_EXTENSION(502)` > 0）就自动打开，用硬件标脏做增量。RPM 标准部署不传
  `FC_TRACK_DIRTY_PAGES`（`dep/template-manager.hcl` 的 `env {}` 块和 `dep/deploy.sh` 的 `envsubst`
  白名单里都没有它），正是按这个默认来的。
- **没有 HDBSS 的机器**：不设变量时脏页跟踪是关的，每次 checkpoint 都是 `"full"`，功能正确。
  要在这类机器上得到增量，给 orchestrator 进程设 `FC_TRACK_DIRTY_PAGES=true`，退化为 KVM 写保护跟踪，
  checkpoint 仍是增量。
- **我们的开发环境（鲲鹏 920B，无 HDBSS）**就是第二种做法：开发栈显式设了 `FC_TRACK_DIRTY_PAGES=true`。
  本说明里的耗时数字都出自这个环境；950 上的数字待补。

`FC_TRACK_DIRTY_PAGES` 是 orchestrator 进程的环境变量，读法如下
（deltabox-dev `4af2872c6`，`packages/orchestrator/internal/sandbox/fc/dirtytracking.go:59-103`）：

| 进程环境里的值 | 结果 |
|---|---|
| 没设 | 跟硬件走：宿主 KVM 有硬件脏状态跟踪（arm64 HDBSS，能力号 502）就开，没有就关 |
| `1` / `t` / `T` / `TRUE` / `true` / `True` | 强制开 |
| `0` / `f` / `F` / `FALSE` / `false` / `False` | 强制关 |
| 其它任何值（空串、`yes`、`on`、拼错的词） | 按 Go 的 `strconv.ParseBool` 解析不了，被忽略，同"没设"一样跟硬件走；orchestrator 启动时打一条 WARN 写明这个值被忽略了 |

orchestrator 启动日志里的 `checkpoint capabilities` 一行会写明最终是开是关以及原因
（`track_dirty_pages` / `track_dirty_pages_reason`）；关着时另有一条 WARN：
`dirty page tracking is off: every checkpoint will copy all of guest memory`。

在无 HDBSS 的机器上做开发或预验证时，打开的办法：在部署机 `/opt/e2b-infra/nomad/template-manager.hcl`
的 `env {}` 块里加一行字面量 `FC_TRACK_DIRTY_PAGES = "true"`，然后
`cd /opt/e2b-infra && bash build.sh -r template-manager`（会重启 orchestrator，运行中的沙箱会被杀掉）。
要持久则改仓库的 `e2b-deploy/dep/template-manager.hcl` 并重打 `e2b-deploy.tar.gz`。

如果你的业务依赖增量的耗时，可以在自己的代码里加一道断言：

```python
ck = sbx.checkpoint.create()
if ck.mem_mode == "full" and not first_checkpoint_of_this_sandbox:
    raise RuntimeError(
        "这次 checkpoint 是全量——宿主的脏页跟踪没开（见上文按平台的说明）"
    )
```

服务端版本较老、不上报这个字段时值为 `None`，此时不要据此判断。

## 5. 需要知道的几件事

**沙箱里没有守护进程。** SDK 把请求发到沙箱地址的 49984 端口，但这个端口
**由宿主上的 orchestrator 截下来自己应答**，不转发进沙箱。因为做一次 checkpoint
要暂停虚机、驱动 hypervisor 的快照接口，这两件事沙箱内部谁也干不了。
所以 `is_available()` 探的是宿主侧那个服务，沙箱活着它就返回 `True`。

**checkpoint 跟着沙箱生死走。** 存在宿主本地，沙箱一销毁全部消失。
这跟 E2B 的 snapshot API 不是一回事，后者是持久化的。要跨沙箱留存，
得自己把内容导出去。

**restore 会掐断已有连接。** 回滚把 guest 的 TCP 状态也退回去了，
跨越 restore 保持着的连接对面已经不认识它们，所以会被主动丢弃。
restore 那一刻还在途的 SDK 调用（`commands.run`、`files` 读写等）会抛
`CheckpointInterruptedException`，而不是"端口没开"——沙箱里的服务没坏，
重新发起调用即可（见第 6 节）。你自己在沙箱里起的长连接要自己处理。

**沙箱要活着。** `create` / `restore` 都要求沙箱处于运行状态；
沙箱超时被回收之后，它的 checkpoint 也一起没了。

**耗时量级**（920B 开发环境，2GB 内存沙箱，KVM 写保护跟踪；950 上的数字待补）：

| 操作 | 典型耗时 |
|---|---|
| 首次 checkpoint（全量） | ~1.5 s |
| 增量 checkpoint，脏页 16 MB | ~0.04 s |
| 增量 checkpoint，脏页 256 MB | ~0.20 s |
| restore | ~0.03–0.12 s |

**链不要拉得太长。** 同一个沙箱上连续 checkpoint，单次耗时会随**代数**缓慢上升
（跟写了多少字节几乎无关）：ext4 套实测约 **0.28 ms/代**，
400 代之后单次从 0.012 s 涨到 0.11 s。几十次量级察觉不到；
要连续做几百次的话，把老 checkpoint `delete()` 掉，或者定期换沙箱。

## 6. 异常与调用方动作

checkpoint 接口的错误按"**调用方接下来该做什么**"分类，而不是按 RPC 怎么结束分类。
服务端在错误体里除了 Connect `code` 还带一个 `reason` 字段，SDK 先按 `reason`
选异常类，没有 `reason`（老服务端）才退回按 `code` 选。

全部继承自 `CheckpointException`（它继承 `SandboxException`），都能从 `e2b` 顶层导入。
每个异常上有三个属性：`reason`（服务端给的原因，老服务端为 `None` 时取该类的默认值）、
`checkpoint_id`（调用里点名的 checkpoint，没有则 `None`）、`sandbox_id`。

| 异常类 | `reason` | HTTP 状态 / Connect code | 出现在 | 沙箱此时的状态 | 调用方该做什么 |
|---|---|---|---|---|---|
| `CheckpointTornException` | `torn` | 500 / `data_loss` | restore 越过了不可回头的点之后失败；之后该沙箱的每次 checkpoint / restore 也都回这个 | 停在两个时刻之间：一部分在 checkpoint 那一刻，一部分在原地，无法判断落了多少 | **不可重试、不可恢复。**销毁这个沙箱，重新建一个 |
| `CheckpointChainBrokenException` | `chain_broken` | 412 / `failed_precondition` | restore | 沙箱照常运行在当前状态；是要恢复的那个 checkpoint 没有可用的磁盘视图（增量链断了） | 先重新做一次 checkpoint（会起一条新链），之后再 restore；这个旧 checkpoint 不要再用 |
| `CheckpointRootfsPoisonedException` | `rootfs_poisoned` | 500 / `internal` | checkpoint | 沙箱照常运行；rootfs 的账本不可信了，之后的 checkpoint 会被拒绝 | **restore 任意一个已有的 checkpoint**，账本会被重新建立，之后 checkpoint 恢复可用 |
| `CheckpointGuestUnresponsiveException` | `guest_unresponsive` | 500 / `internal` | restore | 宿主侧已经完成，虚机已在目标状态；是 guest 里的 envd 在等待时间内（服务端等 45 s）没应答。沙箱**没有**撕裂，卡住的东西在沙箱里面 | 回滚本身已经完成，不要当成"没回滚成"去处理。此时 guest 不应答，这个沙箱暂时执行不了命令；SDK 没有规定进一步动作，由调用方按业务决定（稍后再试命令，或销毁重建） |
| `CheckpointBusyException` | `busy` | 503 / `unavailable`，带 `Retry-After: 1` | checkpoint / restore / delete | 同一沙箱上另一个 checkpoint 操作还没结束（同一沙箱的操作在宿主上串行；服务端排队超过 `CHECKPOINT_LOCK_WAIT_TIMEOUT`，默认 60 s，就回这个） | **可重试。**等 `e.retry_after` 秒（服务端没给或给的是日期时为 `None`）后重试 |
| `CheckpointInterruptedException` | `sandbox_restored` | 409 / `aborted` | **不是** checkpoint 接口自己的错误：是 restore 发生时，对这个沙箱的其他在途调用（命令、文件读写）收到的 | 沙箱已回到 checkpoint 那一刻，沙箱里的服务没坏 | 重新连接、重试这次调用。这次调用在 guest 里是否已经生效无从得知——但回滚反正把 checkpoint 之后的一切都撤销了 |
| `CheckpointDiskFullException` | `disk_full` | 507 / `resource_exhausted` | checkpoint / restore | 服务端在动手之前先查空间，什么都没开始：沙箱照常运行，已有的 checkpoint 完好 | 这是**宿主**的问题，不是这个沙箱的问题：删本沙箱的 checkpoint 多半腾不出足够空间，要找宿主的运维清理存放 checkpoint 的盘。清理之后可重试；紧凑循环重试只会反复被拒 |
| `CheckpointTooManyException` | `too_many_checkpoints` | 429 / `resource_exhausted` | checkpoint | 本沙箱持有的 checkpoint 数到了服务端的每沙箱上限；检查在写入之前，沙箱照常运行，已有的 checkpoint 完好 | 调用方自己能解决：`list()` 出来，`delete()` 掉不要的，再做 checkpoint |
| `CheckpointException`（基类） | 其他 / `None` | 500 / `internal`；或老服务端只给了 `resource_exhausted` | 任意 | 没有更具体的说法 | 调用方无法据此行动；记录 `str(e)` 与 `e.reason`，查 orchestrator 日志 |

下面四种**不**进这个异常族，仍然是 SDK 原有的异常，含义与别处相同：
`not_found` → `NotFoundException`（404：沙箱或 checkpoint 不存在）、
`unauthenticated` → `AuthenticationException`（401：traffic access token 缺失或不对）、
`invalid_argument` → `InvalidArgumentException`（400）、
不带 `reason` 的 `unavailable` → `TimeoutException`（SDK 对这个 code 的通用解释：多半是沙箱已超时）。

> 表里的 HTTP 状态与 code 取自服务端
> `packages/orchestrator/internal/checkpoint/service.go`（deltabox-dev `4af2872c6`）里的
> `writeError` / `writeBusy` / `RestoredAnswer` 调用；"状态 / 该做什么"两列取自 SDK
> `e2b/exceptions.py` 各异常类的 docstring 与 `e2b/sandbox/checkpoint/errors.py` 的映射表。

推荐的处理骨架：

```python
import time
from e2b import (
    CheckpointBusyException, CheckpointTornException, CheckpointRootfsPoisonedException,
    CheckpointTooManyException, CheckpointDiskFullException, CheckpointException,
)

def checkpoint_with_retry(sbx, name=None, attempts=5):
    for _ in range(attempts):
        try:
            return sbx.checkpoint.create(name=name)
        except CheckpointBusyException as e:          # 503，可重试
            time.sleep(e.retry_after or 1)
        except CheckpointTooManyException:            # 429，自己清
            oldest = sbx.checkpoint.list()[0]
            sbx.checkpoint.delete(oldest.checkpoint_id)
    raise RuntimeError("checkpoint 一直忙")

# 以下几种不要自动重试：
#   CheckpointTornException            → 销毁沙箱重建
#   CheckpointRootfsPoisonedException  → 先 restore 一个已有的 checkpoint
#   CheckpointDiskFullException        → 找宿主运维清盘
#   其余 CheckpointException           → 记录后上报
```

凡是先 `except SandboxException` 的老代码不用改也能接住这些异常（它们都是它的子类），
只是分不出该做什么。

## 7. 超时与不重放

**checkpoint / restore / delete 的默认请求超时是 300 秒**
（`e2b.connection_config.CHECKPOINT_REQUEST_TIMEOUT`），`list` 和 `is_available`
仍是连接级默认的 60 秒。单次调用传 `request_timeout=` 仍然优先；
但连接级的 `request_timeout`（`Sandbox.create(request_timeout=...)` 那个）**故意不继承**
到这三个操作上，它是为 envd 的普通请求调的。原因：

- 宿主要暂停虚机、写或读内存快照，出错路径上还要等 guest 里的 envd 最多 45 秒才报失败，
  光是"报错"就可能超过 60 秒；
- 服务端**没有取消**：客户端超时只是放弃了一件服务端还在继续做的事。对 checkpoint 来说
  就是 checkpoint 做成了，但它的 ID（由服务端命名）没送到调用方手里；
- `delete` 不碰虚机，但它和 checkpoint / restore 抢同一把每沙箱锁，可能排在它们后面；
  服务端最多排 60 秒才回 busy，客户端若也是 60 秒就会先超时，拿不到那个可重试的应答。

所以**不要把 `request_timeout` 调到 60 秒以下**。如果确实超时了：先 `list()` 看
checkpoint 是否其实已经做成，再决定要不要重做。

**四个 checkpoint RPC（`create` / `restore` / `list` / `delete`）在传输层一律不重放**
（`retries=0`）。SDK 对 envd 的普通调用在"对端中途断开连接"时默认会自动重发，
那是给幂等调用准备的；checkpoint 的 RPC 不幂等：重放的 `create` 会多做一个调用方
永远不知道的 checkpoint，重放的 `restore` 会把 guest 再回滚一次，重放的 `delete` 会得到 404。
所以连接中途断开时，SDK 会把错误直接交给你，**由调用方决定**：先 `list()` 核对结果，再决定是否重发。

## 8. 出错时

| 现象 | 多半是 |
|---|---|
| `AuthenticationException: 401` | `E2B_API_KEY` 没设或不对 |
| 连到了公网而不是本机沙箱 | `E2B_HTTP_SSL` 没设成 `false`，或 `/etc/resolv.conf` 里少了 `nameserver 127.0.0.1` |
| `NotFoundException` | `checkpoint_id` 不属于这个沙箱，或已被删 |
| `mem_mode` 一直是 `full` | 宿主的脏页跟踪没开：950 上自动开；没有 HDBSS 的机器不设 `FC_TRACK_DIRTY_PAGES` 时是关的，见第 4 节 |
| `import e2b` 报 `duplicate file name checkpoint/checkpoint.proto` | site-packages 里同时存在旧的 `e2b/gsd/` 和新的 `e2b/checkpointd/`。重跑 `install.py`，它会把旧目录挪开 |
| `create` 超时但沙箱还在 | 服务端没有取消：客户端放弃后它仍会把这次 checkpoint 做完，也不会把虚机停在暂停状态。重新 `list()` 看一下；默认超时已是 300 s，见第 7 节 |
| 抛 `CheckpointBusyException` / `CheckpointTooManyException` / `CheckpointDiskFullException` 等 | 见第 6 节，每个异常对应一个明确的动作 |
| restore 之后别的调用抛 `CheckpointInterruptedException` | 正常：那次调用跨越了 restore，被回滚掐断。重试即可，见第 6 节 |
| checkpoint 接口回 401 | 沙箱关闭了公开访问（有 traffic access token）而 SDK 没带。用 `Sandbox.create` / `Sandbox.connect` 得到的对象会自动带 `e2b-traffic-access-token` 头；确认覆盖层是这一版（`install.py --check`） |
